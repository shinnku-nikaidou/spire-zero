An observation is everything the brain learns about the game at a decision, so it is also the limit of what the brain can know. This page lists it field by field, with the actions that answer each kind of screen. The types are in `src/Sts2Ai.Protocol` (`Observation.cs`, `CombatObservation.cs`, `Screens.cs`, `CardChoice.cs`, `CombatAction.cs`); GameBridge fills them from the game ([GameBridge](/en/arch/gamebridge/)).

## 1. One observation per decision

```text
Observation{run: RunView, screen: ScreenView}
```

An `Observation` has two parts. `run` is the run around the player, the same at every screen: the top bar, the deck view and the map ([§2](#sec-2)). `screen` is the screen that asks, one of eleven variants, one per **surface**, the kind of decision screen. In JSON the screen names its variant in a `"surface"` field, so a reader knows which fields follow:

```json
{"run": {"character": "SILENT", "act": 0, "floor": 2, …}, "screen": {"surface": "card_reward", "cards": […], "alternatives": […]}}
```

The surface names are constants in `Surfaces.cs`: `combat`, `card_choice`, `map`, `rewards`, `card_reward`, `bundle`, `event`, `shop`, `rest`, `treasure`, `crystal_sphere`. The surface is also the key Harness routes a decision by ([Harness: routing, budgets and seeds §1](/en/arch/harness/routing/#sec-1)). The end of a run is not a surface; it is the wire message `run_end` ([The wire §3](/en/arch/protocol/wire/#sec-3)).

Observations are built lazily. Inside the brain a decision carries a function that builds its observation, and a brain that never reads it never pays for it (`CombatDecision`, `MacroDecision`, `ChoiceDecision` in `Sts2Ai.Brain/Decisions.cs`). On the wire it is always built, since the brain is elsewhere.

## 2. The run

| field | type | what it is |
|---|---|---|
| `character`, `ascension` | string, int | the character's id, the ascension level |
| `act` | int | the act, counted from 0 |
| `act_id` | string | which of the act's variants the run rolled (`OVERGROWTH`, `HIVE`, `GLORY`, …) |
| `floor` | int | the floor counted over the whole run, as the top bar shows it |
| `hp`, `max_hp`, `gold` | int | the top bar |
| `deck` | `CardView[]` | the deck, sorted by card key ([§4](#sec-4)); each upgradable card also carries its preview, `upgraded` |
| `relics` | `RelicView[]` | the relics, in the order the player holds them |
| `potions` | `(string\|null)[]` | one entry per potion slot: the potion's id, or null for an empty slot |
| `map` | `MapView` | the current act's map |

`MapView` is the map as the map screen draws it:

| field | what it is |
|---|---|
| `points` | every point, sorted by row then column: the start in row 0, the rows, then the boss (and second boss) above the last row |
| `visited` | the points visited in this act, in order; the last is where the player stands |
| `boss`, `second_boss`? | the boss encounters drawn on the boss points |
| `ancient`? | the act's Ancient, drawn on the start point |

Each point is a `MapPointView`: `col`, `row`, `type`, the map icon (`Monster`, `Elite`, `Unknown`, `Shop`, `Treasure`, `RestSite`, `Boss`, `Ancient`), `next`, the points its paths lead to, sorted, and `quest`, set when a quest marks the point (a relic or card that rewards reaching it). A `?` stays `Unknown` after it is visited, as the map shows it; what an unvisited `?` holds never appears.

## 3. A combat

`CombatObservation` is what the player sees of a combat. It is the `combat` screen's payload, and also comes with a card prompt raised in combat.

| field | what it is |
|---|---|
| `encounter`, `room` | the encounter's id; its room type as the map shows it (`Monster`, `Elite`, `Boss`) |
| `act`, `ascension`, `round` | the act from 0, the ascension, the combat's round from 1 |
| `player` | `PlayerView`: `uid`, `character`, `hp`, `max_hp`, `block`, `energy`, `max_energy`, `stars`, `gold`, `powers`, `orb_slots`, `orbs` |
| `hand` | the cards in hand, in hand order, each with its `uid` |
| `draw` | the draw pile, sorted by card key: the player knows what is in it, not its order |
| `discard`, `exhaust` | the discard and exhaust piles, in pile order |
| `potions` | one entry per slot, as in the run |
| `relics` | `RelicView`: `id`, and what its icon and tip show: `counter`, `status` (when not normal), `melted`, `used_up`, `cards` (the cards it keeps, such as Pael's Tooth's), `spent` (its once-a-combat or once-a-turn effect is spent, when its status does not say so: Centennial Puzzle's, or Regalite's this turn) |
| `allies` | creatures on the player's side other than the player: other players, summons |
| `enemies` | `CreatureView`: `uid`, `id` (the monster's), `hp`, `max_hp`, `block`, `powers`, and `intents`: an enemy that lies dead until it revives stays in the list with 0 HP, and its revival is a move |

The nested views:

| type | fields | notes |
|---|---|---|
| `CardView` | `id`, `uid`?, `up`?, `cost`? or `x_cost`?, `stars`?, `enchant`?, `affliction`?, `tinker`?, `keywords`?, `this_turn`?, `vars`?, `upgraded`?, `lasting`?, `stars_lasting`?, `replay`?, `spent`?, `calc`? | `cost` is the energy cost with every modifier; `stars` the star cost, for cards that have one; `enchant` and `affliction` are `{id, amount}`; `tinker` is what the Tinker Time event made of a Mad Science, its type and rider, which its frame shows and its id does not; `keywords` sorted; `this_turn` the keywords an effect gave it for this turn only, which the turn's end takes away (Expertise's Retain, Hand Trick's Sly); `vars` the card's own numbers by name ([§7](#sec-7)); `upgraded` the card after one more upgrade, as the game's upgrade preview shows it, on upgradable deck cards only |
| `PowerView` | `id`, `amount`, `stacks`?, `card`?, `detail`?, `stolen`? | `amount` is the number on the icon; `stacks` the power's own amount when the icon shows another number (Sloth's icon counts this turn's cards; its stacks are the limit); `card` the card the power keeps, as its tooltip names it (Nightmare's); `detail` how far the number its tooltip states has moved from the power's own, when it has (Toric Toughness's block, The Bomb's damage); `stolen` the card it took (Swipe's) |
| `IntentView` | `type`, `damage`?, `hits`? | an intent icon above an enemy: its type, and for an attack the damage per hit against the player and the number of hits |
| `OrbView` | `id`, `passive`, `evoke` | an orb and the numbers it shows |

**Uids.** An action has to name a card or a creature in a way that stays true while the hand changes, and means the same thing in the simulator and in the game. Uids are the game's own per-combat ids, the ones its multiplayer messages use: a hand card's id in the combat's card database (`NetCombatCardDb`), a creature's `CombatId`. Only what the player can point at has one: the cards in hand and the creatures. Cards in the piles have none, because the game numbers cards right after the opening shuffle, so a card's number is its place in the shuffled draw pile.

**Combat actions** (`CombatAction.cs`) have a text form, which is also their JSON:

| action | meaning |
|---|---|
| `play:C` or `play:C:T` | play the hand card with uid C, at the creature with uid T if it needs a target |
| `potion:S` or `potion:S:T` | use the potion in slot S, at T if it needs a target |
| `end_turn` | end the turn |

A line of search may carry the answer to the action's first card prompt after an `@`: the picked options' places in canonical order, comma-separated (`potion:0@3`, `play:12:3@1,3`; `end_turn@2` for a prompt the turn's end or the next turn's start brings; `play:12@` for no pick). It appears only in search and in the logs: the action a host is told has none, and Harness gives the answer to the prompt when it comes ([Combat brain: prompts, moves and workers §1](/en/arch/combat-brain/shared/#sec-1)).

Combat has no potion discard: the protocol's combat actions are these three kinds.

## 4. Identity and order

**A card's key** is its `CardView` serialized without its uid (`ProtocolJson.CardKey`). It holds everything the player sees of the card, so two cards with the same key are the same card to the player. The key gives two guarantees:

- **The same state, the same observation.** The deck is sorted by key, so a deck reached by picking cards in another order looks the same; the draw pile is sorted by key, since its real order is hidden.
- **No order that leaks.** The game's own order of a list can depend on hidden state: a prompt over the draw pile lists the cards in pile order, which the player does not know. A card prompt's options therefore go out in **canonical order**: sorted by key, with ties among identical-looking cards broken by a random stream that knows nothing hidden (`CardChoices.Canonical`, `Sts2Ai.GameBridge/CardChoices.cs:16-25`). The simulator seeds it with the prompt's number since the node's entry, the mod with 0. A card prompt over the deck shows deck views (with `upgraded`), every other prompt plain card views.

**Two index spaces.** An answer on the wire picks by canonical index (`pick:0,2`). The host translates it to the game's own indexes, and that is what the run's trace and the SL node messages record (`card_choice 4,1`), since a replay goes through the game's card selector, which knows no canonical order ([The wire §6](/en/arch/protocol/wire/#sec-6)).

**Lists in the UI's order.** Lists whose order the screen shows and that hide nothing are sent in that order, and actions index into them: rewards, event options, shop slots, the chest's relics, card reward cards.

## 5. Screens and their actions

The screen variants (`Screens.cs`), with the actions each surface takes. The legal list on the wire holds these strings; the rules for which are legal are in [Simulator: whole runs §4](/en/arch/simulator/runs/#sec-4).

| surface | screen fields | actions |
|---|---|---|
| `combat` | `combat`: the `CombatObservation` | `play:C[:T]`, `potion:S[:T]`, `end_turn` |
| `card_choice` | `choice`: the `CardChoice` ([§6](#sec-6)); `combat` too while a combat is going on | `pick:i,j,…` by canonical index; the legal list is empty; an empty pick only if `min` is 0 |
| `map` | `travelable`: the coordinates the player can travel to, in the legal actions' order (the map itself is in `run.map`) | `map:COL,ROW` |
| `rewards` | `rewards`: the buttons not taken yet, `{index, kind, id?, amount?, card?, cards?}`, `kind` one of `gold`, `potion`, `relic`, `card`, `special_card`, `remove_card` | `reward:i`, `rewards_done` |
| `card_reward` | `cards`; `alternatives`, the other buttons by id (skip, reroll, ones relics add) | `card:i`, `card_alt:ID` |
| `bundle` | `bundles`: lists of cards | `bundle:i` |
| `event` | `id`; `page`, the page text's loc key; `options` `{index, key, locked?, relic?, tips?, kills?}`, empty once finished; `finished` | `event:i`, `proceed` |
| `shop` | `entries` `{slot, kind, card? or id?, cost, on_sale?}` for the goods still for sale, `kind` one of `card`, `relic`, `potion`; `removal_cost`, absent once the removal is used | `buy:SLOT`, `remove`, `leave` |
| `rest` | `options` `{id, enabled, heal?}`; `heal`, on the HEAL option, the HP it restores as its text shows (relics change it) | `rest:ID`, `leave` |
| `treasure` | `relics`: the relics in the chest, by id | `relic:i`, `relic_skip` |
| `crystal_sphere` | `rows`, an 11×11 grid where `rows[y][x]` is `#` hidden, `.` uncovered and empty, or what the uncovered cell shows part of (`R` relic, `P` potion, `C` card reward, `G` gold, `X` curse); `divinations_left` | `big:X,Y` (the 3×3 block), `small:X,Y` (one cell) |

Notes on the fields:

- **A card reward's cards** come with the rewards screen's `card` button (`cards`): the game rolls them before the screen shows, and opening the reward to look costs nothing, so the player knows them before opening it.
- **Event options** are named by their text key, the loc key that names the option within its event. `relic` is the relic an Ancient's option gives; `tips` the ids of the cards, relics and potions its hover tips show (`+` marks an upgraded card); `kills` that the button warns it would kill the player; `locked` an option the player cannot take.
- **Shop slots** index the shop's goods in the order the game keeps them (character cards, colorless cards, relics, potions), sold-out ones included, so a slot keeps its number after a purchase; the removal is its own action.
- **Rest options** are named by id (`rest:HEAL`, `rest:SMITH`), not by position.

**The potion belt.** On `map`, `rewards`, `event`, `shop`, `rest`, `treasure` and `crystal_sphere` the legal actions also include the belt: `potion:S` for a potion usable at any time, and `discard_potion:S`. Card rewards, bundles and card prompts get none.

**Inside the brain**, the macro surfaces reach a policy as `MacroDecision{surface, legal, observation}`, a card prompt as `ChoiceDecision{choice, observation}`, a combat decision as `CombatDecision{legal, observation}`. A combat played on its own, outside a run (`combat`, `bench`, `selftest`), has no run, so its decisions and prompts carry the combat only.

## 6. Card prompts

A **card prompt** is the game asking for cards from a list: discard 1, exhaust up to 2, choose 1 of 3, upgrade a card at a rest site, remove one at the shop. The game raises it from inside an action, through one of its `CardSelectCmd.From*` entries, so it can come at any time, in combat or out of it.

```text
CardChoice{options: CardView[] (canonical order), min, max, context: ChoiceContext}
```

An answer is between `min` and `max` distinct indexes into `options` (`CardChoice.Accepts`). A prompt that can be cancelled or skipped has `min` 0, the empty answer being the cancel.

The options alone do not say what the prompt is for: the same five cards mean different things for an upgrade, a removal or a discard. `ChoiceContext` carries that, and GameBridge fills it from the entry the game used ([GameBridge: reading the game §6](/en/arch/gamebridge/observe/#sec-6)):

| field | what it is |
|---|---|
| `purpose` | the kind of prompt: the entry's name without `From`, in snake_case (`deck_for_upgrade`, `deck_for_transformation`, `deck_for_enchantment`, `deck_for_removal`, `deck_generic`, `hand`, `hand_for_discard`, `hand_for_upgrade`, `choose_a_card_screen`, `simple_grid`, `simple_grid_for_rewards`), or for a prompt over a combat pile the pile's name, `draw_pile` or `discard_pile` (in this game version only those two piles are asked from) |
| `source`? | the id of the card, relic, power or event that asks, when the game names one: the entry's `source` argument, else the last model the choice involved |
| `cancelable` | a cancel or skip button closes the prompt: the prompt's own setting, or a choose-a-card screen's `canSkip` |
| `in_combat` | asked during a combat (a card or power resolving), rather than at a rest site, an event or a shop; Harness routes the prompt by it: in combat to the answer the combat brain's action carries, or else the first options (`first`), outside to the macro brain ([Harness: routing, budgets and seeds §1](/en/arch/harness/routing/#sec-1)) |
| `prompt_key`? | the prompt text's loc key, `table.key` |
| `enchantment`? | for `deck_for_enchantment`: the enchantment the picked cards get, `{id, amount}` |

Two details of the bounds (`ChoiceContexts.Bounds`): `max` is never more than the options there are; a choose-a-card screen without a skip button asks its selector for 0 or 1 cards and then insists on one itself, so its `min` is 1. When one entry calls another (a removal goes through the generic deck prompt), the outermost names the purpose. Bundles (Scroll Boxes' choice of card packs) are not card prompts: they have their own surface.

## 7. Text, numbers and what is left out

- **Text is sent as loc keys** (`table.key`), never as the resolved string: event pages, event options by their text key, prompt texts. A brain that wants words looks them up.
- **A card's `vars`** are its own numbers, damage, block, magic number, by name: the base values, not what Strength or Dexterity make of them at play. A number the card calculates from the state (Perfected Strike's damage) is left out; the card shows it as a base plus an extra per count, and both parts are listed.
- **Event numbers** are not included yet: some events keep values among their numbers that the page does not show, so they need a whitelist per event first.
- **Never included**: seeds and random streams, what a `?` holds before it is entered, which move a monster has queued, what a reroll or a transform will give, the draw pile's order ([Overview §3](/en/arch/protocol/#sec-3)).

## 8. Planned: the event stream <Badge text="planned" variant="caution" />

An observation is a snapshot. A player also remembers what happened: which cards were drawn and moved, which intents a monster showed, what a shop offered. To reason about the hidden state from that history (a belief), the brain would need the events too. The plan is for each `decision` message to carry the events since the previous one, a minimal set grown only when a belief needs it:

```text
draw{card}  play{card_uid, target?}  move{card, from, to, pos: top|bottom|random|null}
generate{card, to}  shuffle{}  intents{creature, intents[]}  move_done{creature, effects…}
reward_seen{…}  shop_seen{…}  event_page{…}
```

`move` is a card moving between piles, `move_done` a creature's finished move and its effects; the last line records what a rewards screen, a shop or an event page showed. GameBridge would produce them from the game's hooks ([GameBridge §5](/en/arch/gamebridge/#sec-5)). Today the one piece of history the brain keeps is the record of enemy intents per round, which Harness builds from the observations themselves ([Worlds and worker messages §2](/en/arch/protocol/worlds/#sec-2)).
