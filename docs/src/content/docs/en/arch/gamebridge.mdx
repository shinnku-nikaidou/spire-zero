GameBridge (`Sts2Ai.GameBridge`) is the translation layer between the game and [Protocol](/en/arch/protocol/). It has three jobs: **observe** (read game objects into an observation), **legal** (list the legal actions as protocol text) and **start** (turn one protocol action into the same game call the UI would make, and begin it). It runs inside whichever process hosts the game: a SimWorker running headless, or the Mod in the real game. Because both hosts use it, every rung from R1 to R4 runs the same code.

<Aside title="Status">

Observe, legal and start exist for every surface, and so does the choice context (`src/Sts2Ai.GameBridge`). The event stream is planned.

</Aside>

## 1. Role and rules

- GameBridge is the only code that turns game objects into protocol (observe, legal) and a protocol action into a game call (start). SimWorker and the Mod share it, so R1–R4 (the rungs of the [sim-to-real ladder](/en/arch/evaluation/#sec-1)) use one code path.
- It references the game DLLs, Protocol, and Harmony (the game's own `0Harmony.dll`, for [§5](#sec-5)). Never Brain. Never Godot nodes (`N*` types), the game's UI scene objects. Work that needs nodes lives in the host adapters instead: the Mod's UI adapters ([Mod §4](/en/arch/mod/#sec-4)), and in the simulator, copied node logic ([Simulator §5.2](/en/arch/simulator/#sec-5.2)).
- Observe reads only what the UI shows (the fair-play whitelist, [Protocol §8](/en/arch/protocol/#sec-8)). Each field is mapped from the property the UI binds to (`DisplayAmount`, `IsVisible`, `ShowCounter`, intents via `GetSingleDamage`), never from internal state.
- Start uses the same entry point as the UI. Never state edits, and never commands that skip validation (`CardCmd.AutoPlay`, a raw `new PlayCardAction`, `PlayerCmd.EndTurn`).
- **Settling** (running the game until the next decision point is reached) is host-specific. GameBridge provides only logic predicates for it ([§6](#sec-6)).

## 2. Existing API

What exists in `src/Sts2Ai.GameBridge` today:

| type | member | notes |
|---|---|---|
| `Observe` | `Combat(st, player)` | hand with uids; draw pile sorted by card key; powers only if `IsVisible`, with their `DisplayAmount`; intents of `NextMove` aimed at the player |
| | `Of(run, player, screen)`, `Run(run, player)` | an `Observation`: the `RunView` plus the surface's screen ([§3](#sec-3)) |
| | `Card(card, withUid)`, `CardKey(card)`, `Relic`, `Coord`, `Intents(move, owner, targets)` | `Intents` is reused by CombatBuilder (intent matching) |
| `CombatActions` | `WaitingForInput(player)` | player side, `Phase==Play`, executor idle, actions enabled. Enough headless, but NOT in the real game ([Mod §3](/en/arch/mod/#sec-3)) |
| | `Legal(st, player)` | hand order, then potions by slot, then `end_turn`; `CanPlay()` once per card |
| | `Start(st, player, action)` | `TryManualPlay(target)` / `EnqueueManualUse(target)` / `RequestEnqueue(EndPlayerTurnAction(player, TurnNumber))` |
| | `HandCard(pcs, uid)`, `Creature(st, uid)` | throw on an unknown uid |
| `MapActions`, `RewardActions`, `BundleActions`, `EventActions`, `CrystalSphereActions`, `ShopActions`, `RestActions`, `TreasureActions`, `PotionActions` | `Screen(…)` returns the surface's screen; `Legal(…)` returns action texts; `Start(…, action)` throws if the action is not legal, and returns the game task where the UI awaits one | one static class per surface (`PotionActions` has belt actions only, no screen); grammar in [Protocol §3](/en/arch/protocol/#sec-3); `ActionText` parses |
| `CardChoices` | `Canonical(options, min, max, context, tieBreak)` | sorts by card key, ties by a caller-seeded `Random`, never by game order (it may reflect pile depth); returns `(CardChoice, gameIndex[])` |
| `ChoiceContexts` | `Patch(harmony)`, `Current`, `Bounds(context, minSelect, maxSelect, n)` | the choice context ([§5](#sec-5)) |

## 3. Observation sources

Where each part of the run-level observation ([Protocol §3](/en/arch/protocol/#sec-3)) is read from. Each surface's screen is built by the `Screen(…)` of its class, next to its legal actions. Every source below was read in the game code <Badge text="verified" variant="success" />.

| part | source |
|---|---|
| `RunView` character, ascension, act, floor | `player.Character`, `RunState.AscensionLevel`, `CurrentActIndex` and `Act.Id`, `TotalFloor` |
| hp, gold | `player.Creature.CurrentHp/MaxHp`, `player.Gold` |
| deck | `player.Deck.Cards` → `Observe.Card`, sorted by card key |
| relics, potions | `player.Relics`, `player.PotionSlots` (the combat mappers) |
| map | the points of `RunState.Map` (plus the start, boss and second boss points), with `PointType`, `Children` and `Quests`; `VisitedMapCoords`; `Act.BossEncounter`, the map's second boss, `Act.Ancient` |
| map screen | travelable points: the rules of `NMapScreen.RecalculateTravelability`, copied into `MapActions` as a logic function |
| rewards | the rewards of the `RewardsSet` with `!SuccessfullySelected`; a special card comes from the reward's `CardHoverTip` (its card field is private) |
| card reward | offered cards + alternative ids (computed once per screen, `CardReward.cs:321-330`) |
| bundle | the bundles' cards → `Observe.Card` |
| event | `EventSynchronizer.GetLocalEvent()`: id, `Description` key, `CurrentOptions` (`TextKey`, `IsLocked`, `Relic`, hover tips, `WillKillPlayer`) |
| shop | `MerchantInventory.AllEntries` without the removal (slot order, `IsStocked`, `Cost`, `IsOnSale`), and `CardRemovalEntry` |
| rest | `RestSiteSynchronizer.GetLocalOptions()` (`Id`, `IsEnabled`) |
| treasure | `TreasureRoomRelicSynchronizer.CurrentRelics` |
| crystal sphere | the minigame's cells: `IsHidden`, the item under each uncovered cell (`Item.ToSerializable().type`), divinations left |
| card prompt | options + `CardSelectorPrefs`, via `ChoiceContexts` ([§5](#sec-5)) |

A combat during a run uses the same `Observe.Combat`, inside the screen: `combat`, or `card_choice` with its `combat`.

## 4. Actions per surface

The action grammar is in [Protocol §3](/en/arch/protocol/#sec-3). Each host applies an action its own way. The simulator calls a logic entry in GameBridge; the Mod often goes through the UI node handler that a click would trigger.

| surface | logic entry (GameBridge, used by the simulator) | Mod path |
|---|---|---|
| combat | `CombatActions.Start` | same |
| potion discard | `DiscardPotionGameAction` | same |
| map | `RequestEnqueue(VoteForMapCoordAction(…))` | `NMapScreen.OnMapPointSelectedLocally` (the node does the lock and animation) |
| rewards | `RewardsSetSynchronizer.SelectLocalReward` / `SkipLocalRewardsSet` | reward button handler |
| leave rewards | `ProceedFromTerminalRewardsScreen` / `ActChangeSynchronizer.SetLocalPlayerReady` ([Simulator §5.2](/en/arch/simulator/#sec-5.2)) | proceed button |
| card reward | answer `GetSelectedCardReward` (sim selector) | card holder / skip / reroll buttons |
| card prompts | answer `CardSelectCmd.Selector` (sim) | screen holders + confirm. This UI path records a `PlayerChoice` for replay. `LocalSelector` skips `SyncLocalChoice` (`CardSelectCmd.cs:264-300`) <Badge text="verified" variant="success" />, so it would break SL replay |
| event | `ChooseLocalOption(i)` | option button |
| shop | `entry.OnTryPurchaseWrapper(inv)`; the removal node marks a card removal used (in the simulator a headless patch does, [Simulator §5.2](/en/arch/simulator/#sec-5.2)) | the same call (`ForceClick` on merchant nodes does nothing <Badge text="verified" variant="success" />) |
| rest | `ChooseLocalOption(i)` | option button |
| treasure | `PickRelicLocally(i)` / `SkipRelicLocally()` | chest + relic buttons |
| crystal sphere | `SetTool` + `CellClicked(cell)` | divination buttons + cell click |
| potion use (out of combat) | `EnqueueManualUse(null)` | potion popup |

**Rule:** whenever the Mod path is a node handler, the sim path must equal what that handler calls, minus pure-UI effects. Each such pair gets an R3-vs-R4 equivalence check: the same seed and the same decisions must give the same observation stream ([Mod §8](/en/arch/mod/#sec-8)).

## 5. Choice context

How GameBridge fills `ChoiceContext` ([Protocol §4](/en/arch/protocol/#sec-4)). Every card prompt goes through one of the `CardSelectCmd.From*` entries, and only their arguments say why the game asks. So `ChoiceContexts` patches them with Harmony, the library that patches game methods at runtime: a *prefix* runs before the original method, a *finalizer* after it, even when it throws.

- The targets are every public static `CardSelectCmd.From*` method except `FromChooseABundleScreen`, which has its own surface (`Commands/CardSelectCmd.cs`) <Badge text="verified" variant="success" />. The list is computed by reflection, so new entries are picked up; their arguments still need a review on every game update.
- The prefix reads the entry's arguments into `Current`: `CardSelectorPrefs`, the `source` argument or the `PlayerChoiceContext`'s `LastInvolvedModel`, a `CardPile`, an `EnchantmentModel` with its `amount`, `canSkip`. The finalizer clears it.
- A depth counter makes the outermost entry win (a removal calls `FromDeckGeneric`). The fields are `[ThreadStatic]`.
- `Current` must be read synchronously inside the entry, as the selector call is: once the entry's first await returns, it is gone. The Mod's UI adapter must do the same.
- Each host calls `ChoiceContexts.Patch(harmony)` once, **before any other patch** (SimWorker: `HeadlessPatches.Apply`). A caller compiled earlier, for example while another patch compiles its replacement method, can inline an entry's small async stub and bypass the prefix. This happened headless with SapphireSeed. In the simulator, a prompt without a context throws.

Both hosts share the patch, so they get the same context.

## 6. Decision-point predicates

Which screen is pending is decided by the host. It depends on what the UI would show, and only the host tracks that.

- **Sim:** `RunSession.Decide` ([Simulator §5](/en/arch/simulator/#sec-5)) looks at the open rewards sets (from `testSelector`) and the crystal sphere minigame, then at the room kind and the per-room `RoomProgress`. The game has settled when the combat is `WaitingForInput`, or otherwise when the Pump is empty and the executor is idle.
- **Mod:** the visible screen or overlay, plus node idle checks that must hold for about 3 frames ([Mod §3](/en/arch/mod/#sec-3)).

GameBridge keeps only logic predicates: `CombatActions.WaitingForInput`, `RewardActions.IsTerminal`, and the legal lists.

## 7. Uids and indexes

How an action names the thing it acts on:

| thing | named by |
|---|---|
| hand card (combat only) | its `NetCombatCardDb` id |
| creature (combat only) | its `CombatId` |
| option of a deck or grid prompt | its canonical index (`CardChoices.Canonical`), never a uid: there are no uids outside combat |
| entry of a UI-ordered list (rewards, event options, shop slots, rest options, treasure relics) | the game's index (the order is public) |
| map point | `col,row` |

For the Mod: SL clones must give the same numbers, so ids are fast-forwarded on load ([Simulator §7](/en/arch/simulator/#sec-7)).

## 8. Event stream

This is planned: where each event of the public history stream ([Protocol §5](/en/arch/protocol/#sec-5)) comes from.

- `CardPile.CardAdded` / `CardRemoved` on hand, draw, discard and exhaust (`Entities.Cards/CardPile.cs:35-37`) give draw, move and generate, plus the position for inserts into the draw pile <Badge text="inferred" variant="caution" />.
- `ActionExecutor.AfterActionExecuted` (`GameActions/ActionExecutor.cs:56`) gives plays.
- `CombatManager.TurnStarted`, plus a snapshot of the intents.
- Reshuffle = the draw pile refilled from the discard pile <Badge text="inferred" variant="caution" />; the shuffle command still has to be found.

Only publicly visible effects go in. Inserts at a random position are logged without the position.

## 9. Version adaptation

All knowledge of the game's API lives in three places: here, the SimWorker patches, and the Mod's node adapters. On a game update:

<Steps>

1. Re-decompile the game.
2. Rebuild.
3. Run selftest and the surface-coverage test ([Simulator §9](/en/arch/simulator/#sec-9)).
4. Produce the diff list of touched signatures.

</Steps>

## 10. Tests

- **Whitelist:** a per-field "UI shows it" table, reviewed for every new field.
- **Legal completeness** (Mod debug mode): every enabled UI control corresponds to one legal action.
- **Start round trip:** each legal action executes without an exception and changes `obs_hash` (or ends the surface).
- **Sim same as Mod:** the same state gives the same observation (R3 vs R4 logs).
