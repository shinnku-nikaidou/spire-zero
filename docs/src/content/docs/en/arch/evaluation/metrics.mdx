An evaluation plays one seed set with one champion and writes a report. This page is about what goes into it: the numbers, the seeds and the files. How two reports are compared is the next page, [Gates](/en/arch/evaluation/gates/).

## 1. The main metric

**The win rate** is the share of runs won, with its Wilson 95% interval ([§4](#sec-4)). It is what the game asks of a player, and since plan v7 it is what V decides by and what its gate compares ([Gates §10](/en/arch/evaluation/gates/#sec-10)).

**The mean floor reached** stands in while runs rarely win. Before 2026-10-30 no report won a single run, and 19 of the 23 committed reports won none. A difference of 0 won against 0 won says nothing, while floors still separate two brains, so the C# gate compares floors by default ([Gates §6](/en/arch/evaluation/gates/#sec-6)). The floor is the run's `TotalFloor` where it ended. A won run ends on floor 48, but so does a run that dies at the act 3 boss: of v6-3-2's 65 runs that reached that boss, 23 won and 42 died there, and all 65 count 48. The floor cannot tell a win from a death at the last door.

**HP entering each act's boss.** For each act, the report takes the first boss combat of every run that reached one, and gives how many runs got there and their HP, absolute and as a share of max HP, at its start (`Harness/Reports.cs:43-45`). v6-3-2 entered the act 1 boss in 290 of 300 runs with 63.4 HP (87% of max) on average. Bosses beaten are not in the report; the run records give them ([§8](#sec-8)).

## 2. What must be zero

A report is **void** when any of four counts is above zero (`Metrics.Void`, `Harness/Reports.cs:38`):

| count | what it is | why it voids |
|---|---|---|
| `random_decisions` | decisions answered by the `random` placeholder, summed over the runs' `brains` | a placeholder is no policy; a champion with one is not the brain it claims ([Harness: routing, budgets and seeds §1](/en/arch/harness/routing/#sec-1)) |
| `failed` | runs that threw: an error in the driver, a brain or a worker | the run did not finish as the game would |
| `truncated` | runs still going at `--max-decisions` (20,000) | the same |
| `game_errors` | the game's `Log.Error` lines, in the host and in the workers | the game itself reported a broken state |

A void report stays on the leaderboard, marked and ranked last; a gate gives a void challenger the verdict void, whatever its runs reached ([Gates §6](/en/arch/evaluation/gates/#sec-6)). Six committed reports are void: the five NoSL ones of 2026-10-27 whose card prompts or macro decisions were still random (1,687 to 11,723 random decisions each; `pimc-random` also had 3 failed runs, and `pimc-l0` 2 failed runs and 4 game errors), and the SL random-macro baseline of 2026-10-29 (11,006).

**Failed and truncated runs count as losses** in the win rate, and they are never played again: a seed fixes the run, so playing it again would only repeat it, and dropping it would pick seeds (`Harness/Reports.cs:51`). `learn/gauntlet.py` is the exception: it drops every record with a `failure` before it counts anything (`learn/gauntlet.py:44`), so a failed run there neither voids nor loses ([Gates §10](/en/arch/evaluation/gates/#sec-10)).

Two more counts belong here and do not exist:

- **`NumReloads`**, the game's count of real reloads, must be 0 in the real game <Badge text="planned" variant="caution" />. It is planned as a field of the mod's decision log; nothing reads it ([Environments: information §8](/en/arch/environments/information/#sec-8)).
- **Save exports in NoSL runs** have no counter. A simulated NoSL run never exports a node checkpoint (`SimWorker/Commands/RunCommand.cs:248`), and a NoSL `Dispatcher` refuses one (`Harness/Dispatcher.cs:184`), so an export would end the run as an error, not as a count.

## 3. Secondary metrics

The report's auxiliary numbers (`Harness/Reports.cs:46-64`):

| metric | how it is computed | v6-3-2, `promotion-1-300` |
|---|---|---|
| `elites_per_run` | elite combats per run | 1.08 |
| `card_reward_skips` | card rewards left with no card taken, of those offered, as a rate with its Wilson interval | 29.7% (1,588 of 5,351) |
| `gold_mean` | gold at the end of the run | 208 |
| `seconds_per_run` | the runs' wall time over the runs | 271.2 s |
| `ms_per_decision` | the runs' wall time over all their decisions | 488.6 ms |
| `surfaces` | decisions per surface, summed, most first | combat 118,832, rewards 15,676, map 11,260, … ([Simulator: whole runs §4](/en/arch/simulator/runs/#sec-4)) |

The elites taken, the skip rate, the gold and the HP at each boss are the conservatism monitors: a brain that learns to avoid risk shows it there before it shows in the floor ([Learning: the loop §13](/en/arch/learning/loop/#sec-13)). The run records give more than the report prints: bosses beaten, and where and in what room each run died ([§8](#sec-8)). Wall time depends on the host and its load, so `seconds_per_run` compares only runs played side by side.

**Planned** <Badge text="planned" variant="caution" />, and in no report:

- **Calibration**: how close V's predicted chance to win comes to the outcomes. A Brier score (the mean squared gap between the predicted chance and the run's 1 or 0) exists only in `v.train`'s held-out report for whole runs, `brier_held_out` against `brier_held_out_floor_only`, a model that knows only the floor (`learn/v/train.py:424-446`); no evaluation computes it, and nothing compares it with a constant prediction.
- **Search compute**: branches searched and clone queries per decision. Reports have wall time only.
- **Potion hoarding**: potions held unused.

## 4. The Wilson interval

A win rate measured on 300 runs is not the true rate: another 300 seeds would give another number. A **confidence interval** gives the range of true rates the measurement is consistent with. The textbook one, the normal (Wald) interval $\hat p \pm 1.96\sqrt{\hat p(1-\hat p)/n}$, breaks down exactly where this project lives: with few wins it reaches below 0, and with none it has no width at all, as if 0 wins in 200 proved the rate is 0.

The **Wilson interval** fixes that. Instead of centring on $\hat p$, it asks which true rates $p$ would put the observed $\hat p$ within 1.96 standard errors, $|\hat p - p| \le z\sqrt{p(1-p)/n}$, and solves for $p$. With $z = 1.96$:

$$
c = \frac{\hat p + \frac{z^2}{2n}}{1 + \frac{z^2}{n}}, \qquad
h = \frac{z\sqrt{\frac{\hat p(1-\hat p)}{n} + \frac{z^2}{4n^2}}}{1 + \frac{z^2}{n}}, \qquad
[\,\max(0, c - h),\ \min(1, c + h)\,].
$$

The centre moves towards one half, and the interval never leaves [0, 1]. Zero wins in 200 gives 0–1.9%: even a brain that never won on these seeds may win up to 1.9% of runs. One win in 300 gives 0.1–1.9%, where the normal interval would give −0.3% to 1.0%. The code is `Rate.Wilson` (`Harness/Reports.cs:10-17`; 0 runs give the interval 0–1), and every report and leaderboard prints a rate as `7.7 % (23/300, 5.2 %–11.2 %)` (`Rate.ToString`, `:19`).

## 5. Seed sets

A seed is the game's run seed string, 12 characters such as `3TZ33JATH5R5`. It fixes the map, the encounters, the rewards and every draw the game makes, so a seed set is a fixed set of games. Three kinds, kept disjoint:

- **train** seeds, unlimited, for self-play;
- **promotion** seeds, for gates and leaderboards;
- **final** seeds, generated and registered in the repo before any run on them, to be run in full and reported in full, so that no one can pick seeds that happen to look good. A formal claim needs at least 300 runs.

A seed set is a text file in `eval/seeds/`, one seed per line; `#` starts a comment and blank lines are skipped (`EvalReport.ReadSeeds`, `Harness/Reports.cs:164-165`). Each file's header names the command that made it and the date. The sets so far:

| file | seeds | made by | committed | used by |
|---|---|---|---|---|
| `promotion-1.txt` | 200 | `seeds --base 2 --n 200` | `2783e93`, 2026-10-27 | 20 reports |
| `promotion-1-300.txt` | 300: `promotion-1`'s 200 in its order, then 100 more | `seeds --base 2 --n 300` | `70b52b1`, 2026-10-30 | 3 reports |
| `promotion-1-500.txt` | 500: `promotion-1-300`'s 300 in its order, then 200 more | `seeds --base 2 --n 500` | `7ce03bd`, 2026-10-30 (its header gives 2026-10-31, the date in Taiwan) | plan v7's gate; no report yet |
| `final-1.txt` | 300 | `seeds --base 3 --n 300` | `2783e93`, 2026-10-27 | never run |
| `check-clone-loop.txt` | 29 of `promotion-1`'s seeds, picked by index | by hand | `c5d4552`, 2026-10-29 | the check of the clone-loop fix `f9b9655`; not a report set |

- **Train seeds** are `MakeSeed(1, i)`, what `run --seed 1 --start K` plays. The ledger hands them out in blocks of 100,000, one block per batch, so no two batches share a seed (`eval/silent/ledger.md`, [Learning: reference §5](/en/arch/learning/reference/#sec-5)). The elite gauntlet's 500 evaluation seeds are a block of the train generator kept out of training: `run --seed 1 --start 300000 --n 500`, entered in the ledger and never trained on.
- **Promotion seeds were extended, not rotated.** `promotion-1.txt`'s header still says to rotate to a `promotion-2` (base 4) once it is used up; no `promotion-2` exists. Each extension keeps the earlier seeds first in the same order, so a report on the larger set pairs with older reports on the shared seeds, and v6-3-2's 300 runs on `promotion-1-300` serve as its first 300 runs of `promotion-1-500`.
- **`final-1` has never been played**: every committed report is on `promotion-1` (20) or `promotion-1-300` (3).
- R1–R3 runs are started by the simulator; R4 runs would be started by the mod with the same seed ([Mod: auto-play and safety §2](/en/arch/mod/auto/#sec-2)).

## 6. How the seeds are made

`seeds --base B --n K` (default 300) prints `MakeSeed(B, i)` for i = 0…K−1 (`SimWorker/Commands/EvalCommands.cs:158-172`):

```csharp
// SimWorker/Simulation/GameSeeds.cs:7-12
public static string MakeSeed(int seed, int index)
{
    const string alphabet = "0123456789ABCDEFGHJKLMNPQRSTUVWXYZ"; // 34 characters: no I, no O
    var rng = new Random(unchecked(seed * 1_000_003 + index * 7_919) ^ 0x5eed);
    return string.Concat(Enumerable.Range(0, 12).Select(_ => alphabet[rng.Next(alphabet.Length)]));
}
```

The generator's seed is base × 1,000,003 + index × 7,919, wrapped to 32 bits, XORed with `0x5eed`. .NET's `new Random(int)` then takes its absolute value (with `int.MinValue` read as `int.MaxValue`), so two pairs (base, index) give the same seed string exactly when those absolute values agree. 7,919 is odd, so within one base no two indices below 2³² collide; across bases they can. Computed here for the sets in use: the train generator (base 1) first reaches a generator seed of `promotion-1-500` at train index 242,435,318, and one of `final-1` at index 1,100,994,758; `promotion-1-500` and `final-1` share none, and the elite gauntlet's evaluation block shares none with either. So the sets are disjoint for any block the ledger will hand out. `promotion-1.txt`'s header says that bases differing by less than 7,919 never share a generator seed; that holds only for small indices, since the arithmetic wraps.

A run's own randomness (the placeholders, the brains' seeds, exploration) comes from a hash of the seed string, never from the game's streams, so the seed alone fixes the whole run, whatever the set or the position in it ([Harness: routing, budgets and seeds §5](/en/arch/harness/routing/#sec-5)). That is what makes a champion's report reusable as its side of every later gate ([Gates §2](/en/arch/evaluation/gates/#sec-2)).

## 7. The report

```text
report --seeds FILE --records A[,B…] --out PATH [--previous OLD.json]
```

writes `PATH.json` and `PATH.md` and prints the Markdown (`SimWorker/Commands/EvalCommands.cs:10-53`). The seed set's name is the seed file's name without its extension. The records may come from several processes. `report` refuses, as a command-line mistake (exit 2):

- a boss gauntlet pilot's or an elite gauntlet's record (`auto_win`, `gauntlet`): some of its combats were never played;
- no runs; runs played by two configs (`config` differs in game, commit, champion, environment, rung or rule); two characters or ascensions; a seed run twice; a seed not in the set (`EvalReport.Of`, `Harness/Reports.cs:81-94`).

It sorts the runs into the set's order and dates the report with the day it was made, `yyyy-MM-dd` in the machine's local time. A report with fewer runs than the set is **partial**: its Markdown says so, the leaderboard leaves it out, and `gate --promote` refuses it.

**The JSON** is the `EvalReport` record (`Harness/Reports.cs:73`), in snake case with nulls left out:

| field | what it holds |
|---|---|
| `config` | `game` (the game's version, `v0.111.0`), `commit` (the simulator's full SHA; `-dirty` after it when `src/` had uncommitted changes at build, `SimWorker/Sts2Ai.SimWorker.csproj:40-48`; such a report is for development only), `champion` (the brains' name, [Harness: routing, budgets and seeds §1](/en/arch/harness/routing/#sec-1)), `env`, `rung`; `auto_win` or `gauntlet` never appear, since such records are refused |
| `seed_set`, `set_size`, `date` | the seed file's name and how many seeds it has; the report's date |
| `metrics.wins` | `{hits, of, value, low, high}`: runs won, with the Wilson interval |
| `metrics.floor_mean`, `floor_median` | the floor reached; the median of an even count is the mean of the two middle values |
| `metrics.bosses[]` | per act, counted from 0: `{act, reached, hp_mean, hp_fraction_mean}` |
| `metrics.random_decisions`, `failed`, `truncated`, `game_errors` | the must-be-zero counts ([§2](#sec-2)) |
| `metrics.surfaces`, `elites_per_run`, `card_reward_skips`, `gold_mean`, `ms_per_decision`, `seconds_per_run` | the secondary numbers ([§3](#sec-3)) |
| `metrics.void` | true when any must-be-zero count is above 0 |
| `runs[]` | every run record, in the set's order ([§8](#sec-8)) |

Because the report embeds every run record, combats included, the per-run data of every whole-run evaluation is in git, and any two reports on the same seeds can be paired afterwards; every figure of this chapter does so. What stays out of git are the decision logs, the elite gauntlet's records and the records of gates that did not promote, under `data/CHARACTER/ENV/` on the storage host ([Learning: reference §3](/en/arch/learning/reference/#sec-3)).

**The Markdown** (`EvalReport.Markdown`, `Harness/Reports.cs:96-150`) is one page:

- `# Evaluation DATE: ENV RUNG, SET`, then a **Void** line with its reasons and a **Partial** line when they apply;
- a table: game, commit, champion, environment and rung, and the seed set as `SET: N of M runs, CHARACTER A0`;
- **Main**: the win rate, the floor's mean and median, and each act's boss reached and the HP entering it;
- **Must be zero**: the four counts, then each failure message with how many runs it ended;
- **Auxiliary**: elites per run, card rewards skipped, gold at the end; seconds per run and milliseconds per decision; the surfaces;
- **Against DATE (CHAMPION, commit X)**, with `--previous OLD.json`, or when `gate --promote` writes the champion's successor: then and now for the win rate, the floor's mean, each act's boss reached, random decisions and failed runs; or "Not comparable" when the seed set, the environment or the rung differ.

**Names.** Reports go into `eval/CHARACTER/reports/` as `DATE-ENV-RUNG-SET-NAME.json` and `.md`, in lower case, NAME naming what played: `2026-10-30-sl-r1-promotion-1-300-plan-c2-l0-v6-3-2-clone-p0` is the SL champion's, the SL planner with the combat net c2, L0 with V v6-3-2 on the clone, prompts by `p0`. This is a convention; `--out` takes any path.

## 8. The run record

`run --records FILE` writes one run record per line, flushed as each run ends; a run stopped midway writes nothing ([Simulator: whole runs §5](/en/arch/simulator/runs/#sec-5)). The record (`RunRecord`, `Harness/RunRecords.cs:31-34`; built at `SimWorker/Commands/RunCommand.cs:281-294`):

| field | what it holds |
|---|---|
| `config` | `RunConfig` (`Harness/RunRecords.cs:24`): `game`, `commit`, `champion` (the brain's own name for itself, over the wire too), `env`, `rung` (always `R1`), and `auto_win: true` or `gauntlet: true` for the gauntlets' runs |
| `seed`, `character`, `ascension` | the run |
| `run_id` | the hash of the seed the brain knows the run by, the decision log's `run` ([Harness: the decision log §3](/en/arch/harness/decision-log/#sec-3)); it joins the two for learning |
| `outcome` | `won`, `lost`, `truncated` (the decision cap) or `failed` (it threw) |
| `act`, `floor`, `hp`, `max_hp`, `gold` | where and how it ended: `act` from 0, `floor` the run's total floor (48 for every won run so far); a won run says HP 0, since the game kills the players in the victory room |
| `combats[]` | each combat entered: `act`, `floor`, `encounter`, `room` (`Monster`, `Elite`, `Boss`), and `hp`, `max_hp`, `potions` when it was first seen in progress, before its first decision; then `end` |
| `combats[].end` | `died`, `hp`, `max_hp`, `potions` left, and `enemy_hp` (the living enemies' HP summed) of `enemy_max_hp` (every enemy's max HP); a won combat's enemies are gone, 0 of 0 (`Harness/RunRecords.cs:15`) |
| `surfaces`, `brains` | decisions per surface, and per brain that answered them |
| `card_rewards`, `card_rewards_skipped` | card rewards offered, and those left with no card taken |
| `game_errors`, `failure`, `elapsed_ms` | the game errors, the exception (`Type: first line`) of a failed run, and the run's wall time |

`end` is the target of the combat net's outcome head ([Learning: training the combat net §1](/en/arch/learning/combat-net/#sec-1)). The enemies' HP is in every combat's end since commit `7a9f845` (2026-10-29), on whole runs and on the gauntlets' runs alike (`SimWorker/Simulation/RunSession.cs:256-263`), so the reports played at `b013f95` have it and the earlier ones do not. The records of 2026-10-27 at `18fdb07` and `dc0105a` have no `end` at all.

**A missing end.** The record type says an `end` is missing only when a run stopped in the combat for another reason than a death (failed, truncated). The committed reports show more: `end` is written when the session settles, at the start of its next step (`SimWorker/Simulation/RunSession.cs:233-263`), and `run` stops stepping as soon as the run is over (`SimWorker/Commands/RunCommand.cs:260`), so a death that happens while a decision's own action runs leaves its combat with no `end`. Every report with ends has 1 to 13 such runs, each lost at 0 HP on the floor of that combat; v6-3-2's report has 8 of its 277 losses.

**Where runs die.** The records give what the report does not print. A lost run died in a combat when its last combat is on the floor it ended on and that combat ended in a death or has no end; otherwise it died outside combat (an event, for one). v6-3-2's 277 losses: 133 at a boss, 39 at an elite, 103 in a monster fight, 2 outside combat. `learn/gauntlet.py` uses the same rule but reads a missing end as "outside combat", so for v6-3-2 it reports 10 outside combat, 8 of them deaths in a fight (`learn/gauntlet.py:61-68`). Bosses beaten, counted from the ends: 276 of 290, 94 of 171 and 23 of 65 for the three acts.

## 9. The leaderboard

```text
leaderboard [--character SILENT]
```

reads every report in `eval/CHARACTER/reports/` and every champion file in `eval/CHARACTER/champions/`, writes `eval/CHARACTER/leaderboard.md` and prints it (`SimWorker/Commands/EvalCommands.cs:129-155`, `Leaderboard.Markdown`, `Harness/Reports.cs:174-237`). `learn/challenge.py` runs it after each promotion; otherwise it is run by hand and the board committed with the reports.

- **Boards.** Partial reports are left out. The others are grouped by character, ascension, seed set and rung, one `##` section each, in that order; inside, one `###` table per environment, NoSL first. Two characters, two ascensions or two environments are never ranked together.
- **Columns**: champion, date, commit (7 characters, `-dirty` kept), win rate (as a rate with its interval), floor mean, act 1 boss reached, seconds per run.
- **Order**: void reports last, then by win rate, then by mean floor. A void report gets "(void)" after its name; the report a champion file names gets "**(champion)**". A champion file that names a report of the other environment marks nothing on that board, which is why the NoSL board marks no champion today.
- **SL − NoSL**: after a board's tables, for each champion name with a report in both environments on that board (the latest of each), the runs paired by seed: the win-rate difference in percentage points and the floor difference, each as mean ± 1.96 SD/√n, the wins of each side, and how many seeds SL took further, as far and less far. No board has had one ([Evaluation §3](/en/arch/evaluation/#sec-3)).

The board today (`eval/silent/leaderboard.md`) has two sections: `promotion-1` with 13 NoSL and 7 SL reports, and `promotion-1-300` with the 3 SL reports, v6-3-2 marked. Every report is on it, not only the champions'; the champions and their history are on [Champions and baselines](/en/arch/evaluation/champions/).

**The elite gauntlet's board**, `eval/silent/gauntlet-leaderboard.md`, is kept by hand, since `leaderboard` reads whole-run reports only and the gauntlet's records are refused by `report`. One row per V on the gauntlet's 500 evaluation seeds: progress ± its standard error, each act's boss beaten of reached, runs won, elites per run, elite deaths, the paired difference against the champion before it, and where the records are. Plan v6 ended with it ([Gates §11](/en/arch/evaluation/gates/#sec-11)).

## 10. Tests

- `Harness/EvalReportTests` (`src/Sts2Ai.Tests`), 3 tests: runs are sorted into the set's order, with their floor mean, and the report is not void; runs that break the set are rejected (none, a seed twice, a seed not in the set, another config, character or ascension); a random decision or a failed run voids it. The fixture config is `v0.111.0`, `abc1234`, NoSL, R1 (`src/Sts2Ai.Tests/Fixtures.cs:25`).
- Nothing tests `Rate.Wilson`, the Markdown, the leaderboard or `MakeSeed`. The Wilson figure above is checked against the intervals the reports store.
