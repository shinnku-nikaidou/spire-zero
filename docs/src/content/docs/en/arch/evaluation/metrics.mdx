An evaluation plays one seed set with one champion and writes a report. This page is about what goes into it: the numbers, the seeds and the files. How two reports are compared is the next page, [Gates](/en/arch/evaluation/gates/). The worked numbers below come from one committed report, the **example report**: the champion's Necrobinder on `promotion-1-100`, 47 won of 100.

## 1. The main metric

**The win rate** is the share of runs won, with its Wilson 95% interval ([§4](#sec-4)). It is what the game asks of a player, what V decides by, and what the wins gate compares ([Gates §10](/en/arch/evaluation/gates/#sec-10)).

**The mean floor reached** stands in when wins are rare. A difference of 0 won against 0 won says nothing, while floors still separate two brains, so both gates list the floor difference beside their verdict on wins ([Gates §6](/en/arch/evaluation/gates/#sec-6), [§10](/en/arch/evaluation/gates/#sec-10)). The floor is the run's `TotalFloor` where it ended. A won run ends on floor 48, but so does a run that dies at the act 3 boss: of the example report's 74 runs that reached that boss, 47 won and 27 died there, and all 74 count 48. The floor cannot tell a win from a death at the last door.

**HP entering each act's boss.** For each act, the report takes the first boss combat of every run that reached one, and gives how many runs got there and their HP, absolute and as a share of max HP, at its start (`Harness/Reports.cs:46-48`). In the example report, 95 of 100 runs entered the act 1 boss, with 48.7 HP (69% of max) on average. Bosses beaten are not in the report; the run records give them ([§8](#sec-8)).

## 2. What must be zero

A report is **void** when any of four counts is above zero (`Metrics.Void`, `Harness/Reports.cs:41`):

| count | what it is | why it voids |
|---|---|---|
| `random_decisions` | decisions answered by a placeholder, the macro side's `random` or the combat side's `play`, summed over the runs' `brains` (`Metrics.Placeholders`, `Harness/Reports.cs:39`) | a placeholder is no policy; a champion with one is not the brain it claims ([Harness: routing, budgets and seeds §1](/en/arch/harness/routing/#sec-1)) |
| `failed` | runs that threw: an error in the driver, a brain or a worker | the run did not finish as the game would; 0 in a report made now, since failed runs are left out (below) |
| `truncated` | runs still going at `--max-decisions` (20,000) | the same |
| `game_errors` | the game's `Log.Error` lines, in the host and in the workers | the game itself reported a broken state |

A void report stays on the leaderboard, marked and ranked last; a gate gives a void challenger the verdict void, whatever its runs reached ([Gates §6](/en/arch/evaluation/gates/#sec-6)).

**A failed run is as if never set.** `report` and `gate` read through `RunRecord.Read`, which leaves out every record whose outcome is `failed`, and `RunRecord.SeedsLeft` takes its seed out of the set, so 2 failed of 500 make a report of 498 of 498, neither void nor partial (`Harness/RunRecords.cs:34-41`). A run fails for reasons outside the brain, such as a crashed process or a machine fault, and says nothing of the brain. `learn/gate.py` and `v.train` drop them too (`learn/gate.py:43`, `learn/v/data.py:64`), and a pair needs both runs ([Gates §10](/en/arch/evaluation/gates/#sec-10)).

**Truncated runs count as losses** in the win rate, and they are never played again: a seed fixes the run, so playing it again would only repeat it, and dropping it would pick seeds (`Harness/Reports.cs:54`).

Two more counts belong here and do not exist:

- **`NumReloads`**, the game's count of real reloads, must be 0 in the real game <Badge text="planned" variant="caution" />. It is planned as a field of the mod's decision log; nothing reads it ([Environments: information §8](/en/arch/environments/information/#sec-8)).
- **Save exports in NoSL runs** have no counter. A simulated NoSL run never exports a node checkpoint (`SimWorker/Commands/RunCommand.cs:237`), and a NoSL `Dispatcher` refuses one (`Harness/Dispatcher.cs:173`), so an export would end the run as an error, not as a count.

## 3. Secondary metrics

The report's auxiliary numbers (`Harness/Reports.cs:49-67`):

| metric | how it is computed | the example report |
|---|---|---|
| `elites_per_run` | elite combats per run | 3.36 |
| `card_reward_skips` | card rewards left with no card taken, of those offered, as a rate with its Wilson interval | 35.4% (701 of 1,983) |
| `gold_mean` | gold at the end of the run | 182 |
| `seconds_per_run` | the runs' wall time over the runs | 1,045.7 s |
| `ms_per_decision` | the runs' wall time over all their decisions | 1,358.4 ms |
| `surfaces` | decisions per surface, summed, most first | combat 59,579, rewards 5,668, map 4,237, … ([Simulator: whole runs §4](/en/arch/simulator/runs/#sec-4)) |

The elites taken, the skip rate, the gold and the HP at each boss are the conservatism monitors: a brain that learns to avoid risk shows it there before it shows in the floor ([Learning: the loop §13](/en/arch/learning/loop/#sec-13)). The run records give more than the report prints: bosses beaten, and where and in what room each run died ([§8](#sec-8)). Wall time depends on the machine and its load, so `seconds_per_run` compares only runs played side by side.

**Planned** <Badge text="planned" variant="caution" />, and in no report:

- **Calibration**: how close V's predicted chance to win comes to the outcomes. A Brier score (the mean squared gap between the predicted chance and the run's 1 or 0) exists only in `v.train`'s held-out report for whole runs, `brier_held_out` against `brier_held_out_floor_only`, a model that knows only the floor (`learn/v/train.py:169-184`); no evaluation computes it, and nothing compares it with a constant prediction.
- **Search compute**: branches searched and clone queries per decision. Reports have wall time only.
- **Potion hoarding**: potions held unused.

## 4. The Wilson interval

A win rate measured on 300 runs is not the true rate: another 300 seeds would give another number. A **confidence interval** gives the range of true rates the measurement is consistent with. The textbook one, the normal (Wald) interval $\hat p \pm 1.96\sqrt{\hat p(1-\hat p)/n}$, breaks down exactly where this project lives: with few wins it reaches below 0, and with none it has no width at all, as if 0 wins in 200 proved the rate is 0.

The **Wilson interval** fixes that. Instead of centring on $\hat p$, it asks which true rates $p$ would put the observed $\hat p$ within 1.96 standard errors, $|\hat p - p| \le z\sqrt{p(1-p)/n}$, and solves for $p$. With $z = 1.96$:

$$
c = \frac{\hat p + \frac{z^2}{2n}}{1 + \frac{z^2}{n}}, \qquad
h = \frac{z\sqrt{\frac{\hat p(1-\hat p)}{n} + \frac{z^2}{4n^2}}}{1 + \frac{z^2}{n}}, \qquad
[\,\max(0, c - h),\ \min(1, c + h)\,].
$$

The centre moves towards one half, and the interval never leaves [0, 1]. Zero wins in 200 gives 0–1.9%: even a brain that never won on these seeds may win up to 1.9% of runs. One win in 300 gives 0.1–1.9%, where the normal interval would give −0.3% to 1.0%. The code is `Rate.Wilson` (`Harness/Reports.cs:10-17`; 0 runs give the interval 0–1), and every report and leaderboard prints a rate as `47.0 % (47/100, 37.5 %–56.7 %)` (`Rate.ToString`, `:19`).

## 5. Seed sets

A seed is the game's run seed string, 12 characters such as `3TZ33JATH5R5`. It fixes the map, the encounters, the rewards and every draw the game makes, so a seed set is a fixed set of games. Three kinds, kept disjoint:

- **train** seeds, unlimited, for self-play only;
- **promotion** seeds, for gates and leaderboards;
- **final** seeds, generated and registered in the repo before any run on them, to be run in full and reported in full, so that no one can pick seeds that happen to look good. A formal claim needs at least 300 runs.

A seed set is a text file in `eval/seeds/`, one seed per line; `#` starts a comment and blank lines are skipped (`EvalReport.ReadSeeds`, `Harness/Reports.cs:172-174`). Each file's header says how it was made. The sets:

| file | seeds | made by | used for |
|---|---|---|---|
| `promotion-1.txt` | 200 | `seeds --base 2 --n 200` | reports on 200 seeds |
| `promotion-1-300.txt` | 300: `promotion-1`'s 200 in its order, then 100 more | `seeds --base 2 --n 300` | reports on 300 seeds |
| `promotion-1-100.txt`, `promotion-101-300.txt` | 100 and 200: `promotion-1-300` cut in two, in its order | cut from `promotion-1-300.txt` | the first: the wins gate, every character, and the champion's reports ([Gates §10](/en/arch/evaluation/gates/#sec-10)); the second: runs on the rest of the set |
| `promotion-1-200.txt` | 200: `promotion-1-300`'s first 200, the same seeds as `promotion-1` | cut from `promotion-1-300.txt` | reports on 200 seeds |
| `a10-check-1.txt` | 200 | `seeds --base 4 --n 200` | A10 win rates of nets that trained on, or went on from, other sets' data; registered before any run on it |
| `final-1.txt` | 300 | `seeds --base 3 --n 300` | never run |
| `check-clone-loop.txt` | 29 of `promotion-1`'s seeds, picked by index | by hand | a development check; not a report set |

- **Train seeds and test seeds never meet.** A self-play job plays train seeds only, and an eval job a file of `eval/seeds/` only; training refuses a list holding an eval job's runs ([Learning: reference §5](/en/arch/learning/reference/#sec-5)). `promotion-1-300` and its parts, `final-1` and `a10-check-1` have never been trained on.
- **`eval/seeds/retired/`** holds what can no longer test: `promotion-1-500` (`seeds --base 2 --n 500`, `promotion-1-300` and then 200 more), since medium runs on its last 200 seeds are in data the champion's combat net has learned from.
- **Train seeds** are `MakeSeed(1, i)`, what `run --seed 1 --start K` plays. Each dataset plays its own block of 100,000 indices, so no two datasets share a seed ([Learning: reference §5](/en/arch/learning/reference/#sec-5)).
- **Promotion sets nest.** Each larger set keeps the smaller one's seeds first, in the same order, so a report on the larger set pairs with reports on the smaller one on the shared seeds.
- **`final-1` has never been played**: every committed report is on a promotion set.
- R1–R3 runs are started by the simulator; R4 runs would be started by the mod with the same seed ([Mod: auto-play and safety §2](/en/arch/mod/auto/#sec-2)).

## 6. How the seeds are made

`seeds --base B --n K` (default 300) prints `MakeSeed(B, i)` for i = 0…K−1 (`SimWorker/Commands/EvalCommands.cs:161-176`):

```csharp
// SimWorker/Simulation/GameSeeds.cs:7-12
public static string MakeSeed(int seed, int index)
{
    const string alphabet = "0123456789ABCDEFGHJKLMNPQRSTUVWXYZ"; // 34 characters: no I, no O
    var rng = new Random(unchecked(seed * 1_000_003 + index * 7_919) ^ 0x5eed);
    return string.Concat(Enumerable.Range(0, 12).Select(_ => alphabet[rng.Next(alphabet.Length)]));
}
```

The generator's seed is base × 1,000,003 + index × 7,919, wrapped to 32 bits, XORed with `0x5eed`. .NET's `new Random(int)` then takes its absolute value (with `int.MinValue` read as `int.MaxValue`), so two pairs (base, index) give the same seed string exactly when those absolute values agree. 7,919 is odd, so within one base no two indices below 2³² collide; across bases they can. Computed here for the sets in use: the train generator (base 1) first reaches a generator seed of `a10-check-1` at train index 40,134,134, one of `promotion-1-300` at index 242,435,318, and one of `final-1` at index 1,100,994,758; the three share none. So the sets are disjoint for any train index below 40,134,134. `promotion-1.txt`'s header says that bases differing by less than 7,919 never share a generator seed; that holds only for small indices, since the arithmetic wraps.

A run's own randomness (the placeholders, the brains' seeds, exploration) comes from a hash of the seed string, never from the game's streams, so the seed alone fixes the whole run, whatever the set or the position in it ([Harness: routing, budgets and seeds §5](/en/arch/harness/routing/#sec-5)). That is what makes a champion's report reusable as its side of every later gate ([Gates §2](/en/arch/evaluation/gates/#sec-2)).

## 7. The report

```text
report --seeds FILE --records A[,B…] --out PATH [--previous OLD.json]
```

writes `PATH.json` and `PATH.md` and prints the Markdown (`SimWorker/Commands/EvalCommands.cs:10-51`). The seed set's name is the seed file's name without its extension. The records may come from several processes. `report` refuses, as a command-line mistake (exit 2):

- no runs, or runs played by two configs (`config` differs in game, commit, champion or environment), or a run played by the auto-win rule, which is data for training, not a run of the game ([Simulator: whole runs §8](/en/arch/simulator/runs/#sec-8));
- two characters or ascensions; a seed run twice; a seed not in the set (`EvalReport.Of`, `Harness/Reports.cs:89-103`).

It sorts the runs into the set's order and dates the report with the day it was made, `yyyy-MM-dd` in the machine's local time. A report with fewer runs than the set is **partial**: its Markdown says so, the leaderboard leaves it out, and `gate --promote` refuses it.

**The JSON** is the `EvalReport` record (`Harness/Reports.cs:76`), in snake case with nulls left out:

| field | what it holds |
|---|---|
| `config` | `game` (the game's version, `v0.111.0`), `commit` (the simulator's full SHA; `-dirty` after it when `src/` had uncommitted changes at build, `SimWorker/Sts2Ai.SimWorker.csproj:40-48`; such a report is for development only), `champion` (the brains' name, [Harness: routing, budgets and seeds §1](/en/arch/harness/routing/#sec-1)) and `env` |
| `seed_set`, `set_size`, `date` | the seed file's name and how many seeds it has; the report's date |
| `metrics.wins` | `{hits, of, value, low, high}`: runs won, with the Wilson interval |
| `metrics.floor_mean`, `floor_median` | the floor reached; the median of an even count is the mean of the two middle values |
| `metrics.bosses[]` | per act, counted from 0: `{act, reached, hp_mean, hp_fraction_mean}` |
| `metrics.random_decisions`, `failed`, `truncated`, `game_errors` | the must-be-zero counts ([§2](#sec-2)) |
| `metrics.surfaces`, `elites_per_run`, `card_reward_skips`, `gold_mean`, `ms_per_decision`, `seconds_per_run` | the secondary numbers ([§3](#sec-3)) |
| `metrics.void` | true when any must-be-zero count is above 0 |
| `runs[]` | every run record, in the set's order ([§8](#sec-8)) |

Because the report embeds every run record, combats included, the per-run data of every whole-run evaluation is in git, and any two reports on the same seeds can be paired afterwards; every figure of this chapter does so. What stays out of git are the decision logs and the records of gates that did not promote, under `data/CHARACTER/ENV/` ([Learning: reference §3](/en/arch/learning/reference/#sec-3)).

**The Markdown** (`EvalReport.Markdown`, `Harness/Reports.cs:105-156`) is one page:

- `# Evaluation DATE: ENV, SET`, then a **Void** line with its reasons and a **Partial** line when they apply;
- a table: game, commit, champion and environment, and the seed set as `SET: N of M runs, CHARACTER AN`;
- **Main**: the win rate, the floor's mean and median, and each act's boss reached and the HP entering it;
- **Must be zero**: the four counts, then each failure message with how many runs it ended;
- **Auxiliary**: elites per run, card rewards skipped, gold at the end; seconds per run and milliseconds per decision; the surfaces;
- **Against DATE (CHAMPION, commit X)**, with `--previous OLD.json`, or when `gate --promote` writes the champion's successor: then and now for the win rate, the floor's mean, each act's boss reached, random decisions and failed runs; or "Not comparable" when the seed set or the environment differs.

**Names.** Reports go into `eval/CHARACTER/reports/` as `DATE-ENV-LEVEL-SET-NAME.json` and `.md`, in lower case: LEVEL is the ascension, `a0` or `a10`; NAME names what played: in `DATE-sl-a0-promotion-1-100-plan-C-l0-V-clone-first`, the SL planner with the combat net `C`, L0 with V `V` on the clone, combat prompts no search weighs by `first`. This is a convention; `--out` takes any path.

## 8. The run record

`run --records FILE` writes one run record per line, flushed as each run ends; a run stopped midway writes nothing ([Simulator: whole runs §5](/en/arch/simulator/runs/#sec-5)). The record (`RunRecord`, `Harness/RunRecords.cs:27-30`; built at `SimWorker/Commands/RunCommand.cs:274-279`):

| field | what it holds |
|---|---|
| `config` | `RunConfig` (`Harness/RunRecords.cs:20`): `game`, `commit`, `champion` (the brain's own name for itself, over the wire too) and `env`; and `auto_win`, the acts of the auto-win rule as indexes from 0, only in a run played by it, which no report or gate takes |
| `seed`, `character`, `ascension` | the run |
| `run_id` | the hash of the seed the brain knows the run by, the decision log's `run` ([Harness: the decision log §3](/en/arch/harness/decision-log/#sec-3)); it joins the two for learning |
| `outcome` | `won`, `lost`, `truncated` (the decision cap) or `failed` (it threw) |
| `act`, `floor`, `hp`, `max_hp`, `gold` | where and how it ended: `act` from 0, `floor` the run's total floor (48 for every won run so far); a won run says HP 0, since the game kills the players in the victory room |
| `combats[]` | each combat entered: `act`, `floor`, `encounter`, `room` (`Monster`, `Elite`, `Boss`), and `hp`, `max_hp`, `potions` when it was first seen in progress, before its first decision; then `end` |
| `combats[].end` | `died`, and the `hp`, `max_hp` and `potions` left (`Harness/RunRecords.cs:14`) |
| `surfaces`, `brains` | decisions per surface, and per brain that answered them |
| `card_rewards`, `card_rewards_skipped` | card rewards offered, and those left with no card taken |
| `game_errors`, `failure`, `elapsed_ms` | the game errors, the exception (`Type: first line`) of a failed run, and the run's wall time |

`end` is the target of the combat net's outcome head ([Learning: training the combat net §1](/en/arch/learning/combat-net/#sec-1)).

**A missing end.** The record type says an `end` is missing only when a run stopped in the combat for another reason than a death (failed, truncated). `RunSession` writes the `end` when it settles, and right after a decision whose own action ended the run, such as a card in hand at the turn's end or a play that costs HP; a combat the run died in before its first decision gets its entry then, at 0 HP (`SimWorker/Simulation/RunSession.cs:247-251, 260, 265-272`). The example report has no lost run whose last combat lacks an `end`.

**Where runs die.** The records give what the report does not print. A lost run died in a combat when its last combat is on the floor it ended on and that combat ended in a death or has no end; otherwise it died outside combat (an event, for one). The example report's 53 losses: 43 at a boss, 8 at an elite, 2 in a monster fight, none outside combat. `learn/gate.py` uses the same rule but reads a missing end as "outside combat" (`learn/gate.py:59-66`); with no end missing it gives the same counts. Bosses beaten, counted from the ends: 87 of 95, 75 of 83 and 47 of 74 for the three acts.

## 9. The leaderboard

```text
leaderboard [--character SILENT]
```

reads every report in `eval/CHARACTER/reports/` and every champion file in `eval/champions/`, writes `eval/CHARACTER/leaderboard.md` and prints it (`SimWorker/Commands/EvalCommands.cs:130-159`, `Leaderboard.Markdown`, `Harness/Reports.cs:183-243`). It is run by hand, and the board committed with the reports.

- **Boards.** Partial reports are left out. The others are grouped by character, ascension and seed set, one `##` section each, in that order; inside, one `###` table per environment, NoSL first. Two characters, two ascensions or two environments are never ranked together.
- **Columns**: champion, date, commit (7 characters, `-dirty` kept), win rate (as a rate with its interval), floor mean, act 1 boss reached, seconds per run.
- **Order**: void reports last, then by win rate, then by mean floor. A void report gets "(void)" after its name; the report a champion file names for the character gets "**(champion)**". A champion file that names a report of the other environment marks nothing on that board; the NoSL file names no report, so the NoSL board marks no champion.
- **SL − NoSL**: after a board's tables, for each champion name with a report in both environments on that board (the latest of each), the runs paired by seed: the win-rate difference in percentage points and the floor difference, each as mean ± 1.96 SD/√n, the wins of each side, and how many seeds SL took further, as far and less far. No board has had one ([Evaluation §3](/en/arch/evaluation/#sec-3)).

Each character's board, `eval/CHARACTER/leaderboard.md`, has one section per ascension and seed set and lists every complete report, not only the champions'. The champion files are on [Champions and baselines](/en/arch/evaluation/champions/).

## 10. Tests

- `Harness/EvalReportTests` (`src/Sts2Ai.Tests`), 4 tests: runs are sorted into the set's order, with their floor mean, and the report is not void; runs that break the set are rejected (none, a seed twice, a seed not in the set, another config, character or ascension); a placeholder's decision (`random` or `play`) or a failed run in a report's own runs voids it; `RunRecord.Read` leaves failed runs out and `SeedsLeft` their seeds. The fixture config is `v0.111.0`, a placeholder commit `abc1234`, NoSL (`src/Sts2Ai.Tests/Fixtures.cs:32`).
- Nothing tests `Rate.Wilson`, the Markdown, the leaderboard or `MakeSeed`. The Wilson figure above is checked against the intervals the reports store.
