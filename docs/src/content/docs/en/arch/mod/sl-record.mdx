In SL the brain plans a combat on an exact clone of the current node: the game as it was when the player arrived at the map point, replayed to the decision ([Environments: information §7](/en/arch/environments/information/#sec-7)). The simulator has that for free, since it holds the run. The mod does not: the run is the real game's, and the brain is another process. So the mod keeps a record of the node, its checkpoint and every step the player took in it since, and sends it to the brain before each SL decision. A worker then loads the checkpoint and replays the steps, exactly as it would for a node of its own ([Simulator: worlds and the SL clone §3](/en/arch/simulator/worlds/#sec-3)–[§4](/en/arch/simulator/worlds/#sec-4)). This page is `NodeRecord.cs`, and how it was checked.

The record is kept in both environments, with assist off and with no brain too, so switching to SL works in the room the player is in. Only SL sends it.

## 1. What the record is

| member | what |
|---|---|
| `Node` | the node's number, from 0 at the first node the game entered while the mod ran in this run (a new `RunState` object starts again from −1); −1 before |
| `Checkpoint` | the node's SL checkpoint, a JSON string; null when the node has none |
| `Steps` | the node's steps so far, each a trace line `surface action`, as the simulator's own trace names it: `combat play:3:1`, `map map:4,10`, `card_choice 0,2` |
| `Broken` | why the node cannot be cloned, or null |
| `Running(surface)` | whether a step taken on that surface still plays out ([§4](#sec-4)) |
| `Seen(asking)` | told each frame the decision on screen, which the player's next answer is read against |

A step is only added while the node has a checkpoint and is not broken.

## 2. The checkpoint

**Where.** When the player arrives at a map point, the game saves the run: `SaveManager.SaveRun` with no finished room, called by `RunManager.EnterMapCoordInternal` after it has left the old rooms, cleared the screens and synced the combat state. The simulator takes its checkpoint at that same moment ([Simulator: worlds and the SL clone §3](/en/arch/simulator/worlds/#sec-3)). The mod's prefix on `SaveRun` (`Saving`) starts a node when the finished room is null; the saves inside a room (an event's, a combat's) pass a room and are not node starts. A run's start enters its first point the same way.

**What.** `GameBridge.Checkpoint.Take(me)`: the game's whole save as `SaveManager.ToJson(RunManager.ToSave(null))` builds it, and each relic's state that the save drops ([GameBridge: reading the game §7](/en/arch/gamebridge/observe/#sec-7)). It is opaque to everything but the simulator. The save carries the run's seed and the state of every random stream; SL may know them, as the clone replays the room's true outcomes ([Environments: information §2](/en/arch/environments/information/#sec-2)).

**A continued run.** Loading a saved run enters its saved point again without saving (`RunManager.LoadIntoLatestMapCoord`), so the mod patches that too (`Continuing`):

- saved on arrival (the save has no finished room): the node starts as an arrival does, with a checkpoint taken there;
- saved later in the room (after its fight, after an ancient): the room's start is gone, and the node is broken from the start: "the run was continued from a save made after this room began".

**Starting a node** (`Enter`, `NodeRecord.cs:149-158`): only in a single-player run; `Node` goes up by one; the steps and the screen are cleared; the checkpoint is taken, or the node is broken. A checkpoint that throws leaves the node without one ("no checkpoint was taken"), and logs the error.

The mod never writes `current_run.save`, which is cloud-synced, or any other file under the profile: the prefix only reads.

## 3. Every step, where the game commits it

Each of the player's decisions is read where the game commits it: at the entry points the simulator's own action starts call too ([GameBridge: actions per surface §7](/en/arch/gamebridge/actions/#sec-7)). So the step is known exactly, before the game plays it, and named with GameBridge's own helpers, so a recorded step is the action the simulator would have played.

| the player | hooked (Harmony prefix) | step |
|---|---|---|
| plays a card, uses or throws away a potion, ends the turn, travels | `ActionQueueSynchronizer.RequestEnqueue` with `PlayCardAction`, `UsePotionAction`, `DiscardPotionGameAction`, `EndPlayerTurnAction`, `VoteForMapCoordAction` | `combat play:C[:T]`, `combat potion:S[:T]`, `combat end_turn`; outside combat the belt's `potion:S` or `discard_potion:S` on the screen it is used on; `map map:C,R` |
| answers a card prompt, a card reward, a bundle | `PlayerChoiceSynchronizer.SyncLocalChoice` | `card_choice I,J` (the game's own indexes), `card_reward card:I` or `card_alt:ID`, `bundle bundle:I` |
| picks an event option, a rest option | `EventSynchronizer.ChooseLocalOption`, `RestSiteSynchronizer.ChooseLocalOption` | `event event:I`, `rest rest:ID` |
| takes a reward, proceeds from the rewards | `RewardsSetSynchronizer.SelectLocalReward`; on a rewards screen `SkipLocalRewardsSet`, `RunManager.ProceedFromTerminalRewardsScreen`, `ActChangeSynchronizer.SetLocalPlayerReady` | `rewards reward:I`, `rewards rewards_done` |
| takes or skips a chest's relic | `TreasureRoomRelicSynchronizer.PickRelicLocally` | `treasure relic:I`, `treasure relic_skip` |
| buys, removes a card | `MerchantEntry.OnTryPurchaseWrapper`, `MerchantCardRemovalEntry.OnTryPurchaseWrapper` | `shop buy:I`, `shop remove` |
| divines | `CrystalSphereMinigame.CellClicked` | `crystal_sphere big:X,Y`, `crystal_sphere small:X,Y` |
| leaves an event, a shop, a rest site | the map asking for the travel ([§5](#sec-5)) | `event proceed`, `shop leave`, `rest leave` |

The details that make each step exact (`NodeRecord.cs:162-271`):

- **A card play's card** comes from the action's `NetCombatCard`: the action looks its card up only once it runs, so reading `PlayCardAction.Card` at the enqueue would miss it. A target is kept only for the cards and potions that pick one, as the legal actions name them (`CombatActions.PlayOf`, `PotionOf`).
- **A potion** used in combat (`WasEnqueuedInCombat`) is a combat step; outside combat it is the belt's action on the screen it was used on, if that screen offers it.
- **A travel** must be one the map offers.
- **A card prompt's picks** are the game's own indexes into its options in the game's order, kept as the prompt's `Source` when it was read; a skipped single pick (−1) is no pick. The brain answers in canonical indexes ([The main loop §5](/en/arch/mod/loop/#sec-5)); the trace keeps the game's, as the simulator's does.
- **A card reward's** pick is an index into the screen's cards, then its alternatives, as both the game and the legal actions list them.
- **A reward's** index is its place in the rewards screen's set.
- **No step**: a purchase that changes nothing (too little gold, sold out), or a free one (`ignoreCost`, a relic buying for the player); a divination that uncovers nothing; the calls that leave a chest, or a fight without rewards, which are the same calls as a rewards screen's proceed: only those on a rewards screen are steps, and some screens call two of them, so the first clears the screen.
- **Faster than the screen settles.** The hooks fire at the commit, not at the idle check, so steps the player takes faster than 3 frames apart are still recorded, in order.

Why hooks and not a diff of the states before and after: a diff cannot tell two copies of a card apart, and misses the actions a player queues faster than the screen settles. This settled the open question of how to capture the player's actions.

## 4. Steps that play out

An event option, a rest option, a reward, a purchase and a divination run as the game's own tasks, and the screen shows a step's result only once its task ends. Until then, the screen still shows the decision it answered: an event's gold from before its option, for instance. So postfixes on the same entry points note each step's task by the surface it was taken on (an event's from the synchronizer's pending option tasks), and `Running(surface)` says whether one is still running; `Assist` asks nothing on that surface until it ends ([The main loop §7](/en/arch/mod/loop/#sec-7)). The simulator waits for its running tasks before its next decision in the same way ([Simulator: whole runs §3](/en/arch/simulator/runs/#sec-3)).

## 5. Leaving a room

In the simulator, leaving an event, a shop or a rest site is a decision of its own: `proceed` or `leave`. In the game, the player just opens the map and travels. So the mod takes the leave when the map asks for the travel: when the map is first seen after one of those screens, or when a travel is queued while the last screen seen was not the map, the leave is added for the room's surface, if that screen offered it (`Leave`, `NodeRecord.cs:116-133`). The travel itself follows as `map map:C,R`.

## 6. A broken record

A step the simulator has no decision for ends the record for the rest of the node: the clone could not be replayed past it.

| reason in the log | what happened |
|---|---|
| "a potion thrown away in combat" | the simulator offers no discard in combat |
| "a turn end taken back" | `UndoEndPlayerTurnAction` |
| "a travel to X, which the map does not offer" | |
| "potion:S on a screen that does not offer it" | a belt action outside combat on a screen without it |
| "a card picked outside the prompt's options" | |
| "a card reward closed unanswered" | |
| "a T choice on S" | a choice on a screen the mod does not read, or a card prompt that came without its context |
| "a reward taken from no rewards screen" | |
| "Type: message" | an exception inside a guarded hook, also logged as an error |
| "no checkpoint was taken", "the run was continued from a save made after this room began" | the node never had a checkpoint ([§2](#sec-2)) |

A break is logged once, with the node and its step count: "SL record of node N broken after K steps: …".

**A hook never lets an exception reach the game.** It runs inside the game's own call, so `Guard` catches it and breaks the record instead: around the save and continue hooks, the action queue, the choices, the rest option, the purchases and the divination. The event option, reward, proceed and relic hooks and the task postfixes only add a line or a task, and are not wrapped.

**What a broken node means.** SL combat decisions are not asked in that node: the panel says "No SL clone of this room", with the reason, "the next room has one". Card prompts and the decisions outside combat are still asked, and no node message is sent for them. That suits the brain the mod usually runs, the NoSL champion's file with the SL planner (`first` for combat prompts, L0 on screen afterstates, which need no clone). A brain whose macro side plays on the clone (`--afterstates clone`, the SL champion's) would then build its clones from the previous node's checkpoint and steps, and before any checkpoint fails with "an SL decision before any node checkpoint", which turns the mod off until the next `hello` (`Harness/Dispatcher.cs:191-195`). Holding back every SL decision of a broken node would close that gap.

## 7. What is sent, and when

Before each SL decision, `Assist.SendNode` (`Assist.cs:396-405`) sends what the brain has not had yet ([Protocol: the wire §6](/en/arch/protocol/wire/#sec-6)):

1. `node_checkpoint` with the node's number and checkpoint, once per node: when the node differs from the last one sent in this run;
2. `node_action` for each step not sent yet, with the node's number and the step's number in the node, from 0.

Then the `decision`. Steps after the node's last decision, such as its travel, are never needed and never sent. A node without a checkpoint sends nothing. After a reconnect or a new `hello`, the current node is sent again from its checkpoint.

The brain's Harness keeps the latest checkpoint and its trace, and requires node numbers to rise within a run ([Harness §4](/en/arch/harness/#sec-4)). In NoSL the record is kept but never sent; a host that did send one would get an `error`, since Harness refuses node checkpoints in NoSL.

## 8. Checking it in the game

**The round trip.** `brain --wire FILE` writes every message the hosts send. `clones --wire FILE` reads them back: a `hello` sets the environment, a `node_checkpoint` starts a node, and `node_action` lines must follow in order. For each SL `decision` it loads the clone, the checkpoint and the steps sent before the decision (`RunSession.Load`), and checks that the clone asks the same decision next, observation for observation; a difference names the first JSON path that differs, the game's value and the clone's. Decisions before any checkpoint are counted apart. It prints how many of the SL decisions asked the same, and exits 1 unless all did (`Commands/Clones.cs`; [Simulator: reference §4](/en/arch/simulator/reference/#sec-4)).

**Results.**

- On the simulator's own export (one SL run hosted against `brain`, 455 decisions), every decision is the same.
- In the real game, on floors 2–5 of one SL run played with assist on (4 nodes: 3 combats and an event), 89 of 90 SL decisions were the same. The other was asked while an event option was still running, so the screen still showed the gold from before it; the mod now waits for the step's task ([§4](#sec-4)).
- An earlier capture of floors 1–2 had found that card plays were not recorded, because a queued play looks its card up only when it runs ([§3](#sec-3)).
- A later capture with the task wait in place (2026-10-28, `tmp/assist/`, local) holds three runs as the brain saw them, SL, NoSL and SL again: 150 decisions, 149 of them SL (combat 87, rewards 21, map 11, card prompts 11, card reward 6, event 5, shop 4, rest 2, bundle 1, treasure 1), 12 node checkpoints and 137 node actions; the last SL run went 11 nodes to floor 11. Whether `clones` was run on it is not recorded.

**The SL planner's wait**, from the floors 2–5 capture replayed against a fresh brain on the machine that runs the game (`plan` with an earlier combat net, beam 8×300 on 8 workers): a combat's first decision took 3–15 s, as it plans the whole combat; a replan, when a draw or an enemy leaves the plan, 1–11 s; the other 56 of 66 combat decisions under 50 ms, as they follow the plan. Decisions outside combat took under 20 ms.
