Evaluation answers two questions: how strong is the AI (the leaderboards), and did a change help (the gates). Both environments go through the same pipeline and are always reported separately. Evaluation plays whole runs in the simulator (SimWorker) and, for confirmation, in the real game through the [mod](/en/arch/mod/).

<Aside title="Status">

R1 full-run evaluations exist: `run --seeds FILE --records FILE` plays a seed set and writes one record per run, `report` turns the records into the report of [§6](#sec-6) with the metrics of [§3](#sec-3), and the first promotion and final sets are registered ([§4](#sec-4)). The combat panel exists too ([§5](#sec-5), [Combat brain §7.1](/en/arch/combat-brain/#sec-7.1)), `leaderboard` ranks the reports ([§2](#sec-2)), and the full-run gate (`gate`) promotes a challenger into the environment's champion file ([§5](#sec-5)). The elite gauntlet, V's training game since 2026-10-29, has an evaluation and a gate of its own on fixed seeds (`learn/gauntlet.py`, [§5](#sec-5)), with a leaderboard kept by hand. Planned: the act-level gate, and rungs R2–R4.

</Aside>

## 1. Sim-to-real ladder

Results from the simulator count only if they carry over to the real game. The ladder gets there in four rungs, R1 to R4, each adding one step of realism. Every milestone runs all rungs, reported separately:

| rung | world | measures | today |
|---|---|---|---|
| R1 | full run in the simulator, driven by Harness | the policy | full runs, NoSL ([§6](#sec-6)) |
| R2 | R1 + observation round trip (decisions only on worlds built from observations) | observation reconstruction | combat round trip exists |
| R3 | full run on the real DLL with real unlocks, the lobby's act selection and the live protocol | world setup + interfaces | none |
| R4 | Steam game + mod | everything | none |

**Why one new variable per rung.** Each rung differs from the one below it in one respect only. If the win rate drops between two neighbouring rungs, only one thing changed, so the gap can be attributed to it:

- R1 → R2: observation reconstruction;
- R2 → R3: world setup and interfaces;
- R3 → R4: animation, timing, UI state and the executor (the mod code that performs actions in the game).

If R1 jumped straight to the real game, a lower win rate could have any of these causes, with no way to tell which.

- R4 is expensive (it runs in real time), so it is for confirmation, not for tuning.
- R1 decisions already go through the Build path, which builds worlds from observations ([Simulator §6](/en/arch/simulator/#sec-6)). So for decisions R1 is about the same as R2; what R2 adds is the observation-only state for the host.

## 2. Two leaderboards

A leaderboard holds the results of an environment's champion (the best accepted version of the AI) on a fixed seed set. There is one per environment:

| | NoSL | SL |
|---|---|---|
| seeds | same pre-registered set | same |
| champion | NoSL champion | SL champion |
| info allowed | [Environments §3](/en/arch/environments/#sec-3) | same table |
| budget | per decision, same tier | same |

- The two champions share the macro brain and one V; their combat brains differ ([Environments §5](/en/arch/environments/#sec-5)). Since 2026-10-30 both champion files name the same V, v6-3-2, chosen by its SL results; NoSL plays it with screen afterstates, since the clone is SL's. Until a NoSL report of that V exists, the NoSL champion file names the SL report: a NoSL gate then refuses to pair with it (the environments differ), and the NoSL leaderboard marks no champion.
- Also reported: the SL − NoSL win-rate delta, which is the value of in-node information. This is the formal version of the omniscient-vs-resampled ablation in plan v1 (local note `tmp/notes/plan.md`). For reference, spire-mentor (a prior-art project) lost 22.8–25.5 percentage points (pp) of win rate without its cheat, which covered the whole run. Ours is node-level only, so we expect a smaller delta.
- `leaderboard [--character SILENT]` builds a character's leaderboards from its reports in `eval/CHARACTER/reports/` into `eval/CHARACTER/leaderboard.md`: per ascension, seed set and rung, one table per environment, ranked by win rate and then mean floor, with void reports last and the report of the environment's champion file (`eval/CHARACTER/champions/`) marked ([§5](#sec-5)); partial reports are left out. Below them, for each champion with a report in both environments, the SL − NoSL difference on the same seeds, paired by seed: win rate and floor reached, each with a 95% interval. Every report is on the board, not only accepted champions. The leaderboard is committed with the reports.

<Aside type="caution" title="Never mix environments">

Never put both environments in one table or in one promotion decision.

</Aside>

## 3. Metrics

**Main**

- win rate, with its Wilson 95% interval;
- mean floor reached;
- HP entering each boss.

The Wilson interval is a confidence interval for a proportion such as a win rate. Unlike the simple normal approximation, it stays reliable for small samples and for rates near 0 or 1.

**Must be zero** (otherwise the evaluation is void)

- fallback or random decisions ([Harness §4](/en/arch/harness/#sec-4));
- failed runs (an error in the driver or a brain) and truncated runs (the decision cap);
- game errors (`Log.Error` lines);
- `NumReloads`;
- save exports in NoSL runs ([Environments §6](/en/arch/environments/#sec-6)).

**Auxiliary**

- surface coverage counts;
- compute per decision (branches, wall-clock time, SL clone queries);
- macro calibration: the Brier score (mean squared error between the predicted win probability and the 0/1 result; lower is better) must be below that of a constant prediction;
- conservatism: elites taken, skip rate, HP at the boss, gold/potion hoarding;
- failed and truncated runs also count as losses in the win rate; they are never re-run.

## 4. Seeds

- Three disjoint sets: train, promotion and final.
- Final seeds are generated and registered in the repo beforehand (method and date). All of them are run and all are reported, so no one can pick seeds that happen to look good. A formal claim needs at least 300 runs.
- A seed is the game's run seed string. R1–R3 runs are started by the worker, R4 runs by the mod with the same seed ([Mod §7](/en/arch/mod/#sec-7)).
- Train seeds are unlimited. Promotion seeds are rotated, to avoid overfitting to them.

A seed set is a text file in `eval/seeds/`, one seed per line, with a header comment giving the method and the date. `seeds --base B --n K` writes the K seeds `MakeSeed(B, i)` for i = 0…K−1: 12 characters drawn from a generator seeded with B × 1,000,003 + i × 7,919 (32-bit). Two of the bases below share a generator seed only hundreds of millions of seeds in, so the sets are disjoint. The bases are fixed:

| set | base | seeds |
|---|---|---|
| train | 1 | unlimited (what `run --seed 1` plays) |
| `promotion-1` | 2 | 200, registered 2026-10-27 |
| `promotion-1-300` | 2 | 300, registered 2026-10-30: promotion-1's 200 in its order, then the next 100 |
| `final-1` | 3 | 300, registered 2026-10-27 |

The elite gauntlet's evaluation seeds are a block of the train generator kept out of training: `run --seed 1 --start 300000 --n 500`, fixed, entered in the ledger ([Learning §6](/en/arch/learning/#sec-6)) and never trained on.

A run's random generator (the placeholders, the brain seeds) is seeded from a stable hash of the seed string, so the seed alone fixes the run whatever the set or position.

## 5. Gates

A gate is the test a challenger must pass to replace the champion. Full runs are expensive: at a win rate p of about 0.3, detecting +5 pp with an unpaired comparison takes about 1,300 runs per side, and +2 pp about 8,000. So the gates are tiered, from cheap and narrow to expensive and complete:

| tier | for | method | cost |
|---|---|---|---|
| combat panel | combat search / value | fixed (encounter, deck, seed), CRN; mean HP loss + death rate | seconds to minutes |
| act-level | macro | acts started from a snapshot pool; act clear rate + HP at act end | minutes |
| full-run SPRT | stage promotion | paired on promotion seeds, SPRT (H0: Δ ≤ 0, H1: Δ ≥ δ) | hours |

- **CRN:** challenger and champion share the run seed and the way search seeds are derived. Measure the actual variance reduction once full runs work.
- **Paired tests:** McNemar or paired SPRT. A/A test the gate.

The methods named above:

- **CRN** (common random numbers): both sides play with the same random seeds, so they meet the same luck and only the policy differs; luck that is the same for both cancels out of the difference.
- **SPRT** (sequential probability ratio test) checks the evidence after each pair of runs and stops as soon as it clearly favours one hypothesis: H0, the challenger is not better (Δ ≤ 0), or H1, it is better by at least δ (Δ ≥ δ). Δ is the win-rate difference, challenger minus champion. The error rates are fixed in advance, and a clear result usually needs far fewer runs than a test with a fixed number of runs.
- **McNemar's test** is the standard test for paired win/loss outcomes. It looks only at the seeds where exactly one side won and asks whether those split evenly.
- **A/A test:** run the gate with the champion against itself. There is no real difference, so it must not promote more often than the gate's designed false-positive rate; if it does, the gate is broken.

**The full-run gate as built.** `gate --champion eval/CHARACTER/champions/ENV.json --records A[,B…] [the challenger's run options] [--metric floor|win] [--delta D] [--alpha A] [--beta B] [--not-worse] [--promote PATH] [--env ENV]`.

- **Champion file:** `eval/CHARACTER/champions/ENV.json`, one per character and environment, holds the champion's name as the reports show it, the run options that play it (its character and ascension, `character` and `asc`, among them), its report, the date it became champion, and the gate it passed (none for the first one). `run --champion FILE` and `brain --champion FILE` play it; options given on the command line override the file's. The SL champion's first file (2026-10-28) passed no gate: its baseline on promotion-1 set it, the SL planner c2 at `--effort medium` with L0 n2-b0.03 (commit `3699fc1`), at floor 28.25 with no win and no game error ([§7](#sec-7)). Nor did the next two. Pure-1-g replaced n2-b0.03 on 2026-10-29 as the first pure V, the start of a new line judged by its own report (floor 25.69), whatever the old line had reached. On 2026-10-30 v6-3-2 became the V of both files, by its 300-run SL report on promotion-1-300 (floor 33.56, 23 won, `--afterstates clone`); v6-2's report was +5.92 ± 0.74 floors paired against pure-1-g's on promotion-1, and v6-3-2's +2.20 ± 0.62 against v6-2's.
- **The champion's side** is its report. A seed fixes the whole run ([§4](#sec-4)), so playing the champion again would repeat those runs; the gate plays only the challenger. Both sides must come from the same game version, environment and rung, and be played as the same character at the same ascension; `--env` names the challenger's, and one that is not the champion file's is refused.
- **The challenger's side** is its run records, named by the run options given; every record must have been played by them. Options that explore (`--explore`, `--macro-explore`, `--combat-explore`) are refused: exploration is for self-play ([Learning §5](/en/arch/learning/#sec-5)). So are the records of the boss gauntlet pilot (`auto_win`) and of the elite gauntlet (`gauntlet`): some of their combats were never played.
- **Pairs** go by seed, in the seed set's order. The SPRT looks after each pair and stops at the first clear verdict.
- **Metrics.** `floor` (the default while runs rarely win): the mean floor difference, challenger minus champion, as a Gaussian SPRT with H0 at 0 and H1 at δ = 1.5 floors; the variance is estimated from the pairs so far (at least 1), and no verdict comes before 10 pairs differ. Tied pairs do not count towards the 10: a change that alters only some runs ties most pairs, and with ties alone the variance sits at its floor of 1, so the gate failed such a change at the 10th pair. A change that lifts one run in ten by 15 floors (+1.5 on average) would have failed that way whenever the first 10 runs tied, about 35% of the time; the boss budget's gate did ([Combat brain §5](/en/arch/combat-brain/#sec-5)). `win`: only the pairs where exactly one side won, as in McNemar's test; the challenger's share of them, H0 at 0.5 and H1 at 0.5 + δ, δ = 0.1. α = β = 0.05.
- **Verdicts:** pass, fail, open (the pairs ran out first), or void (the challenger's runs break a must-be-zero rule, [§3](#sec-3)). The exit code is 0 on a pass.
- **Not worse.** A change meant to be cheaper rather than stronger (searching less, the same play otherwise) is promoted when it is not worse: `--not-worse` shifts both hypotheses down by δ, H0 at −δ (worse by δ) and H1 at 0 (for `win`, H0 at 0.5 − δ and H1 at 0.5). The gate's line and its result in the champion file say which test it was. `learn/challenge.py --not-worse` passes it on.
- **Promotion:** on a pass, `--promote PATH` writes the challenger's report to PATH.json and PATH.md and rewrites the champion file, with the gate's result in it. The champion file names the challenger's weights files where they are, with the character and ascension it played. They must be in the character's weights folder, `weights/CHARACTER/`, where a name always means the same file; a promotion with a file elsewhere is refused before anything is written ([Learning §6](/en/arch/learning/#sec-6)). The new report faces the next challengers, so it must cover the whole seed set. The SPRT can pass early: play the challenger in chunks, gate after each, stop at a fail, and after a pass play the rest of the set, then promote. `learn/challenge.py` does exactly that, with the champion's character and ascension ([Learning §2](/en/arch/learning/#sec-2)).
- **Re-baseline.** The champion's report stands for the champion only while the code plays it as it did. A change that makes it play otherwise (a fix in the world builder, the search or L0) makes the report stale, and a gate against it would credit the challenger with the change. The champion then plays the whole seed set again on the new code (`run --champion FILE`), and its champion file names the new report. That is not a promotion: the champion, its date and its gate stay. On 2026-10-27, after the fixes to the search's memo, to L0's upgrade values and to the monsters' move logs in NoSL worlds (commit `432aa0c`), the NoSL champion went from floor 21.88 to 22.70 on promotion-1 (paired +0.81 ± 0.89 floors, 95%; 131 seeds reached the same floor, 42 a higher one, 27 a lower one), the act 3 boss from 1 run to 4. After the NoSL worlds were given the allies and the stunned monsters' next moves (commit `32a0160`), it played again: 22.58, 197 of the 200 seeds to the same floor (paired −0.12 ± 0.18), the act 3 boss in 3 runs. After the fixes to a card's own cost in NoSL worlds and to the shop under Sozu (commit `c5ee8de`) it played once more, on the build the next gates use: all 200 seeds to the same floor.

**The elite gauntlet's gate** (plan v6; [Learning §2](/en/arch/learning/#sec-2)). Each V plays the gauntlet's 500 evaluation seeds ([§4](#sec-4)) with no exploration, at the training's budget (the SL planner's low budget) and with `--afterstates clone`. `learn/gauntlet.py --records R --logs L` reports:
- the mean progress (the floor reached, plus the share of the enemies' HP taken in the combat a lost run died in; a won run +1);
- each act's boss reached and beaten, the runs won;
- the elite fights per run and the deaths in them, and where the runs died;
- from the logs, the rest sites' choices by the share of max HP they were made at, and what the shops sold.

With `--against` it pairs the runs with the champion's by seed, on the seeds both finished (a time-boxed evaluation may not finish them all): the mean difference in progress, its standard error and its 95% one-sided lower bound. A challenger is promoted when the bound is above 0. One gate takes 16–20 minutes on the hosts. The gauntlet's champions and their numbers are in `eval/CHARACTER/gauntlet-leaderboard.md`, kept by hand, since `leaderboard` builds its boards from whole-run reports.

## 6. Reports

Each evaluation writes a JSON file plus a one-page Markdown report with: game version, commit, champion, environment, rung, seed set, budget, all metrics, the must-be-zero metrics, and the diff against the previous evaluation. Reports go into `eval/CHARACTER/reports/` as `DATE-ENV-RUNG-SET-NAME.json` and `.md`; the run records and decision logs behind them stay outside git, in `data/CHARACTER/ENV/` ([Learning §6](/en/arch/learning/#sec-6)).

- `report --seeds FILE --records A[,B…] --out PATH [--previous OLD.json]` writes PATH.json and PATH.md. The records may come from several processes; they must share one config (game, commit, champion, environment, rung), one character and one ascension, and each must play a different seed of the set. A report with fewer runs than the set is marked partial.
- A run record (`run --records`) also holds the run id that the decision log knows the run by ([Harness §6](/en/arch/harness/#sec-6)), which joins the two for learning. It lists each combat the run entered: act, floor, encounter, room type, the HP, max HP and potions at its first decision, and `end`, how it ended: a death, or the HP, max HP and potions left. `end` is missing for a combat the run stopped in without dying (failed, truncated). It is the target of the combat outcome head ([Learning §1](/en/arch/learning/#sec-1)). The gauntlets' records say so in their config (`auto_win` for the boss gauntlet pilot, `gauntlet` for the elite gauntlet, [Simulator §5](/en/arch/simulator/#sec-5)), and `report` refuses them. An elite gauntlet's `end` also gives the enemies' HP and max HP at a death.
- The commit is the build's: a build with uncommitted changes under `src/` gets `-dirty` after it, and such a report is for development only.
