Evaluation answers two questions: how strong is the AI (the leaderboards), and did a change help (the gates). Both environments go through the same pipeline and are always reported separately. Evaluation plays whole runs in the simulator (SimWorker) and, for confirmation, in the real game through the [mod](/en/arch/mod/).

The combat panel exists too ([§5](#sec-5), [Combat brain §7.1](/en/arch/combat-brain/#sec-7.1)). Planned: the act-level and SPRT gates, the leaderboards, and rungs R2–R4.

## 1. Sim-to-real ladder

Results from the simulator count only if they carry over to the real game. The ladder gets there in four rungs, R1 to R4, each adding one step of realism. Every milestone runs all rungs, reported separately:

| rung | world | measures | today |
|---|---|---|---|
| R1 | full run in the simulator, driven by Harness | the policy | full runs, NoSL ([§6](#sec-6)) |
| R2 | R1 + observation round trip (decisions only on worlds built from observations) | observation reconstruction | combat round trip exists |
| R3 | full run on the real DLL with real unlocks, the lobby's act selection and the live protocol | world setup + interfaces | none |
| R4 | Steam game + mod | everything | none |

**Why one new variable per rung.** Each rung differs from the one below it in one respect only. If the win rate drops between two neighbouring rungs, only one thing changed, so the gap can be attributed to it:

- R1 → R2: observation reconstruction;
- R2 → R3: world setup and interfaces;
- R3 → R4: animation, timing, UI state and the executor (the mod code that performs actions in the game).

If R1 jumped straight to the real game, a lower win rate could have any of these causes, with no way to tell which.

- R4 is expensive (it runs in real time), so it is for confirmation, not for tuning.
- R1 decisions already go through the Build path, which builds worlds from observations ([Simulator §6](/en/arch/simulator/#sec-6)). So for decisions R1 is about the same as R2; what R2 adds is the observation-only state for the host.

## 2. Two leaderboards

A leaderboard holds the results of an environment's champion (the best accepted version of the AI) on a fixed seed set. There is one per environment:

| | NoSL | SL |
|---|---|---|
| seeds | same pre-registered set | same |
| champion | NoSL champion | SL champion |
| info allowed | [Environments §3](/en/arch/environments/#sec-3) | same table |
| budget | per decision, same tier | same |

- The two champions share the macro brain and V; their combat brains differ ([Environments §5](/en/arch/environments/#sec-5)). A new V changes both champions, so it is gated in each environment on its own.
- Also reported: the SL − NoSL win-rate delta, which is the value of in-node information. This is the formal version of the omniscient-vs-resampled ablation in plan v1 (local note `tmp/notes/plan.md`). For reference, spire-mentor (a prior-art project) lost 22.8–25.5 percentage points (pp) of win rate without its cheat, which covered the whole run. Ours is node-level only, so we expect a smaller delta.

<Aside type="caution" title="Never mix environments">

Never put both environments in one table or in one promotion decision.

</Aside>

## 3. Metrics

**Main**

- win rate, with its Wilson 95% interval;
- mean floor reached;
- HP entering each boss.

The Wilson interval is a confidence interval for a proportion such as a win rate. Unlike the simple normal approximation, it stays reliable for small samples and for rates near 0 or 1.

**Must be zero** (otherwise the evaluation is void)

- fallback or random decisions ([Harness §4](/en/arch/harness/#sec-4));
- failed runs (an error in the driver or a brain) and truncated runs (the decision cap);
- game errors (`Log.Error` lines);
- `NumReloads`;
- save exports in NoSL runs ([Environments §6](/en/arch/environments/#sec-6)).

**Auxiliary**

- surface coverage counts;
- compute per decision (branches, wall-clock time, SL clone queries);
- macro calibration: the Brier score (mean squared error between the predicted win probability and the 0/1 result; lower is better) must be below that of a constant prediction;
- conservatism: elites taken, skip rate, HP at the boss, gold/potion hoarding;
- failed and truncated runs also count as losses in the win rate; they are never re-run.

## 4. Seeds

- Three disjoint sets: train, promotion and final.
- Final seeds are generated and registered in the repo beforehand (method and date). All of them are run and all are reported, so no one can pick seeds that happen to look good. A formal claim needs at least 300 runs.
- A seed is the game's run seed string. R1–R3 runs are started by the worker, R4 runs by the mod with the same seed ([Mod §7](/en/arch/mod/#sec-7)).
- Train seeds are unlimited. Promotion seeds are rotated, to avoid overfitting to them.

A seed set is a text file in `eval/seeds/`, one seed per line, with a header comment giving the method and the date. `seeds --base B --n K` writes the K seeds `MakeSeed(B, i)` for i = 0…K−1: 12 characters drawn from a generator seeded with B × 1,000,003 + i × 7,919 (32-bit). Two of the bases below share a generator seed only hundreds of millions of seeds in, so the sets are disjoint. The bases are fixed:

| set | base | seeds |
|---|---|---|
| train | 1 | unlimited (what `run --seed 1` plays) |
| `promotion-1` | 2 | 200, registered 2026-10-27 |
| `final-1` | 3 | 300, registered 2026-10-27 |

A run's random generator (the placeholders, the brain seeds) is seeded from a stable hash of the seed string, so the seed alone fixes the run whatever the set or position.

## 5. Gates

A gate is the test a challenger must pass to replace the champion. Full runs are expensive: at a win rate p of about 0.3, detecting +5 pp with an unpaired comparison takes about 1,300 runs per side, and +2 pp about 8,000. So the gates are tiered, from cheap and narrow to expensive and complete:

| tier | for | method | cost |
|---|---|---|---|
| combat panel | combat search / value | fixed (encounter, deck, seed), CRN; mean HP loss + death rate | seconds to minutes |
| act-level | macro | acts started from a snapshot pool; act clear rate + HP at act end | minutes |
| full-run SPRT | stage promotion | paired on promotion seeds, SPRT (H0: Δ ≤ 0, H1: Δ ≥ δ) | hours |

- **CRN:** challenger and champion share the run seed and the way search seeds are derived. Measure the actual variance reduction once full runs work.
- **Paired tests:** McNemar or paired SPRT. A/A test the gate.

The methods named above:

- **CRN** (common random numbers): both sides play with the same random seeds, so they meet the same luck and only the policy differs; luck that is the same for both cancels out of the difference.
- **SPRT** (sequential probability ratio test) checks the evidence after each pair of runs and stops as soon as it clearly favours one hypothesis: H0, the challenger is not better (Δ ≤ 0), or H1, it is better by at least δ (Δ ≥ δ). Δ is the win-rate difference, challenger minus champion. The error rates are fixed in advance, and a clear result usually needs far fewer runs than a test with a fixed number of runs.
- **McNemar's test** is the standard test for paired win/loss outcomes. It looks only at the seeds where exactly one side won and asks whether those split evenly.
- **A/A test:** run the gate with the champion against itself. There is no real difference, so it must not promote more often than the gate's designed false-positive rate; if it does, the gate is broken.

## 6. Reports

Each evaluation writes a JSON file plus a one-page Markdown report with: game version, commit, champion, environment, rung, seed set, budget, all metrics, the must-be-zero metrics, and the diff against the previous evaluation. Reports go into `eval/reports/` as `DATE-ENV-RUNG-SET-NAME.json` and `.md`; raw logs are not committed.

- `report --seeds FILE --records A[,B…] --out PATH [--previous OLD.json]` writes PATH.json and PATH.md. The records may come from several processes; they must share one config (game, commit, champion, environment, rung), and each must play a different seed of the set. A report with fewer runs than the set is marked partial.
- The commit is the build's: a build with uncommitted changes under `src/` gets `-dirty` after it, and such a report is for development only.

## 7. Baselines

Reference results from prior-art projects, and our own floor:

| source | result | note |
|---|---|---|
| FableBot | Ironclad A0 20.7% (71/343, Wilson 16.7–25.3) | the only fair, real-game, adequately sampled result; no Silent |
| AgenticSTS | Silent A0 about 35% (44/125, mixed versions); A8+ 0/25 | LLM + human Silent guide |
| ours: placeholders (`play` combat, random macro) | Silent A0 0% (0/200); mean floor 8.09 | `promotion-1`, R1, NoSL; our floor |
| ours: PIMC + L0 | Silent A0 0% (0/200); mean floor 18.50, act 1 boss in 175 runs | `promotion-1`, R1, NoSL ([Combat brain §7.2](/en/arch/combat-brain/#sec-7.2)) |

The first character is the Silent, and ascension A0 comes first.
