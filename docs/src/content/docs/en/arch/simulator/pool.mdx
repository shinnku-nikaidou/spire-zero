A search plays thousands of actions per decision, in worlds that are copies of the game. The game allows one live combat or run per process ([Combats §1](/en/arch/simulator/combat/#sec-1)), and the real run must stay live while it is searched. So the searches run in other processes: **workers**, the simulator itself started as `serve`, kept by a **worker pool**.

## 1. Why other processes

Three reasons, in order of weight:

- **One live game per process.** The run being played is live in the host. A search world is a combat or a run of its own, so it needs a process where nothing else is live. In-process search would have to put the real combat aside and bring it back by replay at every decision ([Worlds and the SL clone §2](/en/arch/simulator/worlds/#sec-2)).
- **Parallelism.** The worlds of a decision are independent, so K worlds on K workers take about the time of one. The game's model layer is not thread-safe and the pump is single-threaded ([Headless host §7](/en/arch/simulator/headless/#sec-7)), so processes, not threads, are the unit.
- **A boundary for what may be known.** In NoSL a worker gets the observation, never the true state, and builds its worlds from it ([§5](#sec-5)). What crosses to a worker is a protocol message, so it can be read and checked.

`WorkerPool` lives in `Sts2Ai.Harness` (`Sts2Ai.Harness/WorkerPool.cs`), which sees the game only through protocol types; the worker side is the `serve` command of the simulator (`Commands/Serve.cs`). A champion whose combat brain searches (`pimc`, or `plan` in SL) or whose macro brain plays on the clone (`--afterstates clone`) gets a pool, of `--workers` processes, by default one per world (`--worlds`, 8) (`Brains/ChampionOptions.cs:24`).

## 2. The pool

**Starting.** The pool starts its workers in parallel and waits until each has booted (`Sts2Ai.Harness/WorkerPool.cs:33-50`). A worker is the same program started again, as its apphost or as `dotnet` with its dll if that is how the host was started (`Program.cs:20-24`), with `serve` and the champion's `--combat-net` and `--value`, the leaf every search of that worker uses. Booting takes about 1.2 s ([Headless host §2](/en/arch/simulator/headless/#sec-2)). When it is done, the worker writes its hello, `{"game": "v0.111.0"}`, the game version it runs.

**The wire** is one JSON line per message over the worker's stdin and stdout ([Protocol: worlds and worker messages §4](/en/arch/protocol/worlds/#sec-4)). A request carries its type and an id; the reply carries the same id, the answer, an error if the request failed, and the game errors logged while serving it. Worker messages have no protocol version field: the host and its workers are always the same build.

**Serving a set of requests.** A searching brain hands the pool all the requests of one step at once, such as one per world (`WorkerPool.Map`, `Sts2Ai.Harness/WorkerPool.cs:70-88`). Each request goes to whichever worker is free; a worker serves one request at a time; and the replies come back in request order, whatever order they finish in.

The pool keeps each worker for its lifetime. Disposing it closes each worker's stdin, which ends the worker's loop; one that does not exit within 5 s is killed.

## 3. The three requests

Each request is a record in `Sts2Ai.Protocol/Worker.cs`. Three searching brains send them, through a pooled version of themselves in Harness:

| request | sent by | the worker | replies with |
|---|---|---|---|
| `PimcWorldRequest` | `PooledPimc`, NoSL | builds the combat from the observation with the build seed (`SimWorlds.NoSL`), takes world `World` of the `Worlds` drawn from the search seed, and searches this turn after each of the first actions given, with `NodesPerFirst` nodes each | the best line after each first action (`Lines`) |
| `SlTurnRequest` | `PooledPlanner` | loads the node's clone, plays the state's path from the decision, and searches that turn with `Nodes` nodes, keeping up to `Keep` states at the next turn's start that beat `Floor` | the best ends of the turn (`Turn`) |
| `SlMacroRequest` | `PooledClone` | for each path of answers, loads the clone, plays the path from the decision, and records what the game asks next (`NodeProbe`) | one afterstate per path (`Afters`): the run, the surface, the screen and the legal actions |

How each brain splits its work:

- **PIMC** sends one request per world, each with every first action, and merges the replies as in-process PIMC does ([NoSL PIMC: search §2](/en/arch/pimc/search/#sec-2)).
- **The SL planner** sends, for each turn of its beam, one request per state kept. A turn's search lives in one request, so the plan is the one a single process makes ([The SL planner: beam §1](/en/arch/sl-planner/beam/#sec-1)).
- **L0 on the clone** splits a decision's paths into `min(paths, workers)` requests, in order (`Sts2Ai.Harness/PooledClone.cs:14-24`). A path's afterstate depends on the clone and the path only, so the split cannot change a result ([Macro brain: search §6](/en/arch/macro-brain/search/#sec-6)).

## 4. The worker: `serve`

`serve [--combat-net FILE --value FILE]` (`Commands/Serve.cs`) boots the game, writes its hello, then reads one request per line and writes one reply per line until stdin closes.

- **stdout is the wire.** Before the game boots, `serve` keeps the real stdout for the wire and points `Console.Out` at stderr, so nothing the game or a library prints can get into the stream (`Commands/Serve.cs:23-28`). Its logs go to stderr too; the pool keeps the last 20 lines of each worker's stderr for the error message if it dies.
- **One brain of each kind, made once:** PIMC and the SL planner with the worker's leaf.
- **A failed request ends the worker.** If a request throws, the worker replies with the error and exits with code 1 (`Commands/Serve.cs:57-61`): the game may be left set up (a combat still live), and every later request would fail. The error names the exception's type, the innermost exception's top three frames and its message's first line, then the whole exception on the following lines.
- **Game errors per request.** The game's `Log.Error` lines and unobserved task faults logged while serving a request go back in its reply; the host counts them with its own ([Headless host §8](/en/arch/simulator/headless/#sec-8)).

## 5. Self-contained requests

A request carries everything the worker needs, and nothing carries over from one request to the next: a worker builds or loads its world from the request, searches, and drops it. So any free worker can take any request, and a restarted worker is as good as the one it replaces.

**What crosses.** In NoSL only the observation and the record of enemy moves leave the host; the true state never reaches a worker. In SL the node's clone does, which SL may know ([Environments: worlds §4](/en/arch/environments/worlds/#sec-4)). Every combat request also carries the combat's record of enemy moves so far: a NoSL worker builds the monsters' move logs from it ([Combats §5](/en/arch/simulator/combat/#sec-5)), and the leaves of both read it ([Combat brain: the leaf §3](/en/arch/combat-brain/leaf/#sec-3)).

**Determinism.** Replies are merged in request order, never in completion order, and each request's search depends only on the request. So with the same seeds a pooled search gives exactly what an in-process search gives, values included. `selftest --workers N` checks it on 4 decisions, each with a budget of 4 worlds × 120 nodes, and checks that the pooled SL planner plans what the planner plans in one process, nodes included ([Reference §5](/en/arch/simulator/reference/#sec-5)). Measured on 6 combats, PIMC's trace with 8 workers diffed empty against the in-process one.

## 6. Failures

| what goes wrong | what the pool does |
|---|---|
| a worker closes its stdout or breaks the pipe | starts a new worker and sends the request once more; the count is reported as `worker restarts` |
| a worker gives no reply within the timeout, 5 minutes (a request takes seconds at most, so such a worker is stuck, not slow) | kills it, then as above |
| the same request fails that way twice | fails the call |
| a reply that is not valid JSON, or answers another request's id | fails the call at once, with no retry |
| a reply with an error (an exception in the worker) | fails the decision once every reply of the set is in; the worker has exited ([§4](#sec-4)), so the next request sent to it restarts it |
| a worker that does not boot when the pool starts | the pool's constructor throws: no restart |

Sources: `Sts2Ai.Harness/WorkerPool.cs:21, 47, 70-117, 173-190`. `WorkerPoolTests` checks the first three rows with a shell script as the worker and a 1 s timeout: a worker stuck once is restarted and answers; one stuck twice fails the call ([Reference §7](/en/arch/simulator/reference/#sec-7)).

The pool has two gaps. A worker that dies and then fails to boot again leaves the call failed, and the dead worker goes back into the pool, so later calls on it fail without a retry (`Sts2Ai.Harness/WorkerPool.cs:81-84, 112-114`). And the 5-minute timeout also covers the boot of a restarted worker.

A failed call fails the decision, and so the run, with the error in the run's `failure` line ([Whole runs §5](/en/arch/simulator/runs/#sec-5)). There is no fallback to another brain: a run that finishes was played by its champion throughout.

## 7. Speed

Measured with each brain's default budget: PIMC's 8 worlds × 300 nodes, the SL planner's `medium` (a beam of 8, 300 nodes per state and turn).

- **NoSL PIMC**, 6 act-1 combats: 8 workers take 68.7 ms per action against 307.5 ms in one process (9.4 s against 42.1 s in all).
- **The SL champion** (the SL planner and L0 with clone afterstates): its reports record the speed, on each character's 100 runs (`ms_per_decision`, `seconds_per_run`). On average a decision takes 405 ms and a run 336 s for the Silent, 431 ms and 286 s for the Ironclad, 560 ms and 423 s for the Defect, 1,202 ms and 906 s for the Regent, 1,358 ms and 1,046 s for the Necrobinder ([Evaluation: champions and baselines §2](/en/arch/evaluation/champions/#sec-2)).

How throughput grows with processes on one machine is in [Combats §7](/en/arch/simulator/combat/#sec-7): almost linearly up to the physical cores.

## 8. Planned: worlds that stay in a worker <Badge text="planned" variant="caution" />

A request is a whole search, so a worker needs no memory between requests. A search that outgrows one request, such as a search over run worlds ([Worlds and the SL clone §8](/en/arch/simulator/worlds/#sec-8)), would instead open a world in a worker by kind (built, clone, run host) and get a world id; then snapshot, restore, execute, list the legal actions, observe and branch on it, one message each; then close it. Such a world keeps live state in its worker, so its branches should go to that worker first, since a restore elsewhere costs a replay; snapshots stay portable, so any worker can take over. A crash would reopen the worker's worlds from their snapshots.
