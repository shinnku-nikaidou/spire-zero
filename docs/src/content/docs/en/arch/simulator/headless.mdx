The game expects to run inside the Godot engine, with a window, a renderer and a main loop that calls it sixty times a second. This page explains how `Sts2Ai.SimWorker` runs the same code with none of that: what replaces the engine, which game methods are patched and why, and how a single-threaded scheduler, the `Pump`, turns the game's asynchronous code into a deterministic step function. Everything else in the simulator stands on it.

## 1. The model layer and the nodes

Slay the Spire 2 is a Godot 4.5.1 app written in C# on .NET 9.0.7. Its code has two layers:

- **The model layer:** plain C# objects for everything the rules are about: the run (`RunState`, `RunManager`), the combat (`CombatState`, `CombatManager`), creatures, cards, piles, powers, relics, potions, rooms, events, the random streams. Game logic is `async`: playing a card is an action that awaits its hooks, its damage, its follow-ups.
- **The nodes:** Godot scene objects, classes named `N…` (`NGame`, `NCombatRoom`, `NMapScreen`, `NRewardsScreen`…). They draw the model, animate it and turn the player's clicks into calls into the model.

Headless, only the model layer runs. The nodes are never created; where a screen's code decides what happens next (which screen opens after a combat, what the Proceed button does), the simulator's driver does it instead ([Whole runs §3](/en/arch/simulator/runs/#sec-3)). Three things make the model layer run on its own: a stub for the engine's native functions ([§3](#sec-3)), Harmony patches ([§4](#sec-4)), and the game's own `TestMode` ([§5](#sec-5)).

## 2. Boot

`HeadlessGame.Boot` (`Runtime/HeadlessGame.cs:25-56`) runs once per process. It first reads the game's version from its `release_info.json`, then:

<Steps>

1. `GodotNativeStub.Install()`: fill the engine's function table with a stub ([§3](#sec-3)).
2. `HeadlessPatches.Apply()`: install every patch, GameBridge's card-prompt context patches first ([§4](#sec-4)).
3. `TestMode.TurnOnInternal()`: switch on the game's test mode ([§5](#sec-5)).
4. `ModManager.State = Skipped`: mods are never loaded headless (the setter is private; reflection sets it).
5. `AssemblyInfo.Init`, `ModelDb.Init`, `ModelIdSerializationCache.Init`, `ModelDb.InitIds`: load the game's model database, every card, relic, monster and event.
6. `LocalContext.NetId = 1`: the single local player's network id.
7. Settings and preferences for tests (`InitSettingsDataForTest`, `InitPrefsDataForTest`), with `FastMode = Instant`.

</Steps>

Then it subscribes to the game's log (`Log.LogCallback`, every line at Error or above) and to faults of tasks nobody awaited (`TaskHelper.UnobservedFault`), and collects both as **game errors** ([§8](#sec-8)). Booting takes about 1.2 s.

Commands that need no game (`brain`, `report`, `gate`, `leaderboard`, `seeds`, `ranks`, `weights`) never boot it ([Reference §4](/en/arch/simulator/reference/#sec-4)).

## 3. The native stub

The game's C# reaches the engine through GodotSharp, the engine's C# binding, which calls native engine functions through a table of function pointers that the engine fills at startup. With no engine, the table would be empty and the first call would crash.

`GodotNativeStub.Install` (`Runtime/GodotNativeStub.cs:23-51`) fills every slot of the table with one tiny function, `mov rax, imm64; ret`, which returns a pointer into the upper half of a zeroed page. Managed code that touches Godot then runs through: it gets zeroed memory back, which reads as null objects, empty strings and zero numbers, and nothing happens. It is written for linux-x64.

The stub keeps stray calls harmless; it does not make them meaningful. Code that needs a real answer from the engine (the OS, the clock, resources, localization) is patched to get one from managed code ([§4](#sec-4)).

## 4. The patches

A **Harmony patch** rewrites a game method at runtime. Harmony is a .NET library: a *prefix* runs before the original method and may skip it, a *postfix* runs after it, and a *transpiler* rewrites the method's IL (its compiled instructions) instead of wrapping it. `HeadlessPatches.Apply` (`Runtime/Patches/HeadlessPatches.cs:26-33`) installs GameBridge's `ChoiceContexts` first, then every patch class of the assembly. The order matters: patching compiles each replaced method, and a method compiled before the card-prompt patches could inline one of the small `CardSelectCmd` entries and bypass its patch, as SapphireSeed's planting (rewritten by the event transpiler) once did ([GameBridge: reading the game §6](/en/arch/gamebridge/observe/#sec-6)).

None of the patches changes a game rule, except the rule-fidelity group, which puts back the shipped rules where TestMode changed them. The groups, by file in `Runtime/Patches/`:

| group | file | what it does |
|---|---|---|
| engine shells | `Engine.cs` | managed stand-ins for the engine's OS, time, singletons, resources and the player's name |
| asset preloads | `Engine.cs` | off: nothing is loaded from the game's resource packs |
| presentation | `Engine.cs` | model code that reaches presentation without the TestMode guard: the Kaiser Crab's arms (`BeforeDeath` of Rocket and Crusher), SoulNexus (`AfterDeath`), and the `EventPresentation` transpiler (below) |
| text | `Text.cs` | localization returns keys instead of loading tables; the game's own log goes to the simulator's log ([§8](#sec-8)) |
| persistence | `Persistence.cs` | nothing is ever saved: `SaveRun`, progress updates, the progress file and replays are skipped; the save made on arriving at a map point also starts a node for the SL clone ([Worlds and the SL clone §3](/en/arch/simulator/worlds/#sec-3)); the game's real file layer and its save migrators throw if called, except three harmless queries that answer "no such file" |
| rule fidelity | `RuleFidelity.cs` | puts back shipped rules that TestMode changes: a Rolling Boulder hits enemies one by one; the `ShippedBranch` transpiler swaps the TestMode branch for the shipped one in `MerchantPotionEntry`, Cauldron and CallingBell, and throws if it finds no TestMode check left to swap |
| speed | `Speed.cs`, `../FastHookListeners.cs` | `FastCreatures`, `FastPlayerCreatures`, `FastPlayers`: the combat's creature and player lists, which the game rebuilds through three LINQ queries many times per action, built by plain loops into the same list in the same order; `FastHookListeners`: hook dispatch is most of the simulator's time (about 75 dispatches per action), and instead of a new listener list and iterators for each, it fills a pooled list with the same objects in the same order, rechecking each just before use as the game does. `selftest` compares it with the game's own iterators, kept callable through reverse patches, at every cut point |
| choices | `Choices.cs` | `ChooseABundle`, `CrystalSphereScreen` and `CardRemovalUsed`: screens whose choice the driver must answer ([Whole runs §4](/en/arch/simulator/runs/#sec-4)) |
| game quirks | `GameQuirks.cs` | errors the shipped game logs too, fixed so that every game error stays a real one ([§8](#sec-8)) |

**The event transpiler.** Events are the game's most presentational code: their methods open dialogs, play sounds and wait for animations. The `EventPresentation` transpiler (`Runtime/Patches/Engine.cs:129-174`) rewrites every method of every `EventModel` subclass, including its lambdas and async state machines: a call into a Godot object, or one that returns a Godot object, is dropped and gives the default result, and `Task.Delay` becomes a finished task. It touches about 17 event classes. Six of them would fail without it, because they call a node through a null instance or wait on a real-time delay: Amalgamator, DenseVegetation, DollRoom, JungleMazeAdventure, PunchOff and Trial.

## 5. TestMode

The game has a built-in switch for its own automated tests, `TestMode`. With it on, most model code skips presentation (each such place checks `TestMode.IsOn` first), rewards are claimed through a test selector instead of a screen, and a few rules change. The simulator turns it on because it removes most of the presentation for free. The rules it changes are put back, or handled, one by one. The branches that matter for runs (from the local audit `tmp/notes/testmode-audit.md`):

| TestMode branch | handled by |
|---|---|
| rewards claimed by `RewardsSet`'s test selector | the driver answers it ([Whole runs §4](/en/arch/simulator/runs/#sec-4)) |
| ChooseABundle takes the first bundle | the `ChooseABundle` prefix asks the policy instead |
| the act-1 and first-run tweaks in `ActModel` | nothing to do: runs start with every unlock ([Whole runs §2](/en/arch/simulator/runs/#sec-2)) |
| `MerchantRoom.Exit` returns early, writing no history | cosmetic, left as is |
| Rolling Boulder hits all enemies at once | rule fidelity: split into one hit per enemy |
| `MerchantPotionEntry`'s cost, Cauldron, CallingBell | rule fidelity: `ShippedBranch` |

## 6. The JIT

.NET normally uses *tiered compilation*: a method is first compiled quickly, and methods that run often are compiled again later, in the background, with full optimization (a *rejit*). A rejit can silently drop a Harmony patch, because the new code is compiled from the original method. It happened after a few thousand combats, when `RunManager.WriteReplay` ran unpatched. Tiering was also twice as slow on short runs, since Harmony's JIT hook makes every extra compile expensive.

So the project file sets `TieredCompilation=false` (`Sts2Ai.SimWorker.csproj:12-20`): every method is compiled once, fully optimized. Launchers should also set `DOTNET_ReadyToRun=0`, which a project file cannot set: the framework's own code is then compiled fully optimized too, about 20% more combats per second. The real game runs with tiering on, which is a risk for the mod's patches ([Mod: auto-play and safety §5](/en/arch/mod/auto/#sec-5)).

## 7. The Pump: one thread, one order

The game's logic is asynchronous: an action awaits its hooks, a hook awaits a command, and each `await` hands the rest of the method (its *continuation*) to the current `SynchronizationContext`, the .NET object that decides where continuations run. In the engine, that is Godot's main loop, one frame at a time. Headless, it is the **Pump** (`Runtime/Pump.cs:10-91`): a single-threaded `SynchronizationContext` installed on the driver's thread.

- `Post(callback)` puts a continuation in a queue. Nothing runs yet.
- `Drain()` runs everything queued, including what the running callbacks post, until the queue is empty, and returns how many ran.
- `RunUntil(done)` drains, checks the condition, and if it does not hold yet, waits up to 2 ms for something to be posted and tries again. If nothing is posted for 10 s while the condition still fails, it throws `StuckException` with a description of the state.

Because every continuation runs on the driver's thread, in the order it was posted, the same calls always run the same code in the same order. This is where determinism comes from: together with seeded random streams, the same setup and the same actions always give the same state ([Combats §2](/en/arch/simulator/combat/#sec-2)).

**Settling.** To *settle* is to pump until the game waits for the player again: in combat until `CombatActions.WaitingForInput` holds (the player's turn, in the play phase, the action executor idle); outside combat until the queue is empty and the action executor is idle ([Whole runs §3](/en/arch/simulator/runs/#sec-3)).

**Real-time waits break it.** If model code waits on the wall clock (`Task.Delay`), its continuation is posted by a timer thread some milliseconds later. Until then the queue is empty, the executor may look idle, and settling cannot tell "done" from "not yet". The Pump counts how often `RunUntil` had to block for work from another thread (`IdleWaits`); a run batch reports it as `pump idle waits`, which must be 0. Amalgamator's delay is patched; the others are not reached headless: `ActionExecutor.WaitForUnpause` (a 50 ms poll while paused), `CombatState.GodotTimerTask` (the timeout of a creature lookup by network id) and the rest site's hover messages (UI).

## 8. Game errors and logs

The simulator's own rule is that the game logs no errors: a game `Log.Error` line or an unobserved task fault means something ran that should not have. Boot collects both ([§2](#sec-2)), the commands report them per combat or run, `selftest` requires none, and a run with any fails (exit code 1). A worker sends the game errors it saw while serving a request back in its reply, and the host counts them with its own ([The worker pool §6](/en/arch/simulator/pool/#sec-6)).

Some errors are the shipped game's own, and the game quirks group fixes those so that every game error stays a real one. The one fixed so far: a card play in which the player dies (an enemy's Thorns killing the player while a Sly card is played) returns early and leaves the card on its choice context (`PlayerChoiceContext`); the hook that started the play then logs an error. `PopCardAfterEarlyReturn` pops the card, also when the card has left combat (`Runtime/Patches/GameQuirks.cs:18-42`). This is the project's rule for game bugs: no checksum and no fallback, but a quirk that breaks our correctness is fixed where it enters our code ([Introduction §2](/en/#sec-2)).

The game's log lines go to the simulator's log (`Runtime/Patches/Text.cs:31-46`): the game's errors and warnings at Error and Warning, its other lines at Debug, which only `--verbose` shows. How the command line logs is in [Reference §2](/en/arch/simulator/reference/#sec-2).
