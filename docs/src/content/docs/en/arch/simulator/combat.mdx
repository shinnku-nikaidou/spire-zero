Combat is where search spends almost all of its time: the combat brain tries thousands of lines of play for every decision ([Combat brain](/en/arch/combat-brain/)). This page is about the simulator side of that: how one combat runs in the game's own code (a **combat session**), how a search goes back to an earlier point (snapshots and replay), how it guesses what it cannot see (determinization), how it builds a combat from nothing but an observation (**CombatBuilder**), how far such a built combat can be trusted, and what all of it costs.

## 1. A combat session

`CombatSession` (`Simulation/CombatSession.cs`) runs one combat in the real engine. It is set up by a record,

```csharp
CombatSetup(string Character, EncounterModel Encounter, int ActIndex, string Seed, int Ascension = 0,
    Loadout? Loadout = null, CombatObservation? From = null, IReadOnlyList<EnemyTurns>? History = null)
```

and started in four steps:

1. `Player.CreateForNewRun(character, UnlockState.all)`, then the loadout (deck, relics, potions, HP: [Reference §3](/en/arch/simulator/reference/#sec-3));
2. `RunState.CreateForTest` with a `MockSinglePointActMap`, a map with a single point;
3. `RunManager.SetUpTest`;
4. `EnterRoomDebug(Monster, encounter)`.

With `From`, the combat is then made to show that observation ([§5](#sec-5)), and `History` gives its monsters the moves they made before.

This is **not** the way a run enters a combat: it skips rolling what a `?` becomes and the run's room generation (`GenerateRooms`) <Badge text="verified" variant="success" />. That is fine for a combat on its own (the panel, benchmarks, search worlds) and wrong for runs, which start the way the game starts them ([Whole runs §2](/en/arch/simulator/runs/#sec-2)).

**Playing.** `Execute(action)` starts an action through `CombatActions.Start`, the same entry points the UI uses ([GameBridge §4](/en/arch/gamebridge/#sec-4)), then settles: it pumps until the game waits for the player again ([Headless host §7](/en/arch/simulator/headless/#sec-7)). After an end of turn it waits for a later turn; once the combat is over, for an empty queue and an idle executor (`CombatSession.cs:223-230`, 333-341). A combat played out by a policy (`PlayOut`, as rollouts and benchmarks do) stops at 50 rounds or 1,000 actions; its outcome is then `Truncated`, as it is for a combat over with enemies still alive (`CombatSession.cs:79-80`, 192-200).

**Uids.** Actions name cards and creatures by **uid**, a stable id taken from the game rather than a position in a list: a hand card by its `NetCombatCardDb` id, a creature by its `CombatId`. `play:7:2` plays card #7 at creature #2. The game numbers cards in a fixed order, so replays keep the same numbers ([Protocol §3](/en/arch/protocol/#sec-3)).

## 2. Snapshots are recipes

A search must go back: try a line, return to the decision, try another. The game cannot copy its state (its objects are tied to the singletons that hold the one live combat), so a snapshot is not a copy. It is a **recipe**: `(Setup, Trace)`, how the combat started and every step taken since. Each step of the trace is one of

- `Action`: a combat action, in text form (`play:7:2`, `end_turn`);
- `Choice`: the answer to a card prompt, as the game's own option indexes;
- `Determinize(seed)`: a determinization step ([§3](#sec-3)), in text form `determinize:SEED`.

To **restore** a snapshot is to start a new combat from the setup and replay the trace (`CombatSession.cs:110-131`). The same setup and trace always give the same state, because every random draw comes from a seeded stream and the Pump runs every continuation in the same order. The one clock-seeded generator, `Rng.Chaotic`, feeds only cosmetics <Badge text="verified" variant="success" />: monster skins, screen shake, a fake merchant's dialogue, the Trial event's entrant number, the YummyCookie icon, the timing of card-add animations, DenseVegetation's visual offsets. Three fallbacks reach it too, none of which the simulator hits: a monster model that is not a live copy (live monsters have seeded streams), a run started with no seed (the simulator always passes one), and a random variant of a localized text (localization returns keys, [Headless host §4](/en/arch/simulator/headless/#sec-4)).

Replay costs time proportional to its length. Measured on 2026-10-26: a restore costs 0.28 ms plus 0.073 ms per replayed action. For an SL world, which loads the node's checkpoint instead of starting a fresh combat, it is about 0.5 ms plus 0.1 ms per step since the node's entry ([Worlds and the SL clone §7](/en/arch/simulator/worlds/#sec-7)). The figure puts the two cost models side by side; drag the slider to restore deeper into a combat.

A search that stays inside one line replays only when it backtracks, so depth-first search pays these costs once per branch. A copy of the object graph would remove the replay cost, and is a lever kept for later ([§7](#sec-7)).

## 3. Determinize

`Determinize(seed)` replaces everything the player cannot know with a sample drawn from `seed`, and leaves what the player sees unchanged (`CombatSession.cs:237-283`). It is how NoSL's search guesses the hidden state; [Environments: worlds §2](/en/arch/environments/worlds/#sec-2) explains why, with a figure on a real draw pile. What it does:

- reseeds every run stream (`RunRngType`), every player stream (`PlayerRngType`) and the stream of every live monster, allies and pets included;
- reorders the draw pile: first sorted by card key (an order that depends only on what the player sees), then a Fisher–Yates shuffle with the sample;
- numbers the cards outside the hand again (`CombatBuilder.NumberCards`): the game numbers cards in draw order, so the old numbers would leak the true order;
- redraws each enemy's queued move uniformly among the moves that show the same intents, and rewrites the last entry of its move log (`StateLog[^1]`) to match.

The seed comes only from the caller, never from the run. Not modelled yet: a draw-pile card whose place the player knows (one just put on top), and how a monster's history makes some moves likelier than others (`CombatSession.cs:248-249`).

## 4. Hidden state and transpositions

Search remembers the states it has already searched, so that two orders of the same plays are searched once. A state is the observation plus what the observation hides that changes what happens next. `HiddenState.Key` (`GameBridge/HiddenState.cs:19-29`) hashes the draw pile's order, the position (counter) of every run, player and monster stream, and each monster's queued move. The order of this turn's plays is left out on purpose. `HiddenState.Full` (`:36-44`), the SL world's key, adds each monster's move log and this turn's entries of the combat history, as a multiset ([Environments: worlds §4](/en/arch/environments/worlds/#sec-4)).

## 5. CombatBuilder: a combat from an observation

In NoSL, search may not start from the real combat: that would carry the true hidden state into the search. It starts from a combat that **shows the observation** and nothing more. `CombatBuilder.Setup(obs, seed, history)` (`Simulation/CombatBuilder.cs:57-105`) builds one:

1. **Start** the observation's encounter with its deck, relics and HP. A start-of-combat effect can kill a player at low HP (Royal Poison deals 4 at the start of the first turn, which every build starts with), and a dead player's relics, powers and cards stop acting. Such a combat starts again at full HP (`CombatSession.cs:164-168`), and the next step sets the observed HP as always. A relic that keeps a flag by the HP at the start (Red Skull's strength) can then be off, which only that rare start risks.
2. **`Apply`** overwrites everything visible: the round; the enemies (added, removed, reordered); HP and block; energy, max energy and stars; gold; potions; orb slots and orbs, with the numbers they show; relic counters, shown or hidden, statuses, melted and used-up relics; the cards a relic keeps (Pael's Tooth's, whose counter is their number), as canonical copies, since the tooltip shows no upgrades and they come back only after the combat; powers, with their stacks where the icon shows another number, and the card a power keeps; the four piles, card by card, with each card's modifications; intents.
3. **`Resample(StableHash(seed))`** draws the hidden state, as determinization does.
4. **`BuildDifferences`** compares, by JSON path, the input observation with the observation of the rebuilt combat. Empty means exact. A NoSL world refuses a build that is not exact (`Simulation/SimWorlds.cs:34-44`).

The hard parts, each solved in the builder:

- **Knob solving.** A number on screen is computed from internal numbers, differently for each power or relic. The builder tries internal numbers (the amount, dynamic variables, fields, and the int and decimal fields of a power's internal data, such as `HARDENED_SHELL_POWER`'s damage taken this turn) until the display matches (`CombatBuilder.cs:415-457`). A relic seen as used up (a spent `LIZARD_TAIL`, `WINGED_BOOTS` with no flights left) gets its int and bool fields tried the same way, after its counter, until the rebuilt relic is used up too with the counter as observed: `SILVER_CRUCIBLE` is used up only once its counter has run out and a treasure room has been entered.
- **Intents.** The builder chooses among the moves that show the observed intents (`CombatBuilder.cs:164-213`). A stunned enemy gets a synthesized stun move, made the way `Creature.StunInternal` makes one (`FollowUpStateId = StateLog.Last().Id`). Hidden enum switches in powers (`SurroundedPower._facing`), then the monsters' own int fields, are searched to match as many enemies as possible: values 0–99 first, then 100–999, which is how the Waterfall Giant's eruption damage, which grows each time it fires, is found past 100.
- **Uids** match the observation's; the other cards are numbered above them. Cards are taken from the fresh deck by id, upgrade and enchantment before new ones are made (`CombatBuilder.cs:507-534`).
- **Allies.** Creatures on the player's side are built like enemies: a relic's pet, which joins at the start, is matched by monster id; a missing one joins as the player's pet, as a summon makes it (`CombatBuilder.cs:309-336`). Any character can summon Osty with a card from another character's pool (`KALEIDOSCOPE` offers those), which failed one run in 165 of generation 1's self-play before allies were built.
- **Costs.** A card's own cost is set so that the modifiers on top of it (powers, relics) give the cost shown, and it may be below 0 (`CombatBuilder.cs:575-583`). A `PINPOINT` that an Attack Potion made free this turn costs 1 less again for each Skill played this turn, and under Tangled (`TANGLED_POWER` adds 1) it still shows 0. Clamping the card's own cost at 0 failed one run in 452.
- **Mad Science.** A card from the Tinker Time event gets back the type and rider the event chose, which its frame and text show (`CombatBuilder.cs:550-554`, [Protocol §1](/en/arch/protocol/#sec-1)).
- **Move logs.** A monster picks its next move by the moves it made (not the same one three times in a row, a fixed cycle), and a fresh combat's log holds none. With the record of what each enemy showed at the start of each round ([Harness §6](/en/arch/harness/#sec-6)), each monster gets its log: each earlier round's move, then the current one (`CombatBuilder.cs:119-154`). An earlier round matches the move that shows the same intents, else the same intent types and hits, else the same types, since the numbers grow with the monster's strength. A monster with a round that no move matches keeps a fresh log. A stun is not logged, as in the game: a round shown stunned is left out, and a monster stunned now goes on, after the stun, with the move it showed at this round's start. Without the record, every monster has a fresh log.
- **The first move.** From round 2 on the builder marks that the monsters have made their first move (`_performedFirstMove`).

**Approximations.** What the builder cannot see it approximates: this turn's history and the counters inside powers and monsters; how long a cost modifier lasts; the decay of the player's debuffs; a stun's follow-up without the record; and the deck, which is every card seen, generated ones included. [§6](#sec-6) measures what they cost; they have never been checked against observations from the real game.

**Checked by `selftest`**, which cuts each of its combats at up to three random points and builds a combat from each cut's observation; the build must show the observation, restore, and play on. On 2026-10-27 every check passed: Silent 60 of 60 builds, Ironclad 58 of 58, the Silent's elite and boss fights of acts 1, 2 and 3 57, 57 and 58. Other `selftest` builds show numbers only a model's own state holds: a worn Glass orb, a spent Silver Crucible, a Pael's Tooth keeping two cards, Sloth with 1 of 3, Nightmare's copies, a Hardened Shell after damage this turn, a start at 3 HP with Royal Poison, an eruption past 100 ([Reference §5](/en/arch/simulator/reference/#sec-5)).

## 6. Fidelity: how far a built combat can be trusted

A built combat shows the observation, but does it play like the real one? `fidelity` (`Checks/Fidelity.cs`) measures it, apart from what determinization samples on purpose. At every k-th decision of a panel's combats, the real combat plays on with a placeholder policy to the end of the turn, the enemies' turn included (at most 12 actions). A combat built from the decision's observation and record is given the real one's sampled state (the draw order, the random streams, each monster's stream and next move: `CombatSession.Mirror`) and plays the same actions. The first observation that differs, uids aside, is counted by its JSON path.

The Silent's starter deck, policy `play`, every second decision (2026-10-27):

| combats | decisions | the same through the enemies' turn, without the record → with it |
|---|---|---|
| act 1 weak + regular, 30 | 459 | 82.4% → 96.3%; 97.4% with stuns' follow-ups |
| act 2 weak + regular, 30 | 478 | 88.7% → 98.1%; 99.0% with stuns' follow-ups |
| act 1 boss, 9 | 201 | 96.5% → 96.5% |
| act 1 elite, 15 | 289 | 99.0% → 99.0% |

No combat was built wrong, and no action was illegal in a built one. Within the turn at most 1% differ. The rest differ after the turn ends: in act 1 the intents of `TWO_TAILED_RAT`, whose summon depends on counters inside the monster (turns until it may summon, summons so far); in act 2 `PARAFRIGHT`'s; in the boss fights the Waterfall Giant's damage. A stunned `CORPSE_SLUG` (another slug died) went on with the wrong move until stuns took their follow-up from the record.

## 7. Speed

Measured on 2026-10-26, a Release build with `DOTNET_ReadyToRun=0` ([Headless host §6](/en/arch/simulator/headless/#sec-6)). Acts are counted from 1 here, as the game shows them; the command line's `--act` counts from 0.

**Combats** (`bench`, act 1 weak + regular encounters, `play` policy):

| character | combats | combats/s | actions/s | time per combat |
|---|---|---|---|---|
| SILENT | 5,000 | 319 | 10.3k | 3.1 ms |
| IRONCLAD | 2,000 | 379 | | |

Short runs (200 combats) take about 6.7 ms per combat: boot and JIT warm-up dominate.

**Branching** (`forkbench`). A search branch here is a restore, a determinization and a rollout to the end of the combat with the placeholder policy:

| measure | value |
|---|---|
| restore | 0.28 ms + 0.073 ms per replayed action |
| branch | median 2.78 ms, p90 3.97 ms |
| mean root depth / mean rollout | 15.8 / 16.6 actions |
| throughput | 329 branches/s per core |

**Where a search worker's time goes.** Sampled for 40 s in a worker of a whole-run gate (2026-10-27: NoSL worlds built from observations, combat net c2, 4 runs of 8 workers each on 16 threads), the worker searched 87% of the time and waited for requests the rest. Restoring worlds took 48%: starting the combat from its setup 38% (entering the room 9%, applying the observation 8%, resampling 4%, comparing the build with the observation 10%), replaying the line 7%, determinizing 4%. Playing the searched actions took 16%, observations 16% (11% besides that comparison), the combat net 5%. A restore no longer compares the build, which the request's first build has checked (commit `5032064`): the champion's runs are the same, 7% faster under that load.

**More processes** (`bench` with 3,000 combats per process; the wall time includes about 1.2 s of boot each). The machine has 8 physical cores; hyperthreading adds about 8%. The default pool is 8 processes, about 160 MB each.

**Levers**, in order: avoid deep replays (reuse prefixes in depth-first search; node checkpoints, [Worlds and the SL clone §3](/en/arch/simulator/worlds/#sec-3)); filter hook listeners per hook (needs a profiler, `perf`, not installed); a deep copy of the object graph, which removes the replay cost and would be needed for AlphaZero-style search. Whether to copy or replay is decided once profiles show that restoring dominates ([Reference §8](/en/arch/simulator/reference/#sec-8)).
