Combat is where search spends almost all of its time: the combat brain tries thousands of lines of play for every decision ([Combat brain](/en/arch/combat-brain/)). This page is about the simulator side of that: how one combat runs in the game's own code (a **combat session**), how a search goes back to an earlier point (snapshots and replay), how it guesses what it cannot see (determinization), how it builds a combat from nothing but an observation (**CombatBuilder**), how far such a built combat can be trusted, and what all of it costs.

## 1. A combat session

`CombatSession` (`Simulation/CombatSession.cs`) runs one combat in the real engine. It is set up by a record,

```csharp
CombatSetup(string Character, EncounterModel Encounter, int ActIndex, string Seed, int Ascension = 0,
    Loadout? Loadout = null, CombatObservation? From = null, IReadOnlyList<EnemyTurns>? History = null)
```

and started in four steps:

1. `Player.CreateForNewRun(character, UnlockState.all)`, then the loadout (deck, relics, potions, HP: [Reference §3](/en/arch/simulator/reference/#sec-3));
2. `RunState.CreateForTest` with a `MockSinglePointActMap`, a map with a single point;
3. `RunManager.SetUpTest`;
4. `EnterRoomDebug(Monster, encounter)`.

With `From`, the combat is then made to show that observation ([§5](#sec-5)), and `History` gives its monsters the moves they made before.

This is **not** the way a run enters a combat: it skips rolling what a `?` becomes and the run's room generation (`GenerateRooms`) <Badge text="verified" variant="success" />. That is fine for a combat on its own (benchmarks, `selftest`, search worlds) and wrong for runs, which start the way the game starts them ([Whole runs §2](/en/arch/simulator/runs/#sec-2)).

**Playing.** `Execute(action)` starts an action through `CombatActions.Start`, the same entry points the UI uses ([GameBridge: actions per surface §1](/en/arch/gamebridge/actions/#sec-1)), then settles: it pumps until the game waits for the player again ([Headless host §7](/en/arch/simulator/headless/#sec-7)). After an end of turn it waits for a later turn; once the combat is over, for an empty queue and an idle executor (`CombatSession.cs:216-223`, 287-302). Settling is also where a fight past the round cap is lost, as in a run: when the player's turn in round 81 comes, the player dies ([Whole runs §3](/en/arch/simulator/runs/#sec-3)). A combat played out by a policy (`PlayOut`, as rollouts and benchmarks do) also stops at 1,000 actions; its outcome is then `Truncated`, as it is for a combat over with enemies still alive (`CombatSession.cs:73`, 185-193).

**Uids.** Actions name cards and creatures by **uid**, a stable id taken from the game rather than a position in a list: a hand card by its `NetCombatCardDb` id, a creature by its `CombatId`. `play:7:2` plays card #7 at creature #2. The game numbers cards in a fixed order, so replays keep the same numbers ([Protocol: observations and actions §4](/en/arch/protocol/observation/#sec-4)).

## 2. Snapshots are recipes

A search must go back: try a line, return to the decision, try another. The game cannot copy its state (its objects are tied to the singletons that hold the one live combat), so a snapshot is not a copy. It is a **recipe**: `(Setup, Trace)`, how the combat started and every step taken since. Each step of the trace is one of

- `Action`: a combat action, in text form (`play:7:2`, `end_turn`);
- `Choice`: the answer to a card prompt, as the game's own option indexes;
- `Determinize(seed)`: a determinization step ([§3](#sec-3)), in text form `determinize:SEED`.

To **restore** a snapshot is to start a new combat from the setup and replay the trace (`CombatSession.cs:103-124`). The same setup and trace always give the same state, because every random draw comes from a seeded stream and the Pump runs every continuation in the same order. The one clock-seeded generator, `Rng.Chaotic`, feeds only cosmetics <Badge text="verified" variant="success" />: monster skins, screen shake, a fake merchant's dialogue, the Trial event's entrant number, the YummyCookie icon, the timing of card-add animations, DenseVegetation's visual offsets. Three fallbacks reach it too, none of which the simulator hits: a monster model that is not a live copy (live monsters have seeded streams), a run started with no seed (the simulator always passes one), and a random variant of a localized text (localization returns keys, [Headless host §4](/en/arch/simulator/headless/#sec-4)).

Replay costs time proportional to its length: a restore costs 0.28 ms plus 0.073 ms per replayed action. For an SL world, which loads the node's checkpoint instead of starting a fresh combat, it is about 0.5 ms plus 0.1 ms per step since the node's entry ([Worlds and the SL clone §7](/en/arch/simulator/worlds/#sec-7)). The figure puts the two cost models side by side; drag the slider to restore deeper into a combat.

## 3. Determinize

`Determinize(seed)` replaces everything the player cannot know with a sample drawn from `seed`, and leaves what the player sees unchanged (`CombatSession.cs:230-276`). It is how NoSL's search guesses the hidden state; [Environments: worlds §2](/en/arch/environments/worlds/#sec-2) explains why, with a figure on a real draw pile. What it does:

- reseeds every run stream (`RunRngType`), every player stream (`PlayerRngType`) and the stream of every live monster, allies and pets included;
- reorders the draw pile: first sorted by card key (an order that depends only on what the player sees), then a Fisher–Yates shuffle with the sample;
- numbers the cards outside the hand again (`CombatBuilder.NumberCards`): the game numbers cards in draw order, so the old numbers would leak the true order;
- redraws each enemy's queued move uniformly among the moves that show the same intents, and rewrites the last entry of its move log (`StateLog[^1]`) to match.

The seed comes only from the caller, never from the run. Not modelled: a draw-pile card whose place the player knows (one just put on top), and how a monster's history makes some moves likelier than others (`CombatSession.cs:241-242`).

## 4. Hidden state and transpositions

Search remembers the states it has already searched, so that two orders of the same plays are searched once. A state is the observation, with the hand, the discard and the exhaust pile as multisets of cards ([Combat brain: prompts, moves and workers §5](/en/arch/combat-brain/shared/#sec-5)), plus what the observation hides that changes what happens next. `HiddenState.Key` (`GameBridge/HiddenState.cs:19-29`) hashes the draw pile's order, the position (counter) of every run, player and monster stream, and each monster's queued move. The order of this turn's plays is left out on purpose. `HiddenState.Full` (`:36-44`), the SL world's key, adds each monster's move log and this turn's entries of the combat history, as a multiset ([Environments: worlds §4](/en/arch/environments/worlds/#sec-4)).

## 5. CombatBuilder: a combat from an observation

In NoSL, search may not start from the real combat: that would carry the true hidden state into the search. It starts from a combat that **shows the observation** and nothing more. `CombatBuilder.Setup(obs, seed, history)` (`Simulation/CombatBuilder.cs:57-105`) builds one:

1. **Start** the observation's encounter with its deck, relics and HP. A start-of-combat effect can kill a player at low HP (Royal Poison deals 4 at the start of the first turn, which every build starts with), and a dead player's relics, powers and cards stop acting. Such a combat starts again at full HP (`CombatSession.cs:157-161`), and the next step sets the observed HP as always. A relic that keeps a flag by the HP at the start (Red Skull's strength) can then be off, which only that rare start risks.
2. **`Apply`** overwrites everything visible: the round; the enemies (added, removed, reordered); HP and block; energy, max energy and stars; gold; potions; orb slots and orbs, with the numbers they show; relic counters, shown or hidden, statuses, melted and used-up relics; the cards a relic keeps (Pael's Tooth's, whose counter is their number), as canonical copies, since the tooltip shows no upgrades and they come back only after the combat; powers, with their stacks where the icon shows another number, and the card a power keeps; the four piles, card by card, with each card's modifications; intents.
3. **`Resample(StableHash(seed))`** draws the hidden state, as determinization does.
4. **`BuildDifferences`** compares, by JSON path, the input observation with the observation of the rebuilt combat. Empty means exact. A NoSL world refuses a build that is not exact (`Simulation/SimWorlds.cs:37-48`).

The hard parts, each solved in the builder:

- **Knob solving.** A number on screen is computed from internal numbers, differently for each power or relic. The builder tries internal numbers (the amount, dynamic variables, fields, and the int and decimal fields of a power's internal data, such as `HARDENED_SHELL_POWER`'s damage taken this turn) until the display matches (`CombatBuilder.cs:418-460`). A relic seen as used up (a spent `LIZARD_TAIL`, `WINGED_BOOTS` with no flights left) gets its int and bool fields tried the same way, after its counter, until the rebuilt relic is used up too with the counter as observed: `SILVER_CRUCIBLE` is used up only once its counter has run out and a treasure room has been entered.
- **Intents.** The builder chooses among the moves that show the observed intents (`CombatBuilder.cs:164-213`). A stunned enemy gets a synthesized stun move, made the way `Creature.StunInternal` makes one (`FollowUpStateId = StateLog.Last().Id`). Hidden enum switches in powers (`SurroundedPower._facing`), then the monsters' own int fields, are searched to match as many enemies as possible: values 0–99 first, then 100–999, which is how the Waterfall Giant's eruption damage, which grows each time it fires, is found past 100.
- **Uids** match the observation's; the other cards are numbered above them. Cards are taken from the fresh deck by id, upgrade and enchantment before new ones are made (`CombatBuilder.cs:510-537`).
- **Allies.** Creatures on the player's side are built like enemies: a relic's pet, which joins at the start, is matched by monster id; a missing one joins as the player's pet, as a summon makes it (`CombatBuilder.cs:312-339`). Any character can summon Osty with a card from another character's pool (`KALEIDOSCOPE` offers those).
- **Costs.** A card's own cost is set so that the modifiers on top of it (powers, relics) give the cost shown, and it may be below 0 (`CombatBuilder.cs:578-586`). A `PINPOINT` that an Attack Potion made free this turn costs 1 less again for each Skill played this turn, and under Tangled (`TANGLED_POWER` adds 1) it still shows 0.
- **Mad Science.** A card from the Tinker Time event gets back the type and rider the event chose, which its frame and text show (`CombatBuilder.cs:553-557`, [Protocol: observations and actions §3](/en/arch/protocol/observation/#sec-3)).
- **Move logs.** A monster picks its next move by the moves it made (not the same one three times in a row, a fixed cycle), and a fresh combat's log holds none. With the record of what each enemy showed at the start of each round ([Harness §4](/en/arch/harness/#sec-4)), each monster gets its log: each earlier round's move, then the current one (`CombatBuilder.cs:119-154`). An earlier round matches the move that shows the same intents, else the same intent types and hits, else the same types, since the numbers grow with the monster's strength. A monster with a round that no move matches keeps a fresh log. A stun is not logged, as in the game: a round shown stunned is left out, and a monster stunned now goes on, after the stun, with the move it showed at this round's start. Without the record, every monster has a fresh log.
- **The first move.** From round 2 on the builder marks that the monsters have made their first move (`_performedFirstMove`).

**Approximations.** What the builder cannot see it approximates: this turn's history and the counters inside powers and monsters; how long a cost modifier lasts; the decay of the player's debuffs; a stun's follow-up without the record; and the deck, which is every card seen, generated ones included. [§6](#sec-6) says where they show; they are not checked against observations from the real game.

**Checked by `selftest`**, which cuts each of its combats at up to three random points and builds a combat from each cut's observation; the build must show the observation, restore, and play on, and `selftest` fails if any build does not. Other `selftest` builds show numbers only a model's own state holds: a worn Glass orb, a spent Silver Crucible, a Pael's Tooth keeping two cards, Sloth with 1 of 3, Nightmare's copies, a Hardened Shell after damage this turn, a start at 3 HP with Royal Poison, an eruption past 100 ([Reference §5](/en/arch/simulator/reference/#sec-5)).

## 6. Fidelity: how far a built combat can be trusted

A built combat shows the observation: its `BuildDifferences` are empty, or a NoSL world refuses it ([§5](#sec-5)), and `selftest` fails on any build that does not show its observation ([Reference §5](/en/arch/simulator/reference/#sec-5)). Whether it then plays like the real combat is a separate question, with two parts. Some differences are there by design: determinization draws the draw order, the random streams and each monster's next move ([§3](#sec-3)), so every world differs from the real combat in those on purpose. The others come from the builder's approximations ([§5](#sec-5)): what the observation does not show and the builder does not solve for, it leaves as a fresh combat has it.

The approximations do not show at the decision, since the build matches the observation; they show later, mostly in the enemies' turn, through counters kept inside monsters that no screen shows. `TWO_TAILED_RAT` is the plain case: whether it may call for backup depends on its turns until it may summon and its summons so far (`Models.Monsters/TwoTailedRat.cs:40-42`). The builder touches a monster's own fields only when no move would show its intent otherwise ([§5](#sec-5)), so a built rat usually holds a fresh rat's counts, and its next intent can differ from the real one's. Without the record of enemy moves ([Harness §4](/en/arch/harness/#sec-4)) more is guessed: every monster starts with a fresh move log, and a stunned one's follow-up is approximated.

## 7. Speed

Measured on a Release build with `DOTNET_ReadyToRun=0` ([Headless host §6](/en/arch/simulator/headless/#sec-6)). Acts are counted from 1 here, as the game shows them; the command line's `--act` counts from 0.

**Combats.** `bench` plays combats over an encounter pool as fast as it can with a placeholder policy and prints combats and actions per second, the time per combat and its peak memory ([Reference §4](/en/arch/simulator/reference/#sec-4)). With the act 1 weak and regular encounters and `play`, one process plays about 275 combats a second over 3,000 combats, boot included (the figure below). Short batches take longer per combat: boot and the JIT's warm-up weigh more in them.

**Branching.** A search branch here is a restore, a determinization and a rollout to the end of the combat with the placeholder policy. Its restore costs 0.28 ms plus 0.073 ms per replayed action ([§2](#sec-2)), so the deeper in the combat a branch starts, the more of its time is replay.

**Where a search worker's time goes.** A search worker spends most of its time searching, and restoring worlds is the largest share of that: starting the combat from its setup (entering the room, applying the observation, resampling), replaying the line and determinizing. Playing the searched actions, building observations and the combat net take the rest. A restore does not compare the build with the observation: the request's first build has checked it ([Worlds and the SL clone §2](/en/arch/simulator/worlds/#sec-2)).

**More processes** (`bench` with 3,000 combats per process; the wall time includes about 1.2 s of boot each). The machine has 8 physical cores; hyperthreading adds about 8%. The default pool is 8 processes (`--workers`, one per world).

**Levers**, in order: avoid deep replays (reuse prefixes in depth-first search; node checkpoints, [Worlds and the SL clone §3](/en/arch/simulator/worlds/#sec-3)); filter hook listeners per hook, which needs a profile of hook dispatch (a profiler such as `perf`); a deep copy of the object graph, which removes the replay cost and which AlphaZero-style search would need. Whether to copy or replay is an open question ([Reference §8](/en/arch/simulator/reference/#sec-8)).
