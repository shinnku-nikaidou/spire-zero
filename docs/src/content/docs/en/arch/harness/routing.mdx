A run's `Dispatcher` holds four routes, one per side of the routing table, each a brain with the name it goes by in the log. This page is about those routes, what they may spend, where their randomness comes from, and what happens when one of them fails.

## 1. The routing table

Every decision goes to exactly one side:

| surface | side | brains |
|---|---|---|
| `combat` | combat | `plan` (the SL planner, SL only), `pimc` (NoSL only), or the placeholder `play` |
| `card_choice` asked during a combat (`ChoiceContext.InCombat`) | combat prompts | the answer the combat brain's last action carries, if any; else `first`, the first options ([Combat brain: prompts, moves and workers §1](/en/arch/combat-brain/shared/#sec-1)) |
| `card_choice` asked outside combat (upgrade, transform, enchant, remove, …) | macro prompts | L0, the macro brain itself, or `random` |
| `map`, `rewards`, `card_reward`, `bundle`, `event`, `shop`, `rest`, `treasure`, `crystal_sphere` | macro | L0 ([Macro brain](/en/arch/macro-brain/)), or `random` |

The potion belt has no surface of its own: its actions are part of each macro screen's legal list ([GameBridge: actions per surface §6](/en/arch/gamebridge/actions/#sec-6)). A surface outside the table throws "uncovered surface" ([§6](#sec-6)).

**The champion's name.** A run's brains together are its champion, named by `Dispatcher.Champion`:

```text
combat plan COMBAT beam 8x300 easy 4 loss plans 3, combat prompts first, macro l0 VALUE clone, macro prompts l0 VALUE clone
```

That is the SL champion as this code names it, where `COMBAT` and `VALUE` stand for the names of the champion's combat net and V ([Evaluation: champions and baselines](/en/arch/evaluation/champions/)): the SL planner with the combat net in its leaves (its endings priced by V) at the medium budget, `first` for the prompts in combat that no search answered, and L0 with V playing each option on the node's clone, for the macro decisions and the card prompts outside combat. Each brain names its parts: a searching combat brain its combat net; L0 its V, `clone`, and its exploration (`eps ε` for even draws); the budget as [§4](#sec-4) writes it. SimWorker's `ChampionOptions` makes the routes from the command's options and refuses to run if the name it makes is not the one champion files use (`Brains/ChampionOptions.cs:36-60`).

**The environment picks the combat brain.** The macro brain is the same in both environments; the combat brain is not ([Environments: worlds §5](/en/arch/environments/worlds/#sec-5)). The champion factory refuses `plan` and `--afterstates clone` outside SL, `pimc` outside NoSL, and in SL an L0 that does not play on the node's clone, since the afterstates it would predict from the screen are NoSL's. `run` plays its options as given, so SL runs with L0 take `--afterstates clone`. The `brain` command serves both environments: NoSL hosts get `--policy`'s combat brain, SL hosts `--sl-policy`'s, and it sets L0's afterstates by the host's environment, from the screen for NoSL hosts and on the node's clone for SL hosts, so one champion file serves both ([Overview §5](/en/arch/harness/#sec-5)).

## 2. Combat routes

A combat route is a `CombatRoute(Brain, Decide, Budget)`: its name, a function from (decision, seed, the node's clone or null, the combat's moves so far) to a `CombatDecisionResult`, and its budget for the log and the name.

**Placeholders.** `CombatRoute.Of(name, policy)` wraps a policy that does not search (`play`): it gives its pick, with no plan and no candidates.

**PIMC in the pool** (`PooledPimc.Route`, [NoSL PIMC](/en/arch/pimc/)), in NoSL only. With one legal action it answers at once. Otherwise:

- **The worlds**: one `pimc_world` request per world, each rebuilt in its worker from the observation, the record of enemy moves and the build seed, so nothing of the true state leaves the host. Each world's nodes are shared evenly over the first actions. With the same seeds it gives the same answer as PIMC over worlds in one process, which `selftest` checks.
- **Following a cycle**: the route keeps one `TurnPlan` for the run, which keeps a search's plan only when it repeats a cycle and every world planned it the same, since searching again before each repeat would only find the same cycle again ([NoSL PIMC: search §6](/en/arch/pimc/search/#sec-6)). A step of the plan is played without searching while the combat shows the observation the plan expected before it; otherwise the decision is searched again and marked replanned.

**The SL planner in the pool** (`PooledPlanner.Route`, [The SL planner](/en/arch/sl-planner/)). One `SlRoute` per run plans the rest of the combat once and then follows the plan, planning again only where a step does not hold or the plan has run out ([The SL planner §4](/en/arch/sl-planner/#sec-4)). A plan is `SlPlanner.Search` with each turn of the beam sent as one `sl_turn` request per state kept, at the route's budget. The route throws without a node clone (it plays in SL only).

**Two things that last the whole run.** `TurnPlan` and `SlRoute` are made once per run and never cleared, neither at a combat's end nor at a macro decision; the planner's count of unproved losing plans in a row runs across decisions ([The SL planner: beam §6](/en/arch/sl-planner/beam/#sec-6)).

## 3. Macro and prompt routes

A macro or prompt route is a `Route<T>(Brain, Policy)`. Today:

- **L0** (`MacroBrain`, `--macro l0`) answers both the macro decisions and the card prompts outside combat, as one object with one V ([Macro brain: search](/en/arch/macro-brain/search/)). Its exploration (`--explore ε`, even draws, self-play only) draws from its own generator ([§5](#sec-5)).
- **`first`** (`FirstPicks`) answers the card prompts in combat that the combat brain's action does not: the first options in canonical order, as few as the prompt takes, as the search worlds do. The answer an action carries reaches the first in-combat prompt after it (`Dispatcher`), and a prompt that does not accept it goes to `first` too ([Combat brain: prompts, moves and workers §1](/en/arch/combat-brain/shared/#sec-1)).
- **`random`** placeholders answer both macro sides when `--macro random`.

**The node's clone for the macro side.** In SL with `--afterstates clone`, the `Dispatcher` opens the node's clone at each macro decision and each card prompt outside combat, as a `PooledClone` on the run's worker pool (`MacroDecision.With`, `ChoiceDecision.With`). L0 then asks it for afterstates: what the game asks next after each path of answers. `PooledClone` splits the paths into min(paths, workers) contiguous `sl_macro` requests, each worker loading the clone once per path, and checks that every path got an afterstate; since an afterstate depends only on the clone and the path, the split cannot change a result ([Macro brain: search §6](/en/arch/macro-brain/search/#sec-6)).

**The plan.** After the macro answer is checked, the `Dispatcher` asks the policy what it plans after it (`IMacroPolicy.Plan`): L0's is the rest of the act's route on the map, empty elsewhere. Its time is not in the decision's `elapsed_ms`.

**Scored options.** Then it takes the options the policy chose among, with their values (`Scored`): L0's are every legal option with V's chance to win the run after it, the chosen first and then best first, and none when its answer was drawn by exploration ([Macro brain: search §1](/en/arch/macro-brain/search/#sec-1)). A card prompt outside combat gives the answers L0 weighed. They become the recommendation's candidates, and for a host that shows answers each map option gets its route too ([Overview §5](/en/arch/harness/#sec-5)); the decision log does not keep them.

**Explored.** A prompt or macro answer is marked explored when the policy says its last answer was drawn: for L0, by its even draws ([The decision log §6](/en/arch/harness/decision-log/#sec-6)).

## 4. The budget

What a combat search may spend is a `Budget` (`Brain/Combat/CombatBrain.cs:15-36`). Its unit is the **node**: one action simulated in a world. There is no wall-clock budget and no other unit.

| field (JSON) | default | meaning |
|---|---|---|
| `worlds` | 8 | PIMC's worlds per decision; the planner has one world and ignores it |
| `nodes_per_world` | 300 | PIMC: the actions simulated in each world's search of the turn. The planner: in each search of one turn from one state |
| `beam` | 0 | the planner's states kept from one turn to the next; 0 means PIMC |
| `replan` | 1 | the planner's turns of an unproved losing plan played before planning again; 0 plays it to its end |
| `loss_plans` | 0 | the most unproved losing plans the planner makes in a row, in one combat, before the last is played to its end; 0 is no limit |
| `easy_beam` | 0 | the planner's beam when its greedy dive already wins; 0 is `beam` |

**Effort levels** (`--effort`, `Budget.Effort`, [The SL planner: budget §1](/en/arch/sl-planner/budget/#sec-1)):

| level | beam | nodes | easy beam | loss plans |
|---|---|---|---|---|
| `low` | 8 | 300 | 2 | 3 |
| `medium` | 8 | 300 | 4 | 3 |
| `high` | 8 | 300 | – | – |
| `max` | 16 | 300 | – | – |

**As a name** (`Budget.ToString`): `8x300` for PIMC (`beam 16x300` for the planner), then the planner's `easy N`, `replan N` when not 1, and `loss plans N` when limited.

**Planned: budgets by mode** <Badge text="planned" variant="caution" />. Today every mode uses the fixed node budget. The design gives each mode its own unit:

| mode | unit | why |
|---|---|---|
| self-play, evaluation | a fixed number of nodes | reproducible: the same request, seed and budget give the same recommendation |
| assist | wall clock, anytime | a human is waiting: send the best answer so far, then refine it |
| auto-play (R4) | a wall-clock cap and a minimum number of nodes | do not stall, and do not go shallow |

"Anytime" means the search can be stopped at any moment and still has a best answer to give. A planned allocation would stop when the top two candidates are separated by more than their confidence intervals, and otherwise add samples or depth. What is built instead: a fixed number of nodes, shared evenly over the first actions, and following a plan ([NoSL PIMC: budget §1](/en/arch/pimc/budget/#sec-1)).

## 5. Seeds and determinism

A decision's search must give the same answer every time it is asked the same thing, so its randomness comes from Harness, never from the game's random streams, and never from the clock.

**The run id** is the FNV-1a 64-bit hash of the run's seed as a JSON string (quotes included), in hex: seed `0SSL7NS01MU6` gives run `ce13ba5116b7f48a`. The brain sees the run id, never the seed ([Protocol: the wire §3](/en/arch/protocol/wire/#sec-3)).

**A decision's seed** is drawn from the run id and the decision's number, which counts every decision of the run from 0, combat decisions, card prompts and macro decisions alike (`Dispatcher.cs:197-216`):

```text
H        = FNV-1a 64 of the JSON string run_id
z        = H + 0x9E3779B97F4A7C15 · (i + 1)          (mod 2^64)
z        = (z xor (z >> 30)) · 0xBF58476D1CE4E5B9
z        = (z xor (z >> 27)) · 0x94D049BB133111EB
seed(i)  = z xor (z >> 31)
```

This is SplitMix64's step. The decision's number is Harness's own counter, not the wire's `decision_id`. The champion's version is planned to join the hash once brains have versions.

**Who reads it.** Every decision's line logs its seed, but only NoSL PIMC uses it:

- the **build seed** is the seed in upper-case hex (`X16`); the worker resamples what the observation does not fix with a generator seeded by its hash ([Simulator: combats §5](/en/arch/simulator/combat/#sec-5));
- world k is determinized with the hash of `"{seed}:{k}"` ([Simulator: combats §3](/en/arch/simulator/combat/#sec-3)).

The SL planner searches the one exact world and ignores it; the macro and prompt policies never receive it.

**Placeholders and exploration** draw from .NET generators seeded per run, one per stream: `Random(FNV(run_id + stream))` with the stream `""` for the placeholders and `:explore uniform` for L0's even draws (`Brains/ChampionOptions.cs:44-53`). So a run plays the same in any process and over the wire, whether or not it is logged.

**Order, not timing.** A search's requests run in parallel, but the pool returns their replies in request order ([Simulator: the worker pool §2](/en/arch/simulator/pool/#sec-2)), and candidates are sorted by value, with ties kept in the legal order (end turn, then cards, then potions). Which worker finishes first never changes an answer. `run --check` holds a whole run to this ([The decision log §8](/en/arch/harness/decision-log/#sec-8)).

## 6. Failures

There is no fallback: a decision that cannot be answered as specified fails, and the run with it. Nothing is ever answered at random in its place.

**In the `Dispatcher`** (`Dispatcher.cs`):

| case | what happens |
|---|---|
| a combat brain's pick is not legal | `InvalidOperationException` |
| a prompt answer the prompt does not accept (count, range, a repeated index) | `InvalidOperationException` |
| a macro surface with no route | "uncovered surface"; the decision's number and its brain's count are already used up |
| a macro answer that is not legal | `InvalidOperationException` |
| an SL decision that needs a clone, before any checkpoint | `InvalidOperationException` |
| a node checkpoint or action in NoSL | `InvalidOperationException` |
| a checkpoint whose node index does not rise; an action for another node or out of sequence | `InvalidDataException` |

**On the wire** (`BrainServer`): a refused `hello` (the champion factory threw: an unknown environment, `plan` or `--afterstates clone` outside SL, `pimc` outside NoSL, L0 off the node's clone in SL, a champion's name that does not match), a decision outside a run or after a refused node message, an id that does not rise, an observation that does not match its hash, a combat or prompt decision without its screen, an unknown message: each gets an `error`. A refused node message fails the run's next decision. A protocol version that does not match, or an I/O or JSON error, ends the brain's `Serve`, and the brain with it: it serves one host, so there is no next one, and the mod starts it again ([Overview §5](/en/arch/harness/#sec-5)).

**In the worker pool** ([Simulator: the worker pool §6](/en/arch/simulator/pool/#sec-6)):

| case | what happens |
|---|---|
| a worker boots or answers later than the timeout (5 minutes, for booting as for each answer) | killed; the request's first failure restarts it and sends the request again |
| a worker dies (I/O error, end of its output) | replaced, and the request sent again |
| the same request fails a second time | the search fails (an `AggregateException` from the parallel loop) |
| a reply that is not JSON, or has the wrong id | fails, without a retry |
| an error reply | fails after all replies are in, without a retry; the worker that threw exits, so its next use restarts it |
| a combat not built as observed | the worker's error is "not built as observed" with the first 4 differences (`SimWorlds.NoSL`), so the search fails |

A request is mostly seconds: one world's search, one beam state's turn, or a share of a decision's probe paths. The timeout catches a stuck worker, not a slow one.

**In the hosts**: in `run` any exception ends the run as `failed`, with its type and first line, and reports leave it out ([Simulator: whole runs §5](/en/arch/simulator/runs/#sec-5)). Over the wire the simulator's host throws on an `error`, with the same result, and on a recommendation whose id or hash is not the request's. The mod logs a warning, ends the run with `run_end{failed}`, and lets the game go on without the brain ([Mod: the main loop §8](/en/arch/mod/loop/#sec-8)). Evaluation requires decisions by a brain named `random` to be 0, and leaves failed runs out ([Evaluation: metrics, seeds and reports §2](/en/arch/evaluation/metrics/#sec-2)).

**Planned handling** <Badge text="planned" variant="caution" />:

| case | planned | today |
|---|---|---|
| a stale request (a newer `decision_id` exists) | cancel the search, send no reply | the mod drops the late answer; the brain answers every request, and one whose id does not rise gets an `error` |
| a worker crash or timeout | reopen the world on another worker from a snapshot, answer with what finished, mark the line `degraded` | the request is sent once more, which gives the same answer, so nothing is degraded |
| a combat that cannot be built from its observation | report the differences, no search, the host pauses, the bug is logged | the decision fails with the differences, and the run with it |
| the host rejects an action as illegal | the host asks again; twice in a row, pause | GameBridge's starts throw on an illegal action, and the run fails |
