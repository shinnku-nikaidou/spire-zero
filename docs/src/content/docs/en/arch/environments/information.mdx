The [overview](/en/arch/environments/) said in one sentence what each environment may know. This page makes it exact: the public history NoSL decides from, what SL adds inside the node, a table with one row per kind of information, the rulings on the grey cases, and where the line of a node falls. It ends with how the SL clone is made and with the tests that keep each rule true.

A badge <Badge text="verified" variant="success" /> marks a claim checked in the game's source; game file references such as `Runs/RunManager.cs:670-709` point into the decompiled game assembly, `MegaCrit.Sts2.Core` ([Introduction](/en/)).

## 1. NoSL: the public history

A NoSL decision may depend only on

- the **public history** of this run: everything shown on screen so far, and what can be inferred from it;
- rule knowledge: how cards, relics, monsters and the game's odds work;
- anything learned offline, such as V's weights.

"What can be inferred" is not a loophole; it is where a good player's skill lives. Three examples of fair inference:

- **Card counting.** The draw pile's contents are visible (the game lists them), its order is not. After a shuffle, every card drawn tells the player which cards are still to come.
- **A monster's next moves.** A monster shows one intent. Many monsters follow patterns (never the same move three times in a row, a fixed cycle), so its history of intents gives a probability distribution over what it will do after that.
- **Reward odds.** Some odds move with history. Every card the game rolls for a reward that is not rare raises the next roll's chance of a rare by one percentage point (half a point at the Scarcity ascension), up to 40 points above the base, and a rare resets it (`Odds/CardRarityOdds.cs:69-78`) <Badge text="verified" variant="success" />. A combat's chance to drop a potion falls by 10 points after it drops one and rises by 10 after it does not (`Odds/PotionRewardOdds.cs:56-70`). Counting the rewards seen gives the odds.

Search in NoSL works on **determinized samples**: concrete hidden states (a draw order, the monsters' moves, the state of the random streams) drawn so that each agrees with the public history. A search may try lines of play on such a sample freely, because the sample is a guess, not the truth ([Worlds §2](/en/arch/environments/worlds/#sec-2)).

## 2. SL: save & load inside the node

SL is NoSL plus the **true outcome of any sequence of actions inside the current node**. The project calls this "limited cheating". It is the same as a player who may save and quit as often as they like inside the node, and remembers everything they saw.

What SL may know, with examples:

- the draw order and every reshuffle; the monsters' moves; cards generated at random, random targets, random costs and orbs;
- how the order of actions changes all of these. Manipulating the random streams inside the node is allowed: if playing card A before card B makes a random hit land on the other enemy, SL may know it and use it.
- event outcomes. On Slippery Bridge, for example, SL knows which card is taken after each HOLD_ON: `SlipperyBridge.GetNewRandomCard` draws from the event's own `Rng`, which is seeded from the run's seed, the player's slot index (0 in a single-player run) and a hash of the event's id (`Models/EventModel.cs:234`) <Badge text="verified" variant="success" />;
- this node's rewards, including how they would change with the way the node was played;
- which card an Ancient's "random rare card" option gives.

What SL may **not** know: anything about later nodes. What a `?` point will turn out to be, which monsters a later fight will bring, a later reward, a later shop's stock, a later event. This holds even though the simulator that runs SL's searches holds the true random streams for all of them: the clone stops at the node's exit ([§3](#sec-3)), and a search that wants to look past it must use determinized samples seeded by the search itself, as NoSL does.

<Aside type="caution" title="Rejected">

A whole-run horizon ("knows the whole order of this run") was considered and rejected. Do not build it.

</Aside>

## 3. The node

A **node** is one map point (`MapPoint`), from the moment the player arrives at it until the moment they choose the next point on the map. It includes everything that happens at the point:

- every room of it (`MapPointHistoryEntry.Rooms`): an event that starts a combat has two rooms, the event and the combat;
- the rewards screen after a combat, the purchases in a shop, the options of a rest site, the chest of a treasure room, every page of an event.

The boundary, exactly:

- **Entry:** arrival at a map point. The game saves the run there, before it rolls what a `?` becomes and before it builds the room, so the entry state is a complete save (`SerializableRun`). In the simulator the game's `SaveRun` is patched never to write; the save made on arrival, the one with no finished room, starts a node (`Runtime/Patches/Persistence.cs:13-22`), while the saves after a combat win and an Ancient carry a room and never do.
- **Exit:** the map-travel action (`VoteForMapCoordAction`). The travel itself belongs to the current node; everything after it belongs to the next one.
- **Special cases:** the run's first point, where the Ancient Neow waits, is the first node; the code numbers nodes from 0, so it is node 0 (`Protocol/Wire.cs:79-81`). After a boss, the first point of the next act is a new node. The end of the run is an exit too.

Search that would cross the exit, for example to ask what a card is worth in the next fight, may use only determinized samples seeded by the search, never the true streams. No search does this today. The clone enforces the line: once the travel is recorded it stops and refuses any further step (`Simulation/RunSession.cs:235`), a macro probe that travels throws (`Checks/NodeProbe.cs:29`), and L0 values a map move by predicting its afterstate from the screen instead of playing it ([Macro brain: search §2](/en/arch/macro-brain/search/#sec-2)).

## 4. Why the node, and not the game's own saves

The game already has save points, and a player who quits and continues returns to the last one. Why not use those as SL's boundary? Here is where the game autosaves <Badge text="verified" variant="success" />:

- on arriving at a map point, before the `?` roll and before `CreateRoom` (`Runs/RunManager.cs:899-901`, 915, 917). This includes the run's first point: a single-player run has no separate start save, and `EnterAct` enters Neow's point with a save (`Runs/RunManager.cs:1356-1362`, 843); an act that opens without an Ancient starts on a map room, without one (1365-1368);
- on winning a combat, with the room marked as pre-finished (`Combat/CombatManager.cs:1341-1342`);
- when an **Ancient** event finishes, and only for Ancient events (`Rooms/EventRoom.cs:129-141`).

There is no save in the middle of a combat. Reloading replays the room exactly (the same encounter, the same opening hand, the same monster moves), because a save stores the full state `{counter, s0..s3}` (`Saves/SerializableRng.cs:8-21`) of each of the run's twelve random streams and the player's three (`Saves.Runs/SerializableRunRngSet.cs:14-15`, `Saves/SerializablePlayerRngSet.cs:14-15`); an event's own `Rng` and the act maps' are derived from the seed again when needed (`Models/EventModel.cs:234`, `Map/StandardActMap.cs:113`).

So the game's own save & load is a little narrower than a node. After a combat is won, the save has already moved past the combat, so a player cannot test in the real game whether a different line of play would have changed the rewards. The node boundary was chosen anyway, for two reasons: it covers everything that happens at one map point (all its rooms, its rewards, every page of its event), and it gives a single point, the travel, at which to seal the world. Whether the post-combat rewards should follow the game's narrower rule is open question 1 ([§9](#sec-9)).

## 5. The information table

What each environment may use, one row per kind of information. "This node" is the current node; "later nodes" are all the nodes after it.

| information | NoSL | SL |
|---|---|---|
| the screen's history and inferences from it; rule knowledge; anything learned offline (hidden state only as training-time privileged information) | yes | yes |
| this node: draw order and shuffles | which cards (a multiset) only | yes |
| this node: the monsters' next moves | the intents shown, and a posterior from their history | yes |
| this node: generated cards, random targets, costs, orbs | their distribution | yes |
| this node: event outcomes, the chest, rewards | once shown | yes |
| later nodes | no | no |
| the seed string, the RNG state or the save file, read directly | no | no (only through the sealed clone) |
| state edits, the console, debug or multiplayer backdoors | no | no |
| real reloads (`NumReloads > 0`), picking seeds at evaluation | no | no |

Reading the rows:

- **Privileged information** is hidden state used only while training, to make learning targets less noisy; it is never an input of the deployed model ([Learning §4](/en/arch/learning/#sec-4)).
- **A multiset** is a set that counts repeats: "three Strikes, two Defends and one Neutralize", in no order. The observation sends the draw pile sorted by a card key that depends only on what the player sees, so its order carries nothing ([Protocol: observations and actions §4](/en/arch/protocol/observation/#sec-4)).
- **A posterior** is a probability distribution updated by what has been seen. Today NoSL's worlds draw a monster's move uniformly among the moves that show the same intent, and take the order of its earlier moves from the record of its intents ([Simulator: combats §5](/en/arch/simulator/combat/#sec-5)); a full posterior is planned ([Harness §4](/en/arch/harness/#sec-4)).
- **The seed string** never leaves the host: runs are named by a hash of it ([Protocol: the wire §3](/en/arch/protocol/wire/#sec-3)), and the observation has no field for it.
- **Picking seeds** means choosing which seeds to report after seeing results; evaluation's seed sets are fixed and registered before use ([Evaluation §4](/en/arch/evaluation/#sec-4)).

## 6. Grey zones

Rulings for cases the table does not settle, the same in both environments. They come from the fair-play spec, a local note (`tmp/notes/fair-play-spec.md`) that the observation whitelist ([Protocol](/en/arch/protocol/)) implements:

- exact damage math is allowed: the game shows the numbers, and computing with them is what a careful player does;
- powers only if the game shows them (`IsVisible`), with the amount on the icon; the power's own stacks only where its tooltip states them apart from the icon, and the card a power keeps, which its tooltip names (`GameBridge/Observe.cs:180-182`);
- no monster move id is exported (`move_id`): the intent is what the player sees;
- the draw pile only as a multiset, never its order;
- the hidden cells of the Crystal Sphere event (`CRYSTAL_SPHERE`, a minigame) are exported only as hidden (`#`); only uncovered cells show what is under them (`GameBridge/Actions/CrystalSphereActions.cs:24-25`).

## 7. Where the SL clone comes from

An SL search needs the node as it was at arrival, plus everything done in it since. Both come from the **host**: whatever holds the true run, the simulator in self-play or the mod in the real game.

- **In the simulator** (rungs R1–R3 of the [sim-to-real ladder](/en/arch/evaluation/#sec-1), where the simulator plays the run): the worker hosting the run holds the true state. When the game saves on arrival at a map point, it takes a **checkpoint**: the save that `RunManager.ToSave(null)` produces (`Runs/RunManager.cs:670-709`) <Badge text="verified" variant="success" />, which the headless host keeps instead of writing, plus the plain fields of each relic that the save drops (below). The clone is that checkpoint plus the node's trace (every decision since arrival), loaded the way the game's Continue button loads a save and then replayed ([Simulator: worlds and the SL clone §4](/en/arch/simulator/worlds/#sec-4)).
- **In the real game** (R4): the mod takes the same checkpoint in memory, at the same moment, with the same GameBridge code (`Checkpoint.Take`). It never touches `current_run.save`, which Steam syncs to the cloud. It also records every action of the node where the game commits it, and sends both to the brain before each decision ([Mod: the SL record](/en/arch/mod/sl-record/)). A worker loads them through the same Continue path and replays the actions.
- **On the wire** they travel as two SL-only messages: `node_checkpoint` at the node's entry and `node_action` for each decision in it ([Protocol: the wire §6](/en/arch/protocol/wire/#sec-6)). Harness keeps the latest checkpoint and the decisions since, and hands them to the brains as the clone ([Harness §4](/en/arch/harness/#sec-4)).

**A loaded save is not the same as uninterrupted play.** Loading a save re-runs the map's hooks (`Runs/RunManager.cs:815-816`) and `OnRunLoaded` (562-565), and drops every relic field that is not marked as saved: a relic saves only its `[SavedProperty]` members (`Models/RelicModel.cs:556-576`). The relic fields mattered: a relic's status or counter that the save dropped changed every observation of the clone, the clone then no longer matched the real combat, and the SL planner planned again at every step ([Simulator: worlds and the SL clone §6](/en/arch/simulator/worlds/#sec-6)). So the checkpoint carries each relic's plain fields (numbers, flags and enums) and puts them back after loading, and `run --check` now finds no node whose clone differs from its run. There is no checksum and no fallback: a game quirk that breaks our correctness is fixed where it enters our code ([Introduction §2](/en/#sec-2), rule 7).

**NoSL closes this channel.** Both hosts take the checkpoint and keep the node's steps in both environments (`Simulation/RunSession.cs:143-148`; in the mod `NodeRecord`), so that switching to SL in the middle of a room works; only an SL run sends them (`Brains/RunBrains.cs:48-100`, the mod's `Assist.cs:159`). A NoSL brain refuses them: Harness throws on a node message in NoSL, the brain server answers the run's next decision with an error, and the host ends the run as failed, which voids its report ([Overview §5](/en/arch/environments/#sec-5)).

**The decision process never reads saves.** Brain has no reference to the game's assembly, which the compiler enforces and a test checks ([§8](#sec-8)). A save reaches a worker only inside an SL request, as an opaque string.

## 8. Guards

Each rule above has, or will have, a test that keeps it true. "Exists" names where it runs today.

**Both environments**

1. Brain and Protocol reference no game assembly. Exists: `selftest` (with GameBridge as the negative control) and the xUnit `BoundaryTests`, which also covers Harness ([Simulator: reference §5](/en/arch/simulator/reference/#sec-5)).
2. Search randomness comes from the caller only, never from the game's random streams. Holds by construction, with no test: a brain's seed is mixed from the run id (itself a hash of the seed string) and the decision's index (`Harness/Dispatcher.cs:208-227`), and a world's build and sample seeds come from it ([Harness: routing, budgets and seeds §5](/en/arch/harness/routing/#sec-5)).
3. The number of fallback decisions is 0. Exists in effect: there is no fallback code, Harness throws on an uncovered surface (xUnit `DispatcherTests`), and a decision made by a random placeholder voids a report (`Harness/Reports.cs:35-38`, xUnit `EvalReportTests`; [Evaluation §3](/en/arch/evaluation/#sec-3)).
4. `NumReloads == 0` in the real game. Planned, as a field of the mod's decision log ([Mod: auto-play and safety §3](/en/arch/mod/auto/#sec-3)); nothing reads it today. Clones load a save, so their count is 1 or more, wherever they are loaded (workers, and the host process in `run --check`, `selftest` and `clones`).
5. Every observation field has a whitelist test. Planned; the closest checks today are the JSON round trips of every observation in `run --check` and `selftest` ([Protocol §3](/en/arch/protocol/#sec-3)).

**NoSL**

6. Counterfactual: the same public record with a different hidden state (draw order, every stream, monster moves and their private AI fields, generated pools) gives the same decision under a fixed brain seed. Planned; the closest check is `selftest`'s "determinize keeps the observation".
7. Round trip: state → observation → build → observation′ gives an identical observation. Exists for combat: `selftest` builds combats from observations and requires them to show the observation again ([Simulator: combats §6](/en/arch/simulator/combat/#sec-6)), and every NoSL world refuses a build that does not (`Simulation/SimWorlds.cs:34-44`, in workers too).

**SL**

8. Seal: any step after the exit action throws. Exists: `selftest` loads a clone whose travel is recorded and requires it to stop at its horizon and refuse another step (`Checks/SelfTest.Run.cs:55-85`); `run --check` does the same for every node of a run; at run time the probes and the SL world throw (`NodeProbe.cs:29`, `NodeWorld.cs:96`). The SL world of a combat also refuses to step past the combat's end, so search never leaves the room (`selftest`).
9. Horizon counterfactual: perturbing only state that is read after the exit gives the same decision. Planned.
   - Can be perturbed <Badge text="verified" variant="success" />: the `RoomSet` entries past their counters for every act (events, weak, regular and elite encounters, the boss, the second boss, the Ancient; drawn at run start up front by `GenerateRooms`, `Runs/RunManager.cs:743-767`, and consumed through counters, `Rooms/RoomSet.cs:70-108`); the UnknownMapPoint stream (used only when entering a `?`: `Odds/UnknownMapPointOdds.cs:123-177`, called from `Runs/RunManager.cs:985`); the TreasureRoomRelics stream (used only at `Runs/RunManager.cs:486`) and the tail of the shared relic grab bag; the map seeds of future acts (`Rng(seed, "act_N_map")`, `Map/StandardActMap.cs:113`).
   - Cannot be perturbed, because the current node shares them: the Shuffle, MonsterAi and Niche streams, the six Combat* streams, and the player's Rewards, Shops and Transformations streams.
   - Each perturbable field needs a test showing that the current node never reads it.
10. Clone queries are logged per decision. Planned. Today `brain --wire FILE` logs the host's node messages, from which `clones` rebuilds and checks each SL decision's clone ([Mod: the SL record §8](/en/arch/mod/sl-record/#sec-8)); L0's probes on the clone are not logged.

Tests of the environment's own plumbing, besides the guards: Harness refuses node checkpoints in NoSL and hands NoSL no clone (xUnit `DispatcherTests`); a combat net plays only in its environment and an old net in either (`CombatNetTests`); the gate refuses a challenger from another environment (`GateTests`); `--env` defaults to NoSL and reads any case, and `brain` ignores a champion file's environment (`CliTests`); `selftest` checks that the clone keeps the relic state the save drops (`Checks/SelfTest.Run.cs:140-180`).

## 9. Open questions

1. **Rewards after a combat win:** the node rule (today) or the game's narrower save rule ([§4](#sec-4))? Once full runs are common, measure how often rewards depend on how the combat used the random streams. The Rewards stream is shared with shops and events <Badge text="verified" variant="success" />, so inside a combat node this is probably rare.
2. **SL's budget:** give SL the same wall-clock time as NoSL, which is fairer than the same number of branches.
3. **Real reloads to verify clones:** allowed only in tagged validation runs, never scored.
