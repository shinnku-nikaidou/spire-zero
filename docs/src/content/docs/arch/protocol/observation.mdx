观测是大脑在一个决策处得知的关于游戏的一切，所以它也是大脑所能知道的极限。本页逐字段列出它，连同回答每种画面的动作。这些类型在 `src/Sts2Ai.Protocol` 里（`Observation.cs`、`CombatObservation.cs`、`Screens.cs`、`CardChoice.cs`、`CombatAction.cs`）；GameBridge 根据游戏填写它们（[GameBridge](/arch/gamebridge/)）。

## 1. 每个决策一个观测

```text
Observation{run: RunView, screen: ScreenView}
```

`Observation` 有两部分。`run` 是玩家所处的这一局，在每个画面上都一样：顶栏、牌组视图和地图（[§2](#sec-2)）。`screen` 是正在提问的画面，是十一个变体之一，每个**决策界面**（surface）一个；决策界面就是决策画面的种类。在 JSON 里，画面在一个 `"surface"` 字段里说明自己是哪个变体，读取方由此知道后面跟着哪些字段：

```json
{"run": {"character": "SILENT", "act": 0, "floor": 2, …}, "screen": {"surface": "card_reward", "cards": […], "alternatives": […]}}
```

决策界面的名字是 `Surfaces.cs` 里的常量：`combat`、`card_choice`、`map`、`rewards`、`card_reward`、`bundle`、`event`、`shop`、`rest`、`treasure`、`crystal_sphere`。决策界面也是 Harness 路由一个决策时用的键（[Harness：路由、预算与种子 §1](/arch/harness/routing/#sec-1)）。一局的结束不是决策界面，而是线路消息 `run_end`（[线路 §3](/arch/protocol/wire/#sec-3)）。

观测是惰性构建的。在大脑内部，一个决策带着一个构建其观测的函数，从不读取观测的大脑也就从不为它付出代价（`CombatDecision`、`MacroDecision`、`ChoiceDecision`，在 `Sts2Ai.Brain/Decisions.cs` 里）。在线路上它总是会被构建，因为大脑在别处。

## 2. 这一局

| 字段 | 类型 | 是什么 |
|---|---|---|
| `character`、`ascension` | string、int | 角色的 id、进阶等级 |
| `act` | int | 幕，从 0 开始计数 |
| `act_id` | string | 这一局掷出的是该幕的哪个变体（`OVERGROWTH`、`HIVE`、`GLORY`、…） |
| `floor` | int | 按整局计数的层数，与顶栏显示的一致 |
| `hp`、`max_hp`、`gold` | int | 顶栏 |
| `deck` | `CardView[]` | 牌组，按卡牌键排序（[§4](#sec-4)）；每张可升级的牌还带着它的预览 `upgraded` |
| `relics` | `RelicView[]` | 遗物，按玩家持有它们的顺序 |
| `potions` | `(string\|null)[]` | 每个药水槽位一项：药水的 id，空槽位为 null |
| `map` | `MapView` | 当前这一幕的地图 |

`MapView` 就是地图画面画出来的那张地图：

| 字段 | 是什么 |
|---|---|
| `points` | 每个点，先按行再按列排序：第 0 行是起点，然后是各行，再往后是位于最后一行上方的 Boss（和第二个 Boss） |
| `visited` | 本幕走过的点，按顺序；最后一个是玩家所在的位置 |
| `boss`、`second_boss`? | 画在 Boss 点上的 Boss 遭遇 |
| `ancient`? | 本幕的先古之民，画在起点上 |

每个点是一个 `MapPointView`：`col`、`row`；`type`，即地图图标（`Monster`、`Elite`、`Unknown`、`Shop`、`Treasure`、`RestSite`、`Boss`、`Ancient`）；`next`，它的路径通向的点，排好序；以及 `quest`，在有任务标记这个点时设置（奖励到达该点的遗物或卡牌）。`?` 走过之后仍是 `Unknown`，与地图显示的一致；没走过的 `?` 里有什么，从不出现。

## 3. 一场战斗

`CombatObservation` 是玩家在一场战斗里看到的东西。它是 `combat` 画面的载荷，也随战斗中弹出的选牌提示一起出现。

| 字段 | 是什么 |
|---|---|
| `encounter`、`room` | 遭遇的 id；它的房间类型，与地图上显示的一致（`Monster`、`Elite`、`Boss`） |
| `act`、`ascension`、`round` | 幕（从 0 开始）、进阶等级、战斗的回合数（从 1 开始） |
| `player` | `PlayerView`：`uid`、`character`、`hp`、`max_hp`、`block`、`energy`、`max_energy`、`stars`、`gold`、`powers`、`orb_slots`、`orbs` |
| `hand` | 手牌，按手牌顺序，每张带着它的 `uid` |
| `draw` | 抽牌堆，按卡牌键排序：玩家知道里面有什么，不知道它的顺序 |
| `discard`、`exhaust` | 弃牌堆和消耗堆，按牌堆顺序 |
| `potions` | 每个槽位一项，与这一局里一样 |
| `relics` | `RelicView`：`id`，以及它的图标和提示框显示的东西：`counter`、`status`（不是正常状态时）、`melted`、`used_up`、`cards`（它保存的牌，例如佩尔之牙的）、`spent`（一场一次或一回合一次的效果已用掉，而它的状态没有说：百年积木的，或君王矿石本回合的） |
| `allies` | 玩家这一方除玩家以外的生物：其他玩家、召唤物 |
| `enemies` | `CreatureView`：`uid`、`id`（怪物的）、`hp`、`max_hp`、`block`、`powers`，以及 `intents`：倒下、等着复活的敌人留在列表里，HP 是 0，复活也是一个招式 |

嵌套的视图：

| 类型 | 字段 | 说明 |
|---|---|---|
| `CardView` | `id`、`uid`?、`up`?、`cost`? 或 `x_cost`?、`stars`?、`enchant`?、`affliction`?、`tinker`?、`keywords`?、`this_turn`?、`vars`?、`upgraded`?、`lasting`?、`stars_lasting`?、`replay`?、`spent`?、`calc`? | `cost` 是计入所有修正之后的能量费用；`stars` 是星辰费用，只有有星辰费用的牌才有；`enchant` 和 `affliction` 是 `{id, amount}`；`tinker` 是 Tinker Time 事件把一张疯狂科学做成了什么，即它的类型和附加效果，牌框显示这两项，id 却不显示；`keywords` 排好序；`this_turn` 是某个效果只在本回合给它的关键词，回合结束时会被拿走（独门技术给的保留、手上技法给的 Sly）；`vars` 是卡牌自己的数值，按名字给出（[§7](#sec-7)）；`upgraded` 是这张牌再升一级之后的样子，与游戏的升级预览显示的一致，只有可升级的牌组卡牌才有 |
| `PowerView` | `id`、`amount`、`stacks`?、`card`?、`detail`?、`stolen`? | `amount` 是图标上的数字；`stacks` 是能力自己的数量，在图标显示另一个数字时才有（懒惰的图标数的是本回合的牌数，它的层数才是上限）；`card` 是能力保存的牌，与它的提示框里写出的一致（夜魇的）；`detail` 是提示框上写的数字离开能力原本的数值多远，在它离开时才有（坚韧之环的格挡、炸弹的伤害）；`stolen` 是它拿走的牌（顺走的） |
| `IntentView` | `type`、`damage`?、`hits`? | 敌人头上的一个意图图标：它的类型，攻击还带着对玩家的每段伤害和段数 |
| `OrbView` | `id`、`passive`、`evoke` | 一个充能球和它显示的数字 |

**Uid**。动作指名一张牌或一个生物的方式，必须在手牌变化时依然成立，并且在模拟器和游戏里含义相同。uid 是游戏自己在每场战斗内的 id，也就是它的多人联机消息所用的那些：手牌在战斗的卡牌数据库（`NetCombatCardDb`）里的 id，生物的 `CombatId`。只有玩家能指向的东西才有 uid：手里的牌和各个生物。牌堆里的牌没有，因为游戏在开局洗牌之后立刻给牌编号，所以一张牌的编号就是它在洗好的抽牌堆里的位置。

**战斗动作**（`CombatAction.cs`）有一种文本形式，这也就是它们的 JSON：

| 动作 | 含义 |
|---|---|
| `play:C` 或 `play:C:T` | 打出 uid 为 C 的手牌；如果它需要目标，就以 uid 为 T 的生物为目标 |
| `potion:S` 或 `potion:S:T` | 使用槽位 S 的药水；如果需要目标，就以 T 为目标 |
| `end_turn` | 结束回合 |

搜索的路线可以在动作后面带上提示的回答（`potion:0@3`，第一个提示选下标 3 的选项；[回合搜索 §5](/arch/sl-planner/turn-search/#sec-5)）。这只出现在搜索和日志里，宿主收到的动作不带它。

战斗里没有丢弃药水：协议的战斗动作只有这三种。

## 4. 身份与顺序

**卡牌的键**是它的 `CardView` 去掉 uid 之后的序列化结果（`ProtocolJson.CardKey`）。它包含玩家看到的这张牌的一切，所以键相同的两张牌，在玩家看来就是同一张牌。键给出两条保证：

- **同样的状态，同样的观测**。牌组按键排序，所以以另一种顺序拿牌得到的牌组看起来是一样的；抽牌堆按键排序，因为它的真实顺序是隐藏的。
- **不会泄露的顺序**。游戏自己给列表的顺序可能取决于隐藏状态：针对抽牌堆的提示按牌堆顺序列出卡牌，而玩家并不知道这个顺序。因此选牌提示的选项按**规范顺序**发出：按键排序，看起来一模一样的牌之间的平局，用一条对隐藏的东西一无所知的随机数流来打破（`CardChoices.Canonical`，`Sts2Ai.GameBridge/CardChoices.cs:16-25`）。模拟器用进入节点以来这个提示的序号给它播种，Mod 用 0。针对牌组的选牌提示显示牌组视图（带 `upgraded`），其他所有提示显示普通的卡牌视图。

**两套下标**。线路上的回答按规范下标选择（`pick:0,2`）。宿主把它换算成游戏自己的下标，这一局的轨迹和 SL 节点消息记录的就是这个（`card_choice 4,1`），因为重播要经过游戏的选牌器，而选牌器不知道什么规范顺序（[线路 §6](/arch/protocol/wire/#sec-6)）。

**按 UI 顺序的列表**。顺序由画面显示、又不隐藏任何东西的列表，按这个顺序发送，动作用下标指向其中的项：奖励、事件选项、商店槽位、宝箱里的遗物、卡牌奖励里的牌。

## 5. 画面及其动作

各个画面变体（`Screens.cs`），以及每个决策界面接受的动作。线路上的合法动作列表装的就是这些字符串；哪些动作合法的规则见 [模拟器：整局 §4](/arch/simulator/runs/#sec-4)。

| 决策界面 | 画面字段 | 动作 |
|---|---|---|
| `combat` | `combat`：`CombatObservation` | `play:C[:T]`、`potion:S[:T]`、`end_turn` |
| `card_choice` | `choice`：`CardChoice`（[§6](#sec-6)）；战斗进行中时还有 `combat` | `pick:i,j,…`，按规范下标；合法动作列表为空；只有 `min` 为 0 时才能一张都不选 |
| `map` | `travelable`：玩家可以前往的坐标，按合法动作的顺序（地图本身在 `run.map` 里） | `map:COL,ROW` |
| `rewards` | `rewards`：还没领取的按钮，`{index, kind, id?, amount?, card?, cards?}`，`kind` 是 `gold`、`potion`、`relic`、`card`、`special_card`、`remove_card` 之一 | `reward:i`、`rewards_done` |
| `card_reward` | `cards`；`alternatives`，其他按钮的 id（跳过、重抽、遗物添加的按钮） | `card:i`、`card_alt:ID` |
| `bundle` | `bundles`：一组组卡牌 | `bundle:i` |
| `event` | `id`；`page`，页面文本的本地化键；`options` `{index, key, locked?, relic?, tips?, kills?}`，事件结束后为空；`finished` | `event:i`、`proceed` |
| `shop` | `entries` `{slot, kind, card? or id?, cost, on_sale?}`，仍在出售的商品，`kind` 是 `card`、`relic`、`potion` 之一；`removal_cost`，移除服务用过之后就不再出现 | `buy:SLOT`、`remove`、`leave` |
| `rest` | `options` `{id, enabled, heal?}`；`heal` 只在 HEAL 选项上，是它的文字显示的回复生命值（遗物会改变它） | `rest:ID`、`leave` |
| `treasure` | `relics`：宝箱里的遗物，按 id | `relic:i`、`relic_skip` |
| `crystal_sphere` | `rows`，一个 11×11 网格，`rows[y][x]` 是 `#`（隐藏）、`.`（已揭开且为空），或已揭开格子所显示内容的一部分（`R` 遗物、`P` 药水、`C` 卡牌奖励、`G` 金币、`X` 诅咒）；`divinations_left` | `big:X,Y`（3×3 的块）、`small:X,Y`（一格） |

字段说明：

- **卡牌奖励里的牌**随奖励画面的 `card` 按钮一起给出（`cards`）：游戏在画面出现之前就掷好了它们，打开奖励看一眼也没有任何代价，所以玩家在打开之前就知道它们。
- **事件选项**以它的文本键命名，即在所属事件内为这个选项命名的本地化键。`relic` 是先古之民的选项给出的遗物；`tips` 是它的悬停提示显示的卡牌、遗物和药水的 id（`+` 表示升级过的牌）；`kills` 表示按钮警告它会杀死玩家；`locked` 是玩家不能选的选项。
- **商店槽位**按游戏保存商品的顺序给商品编号（角色卡牌、无色卡牌、遗物、药水），售罄的也算在内，所以购买之后槽位的编号不变；移除卡牌是单独的动作。
- **休息选项**按 id 命名（`rest:HEAL`、`rest:SMITH`），而不是按位置。

**药水栏**。在 `map`、`rewards`、`event`、`shop`、`rest`、`treasure` 和 `crystal_sphere` 上，合法动作还包括药水栏：可以随时使用的药水用 `potion:S`，以及 `discard_potion:S`。卡牌奖励、卡包和选牌提示没有这些动作。

**在大脑内部**，宏观决策界面以 `MacroDecision{surface, legal, observation}` 交给策略，选牌提示以 `ChoiceDecision{choice, observation}`，战斗决策以 `CombatDecision{legal, observation}`。在一局之外单独打的战斗（测试集）没有对局，所以它的决策和提示只带着战斗。

## 6. 选牌提示

**选牌提示**是游戏要求从一个列表里选牌：弃 1 张、消耗至多 2 张、3 选 1、在休息处升级一张牌、在商店移除一张。游戏从某个动作内部，通过它的某个 `CardSelectCmd.From*` 入口弹出它，所以它随时可能出现，战斗中和战斗外都有。

```text
CardChoice{options: CardView[] (canonical order), min, max, context: ChoiceContext}
```

回答是 `min` 到 `max` 个互不相同的、指向 `options` 的下标（`CardChoice.Accepts`）。可以取消或跳过的提示，`min` 为 0，空回答就是取消。

只看选项，说不出提示是做什么用的：同样的五张牌，用于升级、移除还是弃牌，意义各不相同。`ChoiceContext` 带着这个信息，GameBridge 根据游戏所用的入口填写它（[GameBridge：读取游戏 §6](/arch/gamebridge/observe/#sec-6)）：

| 字段 | 是什么 |
|---|---|
| `purpose` | 提示的种类：入口的名字去掉 `From`，转成 snake_case（`deck_for_upgrade`、`deck_for_transformation`、`deck_for_enchantment`、`deck_for_removal`、`deck_generic`、`hand`、`hand_for_discard`、`hand_for_upgrade`、`choose_a_card_screen`、`simple_grid`、`simple_grid_for_rewards`）；针对战斗牌堆的提示则是牌堆的名字，`draw_pile` 或 `discard_pile`（在这个游戏版本里，只会从这两个牌堆提问） |
| `source`? | 发起询问的卡牌、遗物、能力或事件的 id，在游戏指明时给出：入口的 `source` 参数，否则是这次选择最近涉及的模型 |
| `cancelable` | 取消或跳过按钮会关闭提示：提示自己的设置，或选卡画面的 `canSkip` |
| `in_combat` | 在战斗中提问（某张牌或某个能力正在结算），而不是在休息处、事件或商店里；Harness 按它路由提示：战斗中交给 `p0`，战斗外交给宏观大脑（[Harness：路由、预算与种子 §1](/arch/harness/routing/#sec-1)） |
| `prompt_key`? | 提示文本的本地化键，`table.key` |
| `enchantment`? | 用于 `deck_for_enchantment`：被选中的牌获得的附魔，`{id, amount}` |

上下限的两个细节（`ChoiceContexts.Bounds`）：`max` 从不超过现有选项的个数；没有跳过按钮的选卡画面向它的选择器要 0 或 1 张牌，然后自己坚持要一张，所以它的 `min` 是 1。一个入口调用另一个入口时（移除要经过通用的牌组提示），由最外层的入口给出用途。卡包（卷轴箱提供的卡包选择）不是选牌提示：它们有自己的决策界面。

## 7. 文本、数值与排除在外的东西

- **文本以本地化键发送**（`table.key`），从不发送解析好的字符串：事件页面、按文本键给出的事件选项、提示文本。想要文字的大脑自己去查。
- **卡牌的 `vars`** 是它自己的数值，伤害、格挡、魔法数字，按名字给出：基础数值，而不是打出时力量或敏捷把它们变成的数值。卡牌根据状态计算出的数值（完美打击的伤害）不包括在内；卡牌把它显示为一个基础值加上每个计数的额外值，这两部分都列出了。
- **事件的数值**暂不包括：有些事件在它们的数值里存着页面不显示的值，所以要先有一份按事件划分的白名单。
- **从不包括**：种子和随机数流、`?` 在进入之前里面有什么、怪物排定了哪个招式、重抽或变化会给出什么、抽牌堆的顺序（[协议 §3](/arch/protocol/#sec-3)）。

## 8. 规划中：事件流 <Badge text="规划中" variant="caution" />

观测是一张快照。玩家还记得发生过什么：抽到并移动了哪些牌、怪物显示过哪些意图、商店提供过什么。要从这段历史推理隐藏状态（即信念），大脑也需要这些事件。计划是让每条 `decision` 消息带上自上一条以来的事件，事件集合保持最小，只在某个信念需要时才扩充：

```text
draw{card}  play{card_uid, target?}  move{card, from, to, pos: top|bottom|random|null}
generate{card, to}  shuffle{}  intents{creature, intents[]}  move_done{creature, effects…}
reward_seen{…}  shop_seen{…}  event_page{…}
```

`move` 是一张牌在牌堆之间移动，`move_done` 是一个生物完成的招式及其效果；最后一行记录奖励画面、商店或事件页面显示了什么。GameBridge 会从游戏的钩子生成它们（[GameBridge §5](/arch/gamebridge/#sec-5)）。如今大脑保存的唯一一段历史，是每回合的敌人意图记录，由 Harness 从观测本身建立（[世界与工作进程消息 §2](/arch/protocol/worlds/#sec-2)）。
