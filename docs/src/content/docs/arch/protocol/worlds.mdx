搜索需要在游戏的副本里试动作，而大脑不能碰游戏。Protocol 给搜索提供一个通向这些副本的接口，即**世界 API**；又给大脑提供一种办法，把整次搜索发给持有这些副本的进程，即**工作进程消息**。两者都在这里定义（`World.cs`、`CombatRecord.cs`、`Worker.cs`）；模拟器实现它们（[模拟器：世界与 SL 克隆](/arch/simulator/worlds/)、[模拟器：工作进程池](/arch/simulator/pool/)）。

## 1. 世界 API

```csharp
public enum PlayEnvironment { NoSL, SL }
public enum CombatStatus { InProgress, Won, Lost }

public interface IWorldSource                     // the worlds of one decision
{
    PlayEnvironment Environment { get; }
    IReadOnlyList<ICombatWorld> Worlds(int k, ulong searchSeed);   // NoSL: k samples; SL: the one exact copy
}

public interface ICombatWorld                     // one simulated combat
{
    CombatObservation Observe();
    RunView Run();                                // the run around the combat, as it stands in this world
    IReadOnlyList<CombatAction> Legal();          // empty once the combat is over
    CombatStatus Status { get; }
    ulong HiddenKey();
    void Execute(CombatAction action);            // card prompts are answered inside the world
    PromptSeen? LastPrompt => null;               // the first prompt the last action raised, and its answer
    WorldSnapshot Snapshot();
    void Restore(WorldSnapshot snapshot);         // a snapshot taken from this same world
}

public sealed record WorldSnapshot(IReadOnlyList<string> Steps);
public sealed record PromptSeen(IReadOnlyList<IReadOnlyList<int>> Groups, int Min, int Max, string Answer);
```

| 成员 | 做什么 |
|---|---|
| `Worlds(k, searchSeed)` | 一个决策的各个世界：NoSL 下是 k 个与观测相符的隐藏状态样本，由搜索种子抽出；SL 下是真实战斗唯一的那份精确副本 |
| `Observe()` | 世界里的战斗在玩家眼中的样子：一个 `CombatObservation`（[观测与动作 §3](/arch/protocol/observation/#sec-3)） |
| `Run()` | 这场战斗所在的这一局在这个世界里的现状，按 V 读它的方式：SL 下是实时游戏的这一局，带着战斗已经永久改变的东西；NoSL 下是请求带来的这一局，换上构建出的战斗里的遗物、药水、生命值、最大生命值和金币。叶子在它上面给战斗的结局定价（[战斗大脑：叶子 §2](/arch/combat-brain/leaf/#sec-2)） |
| `Legal()` | 合法的战斗动作；战斗结束后为空 |
| `Status` | 进行中、赢或输 |
| `HiddenKey()` | 观测所隐藏的、会改变同样的打法从这里往后如何展开的那些东西的哈希：抽牌堆的顺序、每条随机数流的位置、每个怪物排定的招式。它和观测一起，在这个世界之内区分两个状态 |
| `Execute(action)` | 打出一个合法动作；它弹出的选牌提示在世界内部回答：第一个用动作带着的回答（如果有），其余每个都取它的前几个选项，和这一局回答它们的方式一样（[战斗大脑：提示、招式与 worker §1](/arch/combat-brain/shared/#sec-1)） |
| `LastPrompt` | 上一个动作弹出的第一个选牌提示（如果有）：它的选项按玩家能分辨的东西分组，它最少和最多的选择数，以及它得到的回答。搜索会尝试这个提示的其他回答（`PromptSeen.Others`） |
| `Snapshot()`、`Restore(s)` | 世界里的一个时间点，以及回到它的办法 |

**快照是一份配方**：世界从开始以来走过的步骤（确定化步骤、动作、提示的回答），以文本形式保存。搜索把它当作不透明的东西；只有生成它的那个世界会读它，并通过重播这些步骤来还原它（[模拟器：战斗 §2](/arch/simulator/combat/#sec-2)）。因为是文本，它可以传到另一个进程去。

**两种隐藏键**。一个键包含多少东西取决于环境。NoSL 世界的键（`HiddenState.Key`）是抽牌堆的顺序、这一局和玩家的随机数流的计数器，以及每个怪物的随机数流和下一个招式。SL 世界的键（`HiddenState.Full`）还加上每个怪物至今的招式和这场战斗本回合的历史，这样，看起来一样、之后的发展却不同的两个状态就永远不会被合并（[模拟器：战斗 §4](/arch/simulator/combat/#sec-4)）。

世界 API 只覆盖战斗：战斗大脑是它唯一的使用者。宏观大脑在 SL 下的搜索改为在节点的克隆上打，通过 [§4](#sec-4) 的工作进程消息。整局的世界还在规划中（[模拟器：世界与 SL 克隆 §8](/arch/simulator/worlds/#sec-8)）。

## 2. 节点克隆与敌人出招记录

```csharp
public sealed record NodeClone(string Save, IReadOnlyList<string> Trace);
public sealed record EnemyTurns(uint Uid, string? Id, IReadOnlyList<EnemyTurn> Turns);
public sealed record EnemyTurn(int Round, IReadOnlyList<IntentView> Intents);
```

**`NodeClone`** 是当前节点的 SL 克隆：节点的检查点（`Save`，到达时游戏的存档，加上存档丢掉的遗物字段），以及此后节点的每个决策，以轨迹行的形式（`surface action`，选牌提示的选择用游戏自己的下标）。在模拟器之外它是不透明的；模拟器像游戏的「继续游戏」（Continue）那样加载存档，把遗物字段放回去，再重播这些决策（[模拟器：世界与 SL 克隆 §4](/arch/simulator/worlds/#sec-4)）。Harness 根据线路上的节点消息做出克隆（[线路 §6](/arch/protocol/wire/#sec-6)）。

**`EnemyTurns`** 是当前战斗里一个敌人招式的公开记录：到目前为止的每个回合，从最早的开始，它的图标在该回合第一个决策处显示的意图。看着这场战斗的玩家全都看到过。Harness 按每场战斗从观测中保存它（`MoveRecord`），并在每个决策时把它交给战斗大脑；搜索根据它建立怪物的出招日志（[模拟器：战斗 §5](/arch/simulator/combat/#sec-5)），学出来的叶子也读取它（[战斗大脑：叶子 §3](/arch/combat-brain/leaf/#sec-3)）。

## 3. 打过分的动作

```csharp
public sealed record Candidate(string Action, double Value, double Ci, int Samples,
    IReadOnlyList<double>? Values = null, double? Win = null, double? Hp = null,
    IReadOnlyList<string>? Plan = null);
```

一次搜索打过分的一个动作：它在各个世界上的平均值、95% 置信区间的半宽、世界的个数，以及在保留时，它在每个世界里的值（保留 4 位小数，按世界的顺序）。SL 规划器还加上它为这个动作找到的最佳路线如何结束：赢下这场战斗的概率和赢下时持有的生命值；在战斗外，值是 V 给出的这一局的胜率，在地图上 `plan` 带着这个选项的路线。推荐把它们列出时选中的在前（[线路 §7](/arch/protocol/wire/#sec-7)）；战斗网络的 ExIt 目标就是由各个世界的值做成的（[学习：循环 §5](/arch/learning/loop/#sec-5)）。

## 4. 工作进程消息

工作进程就是以 `serve` 启动的模拟器；大脑的工作进程池向它发送请求（[模拟器：工作进程池](/arch/simulator/pool/)）。在工作进程的 stdin 和 stdout 上，每条消息一行 JSON。与线路不同，这些消息没有 `v`：宿主和它的工作进程总是同一个构建。

**为什么用请求，而不是单步**。世界 API 是一步一步的对话，而一次搜索每个决策要走几千步。经管道走一步要花一次几十微秒的往返，和这一步本身差不多（约 0.1 ms）。所以一个请求要的是一整份工作，而世界 API 在工作进程内部、在进程内使用。

| 消息 | JSON `type` | 字段 | 要求做什么 |
|---|---|---|---|
| `WorkerHello` | （无） | `game` | 工作进程启动完毕后的第一行：它运行的游戏版本 |
| `PimcWorldRequest` | `pimc_world` | `id`、`observation`、`first`、`build_seed`、`search_seed`、`world`、`worlds`、`nodes_per_first`、`history`、`run` | PIMC 对一个 NoSL 世界的搜索：用 `build_seed` 从 `observation` 构建战斗，在由 `search_seed` 抽出的 `worlds` 个世界里取第 `world` 个，在 `first` 的每个动作之后搜索本回合，每个用 `nodes_per_first` 个节点；`run` 是这场战斗所在的这一局，供叶子定价用 |
| `SlTurnRequest` | `sl_turn` | `id`、`node`、`path`、`nodes`、`keep`、`history` | SL 规划器的一个回合：加载克隆，从决策处打出 `path`，到达束里的一个状态，再用 `nodes` 个节点搜索那个回合剩下的部分，在下一回合开始时最多保留 `keep` 个状态，外加最好的战斗结束状态 |
| `SlMacroRequest` | `sl_macro` | `id`、`node`、`paths` | 宏观大脑的试探：对每条答案路径，加载克隆，从决策处打出这条路径，记下游戏接下来问什么；一条路径是文本形式的宏观动作，对选牌提示来说是 `pick:` 加上按规范顺序给出的选择 |
| `WorkerReply` | （无） | `id`、`lines`?、`error`?、`game_errors`、`turn`?、`afters`? | 对请求 `id` 的回答：`pimc_world` 用 `lines`，`sl_turn` 用 `turn`，`sl_macro` 用 `afters`；请求失败时改为 `error`；`game_errors`，处理它期间记下的游戏错误行 |

`history` 是这场战斗的敌人出招记录（[§2](#sec-2)），供叶子使用；在 `sl_turn` 里，它记录到被搜索的那个状态为止。

## 5. 回答

```csharp
public sealed record PlannedLine(double Value, IReadOnlyList<CombatAction> Actions, int Nodes = 0,
    IReadOnlyList<ulong>? Hashes = null, bool Repeats = false);
public sealed record TurnSearch(IReadOnlyList<TurnEnd> Ends, int Nodes, bool Cut);
public sealed record TurnEnd(IReadOnlyList<CombatAction> Actions, IReadOnlyList<ulong> Hashes, CombatStatus Status,
    double Value, ulong Key, IReadOnlyList<EnemyTurns> History, double Win = 0, double Hp = 0);
public sealed record Afterstate(RunView Run, string? Surface, ScreenView? Screen, IReadOnlyList<string> Legal, bool? Won = null);
```

| 类型 | 所在位置 | 包含什么 |
|---|---|---|
| `PlannedLine` | `lines` | 搜索找到的一条打法，从它的首个动作开始：它的值、它的动作、首个动作之后模拟的节点数（包括首个动作本身），以及每个动作被打出时所在的战斗观测的哈希，被跟随的计划在每一步之前核对它；以及它是否重复搜索找到的一个循环。`lines[i]` 是 `first[i]` 之后最好的打法 |
| `TurnSearch` | `turn` | 一个回合的搜索得到的各个结束状态：`ends`，如果这个回合能到达战斗结束，先是最好的战斗结束状态，然后是下一回合开始时的各个状态，最好的在前；`nodes`，模拟的动作数；`cut`，是否有东西被略去（节点用完了，某个提示的回答比节点多，或者找到的状态比保留的多） |
| `TurnEnd` | `turn.ends` | 规划器的打法里一个回合结束处的状态：从决策处到达它的动作（最后一个结束回合），每个都带着它的提示回答，以及每个动作之前的观测哈希；它的战斗状态；叶子的值；它的键，由它的观测（各牌堆当作多重集，`PimcBrain.StateKey`）和完整隐藏状态算出，相等的状态按它合并（战斗结束后为 0）；它的敌人出招记录；以及与值来自同一次叶子调用的、从它出发赢下这场战斗的概率和赢下时持有的生命值（战斗结束后为 1 或 0 和持有的生命值） |
| `Afterstate` | `afters` | 一条路径通向什么：那时的这一局；游戏接下来问的决策界面，一局结束后为 null，这时由 `won` 说明它怎样结束（游戏记下胜利时也会杀死玩家，所以从这一局的生命值看不出来）；它的画面；它的合法动作。选牌提示的选项在它的画面里，所以它的合法动作列表为空；战斗的画面装着它的第一个观测，它的动作被略去，因为战斗会结束一次试探 |

`status` 写成数字（0 进行中，1 赢，2 输），哈希和键写成 JSON 数字（[协议 §4](/arch/protocol/#sec-4)）。

## 6. 什么能过去，什么不能

- **NoSL 请求装的是观测和敌人出招记录，从不是真实状态**。工作进程由它们构建自己的世界，所以工作进程不可能比玩家知道得多（[模拟器：工作进程池 §5](/arch/simulator/pool/#sec-5)）。
- **SL 请求装的是节点的克隆**，这是 SL 可以知道的。`TurnEnd` 的键是完整隐藏状态的哈希，它只留在 SL 的搜索里：叶子仍然只读观测。
- **每个请求都是自足的**。没有任何东西从一个请求延续到下一个，所以任何工作进程都能处理任何请求，崩溃的工作进程的请求可以重发。
- **游戏错误会传回来**。工作进程随每个回复返回游戏的错误行，宿主把它们和自己的一起计数（[模拟器：无头宿主 §8](/arch/simulator/headless/#sec-8)）。

规划中 <Badge text="规划中" variant="caution" />：在工作进程里打开一个世界、然后一步步推进它的请求，供一个请求装不下的搜索使用（[模拟器：工作进程池 §8](/arch/simulator/pool/#sec-8)）。
