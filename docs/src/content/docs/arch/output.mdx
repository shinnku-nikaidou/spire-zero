输出层把大脑的答案变成玩家能看到的东西，或者游戏里实际发生的动作。它运行在游戏进程里的 [Mod](/arch/mod/) 中。所有输出模式读的都是 Harness 发来的同一条 `Recommendation` 消息，大脑从不知道当前开着哪种模式。

<Aside title="状态">

先有了一个临时替代：Mod 的文字面板在每个决策界面上显示推荐的动作、本回合剩下的计划和得分最高的几个候选，名字和游戏里一致（[Mod §3](/arch/mod/#sec-3)）。第一个高亮也已经做好：在地图上，推荐的地图点上有一个圆圈，大脑在它之后规划的路线上有一条线，一直画到 Boss（[§3](#sec-3)）。其余部分仍在规划中。背景笔记在本地笔记 `tmp/notes/output-design.md` 里，其中的 Godot 节点名都在游戏源码里核实过。Godot 节点类（`N*` 类型）只按类名引用：每个类名在反编译源码里都是唯一的，按名字就能找到文件。

</Aside>

## 1. 约定

三个消费者读同一条 `Recommendation`（[协议：线路 §7](/arch/protocol/wire/#sec-7)），半自动模式是其中两个的组合。大脑从不知道当前开着哪种模式。它们用到推荐里的这些部分：

- `Plan`：本回合或本屏剩下的动作序列，在地图上是本幕剩下的路线（`plan[0]` 是下一个动作）；
- `Candidates`：考虑过的各个动作，每个带有估值、置信区间和样本数；
- `Facts`：解说可以引用的数字，是解说的唯一来源。

| 模式 | 消费者 | 需要 |
|---|---|---|
| 面板（辅助模式，简单版） | 一个文字面板，适用于所有决策界面 | `Plan`、`Candidates`、`Facts` |
| 高亮（辅助模式，进阶版） | 每个决策界面各自的 `ISurfaceAdapter.AnchorFor`（[Mod §4](/arch/mod/#sec-4)） | 动作 → 节点 |
| 自动 | `ISurfaceAdapter.Execute(plan[0])`，然后重新观测 | 动作 → 入口 |
| 半自动 | 高亮 + 按空格执行 `plan[0]` | 两者都要 |

决策界面（surface）指当前显示的决策屏幕的种类（战斗、地图、商店、选牌提示等）。**锚点**（anchor）是屏幕上某个动作所对应的 Godot 节点，比如要打出的那张牌所在的卡牌槽。

**过期守卫**。推荐只有在它的 `obs_hash` 等于当前哈希时才会被渲染或执行，否则清空输出。等待期间面板显示「thinking…」（思考中）。辅助模式下大脑是**随时可答**（anytime）的：先发出目前最好的答案，再陆续发出更好的（[Harness：路由、预算与种子 §4](/arch/harness/routing/#sec-4)），每次更新都替换面板内容。

## 2. 面板

面板有自己的 `CanvasLayer`。`CanvasLayer` 是 Godot 的一种节点，把它的子节点画在单独的一层上；这里用的是高层，位于游戏 UI 之上。它是左上角附近的一张卡片（`Panel`），F8 连同所有标记一起隐藏和显示：

- **卡头**：冠军、状态、SL/NoSL 开关（[Mod §5](/arch/mod/#sec-5)）和 F8 提示。
- **正文**：下一个动作，接着是到本回合结束为止的带编号计划（在地图上是路线经过的房间）和后面还规划了几个回合；大脑打过分的动作里最好的三个，每个带上它的值 ± 置信区间，在同一个刻度上画成条；最后一行是哪个大脑给出的答案、用了多久。
- **没有答案时**：一行说明原因，下面一行较淡的补充：正在连接；没有大脑在运行，每 2 秒重试；开始或继续一局；多人模式下关闭；大脑出错，下一局重新开启；等待大脑；等待决策；这个房间没有 SL 克隆，下一个房间会有；或者正在思考，附上已用的秒数。

**设置**。玩家的选择存在 `~/.local/state/sts2ai/settings.json`，和大脑的套接字放在一起，不在游戏的档案目录里：

- 辅助开或关：关掉时 Mod 什么都不问大脑，也什么都不画，并且像切换环境一样，对大脑来说结束这一局；
- 环境，SL 或 NoSL；
- 面板；
- 考虑过的动作：关、只显示值、值加上条；
- 卡牌上的顺序编号，以及目标和结束回合的标记；
- 地图路线：关、只显示下一个点、整条路线；
- 面板的不透明度。

这些在 Mod 加到游戏设置画面里的「AI」标签页中设定，排在通用、图形、声音和输入之后（`SettingsTab`）。`NSettingsTabManager._Ready` 上的一个后置补丁在下一次空闲时，用输入标签页的副本和清空后的声音面板副本搭出它；每一行都是 Mod 自己的控件，用游戏的字体，`<  值  >` 式的切换器和一个不透明度滑块，外加一个重置这些设置的按钮。搭建失败时，设置画面保持游戏原样，错误写进日志。

卡片、设置和标签页都已构建，但还没有在真实游戏里运行过。

显示内容随决策界面而变，全部来自 `Recommendation`。ΔP(win) 是估计的整局胜率之差。

| 决策界面 | 面板内容 |
|---|---|
| 战斗 | 带目标的编号计划；1–2 条事实（与另一种打法相比的预期掉血、下回合能否斩杀）；最佳备选及其 ΔP(win) |
| 卡牌奖励 / 选择 | 各个选项，每项带有相对跳过或基线的 ΔP(win) |
| 地图 | 下一个点和路线预览 |
| 事件 / 休息处 / 商店 | 同样的格式 |

- 对每个还没有高亮适配器的决策界面，面板就是兜底的显示方式。
- 可选的零 UI 变体：大脑在本机提供一个网页，显示在第二块屏幕上。只用于最早期的测试；与游戏的连接仍然是 Unix socket。

## 3. 高亮

**跟随式覆盖层**。高亮由 Mod 自己的节点来画，这些节点只存在于 Mod 自己的 `CanvasLayer` 里，盖在游戏上面。每一帧，每个标记读取目标节点在屏幕上的矩形（`GetGlobalRect()`）并跟着移动；目标消失或隐藏时，标记也隐藏。Mod 从不写入游戏节点，原因有二：`NHandCardHolder.UpdateCard()` 在每次状态变化时都会重置 `CardHighlight`（`Nodes.Cards.Holders/NHandCardHolder.cs:613-640`） <Badge text="已核实" variant="success" />；而且青色、金色、红色的光效在游戏里已经各有含义（`NCardHighlight`）。

**样式**。顺序徽标 ①②③，外加一种游戏没用过的描边颜色（紫色）。

**已经做好的**。`CombatMark` 在战斗里标出计划的当前回合：计划打出的每张牌，在它的牌位的点击区域上画紫色描边和它那一步的编号；每个目标生物（`NCreature.Hitbox`）画一个圈，带上瞄准它的各步的编号；结束回合按钮画一个圈，带上它那一步的编号。药水还没有标记。在地图上，`MapMark` 按设置显示路线。和面板一样，战斗标记已经构建，但还没有在真实游戏里运行过。

**锚点**。每个决策界面的标记挂在哪个节点上，已核实（本地笔记 `tmp/notes/output-design.md` §3.2） <Badge text="已核实" variant="success" />：

| 决策界面 | 节点 | 标记 |
|---|---|---|
| 手牌 | `NPlayerHand.Instance.GetCardHolder(card)` | 徽标 + 描边；悬停显示理由 |
| 目标 | `NCombatRoom.Instance.GetCreatureNode(creature)` | 带该牌编号的准星 |
| 药水 | `NPotionHolder` | 徽标 |
| 结束回合 | `NEndTurnButton` | 计划打完时闪动 |
| 战斗内选牌 | 手牌选择模式、`NCombatPileCardSelectScreen` | 勾选标记 |
| 卡牌奖励 | `NCardRewardSelectionScreen` 的卡牌槽 + 跳过 | 每张牌的 ΔP，最佳项描边 |
| 奖励 | `NRewardButton` | 领取顺序 / 跳过 |
| 地图 | `NMapScreen` 里的 `NMapPoint` + 我们自己的 `Line2D` 路线（不用 `NMapDrawings`：它在多人模式下共享） | 下一个点 + 路线 |
| 事件 | `NEventOptionButton` | 最佳项描边，其他项标 ΔP |
| 休息处 | `NRestSiteButton` | 同上 |
| 商店 | `NMerchantCard/Relic/Potion/CardRemoval` | 购买顺序 |
| 网格选牌 | `NCardGridSelectionScreen` 一族、`NCardGrid` | 勾选标记 |

**工作顺序**：

1. 手牌 + 目标；
2. 卡牌奖励；
3. 地图；
4. 事件 / 休息处 / 商店；
5. 网格选牌提示。

**容易踩的坑**：

- 卡牌槽节点会被池化（重复使用）、换父节点，还带动画。跟随式覆盖层能处理这些。
- 屏幕分辨率、UI 缩放和手柄操作：只使用全局矩形。
- 每个动作之后都会重新规划，徽标编号会随之改变。

## 4. 自动

自动循环建立在 Mod 的每帧循环之上（[Mod §3](/arch/mod/#sec-3)）：

<Steps>

1. 等到当前决策界面空闲。
2. 观测。
3. 拿到推荐。
4. 检查它的哈希与当前观测一致，且它的动作合法。
5. 执行 `plan[0]`，只执行这一个。
6. 等待哈希变化，或者超时。
7. 重复。

</Steps>

每个动作之后大脑都重新规划，因为抽到的牌和随机结果会影响下一次决策。速度来自把游戏的 FastMode 设为 Instant，外加可选的每步延迟（[Mod §7](/arch/mod/#sec-7)）。

## 5. 解说

解说是解释一条推荐的文字。

- 它只由 `Facts` 和 `Candidates` 生成，从不对状态做自由推理。NoSL 的事实是概率和期望；SL 的事实可以是确切结果（「先打 A 再打 B → 会抽到 X」）。
- 优先用模板，每种事实一个模板。
- 可选：由便宜的 LLM 润色文字，离线或异步进行（通过项目的 LLM 网关，只用便宜的模型）。输入是事实 JSON 和模板文字。输出要经过检查：文字里的每个数字都必须等于某个事实的值（格式化之后按字符串比较）；不满足就改为显示模板文字。
- LLM 除了事实之外看不到任何游戏状态，也从不影响动作。

## 6. 输出中的公平性

- 执行器只接受 `legal[]` 里的动作。
- 没有修改状态、控制台或读档的接口。
- `NumReloads` 记入日志。
- Mod 除了协议消息之外从不导出任何东西；SL 导出按环境开关（[Mod §6](/arch/mod/#sec-6)）。

## 7. 测试

- **逐个决策界面的锚点解析**：每个已适配决策界面的每个合法动作，都能对应到一个可见节点（在调试覆盖层模式下检查）。
- **过期**：延迟到达的推荐在状态变化之后从不渲染。
- **解说数字检查**。
