大脑用一个动作和一个计划回答一个决策，战斗时还附上它打过分的那些动作。**输出层**把这个答案变成玩家看得到的东西，或者以后变成游戏里发生的事。它运行在游戏进程里的 [Mod](/arch/mod/) 中，每种输出模式读的都是同一条 `Recommendation`：大脑从不知道开着哪种模式。本页写给想改变玩家所见内容的人。[Mod：主循环](/arch/mod/loop/)讲何时询问答案、答案显示多久。

<Aside title="状态">

已实现，并在真实游戏里运行过（2026-10-28）：**面板**，一张盖在游戏上的卡片，显示下一个动作、之后的计划，战斗时还有大脑评分最高的三个动作（[§2](#sec-2)）；它的**设置**，在 Mod 加到游戏设置画面里的「AI」标签页中；以及两种**标记**（[§3](#sec-3)）：在地图上，推荐的点上有一个圆圈，大脑在它之后规划的路线上有一条线，一直到 Boss；在战斗中，计划的步骤编号显示在它本回合要打出的卡牌上，以及它的目标和结束回合按钮上。规划中：其他决策界面上的高亮、自动游玩（[§4](#sec-4)）、解说（[§5](#sec-5)），以及解说需要的事实。Godot 节点类（`N*` 类型）只按类名引用：每个类名在反编译源码里都是唯一的，按名字就能找到文件。背景笔记在本地笔记 `tmp/notes/output-design.md` 里。

</Aside>

## 1. 约定

输出读一条消息 `Recommendation`（[协议：线路 §7](/arch/protocol/wire/#sec-7)），按已实现的样子（`Sts2Ai.Protocol/Wire.cs:62-63`）：

| 字段 | 含义 | 由谁给出 |
|---|---|---|
| `decision_id`、`obs_hash` | 它回答的决策 | |
| `action` | 现在要做的动作 | 每个大脑 |
| `brain` | 给出回答的大脑，用 Harness 给它起的名字（[Harness：路由、预算与种子 §1](/arch/harness/routing/#sec-1)） | |
| `plan`? | 大脑在 `action` 之后规划的内容 | PIMC：本回合剩下的部分，取自第一个世界；SL 规划器：这场战斗剩下的部分；地图上的 L0：通往 Boss 的路线；其他画面和选牌提示都没有 |
| `candidates`? | 大脑打过分的前几个动作，每个带有它的值、95% 置信区间的半宽、样本数等（[协议：世界与工作进程消息 §3](/arch/protocol/worlds/#sec-3)） | 只有战斗大脑 |

`plan` 在 `action` *之后*：下一步是 `action`，`plan[0]` 是再下一步。

**消费者**。大脑从不知道开着哪种模式。

| 模式 | 消费者 | 状态 |
|---|---|---|
| 面板（辅助模式，简单版） | 一张卡片，适用于所有决策界面（[§2](#sec-2)） | 已实现 |
| 标记（辅助模式） | 地图上的圆圈和路线；战斗计划的编号和圆圈（[§3](#sec-3)） | 已实现 |
| 高亮（辅助模式，进阶版） | 其他决策界面的节点，通过适配器（[Mod：自动游玩与安全 §1](/arch/mod/auto/#sec-1)） | 规划中 |
| 自动 | 适配器打出 `action`，然后 Mod 重新观测（[§4](#sec-4)） | 规划中 |
| 半自动 | 标记显示计划，按一个键打出 `action` | 规划中 |

*决策界面*（surface）是当前显示的决策画面的种类（战斗、地图、商店、选牌提示等）。*锚点*（anchor）是画面上一个动作所属的 Godot 节点，例如要打出的那张牌所在的卡牌槽。

**过期的答案**。答案按 id 与开着的决策对应，并按它被问到时的键保存：观测的哈希加上它的合法动作。它只在这个键持续的那些帧上画出来；画面往前走了，面板就为新状态显示「Thinking…」（思考中），Mod 再次询问（[Mod：主循环 §3](/arch/mod/loop/#sec-3)）。Mod 从不读答案的 `obs_hash`。

**规划中**。

- **事实**：一段解释可以使用的数字，作为推荐的一个字段；也是解说唯一的来源（[§5](#sec-5)）。代码里还没有 `Facts`。
- **随时可答**（anytime）：辅助模式下，大脑先发出目前最好的答案，再陆续发出更好的，每一个替换上一个（[Harness：路由、预算与种子 §4](/arch/harness/routing/#sec-4)）。如今大脑每个决策只发一个答案，Mod 收到第一个答案就了结这个决策。

## 2. 面板

面板是盖在游戏上、靠近左上角的一张卡片（`UI/Panel.cs`）。它有自己的 `CanvasLayer`，这是一种 Godot 节点，把它的子节点画在单独的一层上：第 100 层，在游戏的 UI 之上，所有标记都共用这一层。卡片除了它的开关之外不接收点击，所以点击会落到它下面的游戏上。F8 连同所有标记一起隐藏和显示它。

<PanelMock client:visible lang="zh-CN" />

**布局**（`UI/Panel.cs:44-250`）：

- **卡片**：位于 (24, 132)，宽至少 420 px，内边距 16 px（左右两侧 18），圆角半径 14，深紫色边框，一层阴影，以及按不透明度设置填充的近黑色底色。
- **头部**：一个紫色的「AI」徽标；冠军的名字，下面是状态，各占一行，超出空间处用省略号截断；SL/NoSL 开关，选中的一侧填成紫色（多人模式下两侧都不选中，Mod 关闭时没有开关）；以及「F8」。
- **答案**：实心的「1」徽标后面用大号字显示下一个动作；在地图上用一个圆圈代替徽标，接着是「ROUTE TO THE BOSS」（通往 Boss 的路线）和用圆点连起来的路线上的房间；在别处是计划的各步，用空心圆徽标从 2 开始编号；然后是计划后面的回合，「2 more turns planned」（[Mod：主循环 §6](/arch/mod/loop/#sec-6)）。
- **考虑过的动作**，在一条分隔线下面：「CONSIDERED」和「value ±CI」，然后是按大脑顺序排列的前三个候选，最好的在前，第一个是紫色。每个值保留一位小数，`0.0 ±0.0`。开启条形时，每一行还有一条 96 px 的轨道，置信区间画成轨道上的一段，值的位置有一个刻度；三行共用一个刻度范围：从最低的值减去它的区间，到最高的值加上它的区间，两侧各再放宽十分之一。只有当大脑给不止一个动作打过分时才显示，如今这意味着战斗。
- **底部**：给出回答的大脑，以及 Mod 等它的秒数，从发出到收到。
- 没有答案时显示**一条消息**：一个圆点、消息本身和较淡的第二行；玩家可以修正或等它过去的情况用琥珀色，错误用红色。所有消息都列在 [Mod §6](/arch/mod/#sec-6) 里。

只有当显示的内容或绘制它所用的设置变化时，主体才会重新搭建；标记则每一帧都跟着它们的节点走。

**设置**。玩家的选择保存在 `~/.local/state/sts2ai/settings.json`，在大脑的套接字旁边，不在游戏的档案里；每一行、它的取值和默认值见 [Mod §5](/arch/mod/#sec-5)。面板和标记实时读取设置，所以改动立即生效。

**AI 标签页**（`UI/SettingsTab.cs`）位于游戏的设置画面里，排在通用、图形、声音和输入之后。游戏在 `NSettingsTabManager._Ready` 里用场景中的节点搭出它的四个标签页。那里的一个后缀补丁在下一次空闲时运行，这时画面已经完整：它复制输入标签页作为这个标签页的按钮，复制声音面板并清空作为它的面板，所以两者的外观和切换都和游戏自己的一样；副本带上节点和它们的脚本，但不带游戏的信号连接。它把标签栏向左移半格，让它保持居中，把按钮接到管理器自己的标签页切换上，并把这一对加进管理器的标签页。各行是 Mod 自己的控件，用游戏设置行的字体：`<  value  >` 式的步进器和一个不透明度滑块，以及一个把它们重置的按钮。所有东西都在加入画面之前搭好，所以搭建失败时，画面保持游戏搭出的样子，错误写进日志。

**面板的规划**：

| 决策界面 | 内容 |
|---|---|
| 战斗 | 1–2 条事实（与另一种打法相比的预期掉血、下回合能否斩杀）；最佳备选及其 ΔP(win)，即估计的整局胜率之差 |
| 卡牌奖励和选择 | 每个选项，带有相对于跳过或基线的 ΔP(win) |
| 地图、事件、休息处、商店 | 同样的格式 |

如今每个决策界面都用上面那一种布局，值只来自战斗的候选；V 的值不发送。还曾考虑过一个零 UI 变体：大脑在本机提供一个网页，显示在第二块屏幕上，但只用于最早期的测试。

## 3. 高亮

**跟随式覆盖层**。标记由 Mod 自己的节点来画，这些节点只存在于 Mod 的 `CanvasLayer` 里，盖在游戏上面。每一帧，每个标记读取它的目标节点在屏幕上的变换（`GetGlobalTransformWithCanvas()`）和节点的尺寸，所以它能跟住一张会转动、展开成扇形或缩放的牌，并随它移动；目标消失或隐藏时，标记也隐藏。Mod 从不为了绘制而写入游戏的节点，原因有二：`NHandCardHolder.UpdateCard()` 在每次状态变化时都会重置 `CardHighlight`（`Nodes.Cards.Holders/NHandCardHolder.cs:613-640`） <Badge text="已核实" variant="success" />；而且青色、金色和红色的光效在游戏里已经各有含义（`NCardHighlight`）。Mod 唯一改动游戏节点的地方是设置画面（[§2](#sec-2)）。

**样式**：紫色，一种游戏自己的光效不用的颜色：描边、圆圈，以及带普通数字和深色外圈的紫色圆形徽标。

**在地图上**（`UI/MapMark.cs`）：下一个点上有一个脉动的紫色圆圈，它之后路线上的每段路径都有一条紫色的线，从玩家所在的位置一直到路线的终点。地图画面把它的点节点和每段路径的小点存在私有字典里，新的一幕会替换它们；一条线从路径的第一个小点画到最后一个，所以在点的图标前就停住了。圆圈的半径是点的较长边的一半再加 14，随地图缩放，每秒脉动一次，幅度 ±10%。路线设置显示整条路线、只显示圆圈，或者什么都不显示：

<MapRoute client:visible lang="zh-CN" />

**在战斗中**（`UI/CombatMark.cs`）：面板上显示的那份计划，从 `action` 到本回合结束。

- 计划打出的每张牌，在它的卡牌槽的点击区域上画紫色描边，右上角标出它那一步的编号；
- 每个目标（敌人或盟友）在它的生物节点的点击区域外 10 px 处画描边，瞄准它的每一步的编号放在顶边中间的一个徽标里；
- 结束回合按钮画上描边，并标出它那一步的编号。

已经不在的卡牌或生物没有标记。「Order numbers on cards」把卡牌的描边和编号一起关掉；「Target and end-turn marks」管其余的。药水没有自己的标记，但它的目标会得到它那一步的编号。

**锚点**。每个决策界面的节点，已在游戏源码里核实（本地笔记 `tmp/notes/output-design.md` §3.2） <Badge text="已核实" variant="success" />：

| 决策界面 | 节点 | 标记 | 状态 |
|---|---|---|---|
| 手牌 | `NPlayerHand.Instance.GetCardHolder(card).Hitbox`，卡牌按 uid 从 `NetCombatCardDb` 取得 | 描边 + 步骤编号 | 已实现 |
| 目标 | `NCombatRoom.Instance.GetCreatureNode(creature).Hitbox` | 描边 + 各步的编号 | 已实现 |
| 结束回合 | `NCombatRoom.Instance.Ui.EndTurnButton` | 描边 + 步骤编号 | 已实现 |
| 地图 | `NMapScreen` 里的 `NMapPoint`，以及我们自己沿它的路径小点画的 `Line2D`（不用 `NMapDrawings`，它在多人模式下共享） | 圆圈 + 路线 | 已实现 |
| 药水 | `NPotionHolder` | 徽标 | 规划中 |
| 战斗内选牌 | 手牌选择模式、`NCombatPileCardSelectScreen` | 勾选标记 | 规划中 |
| 卡牌奖励 | `NCardRewardSelectionScreen` 的卡牌槽 + 跳过 | 每张牌的 ΔP，最佳项描边 | 规划中 |
| 奖励 | `NRewardButton` | 领取顺序 / 跳过 | 规划中 |
| 事件 | `NEventOptionButton` | 最佳项描边，其他项标 ΔP | 规划中 |
| 休息处 | `NRestSiteButton` | 同上 | 规划中 |
| 商店 | `NMerchantCard/Relic/Potion/CardRemoval` | 购买顺序 | 规划中 |
| 网格选牌 | `NCardGridSelectionScreen` 一族、`NCardGrid` | 勾选标记 | 规划中 |

**工作顺序**：手牌和目标（已完成）；卡牌奖励；地图（已完成）；事件、休息处和商店；网格选牌提示。

**容易踩的坑**：

- 卡牌槽节点会被池化（重复使用）、换父节点，还带动画：跟随式覆盖层每一帧都重新查找它们，以此应对。
- 屏幕分辨率、UI 缩放和手柄输入：只用屏幕变换，从不用局部位置。
- 每个动作之后大脑都重新规划，所以每个答案的编号都从 1 重新开始。

## 4. 自动 <Badge text="规划中" variant="caution" />

自动循环会建立在 Mod 的每帧循环之上（[Mod：主循环 §1](/arch/mod/loop/#sec-1)）：

<Steps>

1. 等到决策界面空闲。
2. 观测。
3. 拿到推荐。
4. 检查它对应当前的键，且它的动作合法。
5. 打出 `action`，只打这一个。
6. 等待键变化，或者超时。
7. 重复。

</Steps>

每个动作之后大脑都重新规划，因为抽到的牌和随机结果会影响下一个决策。速度会来自把游戏的 FastMode 设为 Instant，外加可选的每步延迟（[Mod：自动游玩与安全 §2](/arch/mod/auto/#sec-2)）。

## 5. 解说 <Badge text="规划中" variant="caution" />

解说是用来解释一条推荐的文字。

- 它只由事实和候选生成，从不对状态做自由推理。NoSL 的事实是概率和期望；SL 的事实可以是确切的（「先打 A 再打 B 会抽到 X」）。
- 优先用模板，每种事实一个模板。
- 可选：由一个便宜的 LLM 润色文字，离线或异步进行（通过项目的 LLM 网关，只用便宜的模型）。它的输入是 JSON 形式的事实和模板的文字。它的输出要经过检查：文字里的每个数字都必须等于某个事实的值（格式化之后按字符串匹配）；不满足就改为显示模板的文字。
- LLM 除了事实之外看不到任何游戏状态，也从不影响动作。

这些都还没有实现：推荐里还没有事实（[§1](#sec-1)）。

## 6. 输出中的公平性

| 规则 | 状态 |
|---|---|
| 辅助模式下 Mod 什么都不打出；规划中的执行器只会打出决策合法列表里的动作。大脑的答案由 Harness 对照这个列表检查（[Harness：路由、预算与种子 §6](/arch/harness/routing/#sec-6)） | 成立 |
| 没有修改状态、使用控制台或读档的接口 | 成立 |
| 套接字只传输协议消息。SL 导出只在 SL 下发送，带着节点的存档，其中包括种子和随机数流（[Mod：自动游玩与安全 §4](/arch/mod/auto/#sec-4)） | 成立 |
| Mod 只写它的设置文件和它在游戏日志里的行 | 成立 |
| `NumReloads` 记入日志，且必须为 0 | 规划中 |

协议消息里的一个新字段，如果改变了什么可以离开游戏，就在这里加一行。

## 8. 未决问题

1. 有多个目标的计划在中途有目标死掉时的标记：重新编号，还是保持不变？
2. 如何在不显得杂乱的情况下展示 NoSL 的不确定性（置信区间）。如今：保留一位小数的值，外加一个条形。
