搜索几乎把所有时间都花在战斗上：每个决策，战斗大脑都要试几千条打法（[战斗大脑](/arch/combat-brain/)）。本页讲其中模拟器这一侧：一场战斗怎样在游戏自己的代码里运行（**战斗会话**），搜索怎样回到更早的某一点（快照与重播），它怎样猜测看不到的东西（确定化），怎样只凭一个观测构建出一场战斗（**CombatBuilder**），这样构建出的战斗能信到什么程度，以及这一切的开销。

## 1. 战斗会话

`CombatSession`（`Simulation/CombatSession.cs`）在真实引擎里跑一场战斗。它由一个记录（record）来设置：

```csharp
CombatSetup(string Character, EncounterModel Encounter, int ActIndex, string Seed, int Ascension = 0,
    Loadout? Loadout = null, CombatObservation? From = null, IReadOnlyList<EnemyTurns>? History = null)
```

分四步启动：

1. `Player.CreateForNewRun(character, UnlockState.all)`，然后套用配置（牌组、遗物、药水、生命值：[参考 §3](/arch/simulator/reference/#sec-3)）；
2. `RunState.CreateForTest`，配上 `MockSinglePointActMap`，一张只有一个点的地图；
3. `RunManager.SetUpTest`；
4. `EnterRoomDebug(Monster, encounter)`。

带上 `From` 时，这场战斗接着被弄成显示那个观测（[§5](#sec-5)），`History` 则给它的怪物补上之前出过的招。

这**不是**一局进入战斗的方式：它跳过了掷出 `?` 变成什么，也跳过了这一局的房间生成（`GenerateRooms`）<Badge text="已核实" variant="success" />。对单独的一场战斗（基准测试、`selftest`、搜索世界）这没问题，对整局则是错的；整局按游戏自己的方式开局（[整局 §2](/arch/simulator/runs/#sec-2)）。

**执行动作**。`Execute(action)` 通过 `CombatActions.Start` 发起一个动作，这和 UI 用的是同样的入口（[GameBridge：各决策界面的动作 §1](/arch/gamebridge/actions/#sec-1)），然后稳定下来：让 Pump 一直运行，直到游戏再次等待玩家（[无头宿主 §7](/arch/simulator/headless/#sec-7)）。结束回合之后，它等到之后的某个回合；战斗一结束，则等到队列为空、执行器闲置（`CombatSession.cs:217-224`、333-341）。由策略打完的战斗（`PlayOut`，推演和基准测试都这样做）在 50 回合或 1,000 个动作时停下；这时它的结果是 `Truncated`，敌人还活着而战斗已结束时也是这个结果（`CombatSession.cs:73-74`、192-200）。

**uid**。动作用 **uid** 指称卡牌和生物：uid 是取自游戏的稳定 id，而不是列表里的位置。手牌用它的 `NetCombatCardDb` id，生物用它的 `CombatId`。`play:7:2` 表示把 7 号牌打向 2 号生物。游戏按固定的顺序给牌编号，所以重播时编号保持不变（[协议：观测与动作 §4](/arch/protocol/observation/#sec-4)）。

## 2. 快照是配方

搜索必须能退回去：试一条路线，回到决策点，再试另一条。游戏无法复制自己的状态（它的对象都绑在持有唯一一场活战斗的单例上），所以快照不是副本，而是一份**配方**：`(Setup, Trace)`，即这场战斗怎样开始，以及之后走过的每一步。轨迹的每一步是以下之一：

- `Action`：一个战斗动作，文本形式（`play:7:2`、`end_turn`）；
- `Choice`：对选牌提示的回答，用游戏自己的选项下标；
- `Determinize(seed)`：一个确定化步骤（[§3](#sec-3)），文本形式为 `determinize:SEED`。

**还原**一个快照，就是按设置开一场新战斗，再重播轨迹（`CombatSession.cs:104-125`）。同样的设置和轨迹总是得到同样的状态，因为每次随机抽取都来自带种子的随机数流，而 Pump 以同样的顺序运行每个续体。唯一用时钟做种子的生成器 `Rng.Chaotic` 只影响外观 <Badge text="已核实" variant="success" />：怪物皮肤、屏幕震动、假商人的对白、Trial 事件的参赛者编号、美味饼干的图标、加牌动画的时机、DenseVegetation 的视觉偏移。还有三种后备情况也会用到它，但模拟器一种都碰不到：不是活副本的怪物模型（活着的怪物有带种子的流）、不带种子开始的一局（模拟器总会传入一个种子），以及本地化文本的随机变体（本地化返回的是键，[无头宿主 §4](/arch/simulator/headless/#sec-4)）。

重播的耗时与它的长度成正比。2026-10-26 实测：一次还原耗时 0.28 ms，外加每个重播动作 0.073 ms。SL 世界载入节点的检查点，而不是新开一场战斗，它约为 0.5 ms，外加自进入节点以来每一步 0.1 ms（[世界与 SL 克隆 §7](/arch/simulator/worlds/#sec-7)）。下图把两种开销模型并排放在一起；拖动滑块，就能还原到战斗中更深的位置。

## 3. 确定化

`Determinize(seed)` 把玩家无从知道的一切换成由 `seed` 抽出的样本，玩家看到的东西保持不变（`CombatSession.cs:231-277`）。NoSL 的搜索就是这样猜测隐藏状态的；[环境：世界 §2](/arch/environments/worlds/#sec-2) 解释了为什么，并配有一张基于真实抽牌堆的图。它做的事：

- 为每条整局流（`RunRngType`）、每条玩家流（`PlayerRngType`）以及每个活着的怪物（包括盟友和宠物）的流重新播种；
- 重排抽牌堆：先按卡牌键排序（这个顺序只取决于玩家看到的东西），再用这个样本做一次 Fisher–Yates 洗牌；
- 给手牌以外的牌重新编号（`CombatBuilder.NumberCards`）：游戏按抽牌顺序给牌编号，旧编号会泄露真实的顺序；
- 在显示相同意图的招式中，均匀地重新抽取每个敌人排定的下一招，并改写它出招日志的最后一项（`StateLog[^1]`），使之与新的一招一致。

种子只来自调用方，绝不来自这一局。尚未建模的有：玩家知道位置的抽牌堆里的牌（刚放到顶上的那张），以及怪物的历史怎样让某些招比其他招更可能出现（`CombatSession.cs:242-243`）。

## 4. 隐藏状态与换位

搜索会记住已经搜过的状态，这样同一组出牌的两种顺序只搜一次。一个状态就是观测，加上观测隐藏起来、又会改变接下来发生什么的东西。`HiddenState.Key`（`GameBridge/HiddenState.cs:19-29`）对以下内容做哈希：抽牌堆的顺序，每条整局流、玩家流和怪物流的位置（计数器），以及每个怪物排定的下一招。本回合出牌的顺序是故意不算进去的。`HiddenState.Full`（`:36-44`）是 SL 世界的键，它再加上每个怪物的出招日志和战斗历史里本回合的条目，作为一个多重集合（[环境：世界 §4](/arch/environments/worlds/#sec-4)）。

## 5. CombatBuilder：从观测构建战斗

在 NoSL 下，搜索不能从真实的战斗出发：那会把真实的隐藏状态带进搜索。它从一场**显示该观测**、此外什么也不多的战斗出发。`CombatBuilder.Setup(obs, seed, history)`（`Simulation/CombatBuilder.cs:57-105`）构建这样一场战斗：

1. **开始**观测中的遭遇，带上它的牌组、遗物和生命值。开战效果可能杀死生命值低的玩家（王室猛毒在第一回合开始时造成 4 点伤害，而每次构建都从第一回合开始），死去的玩家的遗物、能力和卡牌就不再起作用。这样的战斗会以满生命值重新开始（`CombatSession.cs:158-162`），下一步照常设成观测到的生命值。按开战时的生命值记下标志的遗物（红头骨的力量）这时可能不对，只有这种罕见的开局才有这个风险。
2. **`Apply`** 覆盖一切可见的东西：回合数；敌人（增加、移除、重排）；生命值和格挡；能量、最大能量和星辰；金币；药水；充能球栏位和充能球，连同它们显示的数值；遗物的计数（显示的或隐藏的）、状态、熔化和用尽的遗物；遗物保存的牌（佩尔之牙的牌，它的计数就是牌的张数），用标准副本，因为提示框不显示升级，而且这些牌要到战斗之后才回来；能力，在图标显示另一个数字时连同它的层数，以及能力保存的牌；四个牌堆，逐张牌，连同每张牌的修改；意图。
3. **`Resample(StableHash(seed))`** 抽取隐藏状态，和确定化的做法一样。
4. **`BuildDifferences`** 按 JSON 路径比较输入的观测与重建后战斗的观测。结果为空就表示完全一致。NoSL 世界拒绝不完全一致的构建（`Simulation/SimWorlds.cs:34-44`）。

难点如下，每一个都在构建器里解决了：

- **旋钮求解**。屏幕上的数字由内部数字算出，每种能力或遗物的算法都不同。构建器逐个尝试内部数字（数值、动态变量、字段，以及能力内部数据里的整数和小数字段，例如硬化外壳 `HARDENED_SHELL_POWER` 本回合已受到的伤害），直到显示一致（`CombatBuilder.cs:415-457`）。被观测为已用尽的遗物（用过的蜥蜴尾巴 `LIZARD_TAIL`、飞行次数用完的羽翼之靴 `WINGED_BOOTS`），在它的计数之后，也用同样的方式逐个尝试它的整数和布尔字段，直到重建的遗物同样用尽、计数也与观测一致：白银熔炉（`SILVER_CRUCIBLE`）要等计数用完、并且进过宝箱房之后才算用尽。
- **意图**。构建器在显示所观测意图的招式中做选择（`CombatBuilder.cs:164-213`）。被眩晕的敌人会得到一个合成的眩晕招式，做法与 `Creature.StunInternal` 相同（`FollowUpStateId = StateLog.Last().Id`）。为了让尽可能多的敌人对上，先搜索能力里隐藏的枚举开关（`SurroundedPower._facing`），再搜索怪物自己的整数字段：先试 0–99 的值，再试 100–999；瀑布巨兽的喷发伤害每喷发一次就涨一次，超过 100 时就是这样找到的。
- **uid** 与观测中的一致；其他牌的编号排在它们之后。先按 id、升级和附魔从新牌组里取牌，不够时才新造（`CombatBuilder.cs:507-534`）。
- **盟友**。玩家一方的生物像敌人一样构建：遗物带来的宠物在开战时加入，按怪物 id 对上；缺少的那个则像召唤那样，作为玩家的宠物加入（`CombatBuilder.cs:309-336`）。任何角色都能用别的角色卡池里的牌召唤奥斯提（万花筒 `KALEIDOSCOPE` 会提供这类牌）；在能构建盟友之前，第 1 代自我对弈的 165 局里有一局因此失败。
- **费用**。牌自己的费用这样设：叠加上它上面的修正（能力、遗物）之后，得到显示的费用；它可以低于 0（`CombatBuilder.cs:575-583`）。一张被攻击药水变成本回合免费的精密瞄准（`PINPOINT`），本回合每打出一张技能牌还会再少 1 费，而在缠结之下（`TANGLED_POWER` 加 1）它仍然显示 0。把牌自己的费用截在 0，曾让 452 局里有一局失败。
- **疯狂科学**。来自 Tinker Time 事件的这张牌，会拿回事件为它选的类型和附加效果，它的牌框和文字都显示着这两项（`CombatBuilder.cs:550-554`，[协议：观测与动作 §3](/arch/protocol/observation/#sec-3)）。
- **出招日志**。怪物按自己出过的招来选下一招（同一招不连出三次、固定的循环），而新开的战斗里日志是空的。有了每个敌人在每回合开始时显示了什么的记录（[Harness §4](/arch/harness/#sec-4)），每个怪物就能得到它的日志：先是之前每一回合的招，再是当前这一招（`CombatBuilder.cs:119-154`）。之前的某一回合匹配显示相同意图的招，否则匹配意图类型和段数相同的招，再否则匹配类型相同的招，因为数值会随怪物的力量增长。有某一回合匹配不到任何招的怪物，保留新开的日志。和游戏里一样，眩晕不进日志：显示为眩晕的回合跳过；当前被眩晕的怪物在眩晕之后，接着出它在本回合开始时显示的那一招。没有记录时，每个怪物都是新开的日志。
- **第一招**。从第 2 回合起，构建器标记怪物已经出过第一招（`_performedFirstMove`）。

**近似**。构建器看不到的东西，它做近似：本回合的历史，以及能力和怪物内部的计数器；费用修正持续多久；玩家减益的衰减；没有记录时眩晕的后续招式；还有牌组，它就是见过的每一张牌，包括生成的牌。[§6](#sec-6) 衡量这些近似的代价；它们从未在真实游戏的观测上检验过。

**由 `selftest` 检查**：它把自己的每场战斗在最多三个随机点切开，从每个切点的观测构建一场战斗；构建结果必须显示该观测、能还原、能接着打下去。2026-10-27 所有检查都通过：静默猎手 60 次构建中 60 次，铁甲战士 58 次中 58 次，静默猎手第 1、2、3 幕的精英战和 Boss 战分别为 57、57 和 58 次。`selftest` 的其他构建显示只有模型自身状态才持有的数字：磨损的玻璃充能球、用过的白银熔炉、保存着两张牌的佩尔之牙、上限 3 张已打 1 张的懒惰、夜魇的复制牌、本回合受过伤之后的硬化外壳、带着王室猛毒以 3 点生命开局，以及超过 100 的喷发（[参考 §5](/arch/simulator/reference/#sec-5)）。

## 6. 保真度：构建出的战斗能信到什么程度

构建出的战斗显示的是那个观测，但它打起来和真实的那场一样吗？测量时不算确定化有意采样的部分。在一组战斗的每第 k 个决策处，真实战斗用占位策略接着打到回合结束，包括敌人的回合（最多 12 个动作）。从该决策的观测和记录构建出的战斗，被赋予真实战斗的采样状态（抽牌顺序、随机数流、每个怪物的流和下一招），并执行同样的动作。第一个不同的观测（uid 不算）按它的 JSON 路径计数。

静默猎手的初始牌组，策略 `play`，每隔一个决策取一次（2026-10-27）：

| 战斗 | 决策数 | 直到敌人回合结束都相同的比例，无记录 → 有记录 |
|---|---|---|
| 第 1 幕弱遭遇 + 普通遭遇，30 场 | 459 | 82.4% → 96.3%；眩晕带上后续招式后为 97.4% |
| 第 2 幕弱遭遇 + 普通遭遇，30 场 | 478 | 88.7% → 98.1%；眩晕带上后续招式后为 99.0% |
| 第 1 幕 Boss，9 场 | 201 | 96.5% → 96.5% |
| 第 1 幕精英，15 场 | 289 | 99.0% → 99.0% |

没有一场战斗构建错，构建出的战斗里也没有一个动作不合法。在回合之内，最多 1% 不同。其余的不同出现在回合结束之后：第 1 幕是双尾鼠（`TWO_TAILED_RAT`）的意图，它的召唤取决于怪物内部的计数器（还要几回合才能召唤、已经召唤了几次）；第 2 幕是寄生惧魔（`PARAFRIGHT`）的意图；Boss 战里是瀑布巨兽的伤害。一只被眩晕的噬尸蛞蝓（`CORPSE_SLUG`，因为另一只蛞蝓死了）一直接着出错误的招，直到眩晕从记录里取得后续招式为止。

## 7. 速度

2026-10-26 实测，Release 构建，`DOTNET_ReadyToRun=0`（[无头宿主 §6](/arch/simulator/headless/#sec-6)）。这里的幕从 1 开始数，和游戏显示的一样；命令行的 `--act` 从 0 开始数。

| 角色 | 战斗数 | 战斗/秒 | 动作/秒 | 每场用时 |
|---|---|---|---|---|
| SILENT | 5,000 | 319 | 10.3k | 3.1 ms |
| IRONCLAD | 2,000 | 379 | | |

短批次（200 场战斗）每场约 6.7 ms：启动和 JIT 预热占了大头。

**分支**。这里的一个搜索分支，是一次还原、一次确定化，再加上用占位策略推演到战斗结束，从战斗中途的切点测量：

| 指标 | 数值 |
|---|---|
| 还原 | 0.28 ms + 每个重播动作 0.073 ms |
| 分支 | 中位数 2.78 ms，p90 3.97 ms |
| 平均根深度 / 平均推演长度 | 15.8 / 16.6 个动作 |
| 吞吐量 | 每核 329 分支/秒 |

**搜索工作进程的时间花在哪里**。在一次整局晋级门槛的某个工作进程里采样 40 s（2026-10-27：从观测构建的 NoSL 世界，一个较早的战斗网络，16 个线程上跑 4 局、每局 8 个工作进程），该工作进程 87% 的时间在搜索，其余时间在等请求。还原世界占 48%：按设置开始战斗 38%（进入房间 9%，套用观测 8%，重采样 4%，比较构建结果与观测 10%），重播路线 7%，确定化 4%。执行搜索中的动作占 16%，生成观测 16%（除去那次比较是 11%），战斗网络 5%。还原不再比较构建结果，因为请求的第一次构建已经检查过（提交 `5032064`）：冠军的对局完全相同，在那样的负载下快了 7%。
