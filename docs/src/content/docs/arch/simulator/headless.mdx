游戏预期在 Godot 引擎里运行：有窗口，有渲染器，还有一个每秒调用它六十次的主循环。本页讲 `Sts2Ai.SimWorker` 怎样在这些都没有的情况下运行同样的代码：用什么代替引擎，哪些游戏方法打了补丁、为什么打，以及一个单线程调度器 `Pump` 怎样把游戏的异步代码变成一个确定性的步进函数。模拟器的其余一切都建立在它之上。

## 1. 模型层与节点

杀戮尖塔 2 是一个用 C# 写成、运行在 .NET 9.0.7 上的 Godot 4.5.1 应用。它的代码分两层：

- **模型层**：规则涉及的一切都是普通的 C# 对象：这一局（`RunState`、`RunManager`）、战斗（`CombatState`、`CombatManager`）、生物、卡牌、牌堆、能力、遗物、药水、房间、事件、随机数流。游戏逻辑是 `async` 的：打出一张牌是一个动作，它要等待它的钩子、它的伤害、它的后续效果。
- **节点**：Godot 场景对象，名字以 `N…` 开头的类（`NGame`、`NCombatRoom`、`NMapScreen`、`NRewardsScreen`……）。它们绘制模型、为模型播放动画，并把玩家的点击变成对模型的调用。

无头运行时只跑模型层。节点从不创建；凡是由画面的代码决定接下来发生什么的地方（战斗之后打开哪个画面，“继续”按钮做什么），都改由模拟器的驱动程序来做（[整局 §3](/arch/simulator/runs/#sec-3)）。三样东西让模型层能独立运行：引擎原生函数的桩（[§3](#sec-3)）、Harmony 补丁（[§4](#sec-4)），以及游戏自带的 `TestMode`（[§5](#sec-5)）。

## 2. 启动

`HeadlessGame.Boot`（`Runtime/HeadlessGame.cs:25-56`）每个进程运行一次。它先从游戏的 `release_info.json` 读出游戏的版本，然后：

<Steps>

1. `GodotNativeStub.Install()`：用一个桩填满引擎的函数表（[§3](#sec-3)）。
2. `HeadlessPatches.Apply()`：安装所有补丁，GameBridge 的选牌提示上下文补丁最先（[§4](#sec-4)）。
3. `TestMode.TurnOnInternal()`：打开游戏的测试模式（[§5](#sec-5)）。
4. `ModManager.State = Skipped`：无头时从不加载 Mod（这个 setter 是私有的，用反射来设）。
5. `AssemblyInfo.Init`、`ModelDb.Init`、`ModelIdSerializationCache.Init`、`ModelDb.InitIds`：加载游戏的模型数据库，即每张卡牌、每件遗物、每个怪物和每个事件。
6. `LocalContext.NetId = 1`：唯一一个本地玩家的网络 id。
7. 测试用的设置和偏好（`InitSettingsDataForTest`、`InitPrefsDataForTest`），并设 `FastMode = Instant`。

</Steps>

然后它订阅游戏的日志（`Log.LogCallback`，Error 及以上级别的每一行）和没有人等待的任务出的错（`TaskHelper.UnobservedFault`），把两者都收集为**游戏错误**（[§8](#sec-8)）。启动大约需要 1.2 s。

不需要游戏的命令（`brain`、`report`、`gate`、`leaderboard`、`seeds`）从不启动它（[参考 §4](/arch/simulator/reference/#sec-4)）。

## 3. 原生桩

游戏的 C# 代码通过 GodotSharp（引擎的 C# 绑定）访问引擎；GodotSharp 通过一张函数指针表调用引擎的原生函数，这张表由引擎在启动时填好。没有引擎，这张表就是空的，第一次调用就会崩溃。

`GodotNativeStub.Install`（`Runtime/GodotNativeStub.cs:20-41`）把表里的每个槽都填成同一个很小的函数 `mov rax, imm64; ret`，它返回一个指针，指向某个清零页面的上半部分。于是碰到 Godot 的托管代码可以一路跑过去：它拿回的是清零的内存，读出来就是空对象、空字符串和零，什么也不会发生。它是为 linux-x64 写的。

桩让零散的调用无害，但不让它们有意义。需要引擎给出真实答案的代码（操作系统、时钟、资源、本地化）打了补丁，改从托管代码得到答案（[§4](#sec-4)）。

## 4. 补丁

**Harmony 补丁**在运行时改写游戏的方法。Harmony 是一个 .NET 库：*前缀*（prefix）在原方法之前运行，可以跳过原方法；*后缀*（postfix）在原方法之后运行；*转译器*（transpiler）则不包裹方法，而是直接改写方法的 IL（编译后的指令）。`HeadlessPatches.Apply`（`Runtime/Patches/HeadlessPatches.cs:26-33`）先安装 GameBridge 的 `ChoiceContexts`，再安装程序集里的每个补丁类。顺序很重要：打补丁会编译每个被替换的方法，而在选牌提示补丁之前编译的方法，可能把某个很小的 `CardSelectCmd` 入口内联进去，从而绕过它的补丁。SapphireSeed 的种植就是这样的方法，事件转译器会改写它（[GameBridge：读取游戏 §6](/arch/gamebridge/observe/#sec-6)）。

除了规则保真这一组，没有任何补丁改变游戏规则；规则保真组把正式版规则放回去：被 TestMode 改掉的，以及游戏通过画面检查、而无头时画面并不存在的。各组补丁，按 `Runtime/Patches/` 里的文件：

| 分组 | 文件 | 作用 |
|---|---|---|
| 引擎外壳 | `Engine.cs` | 引擎的操作系统、时间、单例、资源和玩家名的托管替身 |
| 资源预加载 | `Engine.cs` | 关闭：不从游戏的资源包加载任何东西 |
| 表现层 | `Engine.cs` | 没有 TestMode 守卫就进入表现层的模型代码：帝皇蟹的钳臂（火箭和碾碎爪的 `BeforeDeath`）、灵魂枢纽（`AfterDeath`），以及 `EventPresentation` 转译器（见下文） |
| 文本 | `Text.cs` | 本地化返回键，而不加载文本表；假商人每个招式之前的那句台词跳过不说，因为无头时查它会抛异常（见下文）；游戏自己的日志转到模拟器的日志（[§8](#sec-8)） |
| 持久化 | `Persistence.cs` | 从不保存任何东西：跳过 `SaveRun`、进度更新、进度文件和回放；到达地图点时做的那次存档，同时为 SL 克隆开始一个节点（[世界与 SL 克隆 §3](/arch/simulator/worlds/#sec-3)）；游戏真实的文件层及其存档迁移器一旦被调用就抛异常，只有三个无害的查询例外，它们回答“没有这个文件” |
| 规则保真 | `RuleFidelity.cs` | 放回被 TestMode 改掉的正式版规则：滚石逐个命中敌人；`ShippedBranch` 转译器在 `MerchantPotionEntry`、大锅和召唤铃铛里把 TestMode 分支换成正式版的分支，找不到剩下可换的 TestMode 检查时就抛异常；还有向商人扔恶臭药水，这条规则游戏是通过画面检查的（见下文） |
| 速度 | `Speed.cs`、`../FastHookListeners.cs` | `FastCreatures`、`FastPlayerCreatures`、`FastPlayers`：战斗的生物列表和玩家列表，游戏每个动作都要通过三个 LINQ 查询把它们重建很多次，这里改用普通循环，按相同的顺序建到同一个列表里；`FastHookListeners`：钩子分发占了模拟器的大部分时间（每个动作约 75 次分发），它不再为每次分发新建监听器列表和迭代器，而是把同样的对象按同样的顺序填进一个池化的列表，并像游戏那样在每个对象使用前再检查一次。`selftest` 在每个切点都把它和游戏自己的迭代器比较，后者通过反向补丁保持可调用 |
| 选择 | `Choices.cs` | `ChooseABundle`、`CrystalSphereScreen` 和 `CardRemovalUsed`：需要驱动程序回答其选择的画面（[整局 §4](/arch/simulator/runs/#sec-4)） |
| 游戏怪癖 | `GameQuirks.cs` | 正式版游戏同样会记下的错误，修掉它们，好让每个游戏错误都仍是真问题（[§8](#sec-8)） |

**事件转译器**。事件是游戏里表现层最重的代码：它们的方法会打开对话框、播放声音、等待动画。`EventPresentation` 转译器（`Runtime/Patches/Engine.cs:129-174`）改写每个 `EventModel` 子类的每个方法，包括其中的 lambda 和 async 状态机：对 Godot 对象的调用，或返回 Godot 对象的调用，都会被去掉并给出默认结果，`Task.Delay` 则变成一个已完成的任务。它涉及约 17 个事件类。其中六个没有它就会失败，因为它们通过空实例调用节点，或者等待一个实时的延迟：Amalgamator、DenseVegetation、DollRoom、JungleMazeAdventure、PunchOff 和 Trial。

**通过画面检查的规则**。在战斗之外，恶臭药水可以扔向商人：扔向商店的商人，得到 100 金币；扔向假商人（Fake Merchant，游戏里叫「商人？？？」），就开始一场争夺它的地毯和货架上遗物的战斗。游戏只在那个商人的画面节点存在、而且商品栏没有打开时才允许这样做（`FoulPotion.GetFoulPotionMerchantTarget`），所以无头时它从来扔不出去。`FoulPotionAtMerchants` 允许在商店里、以及在假商人事件的战斗开始之前扔它，这些画面上玩家总能扔它；扔向假商人时，`FoulPotionThrownAtTheFakeMerchant` 像游戏那样从每个玩家的事件开始那场战斗，而不需要事件的画面节点：游戏的代码先要这个节点，没有就直接返回（`Runtime/Patches/RuleFidelity.cs:89-126`）。在那场战斗里，假商人每个招式之前会说一句台词，从怪物的本地化表里抽出来，而无头时这张表没有加载：查找会抛异常，战斗的回合循环也随之终止。这句台词只用于显示，又是用只关乎外观的随机数抽的，所以 `FakeMerchantSaysNothing` 跳过它（`Runtime/Patches/Text.cs:30-39`）。

## 5. TestMode

游戏为自己的自动化测试内置了一个开关 `TestMode`。打开它之后，大部分模型代码会跳过表现层（每个这样的地方都先检查 `TestMode.IsOn`），奖励通过一个测试选择器领取而不是通过画面，还有几条规则会改变。模拟器打开它，是因为它白白去掉了大部分表现层。它改变的规则则逐条放回或处理。对整局有影响的分支：

| TestMode 分支 | 处理方式 |
|---|---|
| 奖励由 `RewardsSet` 的测试选择器领取 | 由驱动程序回答（[整局 §4](/arch/simulator/runs/#sec-4)） |
| ChooseABundle 直接选第一个包 | `ChooseABundle` 前缀改为询问策略 |
| `ActModel` 里针对第 1 幕和第一局的调整 | 无需处理：每局开始时都已全部解锁（[整局 §2](/arch/simulator/runs/#sec-2)） |
| `MerchantRoom.Exit` 提前返回，不写历史 | 只关乎外观，保持原样 |
| 滚石一次命中所有敌人 | 规则保真：拆成每个敌人各命中一次 |
| `MerchantPotionEntry` 的价格、大锅、召唤铃铛 | 规则保真：`ShippedBranch` |

## 6. JIT

.NET 通常使用*分层编译*：方法先被快速编译一遍，常运行的方法之后再在后台带完整优化重新编译（*rejit*）。一次 rejit 可能悄无声息地丢掉 Harmony 补丁，因为新代码是从原方法编译的：打了补丁的方法就会在谁也没选定的时刻以没有补丁的样子运行。在运行时间短的批次上，分层编译也更慢，因为 Harmony 的 JIT 钩子让每次额外的编译都很昂贵。

所以项目文件设了 `TieredCompilation=false`（`Sts2Ai.SimWorker.csproj:12-20`）：每个方法只编译一次，带完整优化。启动程序还应设 `DOTNET_ReadyToRun=0`，这是项目文件设不了的：这样框架自己的代码也会以完整优化编译，每秒多跑约 20% 的战斗。真实游戏开着分层编译运行，这对 Mod 的补丁是个风险（[Mod：自动游玩与安全 §5](/arch/mod/auto/#sec-5)）。

## 7. Pump：一个线程，一种顺序

游戏的逻辑是异步的：动作等待它的钩子，钩子等待一个命令，而每个 `await` 都把方法的剩余部分（它的*续体*，continuation）交给当前的 `SynchronizationContext`，也就是决定续体在哪里运行的 .NET 对象。在引擎里，那是 Godot 的主循环，一帧一帧地跑。无头时，它是 **Pump**（`Runtime/Pump.cs:10-91`）：一个安装在驱动程序线程上的单线程 `SynchronizationContext`。

- `Post(callback)` 把一个续体放进队列。此时什么都还没运行。
- `Drain()` 运行队列里的一切，包括正在运行的回调新投递的东西，直到队列清空，并返回运行了多少个。
- `RunUntil(done)` 先 drain，再检查条件；条件还不成立时，最多等 2 ms，看有没有新投递的东西，然后再试。如果条件仍不成立，而 10 s 内没有任何投递，它就抛出 `StuckException`，附上对状态的描述。

因为每个续体都在驱动程序的线程上、按投递的顺序运行，同样的调用总是以同样的顺序运行同样的代码。确定性就是从这里来的：再加上带种子的随机数流，同样的设置和同样的动作总是得到同样的状态（[战斗 §2](/arch/simulator/combat/#sec-2)）。

**稳定下来**。所谓*稳定*（settle），就是让 Pump 一直运行，直到游戏再次等待玩家：在战斗中，直到 `CombatActions.WaitingForInput` 成立（轮到玩家、处于出牌阶段、动作执行器闲置）；在战斗外，直到队列为空且动作执行器闲置（[整局 §3](/arch/simulator/runs/#sec-3)）。

**实时等待会破坏它**。如果模型代码按墙钟时间等待（`Task.Delay`），它的续体要在若干毫秒之后由一个计时器线程投递。在那之前队列是空的，执行器可能看起来闲置，稳定过程分不出“完成”和“还没”。Pump 统计 `RunUntil` 有多少次不得不阻塞、等别的线程送来工作（`IdleWaits`）；一批对局把它报告为 `pump idle waits`，它必须为 0。Amalgamator 的延迟打了补丁；其他的在无头时不会触及：`ActionExecutor.WaitForUnpause`（暂停时每 50 ms 轮询一次）、`CombatState.GodotTimerTask`（按网络 id 查找生物时的超时）以及休息处的悬停消息（UI）。

## 8. 游戏错误与日志

模拟器自己的规则是：游戏不记任何错误。一行游戏的 `Log.Error`，或一次未被观察到的任务错误，都意味着运行了不该运行的东西。启动时会收集这两者（[§2](#sec-2)），各个命令按战斗或按局报告它们，`selftest` 要求一个都没有，出现任何一个的对局都算失败（退出码 1）。工作进程把它在处理请求时看到的游戏错误放在回复里发回，宿主把它们和自己的一起计数（[工作进程池 §6](/arch/simulator/pool/#sec-6)）。

有些错误是正式版游戏自己的，游戏怪癖组把它们修掉，好让每个游戏错误都仍是真问题。这一组只有一处修复：玩家在其中死亡的出牌（打出一张 Sly 牌时，敌人的荆棘杀死了玩家）会提前返回，把这张牌留在它的选择上下文（`PlayerChoiceContext`）上；随后，发起这次出牌的钩子就记下一条错误。`PopCardAfterEarlyReturn` 把这张牌弹出，即使这张牌已经离开战斗也是如此（`Runtime/Patches/GameQuirks.cs:18-42`）。这是项目对待游戏 bug 的规则：不做校验和，也不做兜底，但破坏我们正确性的怪癖，在它进入我们代码的地方修掉（[前言 §2](/#sec-2)）。

游戏的日志行转到模拟器的日志里（`Runtime/Patches/Text.cs:43-58`）：游戏的错误和警告分别记为 Error 和 Warning，其他行记为 Debug，只有 `--verbose` 才显示。命令行怎样记日志见[参考 §2](/arch/simulator/reference/#sec-2)。
