GameBridge（`Sts2Ai.GameBridge`）是游戏与 [协议](/arch/protocol/) 之间的翻译层。它有三项工作：**observe**（把游戏对象读成观测）、**legal**（以协议文本列出合法动作）和 **start**（把一个协议动作变成 UI 会做的同一个游戏调用，并开始执行）。它运行在承载游戏的进程里：无头运行的 SimWorker，或者真实游戏中的 Mod。因为两种宿主都用它，从 R1 到 R4 的每一级跑的都是同一份代码。

<Aside title="状态">

每个决策界面的 observe、legal、start 都已实现，选牌上下文（choice context）也已实现（`src/Sts2Ai.GameBridge`）。事件流还在规划中。

</Aside>

## 1. 职责与规则

- GameBridge 是唯一把游戏对象变成协议（observe、legal）、把协议动作变成游戏调用（start）的代码。SimWorker 和 Mod 共用它，所以 R1–R4（[仿真到实机阶梯](/arch/evaluation/#sec-1)的各级）走同一条代码路径。
- 它引用游戏 DLL、Protocol 和 Harmony（游戏自带的 `0Harmony.dll`，用于 [§5](#sec-5)）。从不引用 Brain，也从不引用 Godot 节点（`N*` 类型），即游戏 UI 场景里的对象。需要节点的工作放在宿主适配器里：Mod 的 UI 适配器（[Mod §4](/arch/mod/#sec-4)），以及模拟器里复制过来的节点逻辑（[模拟器 §5.2](/arch/simulator/#sec-5.2)）。
- observe 只读取 UI 显示的内容（公平性白名单，[协议 §8](/arch/protocol/#sec-8)）。每个字段都取自 UI 绑定的那个属性（`DisplayAmount`、`IsVisible`、`ShowCounter`，意图通过 `GetSingleDamage`），从不取自内部状态。
- start 使用与 UI 相同的入口。从不直接修改状态，也从不使用跳过校验的命令（`CardCmd.AutoPlay`、直接 `new PlayCardAction`、`PlayerCmd.EndTurn`）。
- **推进到稳定（settle）**，即让游戏一直运行到下一个决策点，由各个宿主自己负责。GameBridge 只为此提供纯逻辑的判定函数（[§6](#sec-6)）。

## 2. 现有 API

`src/Sts2Ai.GameBridge` 里目前已有的内容：

| 类型 | 成员 | 说明 |
|---|---|---|
| `Observe` | `Combat(st, player)` | 手牌带 uid；抽牌堆按卡牌键排序；能力只在 `IsVisible` 时出现，数值用 `DisplayAmount`；意图取自瞄准玩家的 `NextMove` |
| | `Of(run, player, screen)`、`Run(run, player)` | 一个 `Observation`：`RunView` 加上该决策界面的画面（[§3](#sec-3)） |
| | `Card(card, withUid)`、`CardKey(card)`、`Relic`、`Coord`、`Intents(move, owner, targets)` | `Intents` 被 CombatBuilder 复用（意图匹配） |
| `CombatActions` | `WaitingForInput(player)` | 轮到玩家方、`Phase==Play`、执行器空闲、动作已启用。无头时足够，但在真实游戏里**不**够（[Mod §3](/arch/mod/#sec-3)） |
| | `Legal(st, player)` | 先按手牌顺序，再按槽位列药水，最后是 `end_turn`；每张牌调用一次 `CanPlay()` |
| | `Start(st, player, action)` | `TryManualPlay(target)` / `EnqueueManualUse(target)` / `RequestEnqueue(EndPlayerTurnAction(player, TurnNumber))` |
| | `HandCard(pcs, uid)`、`Creature(st, uid)` | 遇到未知 uid 时抛异常 |
| `MapActions`、`RewardActions`、`BundleActions`、`EventActions`、`CrystalSphereActions`、`ShopActions`、`RestActions`、`TreasureActions`、`PotionActions` | `Screen(…)` 返回该决策界面的画面；`Legal(…)` 返回动作文本；`Start(…, action)` 在动作不合法时抛异常，并在 UI 会等待某个游戏任务时返回该任务 | 每个决策界面一个静态类（`PotionActions` 只有药水栏动作，没有画面）；文法见 [协议 §3](/arch/protocol/#sec-3)；由 `ActionText` 解析 |
| `CardChoices` | `Canonical(options, min, max, context, tieBreak)` | 按卡牌键排序，平局用调用方播种的 `Random` 打破，从不用游戏顺序（它可能反映牌在牌堆中的深度）；返回 `(CardChoice, gameIndex[])` |
| `ChoiceContexts` | `Patch(harmony)`、`Current`、`Last`、`Bounds(context, minSelect, maxSelect, n)` | 选牌上下文（[§5](#sec-5)） |

<Aside type="caution" title="已知缺口">

`EndPlayerTurnAction` 这条路径不检查 `CanTurnBeEnded` <Badge text="已核实" variant="success" />。在 Mod 使用它之前，要把这项检查加进 `Legal`。

</Aside>

## 3. 观测来源

整局层面观测（[协议 §3](/arch/protocol/#sec-3)）的每个部分从哪里读取。每个决策界面的画面由它所在类的 `Screen(…)` 构建，与它的合法动作放在一起。下面每个来源都已在游戏代码中读到 <Badge text="已核实" variant="success" />。

| 部分 | 来源 |
|---|---|
| `RunView` 角色、进阶等级、幕、层数 | `player.Character`、`RunState.AscensionLevel`、`CurrentActIndex` 和 `Act.Id`、`TotalFloor` |
| 生命值、金币 | `player.Creature.CurrentHp/MaxHp`、`player.Gold` |
| 牌组 | `player.Deck.Cards` → `Observe.Card`，按卡牌键排序 |
| 遗物、药水 | `player.Relics`、`player.PotionSlots`（战斗用的映射函数） |
| 地图 | `RunState.Map` 的各个点（加上起点、Boss 点和第二个 Boss 点），带 `PointType`、`Children` 和 `Quests`；`VisitedMapCoords`；`Act.BossEncounter`、地图上的第二个 Boss、`Act.Ancient` |
| 地图画面 | 可前往的点：把 `NMapScreen.RecalculateTravelability` 的规则复制到 `MapActions` 里，写成一个纯逻辑函数 |
| 奖励 | `RewardsSet` 中 `!SuccessfullySelected` 的奖励；特殊卡牌取自奖励的 `CardHoverTip`（它的卡牌字段是私有的） |
| 卡牌奖励 | 提供的卡牌 + 替代选项（每个界面只计算一次，`CardReward.cs:321-330`） |
| 卡包（bundle） | 各组卡牌 → `Observe.Card` |
| 事件 | `EventSynchronizer.GetLocalEvent()`：id、`Description` 键、`CurrentOptions`（`TextKey`、`IsLocked`、`Relic`、悬停提示、`WillKillPlayer`） |
| 商店 | `MerchantInventory.AllEntries` 去掉移除卡牌（槽位顺序、`IsStocked`、`Cost`、`IsOnSale`），以及 `CardRemovalEntry` |
| 休息处 | `RestSiteSynchronizer.GetLocalOptions()`（`Id`、`IsEnabled`） |
| 宝箱 | `TreasureRoomRelicSynchronizer.CurrentRelics` |
| 水晶球 | 小游戏的格子：`IsHidden`、每个已揭开格子下的物品（`Item.ToSerializable().type`）、剩余占卜次数 |
| 选牌提示 | 选项 + `CardSelectorPrefs`，通过 `ChoiceContexts` 提供（[§5](#sec-5)） |

一局中的战斗使用同一个 `Observe.Combat`，放在画面里：`combat`，或者带有 `combat` 的 `card_choice`。

## 4. 各决策界面的动作

动作文法见 [协议 §3](/arch/protocol/#sec-3)。每种宿主用自己的方式执行动作：模拟器调用 GameBridge 里的逻辑入口；Mod 往往走点击时会触发的那个 UI 节点处理函数。

| 决策界面 | 逻辑入口（GameBridge，模拟器使用） | Mod 路径 |
|---|---|---|
| 战斗 | `CombatActions.Start` | 相同 |
| 丢弃药水 | `DiscardPotionGameAction` | 相同 |
| 地图 | `RequestEnqueue(VoteForMapCoordAction(…))` | `NMapScreen.OnMapPointSelectedLocally`（由节点负责锁定和动画） |
| 奖励 | `RewardsSetSynchronizer.SelectLocalReward` / `SkipLocalRewardsSet` | 奖励按钮的处理函数 |
| 离开奖励界面 | `ProceedFromTerminalRewardsScreen` / `ActChangeSynchronizer.SetLocalPlayerReady`（[模拟器 §5.2](/arch/simulator/#sec-5.2)） | 继续按钮 |
| 卡牌奖励 | 回答 `GetSelectedCardReward`（模拟器的选择器） | 卡牌槽 / 跳过 / 重抽按钮 |
| 选牌提示 | 回答 `CardSelectCmd.Selector`（模拟器） | 界面上的卡牌槽 + 确认。这条 UI 路径会记录一个 `PlayerChoice` 供重放使用。`LocalSelector` 会跳过 `SyncLocalChoice`（`CardSelectCmd.cs:264-300`） <Badge text="已核实" variant="success" />，因此会破坏 SL 重放 |
| 事件 | `ChooseLocalOption(i)` | 选项按钮 |
| 商店 | `entry.OnTryPurchaseWrapper(inv)`；移除卡牌由移除节点标记为已用（模拟器里由一个无头补丁完成，[模拟器 §5.2](/arch/simulator/#sec-5.2)） | 同一个调用（对商人节点调用 `ForceClick` 没有任何效果 <Badge text="已核实" variant="success" />） |
| 休息处 | `ChooseLocalOption(i)` | 选项按钮 |
| 宝箱 | `PickRelicLocally(i)` / `SkipRelicLocally()` | 宝箱按钮 + 遗物按钮 |
| 水晶球 | `SetTool` + `CellClicked(cell)` | 占卜按钮 + 点击格子 |
| 使用药水（战斗外） | `EnqueueManualUse(null)` | 药水弹出菜单 |

**规则**：只要 Mod 路径是一个节点处理函数，模拟器路径就必须等于该处理函数所做的调用，去掉纯 UI 的效果。每一对这样的路径都有一个 R3 对 R4 的等价性检查：相同种子、相同决策，必须得到相同的观测流（[Mod §8](/arch/mod/#sec-8)）。

## 5. 选牌上下文

GameBridge 如何填写 `ChoiceContext`（[协议 §4](/arch/protocol/#sec-4)）。每个选牌提示都经过某个 `CardSelectCmd.From*` 入口，而只有这些入口的参数能说明游戏为什么要问。所以 `ChoiceContexts` 用 Harmony 给它们打补丁。Harmony 是一个在运行时给游戏方法打补丁的库：**前缀**（prefix）在原方法之前运行，**终结器**（finalizer）在原方法之后运行，即使原方法抛了异常也会运行。

- 目标是除 `FromChooseABundleScreen` 以外的每个公开静态 `CardSelectCmd.From*` 方法；`FromChooseABundleScreen` 有自己的决策界面（`Commands/CardSelectCmd.cs`） <Badge text="已核实" variant="success" />。目标列表用反射计算，所以新增的入口会被自动纳入；但每次游戏更新时，仍要核对它们的参数。
- 前缀把入口的参数读进 `Current`：`CardSelectorPrefs`、`source` 参数或 `PlayerChoiceContext` 的 `LastInvolvedModel`、一个 `CardPile`、一个 `EnchantmentModel` 及其 `amount`、`canSkip`。终结器把它清掉。
- 一个深度计数器让最外层的入口生效（移除卡牌会调用 `FromDeckGeneric`）。`Current` 和计数器是 `[ThreadStatic]`。
- `Current` 必须在入口内部同步读取，选择器的调用就是这样做的：入口第一次 await 返回之后，它就没了。真实游戏里选牌提示的屏幕在这之后才打开，所以前缀还把上下文存进 `Last`，一直保留到下一个入口。Mod 从那里读取屏幕上那个提示的上下文（[Mod §3](/arch/mod/#sec-3)）。
- 每个宿主在**任何其他补丁之前**调用一次 `ChoiceContexts.Patch(harmony)`（SimWorker：`HeadlessPatches.Apply`）。更早编译的调用方（例如另一个补丁在编译它的替换方法时）可能把入口那个很小的 async 存根内联进去，从而绕过前缀。无头运行时 SapphireSeed 就发生过这种情况。在模拟器里，没有上下文的选牌提示会抛异常。

两种宿主共用这个补丁，所以得到的上下文相同。

## 6. 决策点判定

当前悬而未决的是哪个界面，由宿主判断。这取决于 UI 会显示什么，而只有宿主在跟踪这件事。

- **模拟器**：`RunSession.Decide`（[模拟器 §5](/arch/simulator/#sec-5)）先看打开着的奖励组（来自 `testSelector`）和水晶球小游戏，再看房间类型和每种房间的 `RoomProgress`。推进到稳定的条件是：战斗中为 `WaitingForInput`；否则是 Pump 已空且执行器空闲。
- **Mod**：可见的界面或覆盖层，加上节点空闲检查，并且要持续约 3 帧（[Mod §3](/arch/mod/#sec-3)）。

GameBridge 只保留纯逻辑的判定：`CombatActions.WaitingForInput`、`RewardActions.IsTerminal`，以及各个合法动作列表。

## 7. uid 与索引

动作如何指代它作用的对象：

| 对象 | 指代方式 |
|---|---|
| 手牌（仅战斗中） | 它的 `NetCombatCardDb` id |
| 生物（仅战斗中） | 它的 `CombatId` |
| 牌组或网格提示里的选项 | 规范索引（`CardChoices.Canonical`），从不用 uid：战斗外没有 uid |
| 按 UI 排序的列表中的条目（奖励、事件选项、商店槽位、休息处选项、宝箱遗物） | 游戏里的索引（顺序是公开的） |
| 地图点 | `col,row` |

对 Mod 而言：SL 克隆必须给出相同的编号，所以加载时要把 id 快进（[模拟器 §7](/arch/simulator/#sec-7)）。

## 9. 版本适配

所有关于游戏 API 的知识只放在三个地方：这里、SimWorker 的补丁，以及 Mod 的节点适配器。游戏更新时：

<Steps>

1. 重新反编译游戏。
2. 重新构建。
3. 运行 selftest 和决策界面覆盖测试（[模拟器 §9](/arch/simulator/#sec-9)）。
4. 生成受影响签名的差异列表。

</Steps>

## 10. 测试

- **白名单**：一张逐字段的「UI 显示它」表格，每新增一个字段都要评审。
- **合法动作完整性**（Mod 调试模式）：每个启用的 UI 控件都对应一个合法动作。
- **start 往返**：每个合法动作都能无异常地执行，并改变 `obs_hash`（或结束这个决策界面）。
- **模拟器与 Mod 一致**：相同状态给出相同观测（R3 与 R4 的日志对比）。
