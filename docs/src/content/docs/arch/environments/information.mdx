[总览页](/arch/environments/)用一句话说了每种环境能知道什么。本页把它说精确：NoSL 据以决策的公开历史、SL 在节点内额外得到的东西、一张每类信息占一行的表、对灰色情形的裁定，以及节点的界线落在哪里。最后讲 SL 克隆是怎么做出来的，以及守住每条规则的测试。

## 1. NoSL：公开历史

NoSL 的一个决策只能依赖

- 这一局的**公开历史**：到目前为止屏幕上显示过的一切，以及能从中推断出的东西；
- 规则知识：卡牌、遗物、怪物和游戏的概率如何运作；
- 离线学到的任何东西，比如 V 的权重。

「能从中推断出的东西」不是漏洞；好玩家的本事正体现在这里。三个公平推断的例子：

- **记牌**。抽牌堆的内容是可见的（游戏会列出来），顺序不可见。洗牌之后，每抽到一张牌，都在告诉玩家还剩哪些牌要来。
- **怪物接下来的行动**。怪物只显示一个意图。很多怪物遵循固定模式（同一个行动从不连续用三次、固定的循环），所以它的意图历史给出了它在那之后会做什么的一个概率分布。
- **奖励概率**。有些概率随历史变化。游戏为奖励掷出的每一张非稀有卡牌，都会让下一次掷出稀有卡的概率提高一个百分点（在「稀缺」进阶下是半个百分点），最多比基础值高 40 个百分点，掷出一张稀有卡则重置（`Odds/CardRarityOdds.cs:69-78`） <Badge text="已核实" variant="success" />。一场战斗掉落药水的概率，在掉落一次之后下降 10 个百分点，没有掉落则上升 10 个百分点（`Odds/PotionRewardOdds.cs:56-70`）。数一数看到过的奖励，就能得出这些概率。

NoSL 中的搜索在**确定化样本**上进行：具体的隐藏状态（一个抽牌顺序、怪物的行动、随机数流的状态），抽取时保证每一个都与公开历史一致。搜索可以在这样的样本上随意尝试各种打法，因为样本是猜测，不是真相（[世界与两种战斗算法 §2](/arch/environments/worlds/#sec-2)）。

## 2. SL：在节点内存档与读档

SL 等于 NoSL 加上**当前节点内任意动作序列的真实结果**。项目把这叫作「有限作弊」。这相当于一个玩家可以在节点内任意多次地存档退出，并且记得自己看到的一切。

SL 可以知道的东西，附例子：

- 抽牌顺序和每一次重新洗牌；怪物的行动；随机生成的卡牌、随机目标、随机费用和充能球；
- 动作的顺序如何改变上面这些。在节点内操纵随机数流是允许的：如果先打 A 牌再打 B 牌会让一次随机攻击落到另一个敌人身上，SL 可以知道这一点并加以利用。
- 事件结果。比如在滑脚木桥上，SL 知道每次 HOLD_ON 之后会被拿走哪张牌：`SlipperyBridge.GetNewRandomCard` 从事件自己的 `Rng` 里抽取，这个 `Rng` 的种子由本局的种子、玩家的槽位编号（单人局为 0）和事件 id 的哈希得到（`Models/EventModel.cs:234`） <Badge text="已核实" variant="success" />；
- 本节点的奖励，包括它们会如何随节点的打法而变化；
- 先古之民的「随机稀有卡」选项给的是哪张牌。

SL **不能**知道的：关于后面节点的任何东西。一个 `?` 点会变成什么、后面的战斗会出现哪些怪物、后面的奖励、后面商店的货品、后面的事件。即使运行 SL 搜索的模拟器握有所有这些的真实随机数流，这一点依然成立：克隆在节点出口处停下（[§3](#sec-3)），想看得更远的搜索必须像 NoSL 一样，使用由搜索自己播种的确定化样本。

<Aside type="caution" title="已否决">

曾考虑过整局视野（「知道这一局的全部顺序」），已否决。不要实现它。

</Aside>

## 3. 节点

**节点**是一个地图点（`MapPoint`），从玩家抵达它的那一刻起，到玩家在地图上选定下一个点的那一刻为止。它包括在这个点上发生的一切：

- 它的每一个房间（`MapPointHistoryEntry.Rooms`）：一个引发战斗的事件有两个房间，事件和战斗；
- 战斗之后的奖励画面、商店里的购买、休息处的选项、宝箱房的宝箱、事件的每一页。

边界，精确地说：

- **入口**：抵达一个地图点。游戏在这里给这一局存档，在它掷出 `?` 变成什么之前、在它构建房间之前，所以入口状态是一个完整的存档（`SerializableRun`）。在模拟器里，游戏的 `SaveRun` 被打了补丁，从不写盘；抵达时的那次存档，也就是没有已完成房间的那次，开始一个节点（`Runtime/Patches/Persistence.cs:13-22`），而战斗胜利后和先古之民事件后的存档带着一个房间，从不开始节点。
- **出口**：地图移动动作（`VoteForMapCoordAction`）。移动本身属于当前节点；它之后的一切属于下一个节点。
- **特殊情况**：这一局的第一个点，也就是先古之民涅奥等候的地方，是第一个节点；代码从 0 开始给节点编号，所以它是节点 0（`Protocol/Wire.cs:79-81`）。打完 Boss 后，下一幕的第一个点是一个新节点。一局的结束也是一个出口。

会越过出口的搜索，比如想问一张牌在下一场战斗里值多少，只能使用由搜索播种的确定化样本，绝不能用真实的随机数流。如今没有搜索这样做。克隆强制守住这条线：一旦记录了移动，它就停下并拒绝再走任何一步（`Simulation/RunSession.cs:235`），一次会移动的宏观试探会抛出异常（`Checks/NodeProbe.cs:29`），而 L0 给地图移动估值时，是根据画面预测它的后状态，而不是把它打出来（[宏观大脑：搜索 §2](/arch/macro-brain/search/#sec-2)）。

## 4. 为什么以节点为界，而不是游戏自己的存档

游戏已经有存档点，退出再继续的玩家会回到最近的一个。为什么不把它们用作 SL 的边界？下面是游戏自动存档的时刻 <Badge text="已核实" variant="success" />：

- 抵达一个地图点时，在 `?` 掷骰之前、在 `CreateRoom` 之前（`Runs/RunManager.cs:899-901`、915、917）。这包括一局的第一个点：单人对局没有单独的开局存档，`EnterAct` 带着一次存档进入涅奥所在的点（`Runs/RunManager.cs:1356-1362`、843）；不以先古之民开场的一幕从一个地图房间开始，没有这次存档（1365-1368）；
- 战斗胜利时，房间被标记为预先完成（`Combat/CombatManager.cs:1341-1342`）；
- **先古之民**事件结束时，而且只有先古之民事件会这样（`Rooms/EventRoom.cs:129-141`）。

战斗中途没有存档。重新载入会原样重演这个房间（相同的遭遇、相同的起手牌、相同的怪物行动），因为存档保存了每条随机数流的完整状态 `{counter, s0..s3}`（`Saves/SerializableRng.cs:8-21`）：这一局的十二条和玩家的三条（`Saves.Runs/SerializableRunRngSet.cs:14-15`、`Saves/SerializablePlayerRngSet.cs:14-15`）；事件自己的 `Rng` 和各幕地图的 `Rng`，在需要时会再从种子派生出来（`Models/EventModel.cs:234`、`Map/StandardActMap.cs:113`）。

所以游戏原生的存档与读档比节点稍窄一些。战斗胜利之后，存档已经越过了这场战斗，所以玩家在真实游戏里没法测试另一种打法会不会改变奖励。尽管如此，还是选了节点边界，原因有二：它覆盖一个地图点上发生的一切（所有房间、奖励、事件的每一页），并且给出了单独一个点，即移动，在那里封存世界。战斗后的奖励是否应该遵循游戏更窄的规则，是未决问题 1（[§9](#sec-9)）。

## 5. 信息表

每种环境能用什么，每类信息一行。「本节点」指当前节点；「后续节点」指它之后的所有节点。

| 信息 | NoSL | SL |
|---|---|---|
| 屏幕的历史及从中得出的推断；规则知识；离线学到的任何东西（隐藏状态只作为训练时的特权信息） | 可以 | 可以 |
| 本节点：抽牌顺序和洗牌 | 只知道有哪些牌（一个多重集） | 可以 |
| 本节点：怪物的下一步行动 | 显示的意图，以及根据其历史得出的后验 | 可以 |
| 本节点：生成的卡牌、随机目标、费用、充能球 | 它们的分布 | 可以 |
| 本节点：事件结果、宝箱、奖励 | 显示之后 | 可以 |
| 后续节点 | 不可以 | 不可以 |
| 直接读取种子字符串、随机数状态或存档文件 | 不可以 | 不可以（只能通过封存的克隆） |
| 修改状态、控制台、调试或多人模式后门 | 不可以 | 不可以 |
| 真实读档（`NumReloads > 0`）、评估时挑种子 | 不可以 | 不可以 |

如何读这些行：

- **特权信息**是只在训练时使用的隐藏状态，用来让学习目标的噪声更小；它从不是部署模型的输入（[学习 §4](/arch/learning/#sec-4)）。
- **多重集**是计入重复的集合：「三张打击、两张防御和一张中和」，没有顺序。观测发送的抽牌堆按一个只取决于玩家所见内容的卡牌键排序，所以它的顺序不携带任何信息（[协议：观测与动作 §4](/arch/protocol/observation/#sec-4)）。
- **后验**是根据已看到的东西更新过的概率分布。如今 NoSL 的世界在显示相同意图的行动中均匀抽取怪物的行动，并从它的意图记录中取得它之前行动的顺序（[模拟器：战斗 §5](/arch/simulator/combat/#sec-5)）；完整的后验在规划中（[Harness §4](/arch/harness/#sec-4)）。
- **种子字符串**从不离开宿主：对局以它的哈希命名（[协议：线路 §3](/arch/protocol/wire/#sec-3)），观测里也没有它的字段。
- **挑种子**指看到结果之后再选择报告哪些种子；评估的种子集是固定的，在使用前就登记好（[评估 §4](/arch/evaluation/#sec-4)）。

## 6. 灰色地带

对表格没有解决的情形的裁定，两种环境相同。它们来自公平游玩规范，一份本地笔记（`tmp/notes/fair-play-spec.md`），由观测白名单（[协议](/arch/protocol/)）实现：

- 允许精确的伤害计算：游戏显示了这些数字，用它们来计算正是细心的玩家会做的事；
- 能力只在游戏显示时才提供（`IsVisible`），带上图标上的数值；能力自身的层数，只在它的提示文字把层数与图标分开写明时才提供；还有能力保存的那张牌，它的提示文字会写出这张牌（`GameBridge/Observe.cs:180-182`）；
- 不导出怪物的行动 id（`move_id`）：意图就是玩家看到的东西；
- 抽牌堆只作为多重集，从不提供它的顺序；
- 水晶球事件（`CRYSTAL_SPHERE`，一个小游戏）里隐藏的格子只以隐藏状态（`#`）导出；只有被揭开的格子才显示下面是什么（`GameBridge/Actions/CrystalSphereActions.cs:24-25`）。

## 7. SL 克隆从哪来

SL 搜索需要节点在抵达时的样子，加上此后在节点里做过的一切。两者都来自**宿主**：持有真实对局的那一方，自我对弈中是模拟器，真实游戏中是 Mod。

- **在模拟器里**（[仿真到实机阶梯](/arch/evaluation/#sec-1)的 R1–R3 级，由模拟器来打这一局）：承载这一局的工作进程持有真实状态。游戏在抵达一个地图点时存档，此时它取一个**检查点**：`RunManager.ToSave(null)` 产生的存档（`Runs/RunManager.cs:670-709`） <Badge text="已核实" variant="success" />，无头宿主把它留在内存里而不写盘，再加上存档会丢掉的每个遗物的简单字段（见下文）。克隆就是这个检查点加上节点轨迹（抵达以来的每一个决策），像游戏的「继续」按钮载入存档那样载入，然后重放（[模拟器：世界与 SL 克隆 §4](/arch/simulator/worlds/#sec-4)）。
- **在真实游戏里**（R4）：Mod 在同一时刻、用同样的 GameBridge 代码（`Checkpoint.Take`）在内存里取同样的检查点。它从不碰 Steam 会同步到云端的 `current_run.save`。它还在游戏提交每个动作的地方记录节点的每个动作，并在每个决策之前把两者发给大脑（[Mod：SL 记录](/arch/mod/sl-record/)）。工作进程通过同一条「继续」路径载入它们，再重放这些动作。
- **在线路上**，它们以两条只用于 SL 的消息传输：节点入口处的 `node_checkpoint`，以及节点内每个决策的 `node_action`（[协议：线路 §6](/arch/protocol/wire/#sec-6)）。Harness 保存最新的检查点和此后的决策，并把它们作为克隆交给大脑（[Harness §4](/arch/harness/#sec-4)）。

**载入的存档与不间断的游玩并不相同**。载入存档会重新执行地图的钩子（`Runs/RunManager.cs:815-816`）和 `OnRunLoaded`（562-565），并丢掉每个没有标记为保存的遗物字段：遗物只保存它的 `[SavedProperty]` 成员（`Models/RelicModel.cs:556-576`）。这些遗物字段确实有影响：存档丢掉的遗物状态或计数改变了克隆的每个观测，克隆于是不再和真实战斗一致，SL 规划器每一步都要重新规划（[模拟器：世界与 SL 克隆 §6](/arch/simulator/worlds/#sec-6)）。所以检查点带上每个遗物的简单字段（数字、标志和枚举），在载入之后放回去，`run --check` 现在找不到任何克隆与其对局不同的节点。不做校验和，也不做兜底：破坏我们正确性的游戏怪癖，在它进入我们代码的地方修掉（[前言 §2](/#sec-2)，规则 7）。

**NoSL 关闭这个通道**。两种宿主在两种环境下都会取检查点并保存节点的步骤（`Simulation/RunSession.cs:143-148`；在 Mod 里是 `NodeRecord`），这样在一个房间中途切换到 SL 也能工作；只有 SL 对局会把它们发出去（`Brains/RunBrains.cs:48-100`，Mod 的 `Assist.cs:159`）。NoSL 大脑会拒绝它们：Harness 在 NoSL 下收到节点消息就抛出异常，大脑服务器用一个错误回应这一局的下一个决策，宿主把这一局作为失败结束，这会使它的报告作废（[环境 §5](/arch/environments/#sec-5)）。

**决策进程从不读存档**。Brain 不引用游戏的程序集，这由编译器强制保证，并有一个测试检查（[§8](#sec-8)）。存档只会装在一个 SL 请求里、作为一个不透明的字符串到达工作进程。

## 8. 守护测试

上面每条规则都有，或将会有，一个守住它的测试。「已有」写明它如今在哪里运行。

**两种环境**

1. Brain 和 Protocol 不引用任何游戏程序集。已有：`selftest`（以 GameBridge 作为反面对照）和 xUnit 的 `BoundaryTests`，后者也覆盖 Harness（[模拟器：参考 §5](/arch/simulator/reference/#sec-5)）。
2. 搜索的随机性只来自调用方，绝不来自游戏的随机数流。由构造保证，没有测试：大脑的种子由对局 id（它本身是种子字符串的哈希）和决策的序号混合而成（`Harness/Dispatcher.cs:208-227`），世界的构建种子和采样种子都来自它（[Harness：路由、预算与种子 §5](/arch/harness/routing/#sec-5)）。
3. 兜底决策的数量为 0。实际上已有：没有兜底代码，Harness 遇到未覆盖的画面（surface）就抛出异常（xUnit `DispatcherTests`），由随机占位策略做出的决策会使报告作废（`Harness/Reports.cs:35-38`，xUnit `EvalReportTests`；[评估 §3](/arch/evaluation/#sec-3)）。
4. 真实游戏里 `NumReloads == 0`。规划中，作为 Mod 决策日志的一个字段（[Mod：自动游玩与安全 §3](/arch/mod/auto/#sec-3)）；如今没有东西读它。克隆会载入存档，所以无论在哪里载入（工作进程，以及 `run --check`、`selftest` 和 `clones` 中的宿主进程），它们的计数都是 1 或更多。
5. 观测的每个字段都有白名单测试。规划中；如今最接近的检查，是 `run --check` 和 `selftest` 里对每个观测做的 JSON 往返（[协议 §3](/arch/protocol/#sec-3)）。

**NoSL**

6. 反事实：同样的公开记录配上不同的隐藏状态（抽牌顺序、每条随机数流、怪物的行动及其 AI 私有字段、生成池），在固定的大脑种子下给出同样的决策。规划中；最接近的检查是 `selftest` 的「确定化保持观测不变」。
7. 往返：状态 → 观测 → 构建 → 观测′，得到完全相同的观测。战斗部分已有：`selftest` 根据观测构建战斗，并要求它们再次显示出这个观测（[模拟器：战斗 §6](/arch/simulator/combat/#sec-6)），而每个 NoSL 世界都会拒绝做不到这一点的构建（`Simulation/SimWorlds.cs:34-44`，在工作进程里也是如此）。

**SL**
