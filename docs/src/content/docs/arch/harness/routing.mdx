一局的 `Dispatcher` 持有四个路由，路由表的每一侧一个，每个都是一个大脑，带着它在日志里使用的名字。本页讲这些路由、它们能花多少、它们的随机性从哪里来，以及其中一个出故障时会怎样。

## 1. 路由表

每个决策都恰好交给一侧：

| 决策界面 | 一侧 | 大脑 |
|---|---|---|
| `combat` | 战斗 | `plan`（SL 规划器，仅 SL）、`pimc`（仅 NoSL），或占位策略 `play` |
| 战斗中提出的 `card_choice`（`ChoiceContext.InCombat`） | 战斗提示 | 战斗大脑上一个动作带着的答案，如果有的话；否则是 `first`，即最前面的选项（[战斗大脑：提示、招式与 worker §1](/arch/combat-brain/shared/#sec-1)） |
| 战斗外提出的 `card_choice`（升级、变化、附魔、移除……） | 宏观提示 | L0，即宏观大脑本身，或 `random` |
| `map`、`rewards`、`card_reward`、`bundle`、`event`、`shop`、`rest`、`treasure`、`crystal_sphere` | 宏观 | L0（[宏观大脑](/arch/macro-brain/)），或 `random` |

药水栏没有自己的决策界面：它的动作是每个宏观画面合法动作列表的一部分（[GameBridge：各决策界面的动作 §6](/arch/gamebridge/actions/#sec-6)）。表外的决策界面会抛出「uncovered surface」（未覆盖的决策界面，[§6](#sec-6)）。

**冠军的名字**。一局的各个大脑合起来就是它的冠军，名字由 `Dispatcher.Champion` 给出：

```text
combat plan COMBAT beam 8x300 easy 4 loss plans 3, combat prompts first, macro l0 VALUE clone, macro prompts l0 VALUE clone
```

这是这份代码命名的 SL 冠军，其中 `COMBAT` 和 `VALUE` 代表冠军的战斗网络和 V 的名字（[评估：冠军与基线](/arch/evaluation/champions/)）：叶子里用这个战斗网络（它的结局由 V 定价）、用 medium 预算的 SL 规划器；战斗中没有搜索回答的提示用 `first`；宏观决策和战斗外的选牌提示用 L0，它带着 V，在节点的克隆上把每个选项打一遍。每个大脑都说出自己的组成部分：搜索的战斗大脑说出它的战斗网络；L0 说出它的 V、`clone`，以及它的探索（均匀抽取为 `eps ε`）；预算按 [§4](#sec-4) 的写法。SimWorker 的 `ChampionOptions` 根据命令的选项做出各个路由，如果它做出的名字不是冠军文件使用的那个，就拒绝运行（`Brains/ChampionOptions.cs:38-63`）。

**环境决定战斗大脑**。宏观大脑在两种环境里是同一个；战斗大脑则不是（[环境：世界 §5](/arch/environments/worlds/#sec-5)）。冠军工厂在 SL 之外拒绝 `plan` 和 `--afterstates clone`，在 NoSL 之外拒绝 `pimc`，在 SL 下还拒绝不在节点的克隆上打的 L0，因为它从画面预测的后状态是 NoSL 的。`run` 按给定的选项打，所以带 L0 的 SL 对局要用 `--afterstates clone`。`brain` 命令同时服务两种环境：NoSL 宿主得到 `--policy` 的战斗大脑，SL 宿主得到 `--sl-policy` 的，而且它按宿主的环境设定 L0 的后状态，NoSL 宿主从画面预测，SL 宿主在节点的克隆上打，所以一个冠军文件就能服务两者（[概览 §5](/arch/harness/#sec-5)）。

## 2. 战斗路由

战斗路由是一个 `CombatRoute(Brain, Decide, Budget)`：它的名字；一个从（决策、种子、节点的克隆或 null、这场战斗至今的出招）到 `CombatDecisionResult` 的函数；以及它的预算，用于日志和名字。

**占位策略**。`CombatRoute.Of(name, policy)` 包装一个不搜索的策略（`play`）：它给出自己的选择，没有计划，也没有候选。

**池里的 PIMC**（`PooledPimc.Route`，[NoSL PIMC](/arch/pimc/)），仅在 NoSL 下。只有一个合法动作时，它立即回答。否则：

- **各个世界**：每个世界一个 `pimc_world` 请求，每个世界都在它的工作进程里由观测、敌人出招记录和构建种子重建，所以真实状态的任何东西都不会离开宿主。每个世界的节点平均分给各个首个动作。种子相同时，它给出的回答和在一个进程里对各世界做的 PIMC 相同，`selftest` 检查这一点。
- **沿用循环**：路由为这一局保留一个 `TurnPlan`，它只保留重复一个循环、并且每个世界都规划得一样的计划，因为每次重复之前都再搜一遍只会重新找到同一个循环（[NoSL PIMC：搜索 §6](/arch/pimc/search/#sec-6)）。只要战斗显示的是计划在这一步之前预期的观测，计划的这一步就不经搜索直接打出；否则这个决策重新搜索，并标为重新规划。

**池里的 SL 规划器**（`PooledPlanner.Route`，[SL 规划器](/arch/sl-planner/)）。每局一个 `SlRoute`，把战斗剩下的部分规划一次，然后沿用这个计划，只在某一步对不上或计划用完时才重新规划（[SL 规划器 §4](/arch/sl-planner/#sec-4)）。一个计划就是 `SlPlanner.Search`，束的每个回合按保留的每个状态发一个 `sl_turn` 请求，用路由的预算。没有节点克隆时这个路由会抛异常（它只在 SL 下打）。

**两样持续整局的东西**。`TurnPlan` 和 `SlRoute` 每局只做一次，从不清空，战斗结束时不清，宏观决策时也不清；规划器对连续未证明的失败计划的计数跨决策延续（[SL 规划器：束搜索 §6](/arch/sl-planner/beam/#sec-6)）。

## 3. 宏观路由与提示路由

宏观路由或提示路由是一个 `Route<T>(Brain, Policy)`。目前：

- **L0**（`MacroBrain`，`--macro l0`）既回答宏观决策，也回答战斗外的选牌提示，作为一个带一个 V 的对象（[宏观大脑：搜索](/arch/macro-brain/search/)）。它的探索（`--explore ε`，均匀抽取，以及 `--macro-explore τ`，在 V 的估值的对数上做 softmax；仅自我对弈）从它自己的几个生成器里取随机数（[§5](#sec-5)）。
- **`first`**（`FirstPicks`）回答战斗大脑的动作没有回答的战斗中选牌提示：按规范顺序取最前面的选项，取提示允许的最少个数，和搜索世界里的做法一样。动作带着的答案交给它之后的第一个战斗中提示（`Dispatcher`），不接受这个答案的提示也交给 `first`（[战斗大脑：提示、招式与 worker §1](/arch/combat-brain/shared/#sec-1)）。
- **`random`** 占位策略在 `--macro random` 时回答宏观的两侧。

**给宏观一侧的节点克隆**。在 SL 下用 `--afterstates clone` 时，`Dispatcher` 在每个宏观决策和每个战斗外的选牌提示处打开节点的克隆，作为这一局工作进程池上的一个 `PooledClone`（`MacroDecision.With`、`ChoiceDecision.With`）。L0 再向它要后状态：每条答案路径之后游戏接着问什么。`PooledClone` 把路径分成 min(paths, workers) 个连续的 `sl_macro` 请求，每个工作进程为每条路径加载一次克隆，并检查每条路径都得到了一个后状态；因为后状态只取决于克隆和路径，所以怎么分都改变不了结果（[宏观大脑：搜索 §6](/arch/macro-brain/search/#sec-6)）。

**计划**。宏观回答检查过之后，`Dispatcher` 问策略在它之后有什么计划（`IMacroPolicy.Plan`）：L0 的计划在地图上是本幕剩下的路线，在别处为空。它的用时不计入这个决策的 `elapsed_ms`。

**打过分的选项**。接着它取策略从中做选择的那些选项及其估值（`Scored`）：L0 的是每个合法选项，各带 V 给出的、选它之后赢下这一局的概率，选中的在前，其余从好到差；回答是探索抽出来的时就没有（[宏观大脑：搜索 §1](/arch/macro-brain/search/#sec-1)）。战斗外的选牌提示给出 L0 权衡过的那些回答。它们成为推荐的候选，对显示答案的宿主，每个地图选项还带上它的路线（[概览 §5](/arch/harness/#sec-5)）；决策日志不保存它们。

**探索标记**。当策略说它上一个回答是抽取出来的时，提示或宏观回答就标为探索：对 L0 来说，就是它的均匀抽取，或它的 softmax 抽出了低于最优的回答（[决策日志 §6](/arch/harness/decision-log/#sec-6)）。

## 4. 预算

一次战斗搜索能花多少，由一个 `Budget` 规定（`Brain/Combat/CombatBrain.cs:17-48`）。它的单位是**节点**：在一个世界里模拟的一个动作。没有墙钟预算，也没有别的单位。

| 字段（JSON） | 默认 | 含义 |
|---|---|---|
| `worlds` | 8 | PIMC 每个决策的世界数；规划器只有一个世界，忽略它 |
| `nodes_per_world` | 300 | PIMC：每个世界里搜索本回合时模拟的动作数。规划器：从一个状态出发、搜索一个回合时，每次搜索模拟的动作数 |
| `beam` | 0 | 规划器从一个回合到下一个回合保留的状态数；0 表示 PIMC |
| `replan` | 1 | 规划器在重新规划之前，把未证明的失败计划打几个回合；0 表示打到结束 |
| `loss_plans` | 0 | 在一场战斗里，规划器连续做出未证明的失败计划的最大数目，达到后最后一个打到结束；0 表示不限 |
| `easy_beam` | 0 | 贪心下潜已经能赢时规划器的束宽；0 表示用 `beam` |
| `elite`、`boss` | null | 精英战和 Boss 战自己的预算，在它与这个预算不同时才有（`--elite-effort`、`--boss-effort`）；`Budget.For(room)` 给一场战斗它所在房间的预算 |

**力度等级**（`--effort`、`Budget.Effort`，[SL 规划器：预算 §1](/arch/sl-planner/budget/#sec-1)）：

| 等级 | 束 | 节点 | 简易束 | 失败计划 |
|---|---|---|---|---|
| `low` | 8 | 300 | 2 | 3 |
| `medium` | 8 | 300 | 4 | 3 |
| `high` | 8 | 300 | – | – |
| `max` | 16 | 300 | – | – |

**作为名字**（`Budget.ToString`）：PIMC 是 `8x300`（规划器是 `beam 16x300`），然后是规划器的 `easy N`、不为 1 时的 `replan N`，和有限制时的 `loss plans N`；然后是 `elite (…)` 和 `boss (…)`，即按同样的规则写出的各房间的预算，在它有自己的预算时才有。

**规划中：按模式的预算** <Badge text="规划中" variant="caution" />。目前每种模式都用固定的节点预算。设计给每种模式各自的单位：

| 模式 | 单位 | 原因 |
|---|---|---|
| 自我对弈、评估 | 固定的节点数 | 可复现：相同的请求、种子和预算给出相同的推荐 |
| 辅助 | 墙钟时间，随时可停 | 有人在等：先发出目前最好的答案，再逐步改进 |
| 自动游玩（R4） | 墙钟时间上限和最少节点数 | 既不卡住，也不搜得太浅 |

「随时可停」（anytime）是指搜索在任何时刻被停下，都仍有一个最好的答案可以给出。一种规划中的分配方式，会在排名前两位的候选之差超出它们的置信区间时停下，否则增加样本或深度。已实现的则是：固定的节点数，平均分给各个首个动作，以及沿用计划（[NoSL PIMC：预算 §1](/arch/pimc/budget/#sec-1)）。

## 5. 种子与确定性

一个决策的搜索，每次被问同样的东西时都必须给出同样的回答，所以它的随机性来自 Harness，从不来自游戏的随机数流，也从不来自时钟。

**run id** 是这一局种子作为 JSON 字符串（含引号）的 FNV-1a 64 位哈希，写成十六进制：种子 `0SSL7NS01MU6` 得到 run `ce13ba5116b7f48a`。大脑看到的是 run id，从来不是种子（[协议：线路 §3](/arch/protocol/wire/#sec-3)）。

**一个决策的种子**由 run id 和决策的序号抽取；序号从 0 开始计这一局的每个决策，战斗决策、选牌提示和宏观决策都一样（`Dispatcher.cs:197-216`）：

```text
H        = FNV-1a 64 of the JSON string run_id
z        = H + 0x9E3779B97F4A7C15 · (i + 1)          (mod 2^64)
z        = (z xor (z >> 30)) · 0xBF58476D1CE4E5B9
z        = (z xor (z >> 27)) · 0x94D049BB133111EB
seed(i)  = z xor (z >> 31)
```

这就是 SplitMix64 的一步。决策的序号是 Harness 自己的计数器，不是线路上的 `decision_id`。按规划，等大脑有了版本，冠军的版本也会加入哈希。

**谁读它**。每个决策的日志行都记下它的种子，但只有 NoSL PIMC 用它：

- **构建种子**是这个种子的大写十六进制形式（`X16`）；工作进程用一个以它的哈希为种子的生成器，重新采样观测没有确定的东西（[模拟器：战斗 §5](/arch/simulator/combat/#sec-5)）；
- 第 k 个世界用 `"{seed}:{k}"` 的哈希确定化（[模拟器：战斗 §3](/arch/simulator/combat/#sec-3)）。

SL 规划器搜索唯一的精确世界，忽略它；宏观策略和提示策略从不收到它。

**占位策略和探索**从按局播种的 .NET 生成器里取随机数，每个流一个：`Random(FNV(run_id + stream))`，占位策略的流是 `""`，L0 的均匀抽取是 `:explore uniform`，它的 softmax 是 `:explore`（`Brains/ChampionOptions.cs:46-56`）。所以一局在任何进程里、通过线路时都打得一样，不管是否记日志。

**看顺序，不看时序**。一次搜索的各个请求并行运行，但池按请求的顺序返回它们的回复（[模拟器：工作进程池 §2](/arch/simulator/pool/#sec-2)），候选按值排序，平手时保持合法动作的顺序（结束回合，然后是牌，然后是药水）。哪个工作进程先完成，从来改变不了回答。`run --check` 让整局都遵守这一点（[决策日志 §8](/arch/harness/decision-log/#sec-8)）。

## 6. 故障

没有兜底：不能按规定回答的决策就失败，这一局也随之失败。从不随机作答来顶替它。

**在 `Dispatcher` 里**（`Dispatcher.cs`）：

| 情况 | 结果 |
|---|---|
| 战斗大脑的选择不合法 | `InvalidOperationException` |
| 提示不接受的提示回答（数量、范围、重复的下标） | `InvalidOperationException` |
| 没有路由的宏观决策界面 | 「uncovered surface」；这个决策的序号和它的大脑的计数已经用掉了 |
| 不合法的宏观回答 | `InvalidOperationException` |
| 在任何检查点之前、需要克隆的 SL 决策 | `InvalidOperationException` |
| NoSL 下的节点检查点或节点动作 | `InvalidOperationException` |
| 节点下标没有递增的检查点；属于另一个节点或顺序不对的动作 | `InvalidDataException` |

**在线路上**（`BrainServer`）：被拒绝的 `hello`（冠军工厂抛了异常：未知的环境、SL 之外的 `plan` 或 `--afterstates clone`、NoSL 之外的 `pimc`、SL 下不在节点克隆上打的 L0、对不上的冠军名字）、对局之外或被拒绝的节点消息之后的决策、没有递增的 id、与哈希不符的观测、没有对应画面的战斗或提示决策、未知的消息：每种都得到一个 `error`。被拒绝的节点消息会让这一局的下一个决策失败。对不上的协议版本，或 I/O 或 JSON 错误，会让大脑的 `Serve` 结束，大脑也随之结束：它只服务一个宿主，所以没有下一个，Mod 会再启动它（[概览 §5](/arch/harness/#sec-5)）。

**在工作进程池里**（[模拟器：工作进程池 §6](/arch/simulator/pool/#sec-6)）：

| 情况 | 结果 |
|---|---|
| 工作进程启动或回答晚于超时时间（5 分钟，启动和每次回答都一样） | 杀掉；请求的第一次失败会重启它，并把请求再发一次 |
| 工作进程死掉（I/O 错误、它的输出结束） | 替换掉，请求再发一次 |
| 同一个请求第二次失败 | 搜索失败（并行循环抛出的 `AggregateException`） |
| 不是 JSON 的回复，或 id 不对的回复 | 失败，不重试 |
| 带错误的回复 | 等所有回复到齐后失败，不重试；抛异常的工作进程会退出，所以下次用到它时会重启它 |
| 没有按观测构建出来的战斗 | 工作进程的错误是「not built as observed」（没有按观测构建），带上前 4 处差异（`SimWorlds.NoSL`），所以搜索失败 |

一个请求大多只要几秒：一个世界的搜索、一个束状态的一个回合，或一个决策的试探路径中的一份。超时抓的是卡住的工作进程，不是慢的。

**在宿主里**：在 `run` 里，任何异常都会让这一局以 `failed` 结束，带上它的类型和第一行，报告不计入它（[模拟器：整局 §5](/arch/simulator/runs/#sec-5)）。通过线路时，模拟器这个宿主遇到 `error` 会抛异常，结果相同；遇到 id 或哈希不是请求的推荐时也会。Mod 记一条警告，以 `run_end{failed}` 结束这一局，让游戏在没有大脑的情况下继续（[Mod：主循环 §8](/arch/mod/loop/#sec-8)）。评估要求名为 `random` 的大脑做出的决策为 0，失败的对局则不计入（[评估：指标、种子与报告 §2](/arch/evaluation/metrics/#sec-2)）。

**规划中的处理** <Badge text="规划中" variant="caution" />：

| 情况 | 规划 | 目前 |
|---|---|---|
| 过期请求（已有更新的 `decision_id`） | 取消搜索，不回复 | Mod 丢弃迟到的回答；大脑回答每个请求，id 没有递增的会得到 `error` |
| 工作进程崩溃或超时 | 在另一个工作进程上从快照重新打开世界，用已完成的部分作答，把这一行标为 `degraded` | 请求再发一次，得到相同的回答，所以没有任何降级 |
