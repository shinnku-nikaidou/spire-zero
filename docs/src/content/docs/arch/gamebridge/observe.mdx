本页把协议的每个字段追溯到它所来自的游戏对象。像 `Runs/RunManager.cs` 这样的路径在反编译出的游戏（`MegaCrit.Sts2.Core`）里；项目路径都在 `src/Sts2Ai.GameBridge/` 下。这里提到的每个游戏来源都已在游戏代码中读过 <Badge text="已核实" variant="success" />。

## 1. 入口

`Observe`（`Observe.cs`）构建一局和战斗；其他每个画面都由它的决策界面（surface）所属的类构建，与它的合法动作放在一起（[各决策界面的动作](/arch/gamebridge/actions/)）。

| 成员 | 返回 |
|---|---|
| `Of(run, player, screen)` | 一个 `Observation`：一局的视图加上给定的画面 |
| `Run(run, player)` | `RunView`（[§2](#sec-2)） |
| `Combat(state, player)` | `CombatObservation`（[§4](#sec-4)）；玩家没有战斗状态时抛异常 |
| `Card(card, withUid = false)` | 一个 `CardView`；只在要求时才带 uid，用于手牌（[§3](#sec-3)） |
| `DeckCard(card)` | 牌组视图里显示的一张牌，可以升级时带上它的升级预览 |
| `CardKey(card)` | 卡牌的键，即它的视图去掉 uid 之后的 JSON |
| `Relic(relic)`、`Coord(coord)` | 一件遗物，一个地图坐标 |
| `Intents(move, owner, targets)` | 一个招式会在怪物头上显示的意图，瞄准给定的目标；CombatBuilder 复用它，把招式与玩家见到的意图对应起来 |

宿主取来游戏对象（一局的状态、玩家、当前事件、商店的库存）并传进来；除了提示的上下文（[§6](#sec-6)），GameBridge 不持有自己的状态。

## 2. 一局及其地图

| 字段 | 读自 |
|---|---|
| `character` | `player.Character.Id` |
| `ascension`、`act`、`act_id`、`floor` | `RunState.AscensionLevel`、`CurrentActIndex`、`Act.Id`、`TotalFloor` |
| `hp`、`max_hp`、`gold` | `player.Creature.CurrentHp`、`MaxHp`、`player.Gold` |
| `deck` | `player.Deck.Cards`，每张经过 `DeckCard`，按卡牌键排序 |
| `relics`、`potions` | `player.Relics`，经过 `Relic`；`player.PotionSlots`，空槽为 null |
| `map.points` | 地图的网格点（`GetAllMapPoints`），加上不在网格里的起点、Boss 点和第二个 Boss 点；每个点带 `PointType`、它的 `Children`，以及它是否有 `Quests` |
| `map.visited` | `RunState.VisitedMapCoords` |
| `map.boss`、`second_boss`、`ancient` | `Act.BossEncounter`；`Act.SecondBossEncounter`，只在地图有第二个 Boss 点时；`Act.Ancient` |

**顺序**。在游戏里，一个点的子节点是一个哈希集合，它的顺序在不同进程之间不一样；所以各个点按先行后列的顺序排列，每个点的 `next` 也同样排序，这样同一张地图在任何进程里都给出相同的观测（`Observe.cs:52-72`）。

## 3. 卡牌、能力、遗物和意图

**卡牌**（`Observe.Card`，`Observe.cs:115-138`）：

| 字段 | 读自 |
|---|---|
| `id`、`up` | 卡牌的 id；`CurrentUpgradeLevel`，大于 0 时 |
| `uid` | `NetCombatCardDb.Instance.GetCardId(card)`，只用于手牌 |
| `cost`、`x_cost` | `EnergyCost.GetWithModifiers(CostModifiers.All)`，即卡牌显示的费用；`EnergyCost.CostsX` 时为 `x_cost` |
| `stars` | `GetStarCostWithModifiers()`，用于有辉星费用的卡牌（`CanonicalStarCost` ≥ 0） |
| `enchant`、`affliction` | 卡牌的附魔和苦痛，连同它们的数值 |
| `tinker` | 疯狂科学的 `TinkerTimeType` 和 `TinkerTimeRider` |
| `keywords` | `Keywords`，排序后 |
| `this_turn` | `ShouldRetainThisTurn` 或 `IsSlyThisTurn` 在 `Keywords` 之外成立的保留或 Sly：游戏把只给一回合的关键词（独门技术、手上技法）放在它自己的标记里，回合结束时清掉 |
| `vars` | 卡牌中不是计算得出的 `DynamicVars`，按名字，各取其 `BaseValue` |
| `lasting`、`stars_lasting` | 卡牌在打出时或回合结束时失效的改动消失之后的能量和星辰费用，与现在不同时才有：游戏只在费用内部把它们分开，在 `_localModifiers` 和 `_temporaryStarCosts` 里 |
| `replay` | `GetEnchantedReplayCount()`，大于 0 时才有：牌面写的额外打出次数 |
| `spent` | 附魔的 `Status` 是 `Disabled`：一场一次的效果已用掉 |
| `calc` | 卡牌的计算数字 `Calculate(null)`：没选目标时牌面印出的值，用于战斗中的牌 |

**`vars` 是基础值**。也就是卡牌的数字在力量、敏捷或易伤作用于它们之前的样子。计算得出的数字（完美打击的伤害）被略去：卡牌把它显示为一个基础值，加上状态里某样东西每有一个就多出的一份，而这些组成部分都在 vars 里；计算出的值本身只是照搬它的基础值，降级之后就会过时。vars 按名字顺序加入，因为序列化器按字典被填入的顺序写出它。`enchant.extra` 是 Momentum 累积的伤害。

**升级预览**（`DeckCard`）：对牌组里可以升级的卡牌，给出再升级一次之后的卡牌，与游戏自己在牌组视图和升级提示里显示的预览一样。它的做法与游戏做预览的方式相同，在副本上进行：`MutableClone()`，然后 `UpgradeInternal()` 和 `FinalizeUpgradeInternal()`。可变副本没有原卡牌的任何事件订阅者，升级也不运行任何钩子，所以这一局里什么都不会改变（`Observe.cs:202-214`）。

**能力**（`Observe.cs:259-261`）：只取 `IsVisible` 的能力；`amount` 是 `DisplayAmount`，即图标上的数字；`stacks` 是 `Amount`，在它与前者不同时给出；`card` 是能力保存的那张牌；`detail` 是能力的 `DynamicVars` 离开原本数值多远，取总和（一次只有一个在变）；`stolen` 是顺走的 `StolenCard`。那张牌在能力的私有数据里，游戏没有公开它，尽管悬停提示会说出它的名字（夜魇的牌），所以 `HeldCards` 用反射找到它：能力的 `_internalData` 里第一个卡牌类型的字段（`HeldCards.cs:12-27`）。模拟器的 CombatBuilder 构建战斗时，用 `HeldCards.Set` 把这样的牌放回去。

**遗物**（`Observe.cs:263-272`）：`ShowCounter` 时，`counter` 是 `DisplayAmount`；`status`，不是正常状态时给出；`melted`（`IsMelted`）；`used_up`（`IsUsedUp`）；`cards`，佩尔之牙保存的牌；`spent`，遗物名称以 `ThisCombat` 或 `ThisTurn` 结尾的私有布尔字段成立时才有。

**意图**（`Observe.cs:252-257`）：怪物的 `NextMove` 的意图，针对不在玩家一方的怪物，倒下、等着复活的也算。攻击的伤害是针对玩家的 `AttackIntent.GetSingleDamage(targets, owner)`，也就是图标上的数字所来自的同一个调用，攻击次数是 `max(1, Repeats)`。招式本身从不发出去，发出的只有它的意图。

**uid**：生物的 uid 是它的 `CombatId`；手牌的 uid 是它在 `NetCombatCardDb` 里的 id（[协议：观测与动作 §3](/arch/protocol/observation/#sec-3)）。

## 4. 一场战斗

`Observe.Combat(state, player)`（`Observe.cs:76-112`）：

| 字段 | 读自 |
|---|---|
| `encounter`、`room` | `state.Encounter.Id`，及其 `RoomType` |
| `act`、`ascension`、`round` | 这一局的幕和进阶等级；`state.RoundNumber` |
| `player` | 玩家的生物（`CombatId`、生命值、最大生命值、格挡、能力）；战斗状态的 `Energy`、`MaxEnergy`、`Stars`；`OrbQueue.Capacity` 和其中的充能球，带它们的被动值和激发值；玩家的金币 |
| `hand` | `Hand.Cards`，按手牌顺序，带 uid |
| `draw` | `DrawPile.Cards`，按卡牌键排序 |
| `discard`、`exhaust` | `DiscardPile.Cards`、`ExhaustPile.Cards`，按牌堆顺序 |
| `potions`、`relics` | 与一局里相同 |
| `allies` | `state.Allies`，不含玩家 |
| `enemies` | `state.Enemies` |

一局中的战斗使用同一个 `Observe.Combat`，放在 `combat` 画面或选牌提示的画面里。

## 5. 按规范顺序排列的选牌提示

`CardChoices.Canonical(options, min, max, context, tieBreak)`（`CardChoices.cs:16-25`）把游戏的一个提示变成协议的 `CardChoice`：

1. 每个选项变成一个视图：提示的用途以 `deck_` 开头时，是牌组视图（`DeckCard`，带升级预览）；否则是普通的卡牌视图。
2. 每个选项按游戏的顺序，从 `tieBreak` 抽一个数。
3. 选项按卡牌键排序，打平的按抽到的数排序。
4. 它返回这个选择，以及每个规范索引在游戏列表里对应的索引。

为什么用随机的打平规则，而不用游戏的顺序：相同的牌看起来一样，但拿走哪一张可能有影响（两张相同的牌在抽牌堆的不同深度），而游戏给它们的顺序可能跟随隐藏的顺序。来自一条不知道任何隐藏信息的随机数流的打平规则，让这个选择保持公平，同时仍可复现。模拟器用自进入节点以来的提示编号给它做种子（`new Random(prompt)`）；Mod 用 0。

宿主保留游戏的索引：用规范索引给出的回答，在游戏看到之前被翻译回去，一局的轨迹记录的是游戏的索引（[协议：观测与动作 §4](/arch/protocol/observation/#sec-4)）。

## 6. 提示的上下文

每个选牌提示都经过游戏的某个 `CardSelectCmd.From*` 入口，而只有这些入口的参数能说明游戏为什么要问。`ChoiceContexts`（`ChoiceContexts.cs`）用 Harmony 捕获它们，Harmony 是在运行时给游戏方法打补丁的库：**前缀**（prefix）在方法之前运行，**终结器**（finalizer）在方法之后运行，即使方法抛了异常也会运行。

- **目标**：每个公开静态的 `CardSelectCmd.From*` 方法，包括每个重载，`FromChooseABundleScreen` 除外，它是一个独立的决策界面。这个列表用反射找到，所以游戏更新新增的入口不用改代码就会打上补丁。
- **前缀**把入口的参数读进一个 `ChoiceContext`（`ChoiceContexts.cs:47-70`）：`CardSelectorPrefs`（是否可取消、提示的文本），`source` 参数，没有时取 `PlayerChoiceContext` 最后涉及的模型，一个 `CardPile`（它使用途成为 `<pile>_pile`），一个 `EnchantmentModel` 及其 `amount`，`canSkip`。用途是入口的名字去掉 `From`，写成 snake_case。`in_combat` 表示是否有战斗正在进行。
- **最外层的入口生效**。一个入口可以调用另一个入口（删牌会经过通用的牌组提示）：一个深度计数器保留第一个上下文，直到最外层的入口返回。
- **`Current` 和 `Last`**。入口运行期间，`Current` 按线程保存上下文；模拟器的选牌器在入口内部运行，就在那里读取它。在真实游戏里，提示的画面在入口第一次 await 之后才打开，那时 `Current` 已经没了，所以前缀还把上下文存进 `Last`，一直保留到下一个入口，Mod 从那里读取画面上那个提示的上下文（[Mod：主循环 §5](/arch/mod/loop/#sec-5)）。新的上下文对象意味着一个新的提示。
- **最先打这个补丁**。每个宿主在任何其他补丁之前调用一次 `ChoiceContexts.Patch`（模拟器里在 `HeadlessPatches.Apply`，Mod 里在 `Host`）。入口那个很小的 async 存根，可能被内联进更早编译的调用方，例如在另一个补丁编译它的替换方法时，而内联进去的副本会绕过前缀。无头运行时 SapphireSeed 就发生过这种事。

没有上下文的提示在模拟器里会抛异常；Mod 则把它留给玩家。

## 7. SL 检查点

`Checkpoint`（`Checkpoint.cs`）是 SL 下节点的起点（[模拟器：世界与 SL 克隆 §3](/arch/simulator/worlds/#sec-3)）。两种宿主以相同的方式取得它，所以 Mod 发来的克隆能在模拟器里加载。

| 成员 | 做什么 |
|---|---|
| `Take(player)` | 此刻的这一局：游戏自己的存档 `SaveManager.ToJson(RunManager.Instance.ToSave(null))`，加上每件遗物的普通字段，合成一个 JSON 字符串 |
| `Open(checkpoint)` | 只读取一次，供要加载多次的节点使用：`Opened(Save, Relics)` |
| `RestoreRelics(opened, player)` | 存档加载之后，把每件遗物原有的字段还给它；如果加载出的这一局的遗物与检查点的遗物（按顺序）不一致，就抛异常 |

遗物的**普通字段**，是它的数字、标志、枚举或 decimal 类型的可写字段，从它自己的类沿继承层次向上，以类名和字段名为键，按与区域设置无关的格式写出。存档只保留遗物标记为要保存的字段；没有这些普通字段，一件在战斗之间改变状态的遗物（熔岩石在第一个 Boss 之后会停用自己）加载出来就会像刚拿到的新遗物。检查点的 JSON 用的是 .NET 的默认名字（`Save`、`Relics`、`Id`、`Fields`），而不是协议的：除了 `Checkpoint` 自己，它对一切都是不透明的。

## 8. 隐藏状态键

搜索需要知道两个状态什么时候是同一个状态，好只搜一次。观测不够用：两个状态可能看起来一样，打起来却不同。`HiddenState`（`HiddenState.cs`）对观测隐藏的东西求哈希。它从不进入大脑的决策；只有模拟器里的搜索世界会读取它（[协议：世界与工作进程消息 §1](/arch/protocol/worlds/#sec-1)）。

| 键 | 包含 | 用于 |
|---|---|---|
| `Key(state, player)` | 抽牌堆按顺序的卡牌键；一局和玩家的每条随机数流的计数器；每个怪物自己那条流的计数器和它的下一个招式 | NoSL 世界 |
| `Full(state, player)` | `Key`，加上每个怪物至今的招式（它的状态日志），再加上本回合战斗历史里的条目（出牌、抽牌、弃牌、消耗、生成的牌、药水、能力、格挡、能量），作为一个排序后的多重集合 | SL 世界 |

本回合出牌的顺序是故意略去的：同样的出牌换一种顺序，应该汇合成同一个状态。每个键都是它文本的 `ProtocolJson.Hash`。
