**冠軍**是某個環境中已接受的最好版本的 AI：大腦、它們的預算和權重，以及代表它們的報告。本頁是一份紀錄：指明冠軍的檔案、迄今每一個冠軍以及它是怎麼來的、沒有晉級的門檻，以及其他專案和我們自己的各代達到了什麼。門檻如何運作見[晉級門檻](/zh-tw/arch/evaluation/gates/)。

## 1. 冠軍檔案

`eval/CHARACTER/champions/ENV.json`（`nosl.json`、`sl.json`）為每個角色和環境保存一個冠軍，格式為 `ChampionFile` 記錄（`Harness/Gate.cs:116-117`）。今天 SL 冠軍的檔案：

```json
{
  "env": "SL",
  "champion": "combat plan c2 beam 8x300 easy 4 loss plans 3, combat prompts p0, macro l0 v7-1f clone, macro prompts l0 v7-1f clone",
  "options": {
    "env": "SL", "policy": "plan", "macro": "l0", "effort": "medium",
    "value": "weights/silent/v7-1f.json", "afterstates": "clone", "combat-net": "weights/silent/c2.json",
    "character": "SILENT", "asc": "0"
  },
  "report": "eval/silent/reports/2026-10-31-sl-r1-promotion-1-100-plan-c2-l0-v7-1f-clone-p0.json",
  "since": "2026-10-31"
}
```

（檔案裡是一行，這裡展開排版）。

| 欄位 | 內容 |
|---|---|
| `env` | `NoSL` 或 `SL`；挑戰者的 `--env` 與它不同時，門檻會拒絕 |
| `champion` | 冠軍在報告裡顯示的名稱，即路由表每一側的大腦加上預算（[Harness：路由、預算與種子 §1](/zh-tw/arch/harness/routing/#sec-1)） |
| `options` | 打出這個冠軍的對局選項，不帶 `--`，其中包括角色和晉階等級；權重檔案寫成它們在 `weights/CHARACTER/` 裡的路徑 |
| `report` | 挑戰者與之配對的報告：每次門檻中冠軍那一方 |
| `since` | 它成為冠軍的日期（晉級報告的日期，或人工寫入的日期） |
| `gate` | 它通過的門檻，沒有經過門檻而定下的冠軍則沒有這一欄：`metric`、`delta`、`alpha`、`beta`、`pairs`、`decided`、`llr`、`lower`、`upper`、`floor_diff_mean`、`challenger_only_wins`、`champion_only_wins`、`verdict`，有的話還有 `void_reason`，以及 `not_worse`（從 `a2643cf` 起的檔案裡才有；這個欄位隨不更差門檻 `62876d4` 加入） |

**誰讀它**。

- `run`、`brain`、`afterstates` 和 `fork` 接受 `--champion FILE`，打它指明的冠軍（`SimWorker/Commands/Args.cs:173-202`，[模擬器：參考 §3](/zh-tw/arch/simulator/reference/#sec-3)）。檔案的選項排在給定的選項之後，所以給定的優先；指令沒有的選項會被略過（`brain` 沒有 `--env`：每個宿主自己指明）；給定了與檔案不同的 `--policy` 時，保留它自己的預算。
- `gate --champion FILE` 是要打敗的冠軍：它讀取檔案的 `env` 和 `report`（[晉級門檻 §6](/zh-tw/arch/evaluation/gates/#sec-6)）。`learn/challenge.py` 讀取報告的種子集、大小、角色和晉階等級。
- `leaderboard` 在檔案所屬環境的榜上，標出每個檔案指明的報告（[指標、種子與報告 §9](/zh-tw/arch/evaluation/metrics/#sec-9)）。

**由 `--promote` 寫入，或由人工寫入**。`gate --promote` 寫入每個欄位，選項按挑戰者的選項產生（`ChampionOptions.Options`，`SimWorker/Brains/ChampionOptions.cs:86-114`）：對 SL 規劃器是 `beam`、`easy-beam`、`replan`、`loss-plans` 和 `nodes`，而不是 `effort`。還沒有 SL 冠軍是由 `gate` 晉級的；SL 檔案是人工寫的，寫著 `"effort": "medium"`，打的是同樣的預算（[SL 規劃器：預算 §1](/zh-tw/arch/sl-planner/budget/#sec-1)）。重定基線只改 `report`（[晉級門檻 §9](/zh-tw/arch/evaluation/gates/#sec-9)）。

**現在**。兩個檔案都指明 `weights/silent/v7-1f.json` 和 `weights/silent/c2.json`、上面那份報告、自 2026-10-31 起，依據是配對勝局的門檻。SL 打的是 medium 力度的 SL 規劃器，加上在複本上的 L0；NoSL 打的是 8 個世界 × 300 個節點的 PIMC，加上用從畫面預測的後狀態的 L0（`"policy": "pimc", "worlds": "8", "nodes": "300"`）。NoSL 檔案指向 SL 報告，因為這個冠軍還沒有 NoSL 報告；對它的 NoSL 門檻會被拒絕（[評估 §3](/zh-tw/arch/evaluation/#sec-3)）。

**SL 冠軍從沒跑過的門檻**。SL 冠軍的每一次更換都是由一份報告和一個決定定下的，而不是由 `gate`。這裡用門檻自己的規則（預設參數的 C# SPRT，以及計畫 v7 的勝局下界），從已提交的報告算出：

pure-1-g 本來會在層數門檻上失敗，而它這條路線後來的 V 都以很大的差距通過了這個門檻；儘管如此，它仍被保留為純 V 路線的起點。v6-3-1 顯示了層數和勝局的分歧：按層數更差，按勝局明顯更好。

## 6. 未決問題

1. **R4 的吞吐量**：在遊戲的 Instant 速度下一局要幾分鐘，由此能負擔多少局 R4。
2. **不一致種子很少時的勝局門檻**：計畫 v7 的下界讓 3 勝對 0 勝通過（[晉級門檻 §10](/zh-tw/arch/evaluation/gates/#sec-10)）；等第一批門檻顯示出不一致種子有多少之後，再決定是否要求最少的不一致種子數，或改用精確檢定。
3. **門檻的錯誤率**：兩種門檻的誤通過率都沒有量過；A/A 測試需要一種只改變冠軍自身隨機性的方法（[晉級門檻 §4](/zh-tw/arch/evaluation/gates/#sec-4)）。
4. **冠軍的 NoSL 報告**，讓 NoSL 榜重新有冠軍，也讓同一個 V 的 SL − NoSL 能被量出。
5. **`final-1`**：何時在它上面做出第一個正式結論。
