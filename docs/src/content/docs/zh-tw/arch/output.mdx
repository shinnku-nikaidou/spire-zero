大腦用一個動作、一份計畫，以及（戰鬥時）它打過分的那些動作來回答一個決策。**輸出層**把這個答案變成玩家看得到的東西，或者在以後，變成遊戲實際做出的事。它在遊戲行程裡的 [Mod](/zh-tw/arch/mod/) 中執行，每種輸出模式讀的都是同一個 `Recommendation`：大腦從不知道開著的是哪種模式。本頁寫給想改變玩家所見內容的人。[Mod：主迴圈](/zh-tw/arch/mod/loop/)說明何時詢問答案，以及答案顯示多久。

<Aside title="狀態">

已實作，並在真實遊戲裡執行過（2026-10-28）：**面板**，蓋在遊戲上的一張卡片，顯示下一個動作、之後的計畫，戰鬥時還有大腦評分最高的三個動作（[§2](#sec-2)）；它的**設定**，在 Mod 加進遊戲設定畫面的「AI」分頁裡；以及兩種**標記**（[§3](#sec-3)）：在地圖上，推薦的點上有一個圓圈，大腦在它之後規劃的路線上有一條線，一直到頭目；在戰鬥中，計畫在本回合要打的卡牌上、它的目標上和結束回合按鈕上，標出步驟編號。規劃中：其他決策介面上的標示、自動遊玩（[§4](#sec-4)）、解說（[§5](#sec-5)），以及它所需要的事實。Godot 節點類別（`N*` 型別）只按類別名稱引用：每個名稱在反編譯原始碼裡都是唯一的，按名稱就能找到檔案。背景筆記在本地筆記 `tmp/notes/output-design.md` 裡。

</Aside>

## 1. 約定

輸出層讀取一則訊息 `Recommendation`（[協定：線路 §7](/zh-tw/arch/protocol/wire/#sec-7)），目前實作的樣子如下（`Sts2Ai.Protocol/Wire.cs:62-63`）：

| 欄位 | 內容 | 由誰提供 |
|---|---|---|
| `decision_id`、`obs_hash` | 它回答的決策 | |
| `action` | 現在要採取的動作 | 每個大腦 |
| `brain` | 回答的大腦，用 Harness 給它的名字（[Harness：路由、預算與種子 §1](/zh-tw/arch/harness/routing/#sec-1)） | |
| `plan`? | 大腦在 `action` 之後規劃的內容 | PIMC：本回合剩下的部分，取第一個世界的；SL 規劃器：這場戰鬥剩下的部分；地圖上的 L0：通往頭目的路線；其他畫面都沒有，選牌提示也沒有 |
| `candidates`? | 大腦打過分的前幾個動作，每個帶有它的估值、95% 信賴區間的半寬、樣本數等（[協定：世界與工作行程訊息 §3](/zh-tw/arch/protocol/worlds/#sec-3)） | 只有戰鬥大腦 |

`plan` 排在 `action` *之後*：下一步是 `action`，`plan[0]` 是再下一步。

**消費者**。大腦從不知道開著的是哪種模式。

| 模式 | 消費者 | 狀態 |
|---|---|---|
| 面板（輔助，簡單版） | 所有決策介面共用一張卡片（[§2](#sec-2)） | 已實作 |
| 標記（輔助） | 地圖的圓圈和路線；戰鬥計畫的編號和圓圈（[§3](#sec-3)） | 已實作 |
| 標示（輔助，進階版） | 其他決策介面的節點，透過轉接器（[Mod：自動遊玩與安全 §1](/zh-tw/arch/mod/auto/#sec-1)） | 規劃中 |
| 自動 | 轉接器打出 `action`，然後 Mod 重新觀測（[§4](#sec-4)） | 規劃中 |
| 半自動 | 標記顯示計畫，按一個鍵打出 `action` | 規劃中 |

*決策介面*（surface）是正在顯示的決策畫面的種類（戰鬥、地圖、商店、選牌提示等）。*錨點*（anchor）是畫面上某個動作所屬的 Godot 節點，例如要打出的那張牌的卡牌槽。

**過期的答案**。答案按 id 和開著的決策配對，並為被詢問的那個鍵保存：觀測的雜湊加上它的合法動作。它只在這個鍵持續的影格上畫出來；畫面往前走時，面板為新的狀態顯示「Thinking…」，Mod 重新詢問（[Mod：主迴圈 §3](/zh-tw/arch/mod/loop/#sec-3)）。Mod 從不讀答案的 `obs_hash`。

**規劃中**。

- **事實**：解釋可以引用的數字，作為推薦的一個欄位；這是解說唯一的來源（[§5](#sec-5)）。程式碼裡還沒有任何 `Facts`。
- **隨時可答**：輔助模式下，大腦先送出目前最好的答案，再陸續送出更好的，每一個替換前一個（[Harness：路由、預算與種子 §4](/zh-tw/arch/harness/routing/#sec-4)）。目前大腦每個決策只送一個答案，Mod 收到第一個時就結束這個決策。

## 2. 面板

面板是蓋在遊戲上的一張卡片，靠近左上角（`UI/Panel.cs`）。它有自己的 `CanvasLayer`，這是 Godot 的一種節點，把它的子節點畫在單獨的一層上：第 100 層，在遊戲的 UI 之上，所有標記都共用這一層。除了開關上的點選之外，卡片不接收任何點選，所以點選會傳到它下面的遊戲。F8 會連同所有標記一起隱藏和顯示它。

<PanelMock client:visible lang="zh-TW" />

**版面**（`UI/Panel.cs:44-250`）：

- **卡片**：位於 (24, 132)，至少 420 px 寬，16 px 的內距（左右兩側 18），圓角半徑 14，深紫色邊框，一層陰影，以及按不透明度設定填上的近黑色底色。
- **標頭**：一個紫色的「AI」徽標；冠軍的名字，以及它下面的狀態，各佔一行，空間不夠的地方以省略號截斷；SL/NoSL 開關，選中的一邊填上紫色（多人模式下兩邊都不選，Mod 關閉時沒有開關）；還有「F8」。
- **答案**：下一個動作，以大字顯示在一個實心的「1」徽標之後；在地圖上用圓圈代替徽標，接著是「ROUTE TO THE BOSS」（通往頭目的路線）和以圓點連起來的路線房間；其他地方則是計畫的各個步驟，在空心圓徽標裡從 2 開始編號；然後是計畫後面的回合，「2 more turns planned」（[Mod：主迴圈 §6](/zh-tw/arch/mod/loop/#sec-6)）。
- **考慮過的動作**，在一條分隔線下方：「CONSIDERED」和「value ±CI」，然後是按大腦順序排列的前三個候選，最好的在最前面，第一個用紫色。每個值印到小數點後一位，`0.0 ±0.0`。開啟長條時，每一列還有一條 96 px 的軌道，信賴區間在上面畫成一段色帶，估值處畫一道標線，三列共用同一個比例尺：從最低的值減去它的區間，到最高的值加上它的區間，兩側再各放寬十分之一。只在大腦為不只一個動作打分時顯示，目前也就是戰鬥時。
- **底部**：回答的大腦，以及 Mod 從送出到收到為止等了它幾秒。
- **訊息**（代替答案）：一個圓點、訊息本身，以及較淡的第二行；玩家能自行解決或等它過去的情況用琥珀色，錯誤用紅色。所有訊息都列在 [Mod §6](/zh-tw/arch/mod/#sec-6)。

內文只在它顯示的內容改變，或者繪製它所用的設定改變時才重建；標記則每個影格都跟著它們的節點。

**設定**。玩家的選擇存在 `~/.local/state/sts2ai/settings.json`，和大腦的 socket 放在一起，不在遊戲的玩家檔案裡；每一列、它的值和預設值都在 [Mod §5](/zh-tw/arch/mod/#sec-5)。面板和標記即時讀取設定，所以改動會立刻生效。

**AI 分頁**（`UI/SettingsTab.cs`）位於遊戲的設定畫面裡，排在一般、圖形、聲音和輸入之後。遊戲在 `NSettingsTabManager._Ready` 裡用它場景中的節點建出四個分頁。那裡的一個後綴在下一次空閒時執行，好讓畫面已經完整；它複製輸入分頁作為新分頁的按鈕，複製聲音面板並清空作為它的面板，所以兩者的外觀和切換方式都和遊戲自己的一樣；複製的是節點和它們的腳本，不包括遊戲的訊號連接。它把分頁列向左移半格，讓它保持置中，把按鈕接到管理器自己的分頁切換上，並把這一對加進管理器的分頁裡。各列是 Mod 自己的控制項，用的是遊戲設定列的字型：`<  value  >` 切換器、一個不透明度滑桿，以及一個重設它們的按鈕。所有東西都在加入畫面之前建好，所以萬一建置失敗，畫面會保持遊戲建出的樣子，錯誤則記入日誌。

**面板規劃中的內容**：

| 決策介面 | 內容 |
|---|---|
| 戰鬥 | 1–2 條事實（與替代打法相比的預期 HP 損失、下回合能否斬殺）；最佳替代選項及其 ΔP(win)，也就是估計的整局勝率之差 |
| 卡牌獎勵與選擇 | 每個選項，帶上它相對於略過或基線的 ΔP(win) |
| 地圖、事件、休息處、商店 | 同樣的格式 |

目前每個決策介面都用上面這一種版面，估值只來自戰鬥的候選；V 的估值不會送過來。零 UI 的變體，也就是由大腦提供一個本機網頁、顯示在第二個螢幕上，只在最早期的測試時考慮過。

## 3. 標示

**跟隨式覆蓋層**。標記由 Mod 自己的節點畫出，這些節點只存在於 Mod 的 `CanvasLayer` 裡，蓋在遊戲上面。每個影格，每個標記讀取目標節點在畫面上的變換（`GetGlobalTransformWithCanvas()`）和節點的尺寸，所以能跟著一張旋轉、展開或縮放的牌，隨它移動；目標消失或隱藏時，標記也隱藏。Mod 從不為了繪製而寫入遊戲的節點，原因有二：`NHandCardHolder.UpdateCard()` 在每次狀態變化時都會重設 `CardHighlight`（`Nodes.Cards.Holders/NHandCardHolder.cs:613-640`） <Badge text="已核實" variant="success" />；而且青色、金色和紅色的光暈在遊戲裡已經各有含義（`NCardHighlight`）。Mod 唯一會改動遊戲節點的地方是設定畫面（[§2](#sec-2)）。

**樣式**：紫色，遊戲自己的光暈不用這個顏色：描邊、圓圈，以及帶有普通數字和深色外圈的紫色圓形徽標。

**在地圖上**（`UI/MapMark.cs`）：下一個點上有一個脈動的紫色圓圈，在它之後路線的每段路徑上各有一條紫色的線，從玩家所在之處一直到路線的終點。地圖畫面把它的點節點和每段路徑的小點存在私有字典裡，新的一幕會換掉它們；一條線從一段路徑的第一個小點畫到最後一個，所以會在點的圖示之前停住。圓圈的半徑是點的較長邊的一半再加 14，隨地圖縮放，每秒脈動一次，幅度 ±10%。路線設定可以顯示整條路線、只顯示圓圈，或什麼都不顯示：

<MapRoute client:visible lang="zh-TW" />

**在戰鬥中**（`UI/CombatMark.cs`）：面板所顯示的計畫，從 `action` 到本回合結束。

- 計畫要打的每張牌，在它的卡牌槽的點選範圍（hitbox）上畫紫色描邊，右上角標出它那一步的編號；
- 每個目標（敵人或盟友）在它的生物節點的點選範圍上描邊，向外 10 px，所有瞄準它的步驟的編號放在上緣中間的一個徽標裡；
- 結束回合按鈕描邊，並標出它那一步的編號。

已經不在的牌或生物沒有標記。「Order numbers on cards」會把卡牌的描邊和編號一起關掉；「Target and end-turn marks」管其餘的部分。藥水沒有自己的標記，但它的目標會得到它那一步的編號。

**錨點**。每個決策介面的節點，都在遊戲原始碼裡核實過（本地筆記 `tmp/notes/output-design.md` §3.2） <Badge text="已核實" variant="success" />：

| 決策介面 | 節點 | 標記 | 狀態 |
|---|---|---|---|
| 手牌 | `NPlayerHand.Instance.GetCardHolder(card).Hitbox`，卡牌按它的 uid 從 `NetCombatCardDb` 取得 | 描邊 + 步驟編號 | 已實作 |
| 目標 | `NCombatRoom.Instance.GetCreatureNode(creature).Hitbox` | 描邊 + 各步驟的編號 | 已實作 |
| 結束回合 | `NCombatRoom.Instance.Ui.EndTurnButton` | 描邊 + 步驟編號 | 已實作 |
| 地圖 | `NMapScreen` 裡的 `NMapPoint`，以及我們自己沿著它的路徑小點畫的 `Line2D`（不用 `NMapDrawings`，它在多人模式下是共享的） | 圓圈 + 路線 | 已實作 |
| 藥水 | `NPotionHolder` | 徽標 | 規劃中 |
| 戰鬥內選牌 | 手牌選擇模式、`NCombatPileCardSelectScreen` | 勾選標記 | 規劃中 |
| 卡牌獎勵 | `NCardRewardSelectionScreen` 的卡牌槽 + 略過 | 每張牌的 ΔP，最佳項描邊 | 規劃中 |
| 獎勵 | `NRewardButton` | 領取順序 / 略過 | 規劃中 |
| 事件 | `NEventOptionButton` | 最佳項描邊，其他項標 ΔP | 規劃中 |
| 休息處 | `NRestSiteButton` | 同上 | 規劃中 |
| 商店 | `NMerchantCard/Relic/Potion/CardRemoval` | 購買順序 | 規劃中 |
| 網格選牌 | `NCardGridSelectionScreen` 一族、`NCardGrid` | 勾選標記 | 規劃中 |

**工作順序**：手牌和目標（已完成）；卡牌獎勵；地圖（已完成）；事件、休息處和商店；網格選牌提示。

**容易踩的坑**：

- 卡牌槽節點會被池化（重複使用）、換父節點，而且帶有動畫：跟隨式覆蓋層每個影格都重新查找它們，以此應對。
- 螢幕解析度、UI 縮放和手把操作：只用畫面上的變換，絕不用局部座標。
- 每個動作之後大腦都會重新規劃，所以每個答案的編號都從 1 重新開始。

## 4. 自動 <Badge text="規劃中" variant="caution" />

自動迴圈會建立在 Mod 的每影格迴圈上（[Mod：主迴圈 §1](/zh-tw/arch/mod/loop/#sec-1)）：

<Steps>

1. 等到決策介面空閒。
2. 觀測。
3. 取得推薦。
4. 檢查它對應的是當前的鍵，而且它的動作合法。
5. 打出 `action`，只打這一個。
6. 等待鍵改變，或者等到超時。
7. 重複。

</Steps>

每個動作之後大腦都會重新規劃，因為抽到的牌和隨機結果會影響下一個決策。速度會來自把遊戲的 FastMode 設為 Instant，外加可選的每步延遲（[Mod：自動遊玩與安全 §2](/zh-tw/arch/mod/auto/#sec-2)）。

## 5. 解說 <Badge text="規劃中" variant="caution" />

解說是用來解釋一條推薦的文字。

- 它只由事實和候選生成，從不對狀態做自由推理。NoSL 的事實是機率和期望值；SL 的事實可以是確切的（「先打 A 再打 B 會抽到 X」）。
- 優先用範本，每種事實一個。
- 可選：由便宜的 LLM 潤飾文字，離線或非同步進行（專案的 LLM 閘道，只用便宜的模型）。它的輸入是 JSON 格式的事實和範本的文字。它的輸出要經過檢查：文字裡的每個數字都必須等於某個事實的值（格式化之後做字串比對）；不符合時，改為顯示範本的文字。
- LLM 除了事實之外看不到任何遊戲狀態，也從不影響動作。

這些都還沒有實作：推薦目前還不帶任何事實（[§1](#sec-1)）。

## 6. 輸出中的公平性

| 規則 | 狀態 |
|---|---|
| 輔助模式下 Mod 不打出任何東西；規劃中的執行器只會打出決策合法清單裡的動作。大腦的答案由 Harness 對照這份清單檢查（[Harness：路由、預算與種子 §6](/zh-tw/arch/harness/routing/#sec-6)） | 成立 |
| 沒有修改狀態、使用主控台或讀檔的介面 | 成立 |
| socket 只傳輸協定訊息。SL 匯出只在 SL 下傳送，帶有節點的存檔，包括種子和亂數流（[Mod：自動遊玩與安全 §4](/zh-tw/arch/mod/auto/#sec-4)） | 成立 |
| Mod 只寫自己的設定檔，以及它在遊戲日誌裡的那幾行 | 成立 |
| `NumReloads` 記入日誌，而且必須為 0 | 規劃中 |

協定訊息新增的欄位如果改變了可以離開遊戲的內容，就在這裡加一列。

- **過期的答案**：延遲到達的答案在狀態改變之後從不畫出來。

## 8. 未決問題

1. 有多個目標的計畫，在中途有目標死掉時的標記：重新編號，還是保持不變？
2. 如何在不顯得雜亂的情況下顯示 NoSL 的不確定性（信賴區間）。目前的做法：一個到小數點後一位的值和一條長條。
