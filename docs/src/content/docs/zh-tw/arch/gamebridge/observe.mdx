本頁把每個協定欄位追溯到它所來自的遊戲物件。`Runs/RunManager.cs` 這類路徑位於反編譯出的遊戲（`MegaCrit.Sts2.Core`）裡；專案路徑則在 `src/Sts2Ai.GameBridge/` 之下。這裡提到的每個遊戲來源都已在遊戲程式碼中讀過 <Badge text="已核實" variant="success" />。

## 1. 入口

`Observe`（`Observe.cs`）建構一局和戰鬥；其他每個畫面都由它所屬決策介面（surface）的類別建構，和它的合法動作放在一起（[各決策介面的動作](/zh-tw/arch/gamebridge/actions/)）。

| 成員 | 回傳 |
|---|---|
| `Of(run, player, screen)` | 一個 `Observation`：一局的檢視，加上給定的畫面 |
| `Run(run, player)` | `RunView`（[§2](#sec-2)） |
| `Combat(state, player)` | `CombatObservation`（[§4](#sec-4)）；玩家沒有戰鬥狀態時拋出例外 |
| `Card(card, withUid = false)` | 一個 `CardView`；只在要求時才帶 uid，用於手牌（[§3](#sec-3)） |
| `DeckCard(card)` | 一張牌在牌組檢視裡顯示的樣子，能升級時帶上它的升級預覽 |
| `CardKey(card)` | 這張牌的鍵，即它的檢視去掉 uid 之後的 JSON |
| `Relic(relic)`、`Coord(coord)` | 一個遺物、一個地圖座標 |
| `Intents(move, owner, targets)` | 一個招式會在怪物頭上顯示的意圖，瞄準給定的目標；CombatBuilder 重用它，把招式和玩家看到的意圖對應起來 |

遊戲物件（一局的狀態、玩家、當前事件、商店的庫存）由宿主取得並傳入；除了提示的上下文（[§6](#sec-6)），GameBridge 不持有任何自己的狀態。

## 2. 一局與它的地圖

| 欄位 | 讀取來源 |
|---|---|
| `character` | `player.Character.Id` |
| `ascension`、`act`、`act_id`、`floor` | `RunState.AscensionLevel`、`CurrentActIndex`、`Act.Id`、`TotalFloor` |
| `hp`、`max_hp`、`gold` | `player.Creature.CurrentHp`、`MaxHp`、`player.Gold` |
| `deck` | `player.Deck.Cards`，每張都經過 `DeckCard`，按卡牌鍵排序 |
| `relics`、`potions` | `player.Relics`，經過 `Relic`；`player.PotionSlots`，空槽為 null |
| `map.points` | 地圖的格點（`GetAllMapPoints`），加上不在格子裡的起點、頭目點和第二個頭目點；每個點帶上它的 `PointType`、它的 `Children`，以及它是否有 `Quests` |
| `map.visited` | `RunState.VisitedMapCoords` |
| `map.boss`、`second_boss`、`ancient` | `Act.BossEncounter`；`Act.SecondBossEncounter`，只在地圖有第二個頭目點時才有；`Act.Ancient` |

**順序**。在遊戲裡，一個點的子節點是一個雜湊集合，它的順序在不同行程之間各不相同；所以這些點按先列後行的順序排好，每個點的 `next` 也同樣排序，於是同一張地圖在任何行程裡都給出相同的觀測（`Observe.cs:54-74`）。

## 3. 卡牌、能力、遺物與意圖

**一張牌**（`Observe.Card`，`Observe.cs:117-140`）：

| 欄位 | 讀取來源 |
|---|---|
| `id`、`up` | 卡牌的 id；`CurrentUpgradeLevel`，大於 0 時才有 |
| `uid` | `NetCombatCardDb.Instance.GetCardId(card)`，只用於手牌 |
| `cost`、`x_cost` | `EnergyCost.GetWithModifiers(CostModifiers.All)`，即卡牌顯示的費用；`EnergyCost.CostsX` 時有 `x_cost` |
| `stars` | `GetStarCostWithModifiers()`，用於有星辰費用的牌（`CanonicalStarCost` ≥ 0） |
| `enchant`、`affliction` | 卡牌的附魔和苦痛（affliction），連同它們的數值 |
| `tinker` | 瘋狂科學的 `TinkerTimeType` 和 `TinkerTimeRider` |
| `keywords` | `Keywords`，排序後 |
| `this_turn` | `ShouldRetainThisTurn` 或 `IsSlyThisTurn` 在 `Keywords` 之外成立的保留或 Sly：遊戲把只給一個回合的關鍵字（專業知識、掌上戲法）放在它自己的旗標裡，回合結束時清除 |
| `vars` | 卡牌中不是計算得出的 `DynamicVars`，按名稱，每個取它的 `BaseValue` |
| `lasting`、`stars_lasting` | 卡牌在打出時或回合結束時失效的改動消失之後的能量和星辰費用，和現在不同時才有：遊戲只在費用內部把它們分開，在 `_localModifiers` 和 `_temporaryStarCosts` 裡 |
| `replay` | `GetEnchantedReplayCount()`，大於 0 時才有：牌面寫的額外打出次數 |
| `spent` | 附魔的 `Status` 是 `Disabled`：一場一次的效果已用掉 |
| `calc` | 卡牌的計算數字 `Calculate(null)`：沒選目標時牌面印出的值，用於戰鬥中的牌 |

**`vars` 是基礎值**。也就是力量、敏捷或易傷作用在它們身上之前的卡牌數字。計算得出的數字（完美打擊的傷害）不收錄：卡牌把它顯示為一個基礎值，加上狀態中某樣東西每有一個就多出的額外值，而這些部分都在 vars 裡；計算值本身只是照抄它的基礎值，降級之後就過時了。vars 按名稱順序加入，因為序列化器寫出字典時，是按填入的順序寫的。`enchant.extra` 是 Momentum 累積的傷害。

**升級預覽**（`DeckCard`）：對牌組裡一張可升級的牌，給出它再升級一次之後的樣子，和遊戲自己在牌組檢視和升級提示裡顯示的預覽一樣。它的做法和遊戲做預覽的方式相同，在副本上做：`MutableClone()`，然後 `UpgradeInternal()` 和 `FinalizeUpgradeInternal()`。可變副本沒有原物的任何事件訂閱者，升級也不執行任何鉤子，所以這一局裡什麼都不會改變（`Observe.cs:204-216`）。

**一個能力**（`Observe.cs:259-261`）：只收錄 `IsVisible` 的能力；`amount` 是 `DisplayAmount`，即圖示上的數字；`stacks` 是 `Amount`，在它和前者不同時才有；`card` 是能力保存的那張牌；`detail` 是能力的 `DynamicVars` 離開原本數值多遠，加總起來（一次只有一個會移動）；`stolen` 是 順手一揮的 `StolenCard`。這張牌在能力的私有資料裡，遊戲雖然在提示框裡寫出了它（夢魘的牌），卻沒有公開它，所以 `HeldCards` 用反射找到它：能力的 `_internalData` 裡第一個卡牌型別的欄位（`HeldCards.cs:12-27`）。模擬器的 CombatBuilder 建構戰鬥時，用 `HeldCards.Set` 把這樣的牌放回去。

**一個遺物**（`Observe.cs:265-274`）：`ShowCounter` 時，`counter` 是 `DisplayAmount`；`status`，不是正常狀態時才有；`melted`（`IsMelted`）；`used_up`（`IsUsedUp`）；`cards`，佩爾之牙保存的牌；`spent`，遺物名稱以 `ThisCombat` 或 `ThisTurn` 結尾的私有布林欄位成立時才有。

**意圖**（`Observe.cs:254-259`）：怪物的 `NextMove` 的意圖，針對不在玩家一方的怪物，倒下、等著復活的也算。攻擊的傷害是針對玩家的 `AttackIntent.GetSingleDamage(targets, owner)`，也就是圖示上的數字所來自的同一個呼叫，次數則是 `max(1, Repeats)`。招式本身從不送出，只送出它的意圖。

**uid**：生物的 uid 是它的 `CombatId`；手牌的 uid 是它在 `NetCombatCardDb` 裡的 id（[協定：觀測與動作 §3](/zh-tw/arch/protocol/observation/#sec-3)）。

## 4. 一場戰鬥

`Observe.Combat(state, player)`（`Observe.cs:78-114`）：

| 欄位 | 讀取來源 |
|---|---|
| `encounter`、`room` | `state.Encounter.Id`，以及它的 `RoomType` |
| `act`、`ascension`、`round` | 這一局的幕和晉階；`state.RoundNumber` |
| `player` | 玩家的生物（`CombatId`、生命值、最大生命值、格擋、能力）；戰鬥狀態的 `Energy`、`MaxEnergy`、`Stars`；`OrbQueue.Capacity` 和其中的充能球，連同它們的被動和激發數值；玩家的金幣 |
| `hand` | `Hand.Cards`，按手牌順序，帶 uid |
| `draw` | `DrawPile.Cards`，按卡牌鍵排序 |
| `discard`、`exhaust` | `DiscardPile.Cards`、`ExhaustPile.Cards`，按牌堆順序 |
| `potions`、`relics` | 和一局裡的相同 |
| `allies` | `state.Allies`，不含玩家 |
| `enemies` | `state.Enemies` |

一局中的戰鬥使用同一個 `Observe.Combat`，放在 `combat` 畫面或選牌提示的畫面裡。

## 5. 按標準順序排列的選牌提示

`CardChoices.Canonical(options, min, max, context, tieBreak)`（`CardChoices.cs:16-25`）把遊戲的一個提示變成協定的 `CardChoice`：

1. 每個選項變成一個檢視：提示的用途以 `deck_` 開頭時是牌組檢視（`DeckCard`，帶升級預覽），否則是普通的卡牌檢視。
2. 每個選項按遊戲的順序，從 `tieBreak` 抽一個數字。
3. 選項按卡牌鍵排序，平手時按抽到的數字。
4. 它回傳這個選擇，以及每個標準索引所對應的遊戲清單索引。

為什麼用隨機的平手決勝，而不用遊戲的順序：完全相同的牌看起來一樣，但拿走哪一張可能有差別（兩張相同的牌位於抽牌堆的不同深度），而遊戲對它們的排序可能跟著隱藏的順序。用一條不知道任何隱藏資訊的亂數流來決勝，能讓這個選擇保持公平，同時仍然可以重現。模擬器用從進入節點起算的提示編號作為它的種子（`new Random(prompt)`）；Mod 則用 0。

遊戲的索引由宿主保存：以標準索引給出的回答，在遊戲看到之前就被轉換回去，而這一局的軌跡記錄的是遊戲的索引（[協定：觀測與動作 §4](/zh-tw/arch/protocol/observation/#sec-4)）。

## 6. 提示的上下文

每個選牌提示都經過遊戲的某一個 `CardSelectCmd.From*` 入口，而只有這些入口的參數說明了遊戲為什麼要問。`ChoiceContexts`（`ChoiceContexts.cs`）用 Harmony 捕捉它們。Harmony 是在執行時給遊戲方法打補丁的函式庫：**前綴**（prefix）在方法之前執行，**終結器**（finalizer）在方法之後執行，即使方法拋出例外也一樣。

- **目標**：每個公開靜態的 `CardSelectCmd.From*` 方法，包括每個多載，但 `FromChooseABundleScreen` 除外，它有自己的決策介面。這份清單是用反射找出的，所以遊戲更新新增的入口不需改動就會被打上補丁。
- **前綴**把入口的參數讀進一個 `ChoiceContext`（`ChoiceContexts.cs:47-68`）：`CardSelectorPrefs`（是否可取消、提示的文字）、`source` 參數，沒有時則是 `PlayerChoiceContext` 最後涉及的模型、一個 `CardPile`（有它時用途為 `<pile>_pile`）、一個 `EnchantmentModel` 及其 `amount`、`canSkip`。用途是入口名稱去掉 `From`，寫成 snake_case。`in_combat` 表示是否有戰鬥正在進行。
- **最外層的入口勝出**。一個入口可以呼叫另一個入口（刪牌會經過通用的牌組提示）：一個深度計數器保留第一個上下文，直到最外層的入口返回。
- **`Current` 與 `Last`**。入口執行期間，`Current` 按執行緒保存上下文；模擬器的選牌器在入口內部執行，就在那裡讀取它。在真實遊戲裡，提示的畫面在入口第一次 await 之後才開啟，那時 `Current` 已經不在了，所以前綴還把上下文存進 `Last`，一直保留到下一個入口，Mod 就從那裡讀取螢幕上的提示（[Mod：主迴圈 §5](/zh-tw/arch/mod/loop/#sec-5)）。新的上下文物件代表新的提示。
- **最先打這個補丁**。每個宿主在任何其他補丁之前呼叫一次 `ChoiceContexts.Patch`（模擬器裡在 `HeadlessPatches.Apply`，Mod 裡在 `Host`）。入口那個很小的 async 存根，可能被內嵌進一個更早編譯的呼叫方，例如在另一個補丁編譯它的替換方法時，而內嵌的那份副本會繞過前綴。無頭執行時 SapphireSeed 就發生過這種情況。

沒有上下文就到來的提示，在模擬器裡會拋出例外；Mod 則把它留給玩家。

## 7. SL 檢查點

`Checkpoint`（`Checkpoint.cs`）是 SL 下節點的起點（[模擬器：世界與 SL 複本 §3](/zh-tw/arch/simulator/worlds/#sec-3)）。兩種宿主取得它的方式相同，所以 Mod 送出的複本能在模擬器裡載入。

| 成員 | 做什麼 |
|---|---|
| `Take(player)` | 此刻的這一局：遊戲自己的存檔 `SaveManager.ToJson(RunManager.Instance.ToSave(null))`，加上每個遺物的簡單欄位，合成一個 JSON 字串 |
| `Open(checkpoint)` | 讀取它一次，供多次載入的節點使用：`Opened(Save, Relics)` |
| `RestoreRelics(opened, player)` | 存檔載入之後，把每個遺物原有的欄位還給它；如果載入的這一局的遺物和檢查點的不一致（按順序比），就拋出例外 |

遺物的**簡單欄位**是它的數字、旗標、列舉或 decimal 型別的可寫欄位，從它自己的類別沿著繼承階層往上，以類別和欄位名作鍵，並以與文化無關（culture-invariant）的格式寫出。存檔只保留遺物標記為要儲存的欄位；沒有這些簡單欄位，一個在戰鬥之間改變狀態的遺物（熔岩石在第一個頭目之後把自己停用）載入時會像剛拿到的新遺物。檢查點的 JSON 使用 .NET 的預設名稱（`Save`、`Relics`、`Id`、`Fields`），而不是協定的名稱：除了 `Checkpoint` 自己，它對一切都是不透明的。

## 8. 隱藏狀態鍵

搜尋需要知道兩個狀態何時是同一個狀態，才能只搜尋它一次。觀測不夠用：兩個狀態可能看起來一樣，打起來卻不同。`HiddenState`（`HiddenState.cs`）對觀測所隱藏的東西做雜湊。它從不進入大腦的決策；只有模擬器裡的搜尋世界會讀取它（[協定：世界與工作行程訊息 §1](/zh-tw/arch/protocol/worlds/#sec-1)）。

| 鍵 | 內容 | 使用者 |
|---|---|---|
| `Key(state, player)` | 抽牌堆的卡牌鍵，按順序；每一條一局層級和玩家層級亂數流的計數器；每個怪物自己的亂數流的計數器，以及它的下一招 | NoSL 世界 |
| `Full(state, player)` | `Key`，加上每個怪物到目前為止的招式（它的狀態日誌），再加上戰鬥歷史中本回合的條目（出牌、抽牌、棄牌、消耗、生成的牌、藥水、能力、格擋、能量），作為排序後的多重集 | SL 世界 |

本回合出牌的順序是刻意略去的：同樣的出牌換一種順序，應該匯合成同一個狀態。每個鍵都是它的文字的 `ProtocolJson.Hash`。
