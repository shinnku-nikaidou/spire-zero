大腦說的是協定，不認識任何遊戲（[協定](/zh-tw/arch/protocol/)）。總得有東西把遊戲的物件讀成協定的觀測、列出玩家可以做什麼，再把選定的動作帶回遊戲裡。這就是 GameBridge（`src/Sts2Ai.GameBridge`），一個由靜態類別組成的函式庫，兩種遊戲宿主都使用它：無頭執行遊戲的模擬器，以及真實遊戲裡的 Mod。因為兩者共用它，模擬器裡的一個決策和遊戲裡的同一個決策，是由同一份程式碼讀取和命名的。

<Aside title="狀態">

已有：每個畫面的觀測、每種決策介面（surface）和藥水欄的合法動作、模擬器打出的每個動作的開始執行（start）、按標準順序排列並帶有上下文的選牌提示、SL 檢查點，以及搜尋使用的隱藏狀態鍵。規劃中：公開歷史的事件流（[§5](#sec-5)）。

</Aside>

## 1. 三項工作

對每一種決策畫面，GameBridge 都有同樣的三項工作：

| 工作 | 輸入 | 輸出 | 範例 |
|---|---|---|---|
| **observe** | 遊戲的物件 | 一個協定觀測 | `Observe.Combat(state, player)` → `CombatObservation` |
| **legal** | 遊戲的物件 | 合法動作，以文字表示 | `MapActions.Legal(run)` → `["map:0,1", "map:3,1"]` |
| **start** | 一個合法動作 | 在畫面上點一下會發出的那個遊戲呼叫，並且已開始執行 | `MapActions.Start(run, player, "map:0,1")` → 對該地圖點的一次投票，和地圖畫面把它排入佇列的方式一樣 |

它不做的，是判斷**哪一個**畫面在提問，或等待遊戲完成一個動作。這兩件事都取決於畫面顯示什麼，而只有宿主在追蹤這一點：模擬器自己扮演各個畫面的角色（[模擬器：整局 §3](/zh-tw/arch/simulator/runs/#sec-3)），Mod 則查看正在顯示的畫面（[Mod：主迴圈 §4](/zh-tw/arch/mod/loop/#sec-4)）。GameBridge 只保留宿主賴以建構的純判定函式，例如 `CombatActions.WaitingForInput` 和 `RewardActions.IsTerminal`。

## 2. 規則

- **它夾在兩個世界之間，對兩邊都只碰必要的部分**。GameBridge 引用 Protocol 和遊戲的組件（`sts2.dll`、`GodotSharp.dll`、`SmartFormat.dll`，以及遊戲自帶的 `0Harmony.dll`，用於它唯一的那個補丁，[讀取遊戲 §6](/zh-tw/arch/gamebridge/observe/#sec-6)）。它從不引用 Brain，所以決策無法伸手進入遊戲。它不使用 Godot 節點（遊戲的畫面物件，即 `N*` 類別），無頭的遊戲不會建立這些節點；它的文件註解提到它們，只是為了說明畫面在哪裡顯示某個值。
- **觀測畫面所顯示的東西**。每個欄位都取自畫面所繫結的東西：能力的 `DisplayAmount` 和 `IsVisible`、遺物的 `ShowCounter`，意圖的傷害則透過圖示所用的同一個 `GetSingleDamage`。有兩處讀得更深，因為畫面確實顯示了這個值，卻把它存放在私有的地方：能力保存的牌，用反射讀取（`HeldCards`），以及升級預覽，在卡牌的副本上做出來（[讀取遊戲 §3](/zh-tw/arch/gamebridge/observe/#sec-3)）。
- **透過畫面自己的入口開始執行**。動作由遊戲按鈕所做的那個呼叫來執行：一張牌透過 `TryManualPlay` 打出，和從手牌拖出時一樣；一個地圖點由 `VoteForMapCoordAction` 選定，和地圖畫面把它排入佇列時一樣。從不直接修改狀態，也從不透過跳過遊戲檢查的呼叫（`CardCmd.AutoPlay`、直接 `new PlayCardAction`、`PlayerCmd.EndTurn`）。遊戲拒絕的開始執行會拋出例外。
- **不合法就是錯誤**。每個 `Start` 遇到不在其合法清單裡的動作都會拋出例外，而清單從不提供會失敗的東西：沒有空槽時的藥水、金幣不夠的購買。

## 3. 誰使用它

| 宿主 | observe | legal | start |
|---|---|---|---|
| 模擬器（`Sts2Ai.SimWorker`） | 每個決策 | 每個決策 | 它打出的每個動作（[模擬器：整局 §4](/zh-tw/arch/simulator/runs/#sec-4)） |
| Mod（`Sts2Ai.Mod`） | 它向大腦詢問的每個決策 | 同上 | 從不：Mod 只給建議，行動的是玩家。它給模擬器的 start 所呼叫的同一批遊戲入口打補丁，藉此記錄玩家自己的動作，所以 SL 記錄對一步的命名和模擬器完全相同（[Mod：SL 紀錄 §3](/zh-tw/arch/mod/sl-record/#sec-3)） |

Mod 把 GameBridge 的原始碼檔案編譯進自己，在遊戲裡執行。模擬器則以專案參考的方式引用它。CombatBuilder 是模擬器從觀測建構一場戰鬥的方式，它重用 GameBridge 的意圖讀取器，把怪物的招式和顯示出來的意圖對應起來（[模擬器：戰鬥 §5](/zh-tw/arch/simulator/combat/#sec-5)）。

## 4. 跟上遊戲

這個專案對遊戲程式碼所知道的一切，都放在三個地方：GameBridge、模擬器的補丁（[模擬器：無頭宿主 §4](/zh-tw/arch/simulator/headless/#sec-4)），以及 Mod 讀取畫面的程式碼和鉤子（[Mod：主迴圈 §4](/zh-tw/arch/mod/loop/#sec-4)）。遊戲更新時：

1. 反編譯新版遊戲，並針對它重新建置（`Sts2BinDir`，[模擬器：參考 §1](/zh-tw/arch/simulator/reference/#sec-1)）；
2. 執行 `selftest`，再跑幾批 `run --check`，遇到驅動程式不認得的畫面、任何不合法的回答或任何遊戲錯誤，它們都會失敗，並列出從未到達的決策介面（[模擬器：整局 §5](/zh-tw/arch/simulator/runs/#sec-5)）；
3. 閱讀 GameBridge 所碰到的遊戲簽章的差異；選牌提示的入口是用反射找到的，所以新增的入口不需改動就會被打上補丁，但它的參數仍然需要看一下。

Mod 拒絕在不是它建置時所針對的遊戲版本上執行（[Mod §3](/zh-tw/arch/mod/#sec-3)）。

## 5. 規劃中：事件流

一局的公開歷史（抽到和移動的牌、出牌、顯示的意圖、看過的畫面）將來自遊戲自己的鉤子 <Badge text="推斷" variant="caution" />：

- 手牌、抽牌堆、棄牌堆和消耗堆上的 `CardPile.CardAdded` 與 `CardRemoved`（`Entities.Cards/CardPile.cs:35-37`）提供抽牌、移動和生成的牌，插入抽牌堆時還有插入的位置；
- `ActionExecutor.AfterActionExecuted`（`GameActions/ActionExecutor.cs:56`）提供出牌；
- `CombatManager.TurnStarted`（`Combat/CombatManager.cs:273`），加上一份意圖快照，提供回合；
- 洗牌表現為抽牌堆從棄牌堆補滿；洗牌指令本身還有待找到。

只有玩家本來看得到的東西才會放進去：插入到隨機位置的牌，記錄時不帶位置。格式見 [協定：觀測與動作 §8](/zh-tw/arch/protocol/observation/#sec-8)。

## 6. 測試

| 測試什麼 | 在哪裡 |
|---|---|
| GameBridge 確實觸及遊戲（邊界檢查的對照） | `BoundaryTests` |
| 每個戰鬥觀測和動作都能完整往返；從觀測建構出的戰鬥會分毫不差地顯示這些觀測 | `selftest`（[模擬器：參考 §5](/zh-tw/arch/simulator/reference/#sec-5)） |
| 每種決策介面的觀測都能完整往返；大腦給出的每個回答都合法，並能無錯誤地開始執行；對局能完全重播，節點也包括在內 | `run --check`（[模擬器：整局 §6](/zh-tw/arch/simulator/runs/#sec-6)） |
| Mod 的 SL 記錄在它們的複本上重播時，顯示的觀測和遊戲當時顯示的相同 | `clones`（[Mod：SL 紀錄 §8](/zh-tw/arch/mod/sl-record/#sec-8)） |

規劃中：Mod 裡的一項檢查，確認畫面上每個啟用的控制元件都是一個合法動作；以及相同的種子和決策在遊戲和模擬器裡給出相同的觀測（[評估 §2](/zh-tw/arch/evaluation/#sec-2)）。
