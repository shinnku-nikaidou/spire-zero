搜尋幾乎所有的時間都花在戰鬥上：戰鬥大腦為每個決策嘗試數千種打法（[戰鬥大腦](/zh-tw/arch/combat-brain/)）。本頁講其中模擬器這一側的事：一場戰鬥如何在遊戲自己的程式碼裡執行（**戰鬥工作階段**）、搜尋如何回到較早的某一點（快照與重播）、它如何猜測看不到的東西（確定化）、它如何只憑一份觀測就建構出一場戰鬥（**CombatBuilder**）、這樣建出的戰鬥能信任到什麼程度，以及這一切的成本。

## 1. 戰鬥工作階段

`CombatSession`（`Simulation/CombatSession.cs`）在真實引擎裡跑一場戰鬥。它由這樣一個 record 設定，

```csharp
CombatSetup(string Character, EncounterModel Encounter, int ActIndex, string Seed, int Ascension = 0,
    Loadout? Loadout = null, CombatObservation? From = null, IReadOnlyList<EnemyTurns>? History = null)
```

並分四步啟動：

1. `Player.CreateForNewRun(character, UnlockState.all)`，然後套用配置（牌組、遺物、藥水、生命值：[參考 §3](/zh-tw/arch/simulator/reference/#sec-3)）；
2. 用 `MockSinglePointActMap`（只有一個點的地圖）呼叫 `RunState.CreateForTest`；
3. `RunManager.SetUpTest`；
4. `EnterRoomDebug(Monster, encounter)`。

有 `From` 時，接著讓這場戰鬥顯示那份觀測（[§5](#sec-5)），`History` 則給它的怪物之前出過的招式。

這**不是**一局進入戰鬥的方式：它跳過了擲出 `?` 會變成什麼，也跳過了這一局的房間生成（`GenerateRooms`）<Badge text="已核實" variant="success" />。對單獨的一場戰鬥（基準測試、`selftest`、搜尋世界）這沒有問題，對整局則是錯的，整局以遊戲開局的方式開始（[整局 §2](/zh-tw/arch/simulator/runs/#sec-2)）。

**遊玩**。`Execute(action)` 透過 `CombatActions.Start` 發起一個動作，也就是 UI 所用的同一批入口（[GameBridge：各決策介面的動作 §1](/zh-tw/arch/gamebridge/actions/#sec-1)），然後穩定下來：一直推動 Pump，直到遊戲再次等待玩家（[無頭宿主 §7](/zh-tw/arch/simulator/headless/#sec-7)）。結束回合之後，它等到之後的某個回合；戰鬥結束之後，則等到佇列為空且執行器閒置（`CombatSession.cs:216-223`、287-302）。超過戰鬥回合上限的戰鬥也在穩定時算輸，和整局裡一樣：一到第 81 回合玩家的回合，玩家就死去（[整局 §3](/zh-tw/arch/simulator/runs/#sec-3)）。由策略打完的戰鬥（`PlayOut`，推演和基準測試都這樣做）還會在 1,000 個動作時停止；這時它的結果是 `Truncated`，戰鬥結束時仍有敵人活著也是如此（`CombatSession.cs:73`、185-193）。

**uid**。動作用 **uid** 指稱卡牌和生物，uid 是取自遊戲的穩定 id，而不是在清單中的位置：手牌用它的 `NetCombatCardDb` id，生物用它的 `CombatId`。`play:7:2` 表示把 7 號牌打向 2 號生物。遊戲以固定的順序給牌編號，所以重播會保留同樣的編號（[協定：觀測與動作 §4](/zh-tw/arch/protocol/observation/#sec-4)）。

## 2. 快照是配方

搜尋必須能退回去：試一條線，回到決策點，再試另一條。遊戲無法複製它的狀態（它的物件綁在持有那唯一一場活著的戰鬥的單例上），所以快照不是一份複製品，而是一份**配方**：`(Setup, Trace)`，即這場戰鬥如何開始，以及之後走過的每一步。軌跡的每一步是下列之一：

- `Action`：一個戰鬥動作，以文字形式表示（`play:7:2`、`end_turn`）；
- `Choice`：對選牌提示的回答，用遊戲自己的選項索引表示；
- `Determinize(seed)`：一個確定化步驟（[§3](#sec-3)），文字形式為 `determinize:SEED`。

**還原**一個快照，就是從它的設定開一場新戰鬥，再重播軌跡（`CombatSession.cs:103-124`）。同樣的設定和軌跡總是給出同樣的狀態，因為每次隨機抽取都來自帶種子的亂數流，而 Pump 以同樣的順序執行每個後續。唯一用時鐘做種子的產生器 `Rng.Chaotic` 只供給外觀 <Badge text="已核實" variant="success" />：怪物造型、螢幕震動、假商人的對白、審判（Trial）事件的參賽者編號、美味餅乾（YummyCookie）的圖示、加牌動畫的時間點、茂密植被（DenseVegetation）的視覺偏移。另有三條後備路徑也會用到它，模擬器一條都不會碰到：並非場上實例的怪物模型（場上的怪物都有帶種子的流）、沒有種子就開始的一局（模擬器總會傳入種子），以及在地化文字的隨機變體（在地化回傳的是鍵名，[無頭宿主 §4](/zh-tw/arch/simulator/headless/#sec-4)）。

重播花的時間與它的長度成正比：一次還原花 0.28 ms，外加每個重播動作 0.073 ms。SL 世界載入的是節點的檢查點，而不是開一場新戰鬥，它約為 0.5 ms，外加自進入節點以來每一步 0.1 ms（[世界與 SL 複本 §7](/zh-tw/arch/simulator/worlds/#sec-7)）。下圖把這兩種成本模型並排；拖動滑桿，可以還原到戰鬥中更深的位置。

## 3. 確定化

`Determinize(seed)` 把玩家不可能知道的一切換成由 `seed` 抽出的樣本，玩家看得到的東西則保持不變（`CombatSession.cs:230-276`）。NoSL 的搜尋就是這樣猜測隱藏狀態的；[環境：世界 §2](/zh-tw/arch/environments/worlds/#sec-2) 說明了原因，並附有一張以真實抽牌堆為例的圖。它做的事：

- 為每條整局亂數流（`RunRngType`）、每條玩家亂數流（`PlayerRngType`）以及每個場上怪物的亂數流重新播種，盟友和寵物也包括在內；
- 重排抽牌堆：先按卡牌鍵排序（這個順序只取決於玩家看得到的東西），再用樣本做一次 Fisher–Yates 洗牌；
- 重新給手牌以外的牌編號（`CombatBuilder.NumberCards`）：遊戲按抽牌順序給牌編號，舊的編號會洩漏真實的順序；
- 對每個敵人，在顯示相同意圖的招式中均勻地重新抽取它排定的招式，並把它招式日誌的最後一項（`StateLog[^1]`）改寫成與之一致。

種子只來自呼叫方，絕不來自這一局。沒有建模的：玩家知道位置的抽牌堆卡牌（例如剛放到頂上的那張），以及怪物的歷史如何讓某些招式比其他招式更可能出現（`CombatSession.cs:241-242`）。

## 4. 隱藏狀態與換位

搜尋會記住它已經搜尋過的狀態，好讓同一組出牌的兩種順序只被搜尋一次。一個狀態是觀測，其中手牌、棄牌堆和消耗堆作為牌的多重集合（[戰鬥大腦：提示、招式與 worker §5](/zh-tw/arch/combat-brain/shared/#sec-5)），加上觀測所隱藏、而且會改變接下來發生什麼的東西。`HiddenState.Key`（`GameBridge/HiddenState.cs:19-29`）對抽牌堆的順序、每條整局流、玩家流和怪物流的位置（計數器），以及每個怪物排定的招式做雜湊。本回合出牌的順序是刻意排除在外的。`HiddenState.Full`（`:36-44`）是 SL 世界的鍵，它再加上每個怪物的招式日誌，以及戰鬥歷史中本回合的各項，作為一個多重集合（[環境：世界 §4](/zh-tw/arch/environments/worlds/#sec-4)）。

## 5. CombatBuilder：從觀測建構一場戰鬥

在 NoSL 下，搜尋不可以從真實的戰鬥出發：那會把真實的隱藏狀態帶進搜尋。它從一場**顯示這份觀測**、除此之外別無其他的戰鬥出發。`CombatBuilder.Setup(obs, seed, history)`（`Simulation/CombatBuilder.cs:57-105`）建構這樣一場戰鬥：

1. 用觀測裡的牌組、遺物和生命值**開始**觀測中的遭遇。開戰時的效果可能殺死生命值很低的玩家（王室毒藥在第一回合開始時造成 4 點傷害，而每次建構都從第一回合開始），死去的玩家的遺物、能力和卡牌就不再起作用。這樣的戰鬥會以滿生命值重新開始（`CombatSession.cs:157-161`），下一步再照常設成觀測到的生命值。按開戰時的生命值記下一個旗標的遺物（紅頭骨的力量）這時可能不對，只有這種罕見的開局才有這個風險。
2. **`Apply`** 覆寫一切可見的東西：回合數；敵人（新增、移除、重新排序）；生命值和格擋；能量、最大能量和星辰；金幣；藥水；充能球欄位和充能球，連同它們顯示的數值；遺物計數器（顯示的或隱藏的）、狀態、熔化的和用盡的遺物；遺物保存的牌（佩爾之牙的牌，它的計數就是牌數），用標準副本，因為提示框不顯示升級，而且這些牌要到戰鬥之後才回來；能力，圖示顯示另一個數字時連同其層數，以及能力保存的牌；四個牌堆，一張一張地，連同每張牌的修改；意圖。
3. **`Resample(StableHash(seed))`** 抽取隱藏狀態，和確定化的做法一樣。
4. **`BuildDifferences`** 按 JSON 路徑比較輸入的觀測和重建後戰鬥的觀測。為空就表示完全一致。NoSL 世界拒絕任何不完全一致的建構（`Simulation/SimWorlds.cs:37-48`）。

困難的部分，每一項都在建構器裡解決了：

- **旋鈕求解**。螢幕上的數字是從內部數字算出來的，每種能力或遺物的算法都不同。建構器嘗試各種內部數字（數值、動態變數、欄位，以及能力內部資料裡的整數和小數欄位，例如 `HARDENED_SHELL_POWER` 本回合已受的傷害），直到顯示一致（`CombatBuilder.cs:418-460`）。觀測中已用盡的遺物（用過的 `LIZARD_TAIL`、沒有飛行次數的 `WINGED_BOOTS`），在它的計數器之後，以同樣的方式嘗試它的整數和布林欄位，直到重建的遺物也用盡，且計數器與觀測相同：`SILVER_CRUCIBLE` 要等計數器用完、並且進過財寶房之後才算用盡。
- **意圖**。建構器在顯示所觀測意圖的招式中做選擇（`CombatBuilder.cs:164-213`）。被眩暈的敵人得到一個合成的眩暈招式，做法與 `Creature.StunInternal` 相同（`FollowUpStateId = StateLog.Last().Id`）。先搜尋能力裡隱藏的列舉開關（`SurroundedPower._facing`），再搜尋怪物自己的整數欄位，讓盡可能多的敵人吻合：先試 0–99，再試 100–999；瀑布巨獸的噴發傷害每次發動都會成長，超過 100 時就是這樣找到的。
- **uid** 與觀測的一致；其他的牌編在它們之上。牌先按 id、升級和附魔從新牌組裡取用，取不到才新建（`CombatBuilder.cs:510-537`）。
- **盟友**。玩家一側的生物像敵人一樣建構：遺物帶來的寵物在開戰時加入，按怪物 id 對上；缺少的那個則以玩家寵物的身分加入，就像召喚產生它時那樣（`CombatBuilder.cs:312-339`）。任何角色都能用另一個角色卡池裡的牌召喚奧斯提（`KALEIDOSCOPE` 會提供這種牌）。
- **費用**。牌自己的費用被設成：疊上它之上的修正（能力、遺物）之後，得到顯示的費用；它可以低於 0（`CombatBuilder.cs:578-586`）。被攻擊藥水在本回合變成免費的 `PINPOINT`，本回合每打出一張技能牌就再少 1 費，而在纏結之下（`TANGLED_POWER` 加 1）它仍顯示 0。
- **瘋狂科學**。來自動手改造事件的牌，會取回事件所選的類型和附加效果，這些都顯示在它的牌框和文字上（`CombatBuilder.cs:553-557`，[協定：觀測與動作 §3](/zh-tw/arch/protocol/observation/#sec-3)）。
- **招式日誌**。怪物按它出過的招式選擇下一招（同一招不連出三次、固定循環），而新開的戰鬥日誌裡一招也沒有。有了每個敵人在每回合開始時顯示了什麼的紀錄（[Harness §4](/zh-tw/arch/harness/#sec-4)），每個怪物都會得到它的日誌：先是之前每個回合的招式，再是當前這一招（`CombatBuilder.cs:119-154`）。之前的某個回合，對應顯示相同意圖的招式；沒有的話，對應意圖類型和段數相同的招式；再沒有的話，對應類型相同的招式，因為數值會隨怪物的力量成長。只要有一個回合對應不到任何招式，這個怪物就保留新開的日誌。眩暈和遊戲裡一樣不進日誌：顯示為眩暈的回合略過；當前被眩暈的怪物，在眩暈之後繼續出它在本回合開始時顯示的那一招。沒有紀錄時，每個怪物都是新開的日誌。
- **第一招**。從第 2 回合起，建構器會標記怪物已經出過第一招（`_performedFirstMove`）。

**近似**。建構器看不到的東西就用近似：本回合的歷史，以及能力和怪物內部的計數器；費用修正持續多久；玩家減益的衰減；沒有紀錄時眩暈的後續招式；還有牌組，它是見過的每一張牌，包括生成的牌。[§6](#sec-6) 說明它們在哪裡顯現；它們沒有與真實遊戲的觀測核對過。

**由 `selftest` 檢查**：它把每場戰鬥在最多三個隨機點切開，再從每個切點的觀測建構一場戰鬥；建出的戰鬥必須顯示這份觀測、能夠還原，並能繼續打下去，任何一次建構做不到，`selftest` 就失敗。其他的 `selftest` 建構會顯示只有模型自身狀態才持有的數字：一顆磨損的玻璃充能球、一個用過的白銀坩堝、保存著兩張牌的佩爾之牙、3 之 1 的怠惰、夢魘的複製牌、本回合受過傷之後的硬殼、帶著王室毒藥以 3 點生命值開局、超過 100 的噴發（[參考 §5](/zh-tw/arch/simulator/reference/#sec-5)）。

## 6. 保真度：建出的戰鬥能信任到什麼程度

建出的戰鬥顯示了這份觀測：它的 `BuildDifferences` 為空，否則 NoSL 世界拒絕它（[§5](#sec-5)），而任何一次建構沒有顯示它的觀測，`selftest` 就失敗（[參考 §5](/zh-tw/arch/simulator/reference/#sec-5)）。它接下來打起來是否和真實的那場一樣，是另一個問題，分兩部分。有些差異是刻意的設計：確定化抽取抽牌順序、亂數流和每個怪物的下一招（[§3](#sec-3)），所以每個世界在這些方面都刻意與真實戰鬥不同。其餘的差異來自建構器的近似（[§5](#sec-5)）：觀測沒有顯示、建構器也不去求解的東西，它保持新開戰鬥時的樣子。

這些近似在決策點上看不出來，因為建構結果與觀測一致；它們之後才顯現，大多在敵人的回合裡，透過怪物內部那些沒有任何畫面顯示的計數器。`TWO_TAILED_RAT` 是最直接的例子：它能不能呼叫援軍，取決於距離可以召喚還有幾回合、到目前為止召喚了幾次（`Models.Monsters/TwoTailedRat.cs:40-42`）。只有在不改就沒有任何招式能顯示其意圖時，建構器才會去動怪物自己的欄位（[§5](#sec-5)），所以建出的這隻老鼠通常帶著新開時的計數，牠的下一個意圖就可能與真實的那隻不同。沒有敵人招式的紀錄（[Harness §4](/zh-tw/arch/harness/#sec-4)）時，要猜的更多：每個怪物都從新開的招式日誌開始，被眩暈的怪物的後續招式也只能近似。

## 7. 速度

在 Release 建置、`DOTNET_ReadyToRun=0` 下測得（[無頭宿主 §6](/zh-tw/arch/simulator/headless/#sec-6)）。這裡的幕從 1 數起，和遊戲顯示的一樣；命令列的 `--act` 則從 0 數起。

**戰鬥**。`bench` 用佔位策略在一個遭遇池上盡可能快地打戰鬥，印出每秒戰鬥數和動作數、每場戰鬥用時以及它的峰值記憶體（[參考 §4](/zh-tw/arch/simulator/reference/#sec-4)）。用第 1 幕的弱遭遇和普通遭遇、`play` 策略，一個行程打 3,000 場戰鬥，每秒約 275 場，含啟動（見下圖）。短批次每場戰鬥用時更長：啟動和 JIT 預熱在其中佔的比重更大。

**分支**。這裡的一個搜尋分支是一次還原、一次確定化，以及用佔位策略推演到戰鬥結束。它的還原花 0.28 ms，外加每個重播動作 0.073 ms（[§2](#sec-2)），所以分支在戰鬥中開始得越深，它的時間裡重播佔得越多。

**搜尋工作行程的時間花在哪裡**。搜尋工作行程大部分時間在搜尋，其中還原世界佔得最多：從設定開始戰鬥（進入房間、套用觀測、重新取樣）、重播這條線和確定化。打出被搜尋的動作、產生觀測和戰鬥網路佔其餘部分。還原時不比較建構結果與觀測：請求中的第一次建構已經檢查過（[世界與 SL 複本 §2](/zh-tw/arch/simulator/worlds/#sec-2)）。

**更多行程**（每個行程 `bench` 3,000 場戰鬥；實際經過時間包含每個行程約 1.2 s 的啟動）。這台機器有 8 個實體核心；超執行緒約多出 8%。預設的池是 8 個行程（`--workers`，每個世界一個）。

**可用的手段**，按順序：避免深層重播（在深度優先搜尋中重用前綴；節點檢查點，[世界與 SL 複本 §3](/zh-tw/arch/simulator/worlds/#sec-3)）；按鉤子過濾鉤子監聽器，這需要先對鉤子分派做效能剖析（用 `perf` 這樣的效能剖析工具）；物件圖的深複製，它能消除重播成本，AlphaZero 式的搜尋也會需要它。要複製還是重播，是一個尚未解決的問題（[參考 §8](/zh-tw/arch/simulator/reference/#sec-8)）。
