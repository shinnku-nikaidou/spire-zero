## 1. 建置與執行

模擬器是 .NET 專案 `src/Sts2Ai.SimWorker`（目標 `net9.0`），一個帶有許多指令的程式。它參考遊戲自己的組件：`sts2.dll`、`GodotSharp.dll`、`SmartFormat.dll`，以及遊戲為 Mod 附帶的 `0Harmony.dll`，取自遊戲的一份唯讀快照，不複製到它的輸出裡（`src/GameReferences.props:8-19`）。

| 設定 | 在哪裡 | 作用 |
|---|---|---|
| `Sts2BinDir` | MSBuild 屬性，預設 `tmp/gamebin/v0.111.0` | 建置所參考的遊戲快照，會寫進程式裡 |
| `STS2_BIN_DIR` | 環境變數，執行時 | 覆蓋寫進程式的快照；如果那裡沒有 `sts2.dll`，程式拒絕啟動（`Program.cs:35-48`） |
| `TieredCompilation` | `Sts2Ai.SimWorker.csproj:12-20`，關閉 | 每個方法只編譯一次，完全最佳化：分層編譯會在背景重新 JIT 熱門方法，Harmony 補丁可能悄悄失效（在幾千場戰鬥之後見過）；它在短的對局上也慢了 2 倍 |
| `DOTNET_ReadyToRun=0` | 環境變數，由啟動腳本設定 | 框架程式碼也以完全最佳化的方式 JIT 編譯，每秒多約 20% 的戰鬥；缺少它時，輸出的第一行會說明 |
| `SourceRevisionId` | MSBuild，來自 git | 寫進程式的提交，記錄和報告都帶著它；`src/` 下有未提交改動的建置會加上 `-dirty`（`Sts2Ai.SimWorker.csproj:36-48`） |

遊戲的組件由一個解析器找到，它在任何遊戲型別被編譯之前就已安裝好；所以使用這些組件的進入點 `Cli.Run` 不能被內嵌到 `Main` 裡（`Program.cs:10-12`、`Commands/Cli.cs:44`）。

**啟動腳本**。批次和機群執行的是某個固定提交的建置，而不是工作樹：`tmp/build.sh REV`（一個本地腳本）把這個提交打包，以 Release 建置，把 `SourceRevisionId` 設為這個提交，並寫出 `tmp/builds/REV/sim.sh`；它用 `DOTNET_ReadyToRun=0` 執行那個建置的 dll，並把 `HOME` 指向 `tmp/home`。所以透過它啟動的 `brain`，除非 `--socket` 另行指定，否則在 `tmp/home/.local/state/sts2ai/brain.sock` 監聽（[整局 §7](/zh-tw/arch/simulator/runs/#sec-7)）。機群的主機拿到同樣的建置和它們自己的啟動腳本（fleet 技能，`.claude/skills/fleet/SKILL.md`）。

## 2. 命令列

```text
Sts2Ai.SimWorker COMMAND [options]
```

- **解析**用的是 System.CommandLine 2.0.14。`--help` 在根和每個指令上都能用。`--verbose` 放在任何指令之後都能用。沒有回應檔案（response file）：以 `@` 開頭的參數就是一個參數（`Commands/Cli.cs:24`）。
- **stdout 只帶結果**，供腳本讀取；日誌寫到 stderr，每條一行，`12:34:56 INFO    sim: message`，例外的文字在後面幾行（`Runtime/Logs.cs:43-60`）。等級是 Information 及以上，用 `--verbose` 時是 Debug。遊戲自己的日誌歸入類別 `game`：它的錯誤和警告分別在 Error 和 Warning，其他行在 Debug（[無頭宿主 §8](/zh-tw/arch/simulator/headless/#sec-8)）。
- **啟動**。只有需要遊戲的指令才會啟動它（`Cli.Game`）；`brain`、`report`、`gate`、`leaderboard` 和 `seeds` 不啟動。

**結束代碼**（`Commands/Cli.cs:45-67`）：

| 代碼 | 意義 |
|---|---|
| 0 | 完成 |
| 1 | 完成，但有失敗：失敗的戰鬥或對局、不同的重播、遊戲錯誤、沒有通過的門檻 |
| 2 | 命令列或它指定的檔案有錯（也包括 I/O 錯誤、不是有效 JSON 或不是有效資料的檔案） |
| 70 | bug；它的堆疊會被記錄下來 |

按指令：`run`、`bench`、`selftest` 和 `clones` 有失敗時以 1 結束，`gate` 在沒有通過時以 1 結束；`list`、`tables` 和 `combat` 完成時總是以 0 結束；`serve` 在它第一個失敗的請求之後以 1 結束。

## 3. 選項組

有幾組選項由多個指令共用，定義在 `Commands/Args.cs`。

**配置**（loadout，`Args.cs:43-58`）：取代起始配置。

| 選項 | 預設 | 意義 |
|---|---|---|
| `--character` | `SILENT` | 角色 |
| `--deck` | 起始牌組 | `A*5,B+,C+2@SHARP:2`：`*N` 重複，`+` 或 `+N` 升級，`@ENCHANT:AMOUNT` 附魔（`Simulation/Loadout.cs`） |
| `--relics` | 起始遺物 | `A,B`；取代起始遺物，它們的藥水槽生效，在一局裡它們跳過 `FinalizeStartingRelics` |
| `--potions` | 無 | `A,B`；沒有空槽時拋出例外 |
| `--hp` | 角色的 | 起始生命值，限制在最大生命值以內 |
| `--max-hp` | 角色的 | 起始最大生命值 |

**戰鬥池**（pool，`Args.cs:61-96`）：哪些戰鬥，然後是配置。

| 選項 | 預設 | 意義 |
|---|---|---|
| `--act` | 0 | 幕，從 0 算起 |
| `--rooms` | `weak,regular` | 房間種類，取自 `weak`、`regular`、`elite`、`boss` |
| `--encounter` | 無 | 改為單一遭遇；它也會設定幕 |

**預算**（budget，`Args.cs:108-151`）：戰鬥大腦的預算。plan 的選項需要 `--policy plan`。

| 選項 | 預設 | 意義 |
|---|---|---|
| `--worlds` | 8 | PIMC 每個決策的世界數 |
| `--nodes` | 300 | 每個世界的節點數；對 plan 是每個狀態每回合的節點數 |
| `--effort` | `medium` | plan 的力度檔位：`low` 束寬 8、簡易束 2、失敗計畫 3；`medium` 束寬 8、簡易束 4、失敗計畫 3；`high` 束寬 8；`max` 束寬 16；全都是 300 個節點、重新規劃 1（`src/Sts2Ai.Brain/Combat/CombatBrain.cs:20-27`） |
| `--beam` | 力度檔位的值 | plan 每回合保留的狀態數（至少 1） |
| `--easy-beam` | 力度檔位的值 | 貪婪下潛獲勝時保留的狀態數（0：`--beam`） |
| `--replan` | 力度檔位的值 | 未證明的失敗計畫被沿用幾個回合後再重新規劃（0：沿用到底） |
| `--loss-plans` | 力度檔位的值 | 每場戰鬥連續幾個未證明的失敗計畫（0：不限） |

**葉節點**（leaf，`Args.cs:154-162`）：用什麼評估搜尋中未結束的路線。

| 選項 | 意義 |
|---|---|
| `--combat-net FILE` | 戰鬥網路檔案，評估還在進行中的葉節點；已結束的戰鬥按 `LeafValue` 的定價計分。`pimc` 和 `plan` 需要它，`selftest` 也需要 |

**冠軍**（champion，`Args.cs:197-238`）：構成一個冠軍的選項，用於 `run`、`brain` 和 `gate`。

| 選項 | 預設 | 意義 |
|---|---|---|
| `--policy` | `play` | 戰鬥大腦：`pimc`（僅限 NoSL）、`plan`（僅限 SL），或佔位策略 `play` |
| `--macro` | `random` | 戰鬥外的大腦：`l0`（帶 V 的宏觀大腦）或 `random` |
| 預算選項 | | 見上 |
| `--workers` | `--worlds` | 工作行程數，用於 `pimc`、`plan` 或 `--afterstates clone` |
| `--value FILE` | 無 | l0 的 V，一個網路檔案；`--value` 和 `--macro l0` 一起用 |
| `--afterstates` | `screen` | `clone` 在節點的複本上把每個選項打一遍（SL，`l0`） |
| 葉節點選項 | | 見上；`pimc` 和 `plan` 需要它們，也只有這兩者接受它們 |
| `--explore ε` | 0 | l0 把比例 ε 的決策在它們的選項之間均勻抽取，用於自我對弈；需要 `l0`，`gate` 拒絕它 |

**冠軍檔案**，`--champion FILE`（`Args.cs:165-192`），用於 `run` 和 `brain`：打冠軍檔案指明的冠軍（[評估：冠軍與基線 §1](/zh-tw/arch/evaluation/champions/#sec-1)）。檔案的選項排在給出的選項之後，所以給出的選項優先；其中包括它的 `character` 和 `asc`。沒有 `--env` 的指令（`brain`）會略過檔案的 `env`；給出的 `--policy` 如果和檔案的不同，就保留它自己的預算。`gate` 的 `--champion` 是另一個選項：要擊敗的冠軍。

## 5. `selftest`

`selftest` 打戰鬥池裡的 `--n` 場戰鬥（預設 20 場），並執行下列檢查，按它報告時使用的名稱列出（`Checks/SelfTest*.cs`；順序見 `Checks/SelfTest.cs:73-146`）。其中的搜尋用 `--combat-net` 指定的網路評估葉節點，所以必須給出它。任何一項失敗就以 1 結束。

邊界，即 Brain、Protocol 和 Harness 不觸及任何遊戲組件，由單元測試 `BoundaryTests` 在不啟動遊戲的情況下檢查（[§7](#sec-7)）。

**每場戰鬥**，打兩次：確定性（觀測、隱藏狀態和軌跡）、協定往返（觀測，以及動作的文字形式和 JSON 形式）、沒有例外、沒有遊戲錯誤。

**每場戰鬥最多三個隨機切點**（所以在預設的 `--n 20` 下有 60 次建構檢查）：還原；隱藏狀態的還原，逐位元組相同；快速鉤子監聽器給出遊戲原本的結果；確定化保持觀測不變（種子 11 和 22）；確定化之後能重播；確定化之後能繼續打；然後是在切點的觀測上用 `CombatBuilder`：建構出的戰鬥顯示這個觀測，建構出的戰鬥能還原，建構之後能繼續打。

**只存在模型裡的數值的建構**（故障機器人）：一個磨損的玻璃充能球（3/6）、一個用完的白銀坩堝、留著 2 張牌的佩爾之牙、1/3 的怠惰、夢魘、14/20 的硬殼；建構保留一個能力的層數（怠惰仍然允許打出一張牌）和一個能力所帶的牌（夢魘下回合的複製牌）。然後：以 3 點生命值、帶著王室毒藥建構的玩家能活過開局；能找到瀑布巨獸超過 100 的噴發（`DeathBlow` 150）。

**規則**：滾動巨石一個接一個地打敵人（鐵甲戰士帶 10 張滾動巨石，對上戰鬥池裡第一個多敵人的遭遇；如果戰鬥池裡沒有這樣的遭遇，檢查就失敗）；Sly 出牌途中荊棘造成的擊殺沒有遊戲錯誤；配置的遺物給出它們的藥水槽，在戰鬥裡，也在晉階 4 的一局裡；死在玩家自己的行動之中，或死在第一回合開始時，這場戰鬥在記錄裡仍有結束；超過戰鬥回合上限的戰鬥算輸（在第 80 回合以 999 生命值建出來，這時戰鬥仍在進行，那個回合結束後就輸了）；觀測顯示一張牌在戰鬥中累積的東西：謀殺算出的數字、Spiral 附魔給的額外打出次數、打出後用掉的 Glam。

**世界與複本**：世界在選牌提示之後能還原（暖烘烘手套和生存者，6 個世界）；SL 世界顯示這一局的戰鬥，打起來和這一局一樣，並能還原；SL 複本停在它節點的出口，拒絕越過出口再走一步；SL 複本保留存檔丟掉的遺物狀態（手動把第一個遺物設為停用）。

**循環**（寂靜獵手對 535 點生命值，300 個節點）：Monologue 和兩張 Flash of Steel 互相抽到；SL 規劃器（束寬 8）把這個循環重複到獲勝，SL 世界照計畫結束這場戰鬥，PIMC 在 2 個世界上發現它的路線在重複。然後在循環前面加一個提示再測一次：粒子牆要花星，瘋狂之觸能讓它免費，而 `p0` 會把免費給 Haze。

**SL 計畫成立**（一局的第二場戰鬥，150 個節點，束寬 4）：SL 世界照計畫結束它的戰鬥（一場勝利），並拒絕越過結束再走一步；這一局重新打到那個決策，一步一步地照著計畫打；戰鬥的結局正如計畫的估值所說，誤差在 1e-9 以內。

**使用 `--workers N` 時**：池化的 PIMC 在 4 個決策上與行程內的 PIMC 相符，每個決策用 4 個世界 × 120 個節點的預算；池化的規劃器做出的計畫和規劃器在單一行程裡做出的一樣；工作行程裡沒有遊戲錯誤；沒有工作行程重啟。

最後它印出抽牌順序的統計，這不是一項檢查。2026-10-27 的結果：每項檢查都通過，寂靜獵手 60 次建構裡成功 60 次，鐵甲戰士 58 次裡成功 58 次，寂靜獵手第 1、2、3 幕的菁英戰和頭目戰分別是 57、57 和 58 次（[戰鬥 §5](/zh-tw/arch/simulator/combat/#sec-5)）。

## 6. `run --check`

`run --check` 對它打的每一局比較什麼（[整局 §6](/zh-tw/arch/simulator/runs/#sec-6)）：

| 檢查 | 要求 |
|---|---|
| 每個觀測的 JSON 往返 | 完全相同 |
| 透過線路打第二遍，連到行程內的大腦或給定的 `--brain` | 相同的軌跡、觀測雜湊、摘要、地圖雜湊、對局記錄和決策日誌（耗時除外） |
| 第一遍的每個節點，從檢查點載入並重播它的決策 | 逐一顯示這一局的觀測；移動之後停在視野邊界；拒絕再走一步 |
| 遊戲錯誤 | 沒有 |

這時每局的結果行以 `obs <digest>` 結尾，這是由這一局所有觀測雜湊算出的一個雜湊，用來跨行程比較對局；總計裡會多出 `determinism:` 一行。用 `--brain` 時，大腦的決策日誌不在這個行程裡，所以日誌比較是在比較兩份空日誌。

## 7. xUnit 測試

## 8. 未決問題

1. **複製還是重播**。快照是一份配方，還原就是重播它（[戰鬥 §2](/zh-tw/arch/simulator/combat/#sec-2)）。對遊戲的物件圖做深複製可以省掉重播的代價，AlphaZero 式的搜尋會需要這一點。等效能剖析顯示還原佔了搜尋的大部分時間時再決定。
2. **整局世界**：房間池和機率計數器有多少能從公開紀錄推斷，有多少必須來自先驗（[世界與 SL 複本 §8](/zh-tw/arch/simulator/worlds/#sec-8)）。
3. **內嵌執行**：無頭時內嵌執行動作，而不是每影格一次，是否會改變玩家看得到的任何東西；要等遊戲裡的對局能和這裡的對局比較時才知道（[整局 §6](/zh-tw/arch/simulator/runs/#sec-6)）。
