一局的 `Dispatcher` 持有四條路由，路由表的每一側一條，每條都是一個大腦，加上它在日誌裡使用的名字。本頁講這些路由：它們能花多少、它們的隨機性從哪裡來，以及其中一條失敗時會怎樣。

## 1. 路由表

每個決策都只交給恰好一側：

| 決策介面（surface） | 側 | 大腦 |
|---|---|---|
| `combat` | 戰鬥 | `plan`（SL 規劃器，僅 SL）、`pimc`（僅 NoSL），或佔位策略 `play` |
| 戰鬥中問的 `card_choice`（`ChoiceContext.InCombat`） | 戰鬥提示 | 戰鬥大腦上一個動作帶著的回答，如果有的話；否則是 `first`，取最前面的選項（[戰鬥大腦：提示、招式與 worker §1](/zh-tw/arch/combat-brain/shared/#sec-1)） |
| 戰鬥外問的 `card_choice`（升級、轉化、附魔、移除……） | 宏觀提示 | L0，也就是宏觀大腦本身，或 `random` |
| `map`、`rewards`、`card_reward`、`bundle`、`event`、`shop`、`rest`、`treasure`、`crystal_sphere` | 宏觀 | L0（[宏觀大腦](/zh-tw/arch/macro-brain/)），或 `random` |

藥水欄沒有自己的決策介面：它的動作是每個宏觀畫面合法動作清單的一部分（[GameBridge：各決策介面的動作 §6](/zh-tw/arch/gamebridge/actions/#sec-6)）。表外的決策介面會拋出「uncovered surface」（[§6](#sec-6)）。

**冠軍的名字**。一局的各個大腦合起來就是它的冠軍，由 `Dispatcher.Champion` 命名：

```text
combat plan COMBAT beam 8x300 easy 4 loss plans 3, combat prompts first, macro l0 VALUE clone, macro prompts l0 VALUE clone
```

這是這份程式碼所命名的 SL 冠軍，其中 `COMBAT` 和 `VALUE` 代表冠軍的戰鬥網路和 V 的名字（[評估：冠軍與基線](/zh-tw/arch/evaluation/champions/)）：葉節點用這個戰鬥網路（它的結局由 V 定價）、用 medium 預算的 SL 規劃器，戰鬥中沒有搜尋回答的提示用 `first`，宏觀決策和戰鬥外的選牌提示用 L0，它帶著 V，在節點的複本上把每個選項打一遍。每個大腦都會指名自己的組成部分：會搜尋的戰鬥大腦指名它的戰鬥網路；L0 指名它的 V、`clone`，以及它的探索（均勻抽取是 `eps ε`）；預算按 [§4](#sec-4) 的寫法。SimWorker 的 `ChampionOptions` 由指令的選項做出各條路由，如果它做出的名字不是冠軍檔案用的那個，就拒絕執行（`Brains/ChampionOptions.cs:36-60`）。

**環境決定戰鬥大腦**。宏觀大腦在兩種環境裡是同一個；戰鬥大腦不是（[環境：世界 §5](/zh-tw/arch/environments/worlds/#sec-5)）。冠軍工廠在 SL 之外拒絕 `plan` 和 `--afterstates clone`，在 NoSL 之外拒絕 `pimc`，在 SL 下還拒絕不在節點的複本上打的 L0，因為它從畫面預測的後狀態是 NoSL 的。`run` 照給定的選項打，所以帶 L0 的 SL 對局要用 `--afterstates clone`。`brain` 指令同時服務兩種環境：NoSL 宿主得到 `--policy` 的戰鬥大腦，SL 宿主得到 `--sl-policy` 的，而且它按宿主的環境設定 L0 的後狀態，NoSL 宿主從畫面預測，SL 宿主在節點的複本上打，所以一個冠軍檔案就能服務兩者（[概覽 §5](/zh-tw/arch/harness/#sec-5)）。

## 2. 戰鬥路由

戰鬥路由是一個 `CombatRoute(Brain, Decide, Budget)`：它的名字；一個函式，從（決策、種子、節點的複本或 null、這場戰鬥至今的出招）得到一個 `CombatDecisionResult`；以及它的預算，供日誌和名字使用。

**佔位策略**。`CombatRoute.Of(name, policy)` 包裝一個不搜尋的策略（`play`）：它給出自己的選擇，沒有計畫，也沒有候選。

**行程池裡的 PIMC**（`PooledPimc.Route`，[NoSL PIMC](/zh-tw/arch/pimc/)），只在 NoSL 下。只有一個合法動作時，它立即回答。否則：

- **各個世界**：每個世界一個 `pimc_world` 請求，每個世界都在它的工作行程裡由觀測、敵人出招紀錄和建構種子重新建構，所以真實狀態的任何部分都不會離開宿主。每個世界的節點平均分給各個第一個動作。種子相同時，它給出的答案和在單一行程裡搜尋各個世界的 PIMC 相同，`selftest` 會檢查這一點。
- **照循環打**：路由為這一局保有一個 `TurnPlan`，它只保留重複一個循環、而且每個世界都規劃得一樣的計畫，因為每次重複之前都再搜一遍只會重新找到同一個循環（[NoSL PIMC：搜尋 §6](/zh-tw/arch/pimc/search/#sec-6)）。只要戰鬥顯示的是計畫在某一步之前預期的觀測，這一步就不經搜尋打出；否則這個決策重新搜尋，並標為重新規劃。

**行程池裡的 SL 規劃器**（`PooledPlanner.Route`，[SL 規劃器](/zh-tw/arch/sl-planner/)）。每局一個 `SlRoute`，把戰鬥剩下的部分規劃一次，然後照計畫打，只在某一步不成立或計畫用完時才重新規劃（[SL 規劃器 §4](/zh-tw/arch/sl-planner/#sec-4)）。一個計畫就是 `SlPlanner.Search`，束的每個回合按保留的每個狀態各送一個 `sl_turn` 請求，用路由的預算。沒有節點複本時，路由會拋出例外（它只在 SL 下打）。

**持續整局的兩件事**。`TurnPlan` 和 `SlRoute` 每局建立一次，從不清空，戰鬥結束時不會，宏觀決策時也不會；規劃器對連續的沒有證明的失敗計畫的計數，跨決策延續（[SL 規劃器：束搜尋 §6](/zh-tw/arch/sl-planner/beam/#sec-6)）。

## 3. 宏觀路由與提示路由

宏觀路由或提示路由是一個 `Route<T>(Brain, Policy)`。目前：

- **L0**（`MacroBrain`，`--macro l0`）同時回答宏觀決策和戰鬥外的選牌提示，是同一個物件、同一個 V（[宏觀大腦：搜尋](/zh-tw/arch/macro-brain/search/)）。它的探索（`--explore ε`，均勻抽取，僅自我對弈）從它自己的產生器裡抽（[§5](#sec-5)）。
- **`first`**（`FirstPicks`）回答戰鬥大腦的動作沒有回答的戰鬥中選牌提示：按規範順序取最前面的選項，取提示允許的最少數量，和搜尋世界裡的做法一樣。動作帶著的回答會交給它之後的第一個戰鬥中提示（`Dispatcher`），不接受這個回答的提示也交給 `first`（[戰鬥大腦：提示、招式與 worker §1](/zh-tw/arch/combat-brain/shared/#sec-1)）。
- **`random`** 佔位策略在 `--macro random` 時回答宏觀的兩側。

**給宏觀一側的節點複本**。在 SL 下加上 `--afterstates clone` 時，`Dispatcher` 在每個宏觀決策和每個戰鬥外的選牌提示處開啟節點的複本，作為這一局工作行程池上的一個 `PooledClone`（`MacroDecision.With`、`ChoiceDecision.With`）。L0 再向它要後狀態：每條答案路徑之後遊戲接著問什麼。`PooledClone` 把各條路徑拆成 min(paths, workers) 個連續的 `sl_macro` 請求，每個工作行程對每條路徑載入一次複本，並檢查每條路徑都得到了後狀態；由於後狀態只取決於複本和路徑，怎麼拆都不會改變結果（[宏觀大腦：搜尋 §6](/zh-tw/arch/macro-brain/search/#sec-6)）。

**計畫**。宏觀回答檢查過之後，`Dispatcher` 向策略詢問它在這個回答之後的計畫（`IMacroPolicy.Plan`）：L0 的計畫在地圖上是本幕剩下的路線，在其他地方為空。它的時間不計入這個決策的 `elapsed_ms`。

**打過分的選項**。接著它取出策略從中選擇的那些選項，連同它們的估值（`Scored`）：L0 的是每個合法選項，帶著 V 對選了它之後贏下這一局的機率，選中的排第一，其餘最好的在前；回答是由探索抽出的時候則沒有（[宏觀大腦：搜尋 §1](/zh-tw/arch/macro-brain/search/#sec-1)）。戰鬥外的選牌提示給出 L0 權衡過的回答。它們成為推薦的候選，對會顯示回答的宿主，每個地圖選項還會帶上它的路線（[概覽 §5](/zh-tw/arch/harness/#sec-5)）；決策日誌不保存它們。

**經探索的回答**。當策略說它上一個回答是抽出來的，提示或宏觀回答就標為探索：對 L0 而言，是它的均勻抽取（[決策日誌 §6](/zh-tw/arch/harness/decision-log/#sec-6)）。

## 4. 預算

一次戰鬥搜尋能花多少，由一個 `Budget` 決定（`Brain/Combat/CombatBrain.cs:15-36`）。它的單位是**節點**：在一個世界裡模擬的一個動作。沒有掛鐘時間預算，也沒有其他單位。

| 欄位（JSON） | 預設值 | 含義 |
|---|---|---|
| `worlds` | 8 | PIMC 每個決策的世界數；規劃器只有一個世界，忽略它 |
| `nodes_per_world` | 300 | PIMC：每個世界裡搜尋本回合時模擬的動作數。規劃器：從一個狀態搜尋一個回合時，每次搜尋模擬的動作數 |
| `beam` | 0 | 規劃器從一個回合帶到下一個回合的狀態數；0 表示 PIMC |
| `replan` | 1 | 規劃器在重新規劃之前，打一個沒有證明的失敗計畫的回合數；0 表示打到結束 |
| `loss_plans` | 0 | 在同一場戰鬥裡，規劃器最多連續做出幾個沒有證明的失敗計畫，之後最後一個打到結束；0 表示沒有上限 |
| `easy_beam` | 0 | 規劃器的貪婪下潛已經能贏時用的束；0 表示等於 `beam` |

**力度等級**（`--effort`、`Budget.Effort`，[SL 規劃器：預算 §1](/zh-tw/arch/sl-planner/budget/#sec-1)）：

| 等級 | 束 | 節點 | 簡易束 | 失敗計畫 |
|---|---|---|---|---|
| `low` | 8 | 300 | 2 | 3 |
| `medium` | 8 | 300 | 4 | 3 |
| `high` | 8 | 300 | – | – |
| `max` | 16 | 300 | – | – |

**作為名字**（`Budget.ToString`）：PIMC 是 `8x300`（規劃器是 `beam 16x300`），接著是規劃器的 `easy N`、不等於 1 時的 `replan N`，和有上限時的 `loss plans N`。

**規劃中：按模式的預算** <Badge text="規劃中" variant="caution" />。目前每種模式都用固定的節點預算。設計給每種模式各自的單位：

| 模式 | 單位 | 原因 |
|---|---|---|
| 自我對弈、評估 | 固定的節點數 | 可重現：相同的請求、種子和預算給出相同的推薦 |
| 輔助 | 掛鐘時間，隨時可停（anytime） | 有人在等：先送出目前最好的答案，再改進它 |
| 自動遊玩（R4） | 掛鐘時間上限加最少節點數 | 不卡住，也不搜得太淺 |

「隨時可停」是指搜尋在任何時刻被打斷，都還有一個最好的答案可以給出。規劃中的分配會在排名前兩位的候選之差超出它們的信賴區間時停止，否則增加樣本或深度。目前實作的是：固定的節點數，平均分給各個第一個動作，以及照計畫打（[NoSL PIMC：預算 §1](/zh-tw/arch/pimc/budget/#sec-1)）。

## 5. 種子與確定性

一個決策的搜尋，每次被問到同樣的東西都必須給出同樣的答案，所以它的隨機性來自 Harness，從不來自遊戲的亂數流，也從不來自時鐘。

**run id** 是這一局的種子作為 JSON 字串（含引號）的 FNV-1a 64 位元雜湊，以十六進位表示：種子 `0SSL7NS01MU6` 得到 run `ce13ba5116b7f48a`。大腦看到的是 run id，從不是種子（[協定：線路 §3](/zh-tw/arch/protocol/wire/#sec-3)）。

**一個決策的種子**由 run id 和決策的編號抽出，編號從 0 起計入這一局的每個決策，戰鬥決策、選牌提示和宏觀決策都算（`Dispatcher.cs:197-216`）：

```text
H        = FNV-1a 64 of the JSON string run_id
z        = H + 0x9E3779B97F4A7C15 · (i + 1)          (mod 2^64)
z        = (z xor (z >> 30)) · 0xBF58476D1CE4E5B9
z        = (z xor (z >> 27)) · 0x94D049BB133111EB
seed(i)  = z xor (z >> 31)
```

這是 SplitMix64 的一步。決策的編號是 Harness 自己的計數器，不是線路上的 `decision_id`。按計畫，等大腦有了版本，冠軍的版本也會加入雜湊。

**誰讀它**。每個決策的那一行都記下它的種子，但只有 NoSL PIMC 用它：

- **建構種子**是種子的大寫十六進位形式（`X16`）；工作行程用一個以它的雜湊為種子的產生器，重新取樣觀測沒有確定的部分（[模擬器：戰鬥 §5](/zh-tw/arch/simulator/combat/#sec-5)）；
- 世界 k 用 `"{seed}:{k}"` 的雜湊確定化（[模擬器：戰鬥 §3](/zh-tw/arch/simulator/combat/#sec-3)）。

SL 規劃器搜尋唯一的那個確切世界，忽略它；宏觀策略和提示策略從不收到它。

**佔位策略和探索**從每局各自設定種子的 .NET 產生器裡抽，每條流一個：`Random(FNV(run_id + stream))`，佔位策略的流是 `""`，L0 的均勻抽取是 `:explore uniform`（`Brains/ChampionOptions.cs:44-53`）。所以一局不管在哪個行程裡、走不走線路、記不記日誌，都打得一樣。

**看順序，不看時序**。一次搜尋的請求平行執行，但行程池按請求順序回傳回覆（[模擬器：工作行程池 §2](/zh-tw/arch/simulator/pool/#sec-2)），候選按估值排序，平手時保持合法動作的順序（先結束回合，再是牌，再是藥水）。哪個工作行程先完成，永遠不會改變答案。`run --check` 讓整局都受這一點檢驗（[決策日誌 §8](/zh-tw/arch/harness/decision-log/#sec-8)）。

## 6. 失敗

沒有後備：無法按規定回答的決策會失敗，這一局也隨之失敗。從不用隨機的回答頂替它。

**在 `Dispatcher` 裡**（`Dispatcher.cs`）：

| 情況 | 會怎樣 |
|---|---|
| 戰鬥大腦的選擇不合法 | `InvalidOperationException` |
| 提示不接受的提示回答（個數、範圍、重複的索引） | `InvalidOperationException` |
| 沒有路由的宏觀決策介面 | 「uncovered surface」；決策的編號和它的大腦的計數已經用掉了 |
| 不合法的宏觀回答 | `InvalidOperationException` |
| 在任何檢查點之前、需要複本的 SL 決策 | `InvalidOperationException` |
| NoSL 下的節點檢查點或節點動作 | `InvalidOperationException` |
| 節點索引沒有遞增的檢查點；屬於別的節點或序號不對的動作 | `InvalidDataException` |

**在線路上**（`BrainServer`）：被拒絕的 `hello`（冠軍工廠拋出例外：未知的環境、SL 之外的 `plan` 或 `--afterstates clone`、NoSL 之外的 `pimc`、SL 下不在節點複本上打的 L0、對不上的冠軍名字）、在一局之外或在被拒收的節點訊息之後的決策、沒有遞增的 id、與雜湊不符的觀測、沒有對應畫面的戰鬥決策或提示決策、未知的訊息：每一種都得到一個 `error`。被拒收的節點訊息會讓這一局的下一個決策失敗。不相符的協定版本，或 I/O 或 JSON 錯誤，會讓大腦的 `Serve` 結束，大腦也隨之結束：它只服務一個宿主，所以沒有下一個，Mod 會再啟動它（[概覽 §5](/zh-tw/arch/harness/#sec-5)）。

**在工作行程池裡**（[模擬器：工作行程池 §6](/zh-tw/arch/simulator/pool/#sec-6)）：

| 情況 | 會怎樣 |
|---|---|
| 工作行程啟動或回答超過時限（5 分鐘，啟動和每次回答都一樣） | 被殺掉；請求的第一次失敗會重啟它，並再送一次請求 |
| 工作行程死掉（I/O 錯誤、它的輸出結束） | 被替換，請求再送一次 |
| 同一個請求第二次失敗 | 搜尋失敗（平行迴圈拋出的 `AggregateException`） |
| 不是 JSON 或 id 不對的回覆 | 失敗，不重試 |
| 錯誤回覆 | 等所有回覆都到齊後失敗，不重試；拋出例外的工作行程會結束，所以下次用它時會重啟 |
| 沒有按觀測建構出來的戰鬥 | 工作行程的錯誤是「not built as observed」，附上前 4 項差異（`SimWorlds.NoSL`），所以搜尋失敗 |

一個請求大多只要幾秒：一個世界的搜尋、一個束狀態的回合，或一個決策的試探路徑中的一份。時限抓的是卡住的工作行程，不是慢的工作行程。

**在宿主裡**：在 `run` 裡，任何例外都會讓這一局以 `failed` 結束，附上它的型別和第一行，報告不計入它（[模擬器：整局 §5](/zh-tw/arch/simulator/runs/#sec-5)）。走線路時，模擬器的宿主遇到 `error` 會拋出例外，結果相同；遇到 id 或雜湊不是請求那個的推薦也會拋出例外。Mod 記下一條警告，用 `run_end{failed}` 結束這一局，讓遊戲在沒有大腦的情況下繼續（[Mod：主迴圈 §8](/zh-tw/arch/mod/loop/#sec-8)）。評估要求名為 `random` 的大腦做的決策是 0，失敗的對局則不計入（[評估：指標、種子與報告 §2](/zh-tw/arch/evaluation/metrics/#sec-2)）。

**規劃中的處理** <Badge text="規劃中" variant="caution" />：

| 情況 | 規劃中 | 目前 |
|---|---|---|
| 過期請求（已有更新的 `decision_id`） | 取消搜尋，不送回覆 | Mod 丟棄遲到的回答；大腦回答每個請求，id 沒有遞增的請求得到 `error` |
| 工作行程崩潰或超時 | 在另一個工作行程上從快照重新開啟世界，用已完成的部分作答，把這一行標為 `degraded` | 請求再送一次，得到相同的答案，所以沒有任何降級 |
| 無法從觀測建構的戰鬥 | 報告差異，不搜尋，宿主暫停，記錄這個 bug | 決策帶著差異失敗，這一局也隨之失敗 |
| 宿主認為動作不合法而拒絕 | 宿主重新請求；連續兩次就暫停 | GameBridge 開始執行動作時遇到不合法的動作會拋出例外，這一局失敗 |
