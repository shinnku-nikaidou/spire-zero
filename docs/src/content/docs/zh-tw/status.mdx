## 2. 主要缺口與風險

1. **CombatBuilder 的近似**。回合歷史、內部計數器、費用修改的持續時間、眩暈後續動作都是近似的，而且從沒用真實遊戲的觀測驗證過（[模擬器：戰鬥 §6](/zh-tw/arch/simulator/combat/#sec-6)）。
2. **怪物動作重取樣**目前在「顯示相同意圖」的動作裡均勻選取，需要改成根據怪物歷史得到的後驗（[Harness §3](/zh-tw/arch/harness/#sec-3)）。
3. **選牌提示的上下文依賴非同步入口上的 Harmony 前綴**：內嵌或 rejit 都可能繞過它們（[GameBridge §5](/zh-tw/arch/gamebridge/#sec-5)、[Mod §10](/zh-tw/arch/mod/#sec-10)）。
4. **開局用的是 `UnlockState.all`**，不是使用者自己的存檔進度；晉階等級也沒有限制在角色允許的最大值以內（[模擬器：整局 §2](/zh-tw/arch/simulator/runs/#sec-2)）。
5. **新增的遊戲程式碼如果在事件之外（事件由 transpiler 覆蓋）呼叫 Godot 節點**而沒有 TestMode 保護，只會在 `run` 批次執行裡以遊戲錯誤的形式暴露出來（[模擬器：無頭宿主 §4](/zh-tw/arch/simulator/headless/#sec-4)）。
6. **真實遊戲裡的 Harmony 補丁與分層 JIT**：執行時可能重新編譯某個方法，悄悄丟掉補丁（[Mod §10](/zh-tw/arch/mod/#sec-10)）。
7. **戰鬥大腦 v0 的盲區**。選牌提示按固定規則（`p0`）回答，搜尋內和真實戰鬥裡都是如此，不經過搜尋；NoSL 的搜尋只看本回合；SL 的規劃器看得到整場戰鬥，但被證明的計畫很少；沒有證明的失敗預設連續最多 3 個計畫，第三個打到結束，所以只有更晚的計畫才能贏下的戰鬥會輸掉（[SL 規劃器：束搜尋 §6](/zh-tw/arch/sl-planner/beam/#sec-6)、[SL 規劃器：束搜尋 §5](/zh-tw/arch/sl-planner/beam/#sec-5)）；葉節點是手工的，忽略了大多數能力（[戰鬥大腦：葉節點 §2](/zh-tw/arch/combat-brain/leaf/#sec-2)）。
8. **連戰的 V 打整局**。V 在普通怪物戰不花代價的地方訓練，所以它按那種遊戲來評估路線和休息處。v6-3-2 在整局裡輸掉的對局約有一半輸在兩個頭目之間，而兩個網路在連戰裡的高下，到了整局裡並不總是成立（[學習 §2](/zh-tw/arch/learning/#sec-2)、[§8](/zh-tw/arch/learning/#sec-8)）。
9. **V 的標籤帶著它們那一局之後的抽取**，而 V 不知道一局的 ε 是多少（[學習 §5](/zh-tw/arch/learning/#sec-5)）。
