## 0. 一頁看完

- **現況**：NoSL 的世界早就在 Rust 引擎裡：真實戰鬥的匯出，看不見的部分在引擎裡重抽（11-17 的 (c)）。但搜尋本身還在 C#：
  `PimcBrain` 在每個世界裡把這一回合深度優先搜一遍、`LoopSearch` 處理循環、葉節點的 c 用 C# 的 ONNX 推論再由 V 定價、
  8 個世界取平均。SL 的那一份 11-19 已經整個在 Rust（B、C、D2 進了 main），用戶在那個 session 說了「刪掉，只留 Rust」。
  NoSL 是 C# 的回合搜尋（`PimcBrain` 的世界搜尋、`LoopSearch`）還得留著的唯一理由。
- **量到的**（本機，nosl.json 的冠軍，PIMC 8 個世界各 300 個 node，四局）：單執行緒的三局，戰鬥搜尋佔整局 CPU 78–85 %。
  一個 node 的搜尋時間：單執行緒 273–365 µs，4 執行緒 370 µs。其中：
  - 引擎走一步 29–39 %：搬到 Rust 也不會變。
  - ONNX 推論 17–27 %：一次只推一個狀態，每次 198–258 µs。
  - C# 自己的部分約三分之一：讀觀測的 JSON、token、張量、定價、簿記，約 85–117 µs。搬到 Rust 省下的就是這一塊。
- **做法**：Rust 新寫一個 `search/pimc.rs`，把 `PimcBrain` 的世界搜尋、node 的平分、記憶表、循環和合併照 C# 一行一行搬過來。
  其餘都用 SL 已經搬好的：重抽世界（`determinize`）、狀態、動作排序、循環、token、葉節點、執行緒。
  一個決策只呼叫一次 FFI：C# 給匯入好的真實戰鬥和預算，Rust 抽 8 個世界、搜、合併，交回候選和計畫。
  `TurnPlan`、route、宏觀、V 留在 C#；V 照 SL 的方式由 Rust 回呼 C#。
- **保證不退步**：和 SL 同一個規矩，逐位元相同。同一個決策，Rust 和 C# 的每個候選的值、計畫、計畫的觀測雜湊都要逐位元相同；
  整局的決策逐筆相同。所以 v0g0-nosl「搜尋先不換」的約定不受影響。之後的 NoSL 測試，兩對網路都用新的搜尋打。
- **速度（估計，不是實測）**：
  - 只搬：約 1.3 倍。省掉 C# 那三分之一，Rust 做同樣的事估計 20–30 µs；引擎和 ONNX 不變。
  - 再加兩個選項：
    - **P1 終點快取**：同一個世界裡，觀測完全一樣的終點只推一次，逐位元不變。量到的：少推 6.0–8.4 % 的終點（第 2.3 節）。
      只省幾個百分點。
    - **P2 終點成批推論**：16 個一批，SL 的做法。ONNX 每個狀態約便宜 6 倍（SL 量到一批 16 個 548 µs）。和只搬合起來估計約 1.9 倍。
      但批次會把每個狀態填補到同一批最寬的那個，值的最後幾位會變；最好和第二好相差不到 1e-6 的決策可能換邊，
      決策就不再逐筆相同（第 2.4 節）。要不要做，由用戶定。
- **搬完之後刪**：C# 的 `PimcBrain` 世界搜尋、`LoopSearch`、`EnginePimc` 的執行緒。
  `CombatNet` 和 `CombatTokens`（C#）還要留，因為還有別的地方用：宏觀大腦給事件裡的戰鬥估值、訓練用的 token server。
- **協調**：SL 搜尋那個 session 正在做 C5（刪 C# 的 SL 搜尋），改的是 `CombatBrain.cs`、`EnginePlanner.cs` 這些檔，
  `search/` 也是它寫的。等它的 C5 commit 之後再開始。

  NoSL 的 C# 程式在那之後沒有變；引擎多了 D2，回合開始的提示答得快一點，所以量到的引擎時間對今天的 main 略偏高。

- 機器：SL 那個 session 的工作同時在跑，負載約 7–8（16 核），所以絕對時間偏高，比例可信。

### 2.3 同一個世界裡重複推論的終點（P1）

`PimcBrain` 的記憶表只記玩家能出牌的狀態。同一個終點（結束回合之後）被不同的路走到，每次都重新推論一次；
SL 的 `TurnDfs` 不會，它用鍵把終點去重。

| 局 | 進行中的終點 | 狀態鍵相同 | 觀測文字完全相同 |
|---|---:|---:|---:|
| REGENT A10，種子 778 | 61,838 | 11,211（18.1 %） | 5,210（8.4 %） |
| SILENT A0，種子 779 | 252,125 | 43,768（17.4 %） | 15,216（6.0 %） |
| DEFECT A10，種子 780 | 308,299 | 76,373（24.8 %） | 沒量 |

- 鍵都含隱藏鍵和 run 的雜湊。
- 葉節點只讀觀測、run 和決策時的敵人行動紀錄，同一個決策裡紀錄都一樣。所以觀測文字和 run 都相同的終點，推出來的值必然逐位元相同。
  快取只能用「觀測文字完全相同」這一欄。「狀態鍵相同」的終點，手牌、棄牌堆、藥水的順序可能不同，張量的順序跟著變，值的最後幾位就可能不同。
- 加了計數的局，決策和沒加的那局逐筆相同（REGENT）。SILENT 單執行緒和 4 執行緒的決策也逐筆相同。

### 2.4 最好和第二好的候選差多少（P2 會動到的）

決策日誌裡至少兩個候選的決策，最好減第二好（各欄不重疊）：

| 局 | 決策 | 完全相同 | < 1e-9 | < 1e-6 | < 1e-4 | ≥ 1e-4 |
|---|---:|---:|---:|---:|---:|---:|
| REGENT A10 | 271 | 86 | 0 | 4 | 36 | 145 |
| SILENT A0 | 606 | 180 | 7 | 94 | 114 | 211 |

- 「完全相同」的多半是兩個第一步走到同一批終點（例如兩張牌換個順序打）。
- 換成成批推論後，一個狀態的值的最後幾位會隨同批的其他狀態變。C# 的 `CombatNet.Outcomes` 註解寫的就是這件事。
  差在 1e-6 以內的決策可能換邊：SILENT 是 101 / 606，REGENT 是 4 / 271。「完全相同」的那些，P1 的快取讓同一個觀測只推一次，
  兩邊仍然相同；但只是狀態鍵相同的，可能被拆開。
- 實際換邊多少，要做出來用 same-decisions 數，這裡沒量。

## 3. 設計

### 3.1 Rust：`engine/crates/sts2ai-engine/src/search/pimc.rs`（手寫）

- **一個世界的搜尋**：照 `PimcBrain.WorldSearch` 移過來。
  - `Root`：每個第一步各分 `nodesPerFirst`，每一步從根開始。
  - `First`：搜完後跑 `Loops::run_found`，比值。如果全是循環、又沒剩 node，就走退路：打出這一步，提示用第一個答案，結束回合，問葉節點。
  - `After`、`Reached`、`Best`：
    - 記憶表的鍵是（狀態鍵、隱藏鍵），被預算切斷的狀態不記（`_cuts`）。
    - 每個狀態試的動作用 `order::actions`。
    - 提示上照 `shareTo` 平分 node。
    - 循環交給 `Loops::intercept`。
  - 和 SL 的 `turn.rs` 是兩個不同的演算法：
    - PIMC 每個狀態記最好的一條線。
    - 終點當場問葉節點。
    - 沒有 HP 剪枝、沒有免費丟藥水的比較。
    - 快照不放掉。
- **葉節點**：一次一個狀態（`Leaf::outcome`），和 C# 的 `CombatNet.Outcome` 一樣是一批一個，輸出才逐位元相同。
  - 敵人行動紀錄用決策時的那一份，終點不再補上新回合的意圖，和 C# 一樣。
  - SL 會在終點補，但 token 只讀當前回合之前的回合，兩者讀到的其實一樣（讀程式碼）。
- **世界**：
  - 根由 C# 匯入（一個決策一次）。
  - 每個世界在自己的工作裡，從根的一份複本 `determinize(WorldSeed(seed, k))`。`WorldSeed` 是 "{seed}:{k}" 的 FNV-1a，照搬。
  - 狀態用 `State::new(world, sample: true)`，隱藏鍵是 `keys::key`（C#：`HiddenState.Key`），和 C# 抽出的世界一樣。
- **合併**：照 `Merge` 和 `Summarize`。
  - 每個第一步的值：各世界最好的線的平均，信賴區間 1.96 × 標準誤，各世界的值四捨五入到 4 位。
  - 候選照值排序。
  - 計畫是最好的一步在第一個世界裡的線。所有世界的線和觀測雜湊都相同時，才交回計畫的雜湊。
  - 線是循環時標 `Repeats`。
- **執行緒**：一個世界一個工作，用工作佇列，結果照世界順序收（`threads.rs` 的做法）。
  和 C# 的 `Parallel.For` 一樣，結果和執行緒數無關。
  第一個失敗的世界照它丟出的錯誤回報。
- **token**：加上環境標記。Rust 的 `tokens::of` 現在只會寫 SL 的（沒有 `env:NoSL`）；C# 的 `CombatTokens.EnvTokens` 在 NoSL
  會在 context 裡加 `env:NoSL`。
- **V**：照 SL，回呼 C#。C# 給的是 NoSL 環境的 V（`In(NoSL)`），價格照 C# 的鍵快取。

### 3.2 C ABI 和 C# 這邊

- `sz_pimc(net, world, 歷史, 第一步的順序, worlds, nodes, seed, threads, price, ctx) -> 結果`。
  結果是 JSON：每個第一步的候選、最好的線、計畫的雜湊（或空）、`Repeats`。錯誤照現在的做法，用 `sz_last_error`。
- `EnginePimc.Decide`：
  - `Unplanned`（停在提示上就答第一個選項）和只有一個動作的情況留在 C#。
  - 匯入真實戰鬥，叫 `sz_pimc`，組出 `CombatDecisionResult`。
  - `TurnPlan`、route、mod 的 brain 都不變。
- `--combat-search engine|cs|check` 開放給 pimc。check 讓 C# 和 Rust 每個決策各搜一次，比每個候選的值（逐位元）、
  計畫和雜湊，第一個不同就停下並指出位置。現在這個選項只給 plan。

### 3.3 搬完之後刪什麼

- 刪：
  - `PimcBrain` 的 `WorldSearch`、`SearchWorld`、`Decide`（`IWorldSource` 那條路）。
  - `LoopSearch.cs`。它的 C# 測試（`LoopSearchTests` 約 20 個、`PimcMemoTests`）照同樣的小戰鬥搬到 Rust 的測試。
  - `EnginePimc` 的 `Parallel.For`。
- 留：
  - `PimcBrain` 的 `Ordered`、`Forced`、`Only`、`Unplanned`，SL 的 route 也在用。可以移到一個小檔。
  - `CombatNet` 和 `CombatTokens`：`MacroLeaf` 的 `fights` 給事件裡將開的戰鬥估值，訓練的 token server 寫 token。
  - 之後仍然兩份並存、要一起改的：c 的 token 和張量、定價（C# 和 Rust）。SL 的計畫已經有一個測試，在錄下的狀態上逐位元比對兩邊；
    要擴大到 NoSL 的環境標記。

## 4. 速度的選項

| 選項 | 決策 | 估計（相對今天） | 要多做的 |
|---|---|---|---|
| 只搬 | 逐位元相同 | 約 1.3 倍 | 第 3 節 |
| P1 終點快取 | 逐位元相同 | 再省幾個百分點（少推 6.0–8.4 % 的終點） | 一個世界一張表，鍵是觀測文字的雜湊加 run 的雜湊 |
| P2 終點成批推論 | 近乎平手時可能換邊 | 合起來約 1.9 倍 | 見下 |

P2 的做法（讀程式碼）：
- 世界的搜尋怎麼走，只看 node 數和預算有沒有被切斷，不看值。
  「全是循環」的退路也只看結構：循環的線是負無窮，葉節點的值最低是 0。
- 所以可以先把樹走完、終點照找到的順序 16 個一批推論，再由下往上取最好的線。同值時照 C# 的規則，先找到的贏。
- 循環的現金化（`LoopSearch` 決定要重複幾次）要邊走邊看值，那一段照舊一次一個；量到它幾乎不花時間。

## 5. 驗證

1. token 和張量：錄下的 NoSL 終點上，Rust 和 C# 的 token、張量、ONNX 輸出逐位元相同（含 `env:NoSL`）。
2. check：六個角色 A0 和 A10 各一局，加 Dread A10 一局（(c) 之後 NoSL 打得了 Dread）。每個決策都比，0 差異。
3. same-decisions：同一批種子，engine 和 cs 各跑整局，決策逐筆相同。
4. `selftest`（含「pimc 在 1 和 4 個執行緒上選的一樣」）、C# 和 Rust 的單元測試。
5. `run --check` 一局 NoSL：走線路，也就是 mod 的路。
6. 量：
   - 第 2 節的三個種子：每局 CPU、µs/node。
   - 峰值記憶體：Rust 的葉節點每個執行緒一個 ONNX session；SL 搬完後最大行程的峰值多了 200–330 MB。
   - NoSL 的步驟上池子時，6 G 的 gcphk 那幾台今天都先關掉。所以要報告每局的記憶體。
7. P2 只在用戶說要時做。做的話用 same-decisions 數換邊的決策，報數字。
