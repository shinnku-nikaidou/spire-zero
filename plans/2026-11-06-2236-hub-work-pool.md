## 2. Words

- **Job**: as today: one folder `data/JOB`, one `manifest.json`, one queue of chunks on the hub, one REV, one set of
  options and inputs.
- **Step**: the jobs launched with one deadline name (`DEADLINE=NAME`, as today; by default a job alone is a step of its
  own). A step has one deadline and one priority. A gate (10 jobs) is one step; a generation (15 jobs) is one step.
- **Worker**: one process per host (`job/worker.py`, standard-library python3; every host has 3.10 or newer), running
  N threads, N read live from a file. A thread is today's slot: one `run` at a time, so N counts like SKILL.md's
  "SL runs".

## 3. The design

### 3.1 The order: which chunk a thread gets

On each request the hub walks the open steps (deadline not passed, not stopped):

1. **Between steps**: higher priority first; at equal priority, the step launched first. Default priority: `selfplay`
   0, `eval` and `forks` 1 (data fills the fleet, everything else is waited on). `PRIORITY=N` at launch, and
   `box.py priority NAME N` changes it live. A gate launched beside a running generation takes every thread as its run
   ends; nothing is killed, and the generation picks up again once the gate's queues are empty.
2. **Inside a step**: the job given the fewest chunks so far (ties: launch order). So the step's jobs move through
   their ranges together: a gate's ten jobs through promotion-1-100 seed by seed (launched per character, champion
   then challenger: SILENT v9-1 0, SILENT v9-2 0, IRONCLAD v9-1 0, ... NECROBINDER v9-2 0, SILENT v9-1 1, ...), a
   generation's jobs through their ledger blocks evenly. **This is what keeps a gate's pairs paired**: at any moment
   both sides of a character have been dealt the same head, give or take one seed, and at the deadline their finished
   heads differ only by what was in play.
3. **The deadline guard** (slow hosts near the end). The worker reports each whole chunk's play time with its next
   request; the hub keeps, per host and job, the median of the last 5. A job is skipped for a thread when
   now + that median > the step's deadline (or the thread's own end, 3.3). The thread then gets the next job of the
   step (a faster character), the next step (data), or nothing (it asks again in 60 s). So gcpsg stops starting
   22-min Regent runs 22 min before the deadline, and the last seeds go to the threads that can finish them. With no
   sample yet (a host's first chunk of a job), no guard.
4. **A job that keeps failing**: when a host's chunks of a job fail twice in a row (fewer runs than dealt, before the
   deadline, not stopped), the hub gives that host no more of that job (`JOB/deal/refused-HOST`, with the reason;
   `status` shows it). A bad launch burns two chunks per host, not the whole queue; one failure (pushqkzh's bit flips)
   changes nothing.

k (`CHUNK`) stays a job option, default 1, and stays 1 for SL runs: requests cost 0.003-0.8 s against runs of 5-25
min, and k = 1 keeps both the ragged edge and what a deadline throws away at one run per thread.

### 3.2 The hub

`deal.py` stays the dealer, one thread, state in files (a restart loses nothing but the guard's medians, which refill
from the next chunks). New files in the store:

```
pool/token                the pool's token (in dist/pool.json for the workers, behind the x-api-key)
pool/steps/NAME.json      {"priority", "deadline_epoch", "launched", "stopped", "jobs": [JOB...]}: written by box.py
pool/held/SHARD           "JOB INDEX N", the chunk thread SHARD holds
pool/lost/HOST            a host gone for good (box.py lost)
pool/seen-HOST            the host's last look: time, threads
pool/cpu-HOST.txt         "EPOCH THREADS BUSY NCPU", one line a minute (today's cpu.sh, now per host)
JOB/deal/queue.txt, pos, claims.log    as today
JOB/deal/job.json         rev, options, chunk, inputs file, step: written by box.py at launch
JOB/deal/stopped          why, when a job is stopped (box.py stop)
```

Two requests, both with the pool token:

- `GET /next?shard=HOST-i&last=JOB/INDEX&took=S&until=EPOCH` answers `JOB INDEX N`, or 204 when nothing fits now.
  As today, a shard whose held chunk is not `last` lost its answer and gets the same chunk again (so a worker that
  restarts replays what it held, if its step is still open). `took` is the play time of `last` if it finished whole.
- `GET /pool?host=H&threads=N&busy=B&ncpu=C` (each worker, once a minute) answers JSON: the hub's clock, each open
  step's deadline and stop, each of their jobs' `job.json`. It writes `seen-HOST` and a line of `cpu-HOST.txt`.

`/claim` and the per-job tokens go once no old-style job is left (after v9-2's gate is fetched).

`dist.py` keeps serving files and taking chunks (`PUT /chunk/JOB/SHARD/INDEX`), with two changes: a job is one with
`deal/job.json`, and a chunk may have an empty `done-` (no run finished: cut at the deadline, or failed), so that every
chunk dealt comes back with its output and its end line.

### 3.3 The worker

Every host and every notebook runs the same `worker.py`. On a host it lives in `~/sts2/pool/` (mode 700):
`worker.py`, `config.json` (dist URL, x-api-key, the hub's certificate; mode 600), `threads`, `worker.log`, `outbox/`,
`work/SHARD/`.

- **Threads, live.** `threads` holds a number, or windows in UTC+8 with a last line for the rest of the day; the first
  line that holds now wins. The worker reads it every 10 s: it starts the threads missing, and a thread whose number is
  no longer below N ends after its chunk (nothing is killed). A thread passes the end of its window as `until`, so the
  guard does not start a run that would cross it. pushqkzh's file:
  ```
  # threads: a number, or HH:MM-HH:MM N windows in UTC+8 and a last line with a number
  19:00-06:00 13
  4
  ```
  `box.py threads HOST N|WINDOWS` writes it and reads it back.
- **A thread**: ask `/next`; 204: wait 60 s and ask again (a worker idles until new work comes, nobody restarts it).
  For `JOB INDEX N`: the job's spec from the `/pool` copy; the build and inputs ready (below); then
  `sim-REV.sh run OPTIONS --start INDEX --n N --log ... --records ...` in the job's inputs, in its own process group,
  checked every 10 s against the step's deadline (in this host's clock) and the job's stop: TERM, KILL 30 s later,
  as `slot.sh` does now. The whole runs go into one chunk tar (`rec-`, `log-`, `out-` zstd, `counts-`, `done-` last,
  the `out-` ending with `box: SHARD INDEX ended TRUE-EPOCH WHY`), into the outbox; one sender thread PUTs them to
  `dist.py` in order and tries again until the hub answers (the notebook's way: 2,298 runs in v9g0's second box,
  2,082 in v9g1).
- **Build and inputs, on first need.** A job names REV and an inputs file. The first thread that needs them downloads
  `dist/sts2-REV.tar.zst` (today's `dist-admin.py publish` bundle; the worker keeps only `builds/REV/` and
  `sim-REV.sh`, the same launcher `deploy.sh` writes, when `dotnet/` and `gamebin/` are there) and
  `dist/inputs-KEY.tar.zst` into `~/sts2/inputs/KEY/`, under a lock; the host's other threads wait for it. KEY is REV
  for inputs from git at REV (as `dist-admin.py jobs` names them now), the first 12 hex of the tar's SHA-256 for
  `INPUTS=DIR`. About 45 + 14 MB once per rev per host; `dist.py` sends 2 large files at once at 3 MB/s each, so 8
  hosts at a new rev take about 1-2 min. `box.py run` puts both on the hub before the job opens.
- **Clock.** Each `/pool` answer carries the hub's time (NTP-synced, checked tonight); the worker keeps the offset with
  the shortest round trip of the last 10 looks (round trips 0.003-0.8 s). Deadlines are true time; end lines are
  written in true time, so `stop_spread_s` needs no per-host offsets in the manifest.
- **Started once**: `box.py up HOST THREADS` ships `worker.py` and `config.json`, writes `threads`, starts it at nice 19
  (`setsid nohup`); with a worker already running it asks it to drain (threads end after their chunk) and start the new
  `worker.py`. `box.py down HOST` ends it now: runs in play killed, their finished runs and the outbox sent, then exit.
  `box.py threads HOST 0` is the gentle way.

The notebook becomes: install (as now), fetch `dist/worker.py`, run it with `--threads` from `capacity()` and
`--until-empty` (end once no thread got work for 10 min and the outbox is empty). Its shards stay `nbHEX-I`. Its
`sim_line` (the cgroup namespace for Colab's `..`) moves into `worker.py`, used only where `/proc/self/cgroup` has
`/..`. `colab-worker.sh` and `colab-watch.py` stay, with the outbox's new path.

### 3.4 One job, one folder

- `box.py run JOB REV UNTIL PURPOSE RANGE -- RUN-OPTION...`: no `HOST=SLOTS`. Same checks as now (pushed REV, the
  name, train and test seeds apart, launched once, a deadline a minute away), the same queue (RANGE, `CHUNK`, `AFTER`),
  then `JOB/deal/{queue.txt,job.json}`, the bundle and inputs on the hub, and the job appended to its step
  (`DEADLINE=NAME`, `PRIORITY=N`). A second job of a step must give the step's deadline (`box.py deadline` moves it).
  The manifest loses `shards` and `box.hosts` at launch and gains `box.step` and `box.priority`.
- `box.py deadline NAME UNTIL`: the step's file on the hub and each manifest's `deadline_changes`; no host is touched.
  The workers see it within a minute. A step may now be extended after its deadline, as long as its jobs are not fetched.
- `box.py stop JOB|NAME REASON` replaces `stop.sh`: `JOB/deal/stopped` (or every job of the step); runs in play are
  killed within about a minute, their finished runs kept.
- `box.py lost HOST REASON`: once, for the pool; what its threads held is not waited for (and not dealt again).
- `box.py status [JOB...|NAME]`: from the hub alone, in one call: per job runs, wins, floor, deaths by act, chunks given
  of the queue, held now by host, refused hosts; per host threads, busy CPUs and last look; the hub's free space.
- `box.py fetch JOB|NAME`: waits until the job is over (deadline passed, stopped, or queue used up) and every chunk in
  `claims.log` has its `done-` on the hub, but those held by a lost host; 15 min past the deadline it names the chunks
  missing (shard, index, host). Then as now: the small files here, the manifest closed with `done`, `prefix`, runs by
  shard, and new `box.hosts` (chunks and runs each host played), chunk ends and `stop_spread_s` from the end lines, the
  `cpu-HOST.txt` lines of the job's span; the step's file leaves `pool/steps/` once all its jobs are fetched.
- `pull.sh`, `learn/gate.py`, training: unchanged. The files keep their names (`rec-SHARD-INDEX.jsonl.zst`, ...);
  the output becomes one `out-SHARD-INDEX.txt.zst` per chunk, as notebooks already send.

- The ledger's blocks, entered and committed before a launch; a box still plays its block from the front.

- The host limits table: a host's threads stay within its "SL runs"; pushqkzh 13 only 19:00-06:00 UTC+8 (its

  its row says (no large data generation there since 2026-11-03).
- Data: hosts → hub → pushqkzh; this machine gets only small files; `backup.sh`, `backup-sg.sh` unchanged.
- `tmp/compute-timetable.md`: a row per step (its jobs, deadline, purpose; at fetch which hosts played how many chunks,
  the box's numbers) and a row per host's worker span (threads, from - to). Its rules' "one row per job and host" says so.
- docs/ never mentions hosts or the pool.

## 6. Not doing

- Dealing a lost host's held seeds again: a gate still plays its holes with `AFTER=` (a host that was only slow
  would send them later, and the seed would be played twice).
- Weights between a step's jobs (all are dealt evenly), and any per-host or per-character routing beyond the guard.
- Encoding the limits table in code: SKILL.md stays the limit, `box.py threads` writes what it is told.
- Killing runs when a thread count drops: they finish.
