# SL 的戰鬥搜尋整個移到 Rust（台灣時間 2026-11-18 21:32 起草）

起草於 2026-11-18 21:32（台灣時間），在「combat 移植到 Rust」這個 session。還沒有任何程式改動。

用戶的話（2026-11-18）：

- 「你開一個新的session, 討論整個combat部分移植到rust上，現在有點太慢了」
- 「ABC+N2」（回答下面第 1 節的選項：A、B、C 都做，網路推論用 N2）
- 「D. 引擎要做啊，不能重跑啊，如果按照指定順序選的，怎麼能從0開始重新跑呢？我知道很難，但重新跑真的不合理」
- 「加 ort 依賴，no problem」

## 0. 一頁看完

- **做什麼**：SL 的戰鬥搜尋，從一個回合的 DFS 到 beam 和 solver，整個移到 Rust 引擎的函式庫裡。戰鬥網路 c 也在 Rust 裡推論，
  用 ONNX Runtime 的 Rust 綁定 `ort`（N2，用戶同意加這個依賴）。引擎回答提示時不再從動作開頭重跑。分四步，每一步對拍通過才走下一步：
  - **A**：先在 C# 這邊省，馬上能用：server GC、觀測讀得便宜一點、路徑不再每個終點複製一份。
  - **D**：引擎回答提示時，從提示前最後一個「遊戲的程式沒有跑到一半」的地方接著跑，不再從動作開頭（例如結束回合之前）重跑。
    回合開始的提示（Toasty Mittens）不再重跑自己的回合結束和敵人的回合。
  - **B**：一個回合的搜尋（現在的 `TurnDfs`，含循環、藥水免費丟棄、HP 剪枝）和葉節點（c 的 token、張量、推論、定價）移到
    Rust。一次 FFI 呼叫搜完一整個回合。beam、solver、route 還在 C#。
  - **C**：beam 和 solver 也移到 Rust。每個決策一次 FFI 呼叫；solver 的表在 Rust 裡；執行緒用工作佇列。之後刪掉 C# 的 SL 搜尋。
- **留在 C#**：route（照計畫走、輸的計畫重規劃、solver 的背景執行緒開關）、協定、mod 的 brain、宏觀決策、V（Rust 回呼 C# 取價）、
  卡在提示上的根怎麼跨（在節點的複本上，Rust 回呼 C#）、NoSL 的整個 PIMC。
- **保證不退步**：Rust 的搜尋和 C# 的逐位元相同：同樣的根，同樣的 node、同樣的終點、同樣的值、同樣的決策。整局用
  same-decisions 比對，0 差異才算過。
- **順序**：A → D → B → C。A 和 D 互不相干；D 在 B 之前，B 的新程式就不會和 D 改到同一批引擎檔案。
- **不做**：大回合內多執行緒（沒有選）；NoSL；兩個網路的結構；把翻譯出來的整份遊戲程式改成能停在任意一行再接著跑（3 節 D 的最後一段）。

## 1. 為什麼：量到的

工作資料夾 `tmp/combat-rust/`：HEAD 的副本加計時探針，一個指令 `turnprof` 從 friend 那局（Regent A10）的回合起點把一個回合
整個搜完（`SearchTurn`，沒有 node 上限，留下每個終點，和 solver 搜一個狀態一樣）。機器上另一個工作同時在跑，負載約 6。

HUNTER_KILLER 第 2 回合，9 張手牌、4 能量，有 Toasty Mittens：25,573 個 node、16,498 個終點。單執行緒每個 node 297 µs CPU：

| 部分 | µs/node | 佔比 |
|---|---:|---:|
| Rust 引擎走一步（`sz_world_step`） | 139 | 47 % |
| ├ 回合結束後提示的回答（每次 147 µs；每答一次就從結束回合前重跑敵人回合） | 95 | 32 % |
| ├ 結束回合（每次 157 µs） | 25 | 8 % |
| └ 出牌（每次 95 µs） | 19 | 6 % |
| C# 讀觀測（JSON 4、雜湊 2、反序列化 41；每份 2.6 KB） | 47 | 16 % |
| 葉節點：ONNX 22（16 個一批，每批 548 µs）、token 7、組張量 12、定價 2 | 45 | 15 % |
| C# 簿記（敵人行動紀錄、run、路徑複製、還原和釋放世界、動作排序） | 33 | 11 % |
| 其他（GC 暫停 16，迴圈本身） | 31 | 10 % |

- 每個 node 配置 74 KB 的短命物件；搜完後每個終點還留 962 B。
- 8 份同時搜（像 solver 的一批）：總共 15,700 node/秒，每執行緒 52 % 的效率，GC 暫停佔牆鐘時間 34 %。
  server GC：18,800 node/秒（+20 %），暫停 17 %。
- OVICOPTER 第 5 回合（6,746 個 node）：293 µs/node，比例相同。
- 先前量到的：solver 在 HUNTER_KILLER 上 145 萬個狀態時表本身 1.45 GB（每個狀態約 1 KB），整個行程 7.5 GB；OVICOPTER 8 個百萬 node
  的回合同時搜時 13 GB 爆掉。大的是回合搜尋時的物件，不是表。

估計（扣掉量到的 C# 部分，不是實測）：B 之後單執行緒這個回合約 175 µs/node（1.7 倍）；8 執行緒因為沒有 GC 停頓和配置，會好更多。
一個終點在 Rust 裡約 60–100 B，solver 的一個狀態約 100–150 B。

討論時的選項：A 只在 C# 省；B 回合搜尋到 Rust；C 再加 beam 和 solver；D 引擎的提示接續。推論 N1 留在 C# 由 Rust 回呼；
N2 在 Rust 用 `ort`。用戶選 A、B、C 和 N2，接著加上 D。

## 2. 架構

### 2.1 Rust 這邊（`engine/crates/sts2ai-engine/src/search/`，手寫）

- **世界**：搜尋對一個 trait 寫（走一步、狀態、回合、提示、兩個鍵、觀測、run 的變化、合法動作）。引擎的世界（現在 `ffi::Handle`
  裡的那個）實作它；卡在提示上的根另有一個實作（2.3）；測試用的小戰鬥也實作它（現在 C# 測試裡的 toy world 搬過來）。
- **回合搜尋**：`TurnDfs` 照 C# 一行一行移過來：動作的順序和同樣動作只試一次（`PimcBrain.Ordered`、`PromptAnswers`）、
  node 的分配（每個第一步平分再加上前面剩的）、轉置（狀態鍵＋完整隱藏鍵）、`LoopSearch`、`LifeBound` 的剪枝、終點一批批問葉、
  藥水免費丟棄（`Thrown`）、結果的排序。路徑存成這個回合搜尋樹的父節點指標，終點只記指向樹的索引。
- **葉節點**：`CombatTokens.Of`、`CombatNet` 的 `Feed`、`Stack`、`Priced`、`FreeDisposal` 移過來，讀引擎自己的觀測結構
  （`protocol.rs` 的 `CombatObservation`），不再經 JSON。批次照 C# 的規則：一個回合搜尋的終點照找到的順序，16 個一批，
  所以送進 ONNX 的張量和 C# 逐位元相同。`MoveRecord` 也移過來。
- **推論（N2）**：crate `ort`（用戶 11-18 同意加），關掉預設功能，開 `load-dynamic`：建置時不下載任何東西，執行時載入 C# 那邊已經帶著的
  ONNX Runtime 1.31（NuGet `Microsoft.ML.OnnxRuntime` 的 `libonnxruntime.so` / `.dylib` / `onnxruntime.dll`，路徑由 C# 給）。
  一個行程只有一份 ONNX Runtime。session 設定和 C# 一樣（intra-op 1、inter-op 1），輸出才會逐位元相同。`ort` 用哪個版本，
  加的時候選它支援的 C API 不高於 1.31 的最新版（ONNX Runtime 的 C API 向後相容，新的執行庫能提供舊版的 API）。
  載入網路時照 C# 的做法用檔案裡的測試狀態檢查（和訓練器的輸出差 1e-3 以內）。
- **V**：不移。葉節點要 V 的價時回呼 C#：給 run 的變化、HP、藥水，C# 組出 `RunView` 交給 `IRunValue`。Rust 照 C# 的方式快取
  （run 不含 HP 和藥水的鍵、HP、藥水）。V 一個回合只被叫幾十次。
- **beam 和 solver（C 步）**：`SlPlanner.Search` 的 beam（含 dive、easy beam、replan、turn decay、`Rank`、`Picked`）和 `SlSolver`
  （佇列、表、`Advance`、`Seed`、`Purge`）照 C# 移過來。執行緒用 `std::thread::scope`（不加 crate），一個工作佇列：一個狀態搜完就
  拿下一個，不再整批等最慢的。結果和執行緒數無關：工作照順序編號，結果照編號合併，和現在 `Parallel.For` 照 job 順序回傳一樣。
  solver 的表：一個狀態存鍵、值、回合數、敵人行動紀錄的索引（同一份紀錄只存一次）、HP 上限、藥水的索引、父狀態和邊；邊存成
  那個回合搜尋樹的路徑（動作和觀測雜湊）。

### 2.2 C ABI

- `sz_planner_new(net 檔、ONNX Runtime 的路徑、V 的回呼、執行緒數)`、`sz_planner_free`。
- B：`sz_turn_search(planner, world, 敵人行動紀錄, nodes, keep, 剪枝的界) -> 終點`（緊湊的二進位：每個終點的固定欄位、
  動作、觀測雜湊；敵人行動紀錄每種只寫一次）。C# 的 `EnginePlanner.Searcher` 改叫它。
- C：`sz_plan(planner, world, 敵人行動紀錄, budget) -> 計畫`（beam）；solver 是一個控制代碼：`sz_solver_new`、`_seed`、
  `_run(nodes)`、`_advance(played, 敵人行動紀錄)`、`_result(replan)`、`_stop`、`_free`。背景模式（mod 的 brain）裡 C# 的執行緒
  反覆叫 `_run`，`_stop` 設一個旗標，回合搜尋在下一步停下（取代現在 `Stoppable` 世界丟的例外）。
- 每個函式照現在的做法接住 panic，錯誤用 `sz_last_error`。

### 2.3 卡在提示上的根

現在一個卡在提示上的根（戰鬥一開始的提示、計畫走完時、某步不成立時）在節點的複本上跨過提示（`PromptRoot`，經 worker），
玩家能再出牌時才匯入引擎。C 步裡這變成 Rust 的另一個世界實作：在提示上時回呼 C# 跨一條答案路徑（C# 照現在的 `Crossing`，
含預先一批批跨），拿回提示的觀測和隱藏鍵，或能出牌時的匯出，由 Rust 匯入。B 步這種根還用 C# 的 `TurnDfs`（B 和 C 之間兩份並存，
C# 那份同時是對拍的參照）。

### 2.4 C# 剩什麼、刪什麼

- 留：`SlRoute`、`TurnPlan`、`SolverRoute`（改叫 Rust 的 solver）、`EnginePlanner`（匯入、回呼、計時）、`PromptRoot.Crossing`、
  `PlanMeter`、協定、`BrainServer`、宏觀。
- C 過了之後刪：`SlPlanner` 的 beam 和 `TurnDfs`、`SlSolver`、`LifeBound`。它們的測試（`SlPlannerTests` 約 34 個、solver 的）
  照同樣的小戰鬥搬到 Rust 的測試。route 的 C# 測試改用一個假的規劃器介面。
- 兩份並存、要一起改的：`LoopSearch`（NoSL 的 PIMC 也用）、`CombatTokens`（訓練紀錄和 NoSL 也用）、`CombatNet` 的張量和定價
  （NoSL 用）。每次改 c 的輸入或循環的規則，C#、Rust 都要改（訓練器的 Python 本來就要）。一個測試在錄下的狀態上逐位元比對
  兩邊的 token 和張量，不同就失敗。

## 3. 步驟

每一步：先寫，再對拍到 0 差異，再量，回報數字，用戶看了再走下一步。時間表每次用機器都記一列。

### A. C# 這邊先省

1. **server GC**：SimWorker（self-play、測試、`run`、mod 的 brain）開 server GC。先量：friend 那局在 max 的牆鐘時間和
   峰值記憶體、mod 的 brain 在 8 執行緒時的記憶體。server GC 每個核心一個堆，記憶體會多；數字給用戶看，用戶決定 mod 要不要跟著開。
2. **觀測讀得便宜一點**：協定的 JSON 改用 System.Text.Json 的 source generator（現在是反射），不改格式、不改任何值。量反序列化
   每次的微秒數。
3. **路徑不再每個終點複製**：`TurnDfs` 的終點記指向一棵共用的路徑，到要交出 `TurnEnd` 時才展開。這在 `SlPlanner.cs`
   （max-solver 那個 session 的檔案），先和它協調；B 會整段換掉它。
4. 對拍：same-decisions 六局（六個角色，A0 和 A10，medium），決策逐筆相同。量：上面 `turnprof` 的兩個回合、六局的每局 CPU。

### D. 引擎：回答提示不從動作開頭重跑

**現在怎麼做**（engine/DESIGN.md 的 Choices）：翻譯出來的遊戲程式是一條直線的 Rust，提示出現在一個函式的半中間，
那一刻呼叫堆疊上一層層的區域變數（卡片效果、hook 的迴圈、回合流程）沒辦法存起來再分給每個答案各一份。所以停在提示上的世界
只記「動作之前的戰鬥、動作、已經給的答案」，下一個答案把整個動作從頭再跑一次（結果一樣，因為隨機數也是狀態的一部分）。
Toasty Mittens 的選擇在下回合開始的 `AfterPlayerTurnStart` 裡，這個動作是「結束回合」，所以每個答案都重跑自己的回合結束、
敵人的回合、下回合開始；暫停的 hook 接回來時（`hook_player_choice_context.rs` 的 `resume`）也從同一個起點再重播一次。

**改成**：停在提示上的世界記住提示之前**最後一個接續點**，下一個答案從那裡接著跑。接續點是遊戲的程式沒有跑到一半、
戰鬥完全是資料的地方，都在手寫的回合流程裡（`manual/combat_manager.rs`，它的狀態本來就在戰鬥裡）：

1. **每一方的回合開始之前**（`turn_loop` 裡呼叫 `start_turn` 之前）：敵人的回合已經跑完，佇列是空的，沒有 hook 暫停著。
   接續時從 `turn_loop` 的這一點進去（多一個等待狀態，只在接續點的那份戰鬥上），之後照常；不改原本的執行順序。
   Toasty Mittens 的答案從這裡跑：不再重跑回合結束和敵人的回合。
2. **玩家回合的準備裡、`AfterPlayerTurnStart` 的 hook 之前**：`SetupPlayerTurn`（能量、抽牌、然後那些 hook）改成手寫，
   在抽完牌、開始跑 hook 之前多一個接續點。答案從這裡跑：連抽牌也不重跑。
3. 暫停的 hook 接回來時的重播（`StepStart`）也從最後一個接續點開始，不從動作開頭。

接續點是戰鬥的一份複本（寫入時才複製，一份約 1 µs）。一次只留最新的一個，前一個放掉，之後寫入的物件就不必為它複製。
一步沒有停在提示上，就在步尾放掉。

之後還會重跑的，只有從最後一個接續點到提示之間那一小段：hook 自己的程式從開頭到它問的那一行（例如 Toasty Mittens 的
`Flash()` 和選牌之前的那幾行）。要連這一段也不重跑，就得把翻譯出來的每一個 async 方法都改成能停在任意一行、區域變數存在
戰鬥裡的狀態機（C# 編譯器對 async 做的事），等於重寫翻譯器的輸出、所有程式都變慢、對拍從頭來過。這不在本計畫裡；
1、2 做完後量剩下多少，數字給用戶看。

**驗**：
- 引擎測試：在兩個 dump 的所有提示上，接續跑出的世界和從頭重跑的逐位元相同（觀測的位元組、完整隱藏鍵的文字、兩個鍵）。
- 四項檢查兩個 dump 全過（`sim parity`），經 C ABI 的掃描 0 差異。
- 搜尋：`turnprof` 的回合結果逐位元相同；same-decisions 六局逐筆相同。
- 量：回答一個提示的微秒數（f29 第 2 回合現在 147 µs）、`turnprof` 的每個 node、六局的每局 CPU。

### B. 回合搜尋和葉節點到 Rust

1. Rust：世界的 trait、`MoveRecord`、動作排序、`LifeBound` 的檢查、`LoopSearch`、`TurnDfs`、token、張量、`Priced`、
   `FreeDisposal`、V 的回呼。加 `ort`（第 2.1 節的設定）。小戰鬥的測試從 C# 搬過來（`LoopSearchTests` 約 20 個、
   `SlPlannerTests` 裡回合搜尋的那些）。
2. 張量對拍：所有錄下的終點，Rust 和 C# 的 token、張量逐位元相同，ONNX 的輸出逐位元相同。
3. 回合對拍：一個新的 sim 指令，在真的對局裡每個回合起點讓 C# 和 Rust 各搜一次（300 node 和沒有上限各一次），比 node 數、
   cut、剪枝數，以及終點的順序、動作、觀測雜湊、狀態鍵、值、勝率、HP、藥水、HP 上限。根：friend 那局的 352 個回合起點，
   加上六個角色 A0 和 A10 的對局。0 差異才算過。
4. 接上：`EnginePlanner.Searcher` 改叫 `sz_turn_search`。same-decisions 六局逐筆相同。
5. 量：`turnprof` 的回合（單執行緒、8 執行緒）、六局的每局 CPU、friend 那局在 max 的時間和記憶體。

### C. beam 和 solver 到 Rust

1. 開始前問 max-solver 那個 session 它的計畫走到哪裡；移的是當時 HEAD 的 `SlPlanner`、`SlSolver`、`SolverRoute` 的
   規則。之後 solver 規則的改動直接改 Rust。
2. Rust：beam、solver、工作佇列、卡在提示上的根的世界（2.3）。`SolverRoute` 改叫 Rust 的 solver（背景模式照 2.2）。
3. 對拍：同一個決策點 C# 和 Rust 的計畫逐欄相同（beam 每個 effort；solver 在同步模式下每個決策 `Budget.Solve` 個 node）；
   same-decisions 六局 medium，加上 friend 那局在 max（同步模式）。0 差異才算過。
4. 量：friend 那局在 max 的每個決策時間和峰值記憶體（之前爆掉的 OVICOPTER）；solver 每個狀態的記憶體；六局的每局 CPU；
   mod 的 brain 在背景模式的記憶體。
5. 刪 C# 的 SL 搜尋（2.4），測試搬完，兩個測試專案和 Rust 的測試都過。

## 4. 建置和發佈

- 引擎的函式庫照現在的做法建：linux-x64 在這台、osx-arm64 在 Mac、win-x64 在 Windows VM。三個地方都要能抓到 `ort`
  （cargo 的下載）。
- mod 的發佈包裡 ONNX Runtime 本來就有；Rust 從 C# 給的路徑載入同一份。
