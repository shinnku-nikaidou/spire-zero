## 2. 現況（為這份計畫讀過的程式碼）

- **NoSL 怎麼用兩個網路**：`PimcBrain`（`src/Sts2Ai.Brain/Combat/CombatBrain.cs`）每個世界搜這一回合，葉子是下一回合開始時的
  戰鬥網路，結局由 V 定價（`ICombatLeaf`）。戰鬥外用 `ScreenAfterstates`：從螢幕預測每個選項之後的局面，交給 V。
- **context 是加總的袋子**，兩個網路都有。V 的 context：角色、幕、Boss、Ancient，Dread 模式下再加 `mode:` 和 `dominion:`
  （`RunNet.Tokens`，`CombatTokens.ModeTokens`）。戰鬥網路的 context：角色、遭遇、房間、幕，加同樣的模式標記。
- **Dread 的先例**：`learn/carry.py` 把舊網路搬到新的表，`mode:`、`dominion:` 開頭的新列從零開始（`ZERO`）。context 是加總，
  所以搬過去的網路對舊表讀得到的每個狀態給出原來的值；檔案裡的測試狀態會重新估一次，載入時大腦也會檢查。
- **`--init` 不接受表不同的網路**（`v.train`：`holds other tables than learn/game_ids.json's`）。表一改，要先 carry 才能接著訓練。
- **訓練從來都是 `--init`**。沒見過的列不會動，所以從零開始的列在只有 SL 資料的訓練之後仍然是零。
- **V 的樣本**（`learn/v/data.py`）：決策日誌裡每個戰鬥外決策的 `run_view` 是一個樣本；地圖移動多一個樣本，選中的點的
  後狀態（`entered`）。日誌的每一行有 `env`、`surface`、選的動作、`run_view`、是否隨機抽的，**沒有螢幕**（事件是哪個、
  選項的 key 都不在裡面）。V 的 reader 不看 `env`。
- **戰鬥網路的樣本**（`learn/combat/data.py`）：每回合開始一個樣本，標籤是這場戰鬥真正的結局。`--env` 只收一個環境，
  別的環境的行會被拒絕（`each environment has its combat nets`）。
- **事件選項**（`EventOptionView`）：有 `Key`、`Relic`、`Kills`、`Tips`。`ScreenAfterstates` 對結果不在螢幕上的選項
  （大多數事件選項、重抽、變化）回傳原來的局面，所以這些選項平手。
- **事件選項的 key 列得出來**（2026-11-17 查過，讀的是反編譯的遊戲程式和文字表，沒有跑程式）：
  - key 是遊戲自己的文字 key，形如 `WELLSPRING.pages.INITIAL.options.BATHE`，事件的 id 和頁都在裡面。
  - 遊戲用 key 建選項時會到 `events` 文字表找 `key.title`，找不到就丟例外。所以文字表裡所有 `….options.….title`
    就是名單。v0.113.0 的文字表：62 個事件，219 個選項 key，一個事件最多 13 個，中位數 3 個。
  - 不在文字表裡的只有幾種：遺物選項（key 用遺物的 id 組成，主要是 Ancient；它們帶 `Relic`，今天已經能從螢幕預測）、
    Doll Room（key 是遺物的名字）、Neow 的 Blitz 和自訂規則選項。
- **SL 的副本怎麼看事件**（`CloneSearch`）：每個選項都在副本上真的玩一次。選完之後如果還在同一個房間裡（選牌、獎勵、
  事件的下一頁），就繼續往下搜，直到離開這個房間、進戰鬥或這一局結束。它回傳每個選項的估值和走到的那條線，
  但決策日誌今天只記選中的動作。
- **V 讀的局面有兩種**（`MacroLeaf`）：這個點已經做完，或正要進入一個點（`Map.Entering`）。同一個決策的選項必須用同一種來估。
- **TD 標籤**（`learn/v/bootstrap.py`）：訓練局分兩半，各訓練一個 V，互相標對方那一半。
- **資料集工具**（`pool/box.py`）：資料集檔只收 SL、plan、l0 的冠軍。NoSL 的測試工作（`CHAR/nosl/eval/...`）已經在池子上跑過。
- **表**（`learn/game_ids.json`，模擬器的 `tables` 指令寫的）：沒有事件選項。

## 3. 設計

結構不動：層、寬度、V 的 64 個樓層風險、戰鬥網路的 51 個結局機率和藥水、TD 標籤、第二個頭，全部照舊。只多兩種 context 標記。

### 3.1 環境標記 `env:NoSL`（兩個網路）

- NoSL 的每個狀態帶 `env:NoSL`；SL 的狀態不帶，和今天一樣。
- 它是輸入：context 袋裡多一項，和 `character:`、`mode:Dread` 同一個位置、同一種查表加總。
- 環境寫在觀察上，和 `Mode` 同樣的位置（`RunView`、`CombatObservation`），由知道環境的那一邊蓋上去：模擬器的
  `Dispatcher`，mod 裡是大腦的選項。這樣日誌裡的 `run_view` 本來就帶著它，訓練和實戰讀的是同一個東西。
  今天的 NoSL 測試日誌沒有這個欄位，但每一行有 `env`，reader 可以補上。
- 它學到的是差距：同一個局面，NoSL 的死亡風險比 SL 高多少。標記進了後面兩層，會和血量、牌組、敵人一起作用，
  所以差距可以隨局面變。

### 3.2 事件選項標記 `pending:選項的 key`（只有 V），由 SL 的副本來教

- **V 多讀什麼**：NoSL 裡，事件選項之後的局面 = 選之前的局面 + `pending:KEY`。KEY 是遊戲的文字 key（事件的 id 已經在裡面）。
  這是地圖 `Entering` 的延伸：已經選了、還沒結算。只寫「是什麼」，沒有人寫的分數。
- **名單**：`tables` 指令從遊戲的 `events` 文字表列出所有選項 key，寫進 `game_ids.json`，一個 key 一列。
- **同一種局面才能比**：一個事件決策的所有選項都帶各自的標記。兩種例外照舊，不帶標記：
  - 會死的選項（`Kills`）：遊戲規則，值 0。
  - 遺物選項（帶 `Relic`）：今天已經從螢幕預測成「多了這個遺物」的局面。
  - 一個決策裡兩種選項混在一起時怎麼比，第 1 步實作時看 Ancient 的實際螢幕再定；定不下來就回報用戶。
- **不在名單裡的 key**（Doll Room、Neow 的自訂規則）：落到「不認識的 id」那一列，和其他表一樣。
- **教材從 SL 的副本來**：
  - SL 的決策日誌多記：事件決策的每個選項的 key，和每個選項那條線走到底的局面（`run_view`）。
  - 每一筆樣本 = 選之前的局面 + 這個選項的標記 + `env:NoSL`。標籤 = 凍結的 V 在這個選項走到底的局面（也帶 `env:NoSL`）
    上給的樓層風險。和多步目標同一套做法（`boot`），只是「之後的狀態」換成選項自己的結果。
  - 量大：每一局 SL 的每個事件、每個選項都是一筆，不用多打一局。
  - 沒有選擇偏差：每個選項都記，不只 SL 最後選的那個。
  - 雜訊小：標籤是選完之後那個局面的估值，不是整局的輸贏。
  - 選了之後會發生什麼是遊戲規則，和環境無關；NoSL 之後怎麼打由環境標記負責。
- **選項通到戰鬥的**：副本停在戰鬥開始，那裡的值是戰鬥網路給的，不是 V 的樓層風險，沒辦法直接當這種標籤。
  這種選項只用「真的被選中」的樣本（和地圖的 `entered` 同一個做法，標籤是這一局自己的結果）。
- **SL 不讀它**：SL 照舊用副本，SL 的狀態不帶這個標記。
- **現有資料用不上**：舊日誌沒記事件選項。事件的教材從「日誌改完之後的 SL 對局」開始累積。
- 先只做事件。重抽、變化這些看不見結果的選項，之後有量到需要再用同一個機制加。

### 3.3 遷移

- `carry.py` 的 `ZERO` 加 `env:`、`pending:` 兩個前綴。搬過去的網路：SL 的每個狀態給出原來的值；NoSL 的狀態一開始
  等於 SL 的值，也就是今天的 NoSL。
- 表一改，`--init` 就只收新表的網路，而且沒 carry 的舊網路讀到 `env:NoSL` 會落到「不認識的 id」那一列，NoSL 的值會變。
  所以新結構進 main 的那一次提交，要同時把當時的冠軍一對搬過去，兩個冠軍檔一起改。這需要用戶發話（第 6 節）。
- 之後訓練出來的每一對（包括 v11-1）都從搬過去的網路 `--init`，所以直接就是新結構，不用再搬。

### 3.5 自我對局：一個資料集檔同時開 SL 和 NoSL

- **搜尋**：NoSL 照 `nosl.json`，pimc，8 個世界各 300 個節點。不換演算法。
- **資料集檔的寫法**（`eval/datasets/NAME.toml`）：環境寫在「遊戲」上。一個遊戲本來就寫規則、力度、模式，現在多一項 `env`；
  沒寫就是 SL，和今天的檔案一樣。列（`[[runs]]`）照舊指向一個遊戲。

  ```toml
  champion = "eval/champions/sl.json"          # SL games play with it, as today
  nosl_champion = "eval/champions/nosl.json"   # NoSL games play with it (pimc, 8 worlds x 300 nodes)

  [games.full]                                 # SL, as today
  auto_win = []
  effort = { monster = "high", elite = "high", boss = "high" }

  [games.nosl]                                 # NoSL: no effort, its budget is the champion file's worlds and nodes
  env = "nosl"
  auto_win = []

  [[runs]]
  game = "full"
  asc = 10
  n = 6500

  [[runs]]
  game = "nosl"
  asc = 10
  n = 2000                                     # every amount here is made up
  ```

- **一個檔就是一個步驟**：SL 和 NoSL 的工作同一個名字、同一個期限、同一個優先度。工作的資料夾照環境分：
  `CHAR/sl/selfplay/NAME/...` 和 `CHAR/nosl/selfplay/NAME/...`。資料集檔兩邊各放一份。
- **種子**：一個角色一個區塊，SL 和 NoSL 的列依序往下拿，同一個種子不會用兩次。
- **探索**：階層照舊寫在檔裡，SL 和 NoSL 的列都能用（一列可以有自己的）。讀程式碼的結果：探索做在 l0 裡，和環境無關；
  估值平手的選項在 τ > 0 時是均勻抽的，所以 NoSL 裡還沒學過的事件選項本來就會被輪流選到。第 3 步在實際的局上確認。
- **進度表**：按角色、難度之外，再分環境列。
- **一件量到的事**：2026-11-17 的 NoSL 測試裡，6 G 記憶體的小機器跑 3 條 NoSL 的局時記憶體不夠，後來只讓它拿別種工作。
  池子今天只能按工作的種類挑，不能按環境挑。混合的步驟開出去之前，第 3 步的 smoke 要看這些小機器。
- 局數、難度、哪些模式：用戶給。可以參考的事實：NoSL 在 A10 贏不到 3 %，大多數局死得早；A0 贏約 47 %，走得到後面。

## 4. 步驟

每一步做完在第 7 節記一行。第 1 步進 main、第 4 步、第 5 步要用戶發話才做。

1. **結構**
   - 兩種標記進編碼（`RunNet.Tokens`、`CombatTokens`）；觀察上的環境欄位。
   - NoSL 事件選項的後狀態帶標記（`ScreenAfterstates`）。
   - 事件選項的 key 進 `tables` 和 `game_ids.json`；`carry.py` 的兩個前綴；冠軍一對搬過去。
   - SL 的決策日誌記事件選項的 key 和每個選項走到底的局面。
   - 做完的樣子：搬過去的一對在 SL 的測試狀態上給出原來的值；同一個局面帶不帶 `env:NoSL` 給出同一個值（列是零）；
     跑一小批局，螢幕上出現過的選項 key 除了 3.2 列的例外都在表裡；單元測試通過。
2. **訓練程式**
   - 戰鬥網路的 reader 收混合的環境；V 的 reader 加事件選項的樣本；報告分環境列留出損失。
   - 做完的樣子：用 2026-11-17 NoSL 測試的日誌加一小份新版日誌的 SL 對局，本機跑通一次小訓練（只看流程，不看分數）。
3. **工具**
   - `box.py` 的資料集檔收帶 `env` 的遊戲和 `nosl_champion`，一個檔同時開兩個環境的工作；進度表分環境列。
   - 確認探索在 NoSL 的行為；池子上跑一個小的 smoke，看小機器的記憶體。
   - 這一步不動網路的表，可以先進 main。
4. **資料**（等用戶：局數、時間）：一個資料集檔，同時有 SL 的列和 NoSL 的列。
   - NoSL 的局：教環境標記。
   - SL 的局：教事件選項，也照舊是 SL 的訓練資料。它要在第 1 步進 main 之後才開始，日誌才有事件選項。
5. **訓練一對**：原有的 SL 資料、新的 SL 資料、NoSL 的資料合併，從當時的冠軍一對 `--init`（等用戶）。
6. **測試**，報數字，用戶決定。

## 5. 不在這份計畫裡

- **資訊集搜尋**。用戶 2026-11-17 定了先不換。「pimc毛病」那個 session 提的：節點只用看得見的狀態當 key，
  8 個世界走同一棵樹、在同一個節點必須選同一個動作，抽牌或擲骰把世界分組。它不用重訓就能單獨測，
  所以等這份計畫的一對出來之後，可以用同一批種子和現在的搜尋對比一次。
  讀過之後我的兩點看法（推論，沒量過）：
