## 1. 為什麼

- SL 冠軍（同一對網路，high）在 A10 每個角色 200 局：172 / 151 / 146 / 116 / 104 / 25，合計 714 / 1,200。
- 2026-11-14 的 NoSL 檢查（26 局，舊版）：有 2 個以上選項的事件決策 139 個，其中 120 個所有選項的估值相同，選了第一個。

沒量過、只是從程式碼讀出來的推論：

- 兩個網路只從 SL 的對局學。戰鬥網路的標籤是「SL 把這場打完」的結局，V 的標籤是「之後每個房間都由 SL 來打」的結局，

- NoSL 的搜尋只看這一回合，回合之後全靠戰鬥網路，所以這個偏差在 NoSL 的影響比在 SL 大。

## 2. 現況（為這份計畫讀過的程式碼）

- **NoSL 怎麼用兩個網路**：`PimcBrain`（`src/Sts2Ai.Brain/Combat/CombatBrain.cs`）每個世界搜這一回合，葉子是下一回合開始時的
  戰鬥網路，結局由 V 定價（`ICombatLeaf`）。戰鬥外用 `ScreenAfterstates`：從螢幕預測每個選項之後的局面，交給 V。
- **context 是加總的袋子**，兩個網路都有。V 的 context：角色、幕、Boss、Ancient，Dread 模式下再加 `mode:` 和 `dominion:`
  （`RunNet.Tokens`，`CombatTokens.ModeTokens`）。戰鬥網路的 context：角色、遭遇、房間、幕，加同樣的模式標記。
- **Dread 的先例**：`learn/carry.py` 把舊網路搬到新的表，`mode:`、`dominion:` 開頭的新列從零開始（`ZERO`）。context 是加總，
  所以搬過去的網路對舊表讀得到的每個狀態給出原來的值；檔案裡的測試狀態會重新估一次，載入時大腦也會檢查。
- **`--init` 不接受表不同的網路**（`v.train`：`holds other tables than learn/game_ids.json's`）。表一改，要先 carry 才能接著訓練。
- **訓練從來都是 `--init`**。沒見過的列不會動，所以從零開始的列在只有 SL 資料的訓練之後仍然是零。
- **V 的樣本**（`learn/v/data.py`）：決策日誌裡每個戰鬥外決策的 `run_view` 是一個樣本；地圖移動多一個樣本，選中的點的
  後狀態（`entered`）。日誌的每一行有 `env`、`surface`、選的動作、`run_view`、是否隨機抽的，**沒有螢幕**（事件是哪個、
  選項的 key 都不在裡面）。V 的 reader 不看 `env`。
- **戰鬥網路的樣本**（`learn/combat/data.py`）：每回合開始一個樣本，標籤是這場戰鬥真正的結局。`--env` 只收一個環境，
  別的環境的行會被拒絕（`each environment has its combat nets`）。
- **事件選項**（`EventOptionView`）：有 `Key`、`Relic`、`Kills`、`Tips`。`ScreenAfterstates` 對結果不在螢幕上的選項
  （大多數事件選項、重抽、變化）回傳原來的局面，所以這些選項平手。
- **事件選項的 key 列得出來**（2026-11-17 查過，讀的是反編譯的遊戲程式和文字表，沒有跑程式）：
  - key 是遊戲自己的文字 key，形如 `WELLSPRING.pages.INITIAL.options.BATHE`，事件的 id 和頁都在裡面。
  - 遊戲用 key 建選項時會到 `events` 文字表找 `key.title`，找不到就丟例外。所以文字表裡所有 `….options.….title`
    就是名單。v0.113.0 的文字表：62 個事件，219 個選項 key，一個事件最多 13 個，中位數 3 個。
  - 不在文字表裡的只有幾種：遺物選項（key 用遺物的 id 組成，主要是 Ancient；它們帶 `Relic`，今天已經能從螢幕預測）、
    Doll Room（key 是遺物的名字）、Neow 的 Blitz 和自訂規則選項。
- **SL 的副本怎麼看事件**（`CloneSearch`）：每個選項都在副本上真的玩一次。選完之後如果還在同一個房間裡（選牌、獎勵、
  事件的下一頁），就繼續往下搜，直到離開這個房間、進戰鬥或這一局結束。它回傳每個選項的估值和走到的那條線，
  但決策日誌今天只記選中的動作。
- **V 讀的局面有兩種**（`MacroLeaf`）：這個點已經做完，或正要進入一個點（`Map.Entering`）。同一個決策的選項必須用同一種來估。
- **TD 標籤**（`learn/v/bootstrap.py`）：訓練局分兩半，各訓練一個 V，互相標對方那一半。
- **資料集工具**（`pool/box.py`）：資料集檔只收 SL、plan、l0 的冠軍。NoSL 的測試工作（`CHAR/nosl/eval/...`）已經在池子上跑過。
- **表**（`learn/game_ids.json`，模擬器的 `tables` 指令寫的）：沒有事件選項。

## 3. 設計

照舊的：層數、V 的 64 個樓層風險、戰鬥網路的 51 個結局機率和藥水、TD 標籤、第二個頭。
多的：兩個網路各一個環境標記；V 多一組「事件選項」的輸入（3.2）。SL 和 NoSL 仍然是同一個結構、同一份權重。

原則（用戶 2026-11-17）：玩家在做決定時看得見的東西，網路都要讀到，而且走它已經認得的表，
這樣網路對那樣東西原有的認識才用得上。只有真的看不見的部分才留給期望值。

### 3.1 環境標記 `env:NoSL`（兩個網路）

- NoSL 的每個狀態帶 `env:NoSL`；SL 的狀態不帶，和今天一樣。
- 它是輸入：context 袋裡多一項，和 `character:`、`mode:Dread` 同一個位置、同一種查表加總。
- **環境不寫在觀察上，由大腦交給編碼器**（審閱後改的）。大腦建立時就知道自己的環境，網路編碼每個狀態時加上標記
  （`CombatTokens.Of`、`RunNet.Tokens` 多一個環境參數）。訓練時用日誌每一行本來就有的 `env`。
  - 原因：NoSL 的每場戰鬥是照觀察重建的，重建完會逐欄比對（`CombatBuilder.Differences`），不一樣就丟
    `not built as observed`。觀察上多一個環境欄位，每場 NoSL 戰鬥都會在這裡失敗。
  - 就算繞過去，搜尋裡的葉子讀的是每個世界自己寫的觀察（Rust 引擎或重建的戰鬥），上面不會有這個欄位：
    訓練時帶標記、搜尋時不帶，而且不會報錯。
  - 網路檔裡的測試狀態要記下各自的環境，載入時的檢查才對得上。
- 它學到的是差距：同一個局面，NoSL 的死亡風險比 SL 高多少。標記進了後面兩層，會和血量、牌組、敵人一起作用，
  所以差距可以隨局面變。

### 3.2 事件選項的輸入（只有 V）：按鈕上看得見的全部，由 SL 的副本來教

**玩家在事件按鈕上看得見什麼**（2026-11-17 讀遊戲的程式查的）：

| 看得見的 | 例子 | 今天的螢幕有沒有 |
|---|---|---|
| 是哪個選項 | `WELLSPRING.pages.INITIAL.options.BATHE`；62 個事件、219 個 | 有（`Key`） |
| 選項點名的牌、遺物、藥水 | Slippery Bridge 要丟掉哪張牌，Museum of Torture 給哪個遺物，Stone of All Time 喝哪瓶藥水 | 有（`Tips`，牌帶升級） |
| 文字裡的數字 | 給多少金幣、扣多少血、回多少血。19 個事件在執行時才算，其中 13 個是擲出來的（例如金幣 41 到 69） | **沒有**，要加 |
| 鎖住沒有 | | 有（鎖住的不能選，不用估） |

**V 怎麼讀**：NoSL 裡，事件選項之後的局面 = 選之前的局面 + 這個選項的四樣東西。和地圖的 `Entering` 一樣寫在 `RunView` 上。

- **哪個選項** → context 袋多一項 `pending:KEY`。名單由 `tables` 從遊戲的 `events` 文字表列出來。
- **點名的牌** → 走牌的表，再過牌組用的同一個牌編碼器，加總成 body 輸入的新一段。「遺物保管的牌」（`held`）今天就是這樣讀的。
- **點名的遺物、藥水** → 走遺物的表、藥水的表，各加總成新一段。
- **數字** → 新的表，一個事件的一個變數一列（例如 `WELLSPRING.BatheCurses`）；數值乘上那一列再加總，成新一段。
  遺物的計數器今天就是這樣讀的。數值照牌的數字的做法縮放和封頂。

**為什麼這樣才學得到細的關係**：

- 牌、遺物、藥水用的是 V 已經學好的同一批列。「丟掉這張牌，對這副牌組值多少」可以直接用上 V 對這張牌的認識，
  不用每個事件、每張牌從頭學。
- 四樣東西和整個局面一起進 body 的兩層，所以選項的價值可以隨血量、牌組、遺物、樓層而變。
- 教材的每一筆都是「這個局面 + 這個選項 + 按鈕上這些東西 → 這一局真正走到的結果」，不是把不同情況混在一起。
- 真的看不見的部分（例如隨機遺物會是哪一個），V 學到的是在看得見的東西都給定之下的期望值。這是不看答案能做到的上限。

**同一種局面才能比**：一個事件決策的所有選項都用這組輸入。兩種例外照舊：

- 會死的選項（`Kills`）：遊戲規則，值 0。
- 遺物選項（帶 `Relic`，主要是 Ancient）：今天已經從螢幕預測成「多了這個遺物」的局面。
- 一個決策裡兩種選項混在一起時怎麼比，第 1 步實作時看 Ancient 的實際螢幕再定；定不下來就回報用戶。
- **留在事件螢幕上的動作**（審閱後加的）：隨時能喝的藥水在事件螢幕上也是合法動作，它的後狀態是「少一瓶藥水」，
  不帶選項的輸入，和事件選項不是同一種局面。照地圖今天的做法：留在螢幕上的動作，值是它之後最好的那個事件選項。
  不這樣做的話，只要所有選項都估得比現在的局面低，V 就會先去喝藥水。

**教材從 SL 的副本來**：

- SL 的決策日誌多記：事件決策的螢幕（每個選項的 key、點名的東西、事件的數字），和每個選項走到底的局面（`run_view`）。
- **走到底的那條線由 NoSL 的決策方式來走**（審閱後改的）：選項之後如果還在房間裡（選牌、獎勵、下一頁），
  每一步都用 NoSL 的做法選（只看螢幕），副本照實執行，直到離開房間。
  - 原因：SL 自己的搜尋是在副本上把後續每個答案都試過再取最好的。後續是「選一張牌變化」這類看不見結果的步驟時，
    那是 N 次真實結果裡最好的一次，NoSL 做不到，標籤會偏高。
  - 走到戰鬥開始：這一筆不用（見下面）。走到這一局結束：標籤是「死在這一層」。回到已經決定過的局面：這一筆不用。
- 每一筆樣本 = 選之前的局面 + 這個選項的輸入 + `env:NoSL`。標籤 = 凍結的 V 在這個選項走到底的局面（也帶 `env:NoSL`）
  上給的樓層風險。和多步目標同一套做法（`boot`），只是「之後的狀態」換成選項自己的結果。
- 量大：每一局 SL 的每個事件、每個選項都是一筆，不用多打一局。
- 沒有選擇偏差：每個選項都記，不只 SL 最後選的那個。
- 雜訊小：標籤是選完之後那個局面的估值，不是整局的輸贏。
- 選了之後會發生什麼是遊戲規則，和環境無關；NoSL 之後怎麼打由環境標記負責。

**NoSL 自己的局也教**：NoSL 的日誌記選中的選項的輸入。選中的那一筆照地圖 `entered` 的做法當樣本，
標籤是這一局自己之後的結果。通到戰鬥的選項只有這一種樣本：副本停在戰鬥開始，那裡的值是戰鬥網路給的，不是 V 的樓層風險。
SL 的局選中的選項不當這種樣本（審閱後改的）：它之後的結果是 SL 打出來的，貼上 `env:NoSL` 會把通到戰鬥的選項教得偏高。

**其他**：

- 不在名單裡的 key（Doll Room、Neow 的自訂規則）：不出 `pending:` 標記（審閱後改的），點名的東西和數字照常讀。
  「不認識的 id」那一列不是零（紀錄裡量過它能把估值移動 0.227），落到那一列會平白改變估值。
- SL 不讀這組輸入：SL 照舊用副本。
- 現有資料用不上：舊日誌沒記事件的螢幕。事件的教材從「日誌改完之後的 SL 對局」開始累積。
- 第 1 步要查：事件文字裡提到、但不在點名的東西裡的牌或遺物有沒有。有的話補進螢幕。
- 先只做事件。其他看不見結果的選項（重抽、變化），之後用同一組輸入加。

### 3.3 遷移

- context 袋的新列（`env:`、`pending:`）從零開始，`carry.py` 的 `ZERO` 加這兩個前綴。
- V 的新段（點名的牌、遺物、藥水、數字）：body 第一層對應新段的權重從零開始；數字的新表照其他表的做法隨機起始
  （兩邊都是零的話，梯度是零，永遠學不動）。`carry.py` 要多做這一件：把 body 第一層加寬。
- 搬過去的網路：SL 的每個狀態給出原來的值；NoSL 的狀態一開始等於 SL 的值，也就是今天的 NoSL。
- V 的 ONNX 圖多了輸入，所以所有還要用的 V 檔都要搬一次；戰鬥網路只多 context 的一列。
- 表一改，`--init` 就只收新表的網路，而且沒 carry 的舊網路讀到 `env:NoSL` 會落到「不認識的 id」那一列，NoSL 的值會變。
  所以新結構進 main 的那一次提交，要同時把當時的冠軍一對搬過去，兩個冠軍檔一起改。這需要用戶發話（第 6 節）。
- 之後訓練出來的每一對（包括 v11-1）都從搬過去的網路 `--init`，所以直接就是新結構，不用再搬。

### 3.4 訓練

- SL 和 NoSL 的資料合併，訓練同一份權重，兩個網路一起（一對）。
- 戰鬥網路的 reader 改成每一行按自己的 `env` 加標記，不再拒絕混合。

## 8. 實作和上面的設計不同的地方（第 1–3 步寫的時候定的）

- **待結算選項的 key 是 V 自己的一張表（`pending`），不放在 context 袋裡。** 這張表的第 0 列（表裡沒有的 key）固定是零，

  Ancient 的遺物選項（它們本來就走「多了這個遺物」）。
- **「是不是自己的」也讀。** 按鈕點名的牌、遺物、藥水各帶一個標記：是不是玩家自己的（牌組裡那張、身上那個遺物、腰帶上那瓶）。
